Контур ktalk — 11 файлов в двух репозиториях (пакет `ktalk-mcp` + активы `.claude/` в vault'е

## Тема 2 — Конвенции машинного централизованного хранилища

### XDG Base Directory Specification

Спецификация (freedesktop.org) определяет для Linux/Unix: `$XDG_DATA_HOME` (дефолт
`~/.local/share`) — постоянные пользовательские данные приложения; `$XDG_CONFIG_HOME` (дефолт
`~/.config`) — конфигурация; `$XDG_CACHE_HOME` (дефолт `~/.cache`) — некритичный кэш;
`$XDG_STATE_HOME` (дефолт `~/.local/state`) — состояние, не входящее ни в данные, ни в кэш (логи,
history, undo). Спецификация — Linux-специфична по происхождению; macOS её официально не
поддерживает на уровне ОС ([secondary, общеизвестный факт экосистемы, без прямой проверки на
этой сессии] — [established]).

### macOS: `~/Library/Application Support` vs XDG-подобные пути

На macOS canonical-конвенция Apple — `~/Library/Application Support/<Vendor>/<App>/` для
персистентных данных приложения (см. каталог на этой машине: `Claude`, `Code`, `Cursor`,
`Docker Desktop` и десятки других следуют этому паттерну — [primary, `ls` этой машины]).
Кроссплатформенные CLI-инструменты (в первую очередь портированные с Linux/пришедшие из
Node/Python-экосистемы) часто игнорируют это и используют XDG-пути буквально (`~/.local/share`,
`~/.config`) даже на macOS — на этой машине это `uv` (`~/.local/share/uv/{tools,python,
credentials}`) и Claude Code CLI частично (`~/.local/share/claude/versions/`, но не
пользовательские данные — те в `~/.claude/`). Однозначной доминирующей конвенции на этой машине
нет — соседствуют три паттерна одновременно: Apple-native, XDG-buквальный и произвольный dotdir
в `$HOME`.

### Что фактически наблюдается на этой машине

| Путь | Кто использует | Паттерн |
|------|-----------------|---------|
| `~/.claude/` | Claude Code CLI (настройки, история, плагины, память, кэш) | dotdir в `$HOME`, не XDG, не Apple |
| `~/.local/share/claude/versions/` | Claude Code CLI (версии бинарника) | XDG-подобный, буквальный |
| `~/.local/share/uv/{tools,python,credentials}` | `uv` (Python-тулинг) | XDG-подобный, буквальный |
| `~/.local/share/obsidian-mcp-*` | сторонние MCP-серверы (не Anthropic) | XDG-подобный |
| `~/Library/Application Support/Claude/` | Claude Desktop (Electron-приложение) | Apple-native |
| `~/Library/Application Support/Code`, `/Cursor`, `/Docker Desktop` и др. | сторонние GUI-приложения | Apple-native |
| нет отдельного примера | — | `~/.config` на этой машине не проверялся отдельно (не входил в задание) |

XDG-переменные окружения (`XDG_DATA_HOME` и т.д.) в текущей сессии не заданы — любой инструмент,
буквально следующий спецификации, на этой машине падает на дефолты (`~/.local/share`,
`~/.config`, `~/.cache`).

### SQLite и облачная синхронизация — известные проблемы блокировок

Публично задокументированный факт экосистемы SQLite (официальная документация проекта, раздел
о WAL): WAL-режим держит shared-memory файл (`-shm`) и полагается на `mmap`/файловые блокировки
POSIX, которые многие реализации сетевых и облачных файловых систем (в том числе клиенты Dropbox,
Google Drive, OneDrive, iCloud Drive) не поддерживают надёжно — блокировки могут не работать
между процессами на разных узлах синхронизации, а сам факт синхронизации файла БД во время
записи создаёт риск повреждения (частичная запись при поднятии файла на сервер и его подмене на
другом устройстве). Официальная рекомендация SQLite — не размещать файл БД (тем более в WAL) на
сетевом или облачно-синхронизируемом томе — [secondary: общеизвестная, многократно
задокументированная в экосистеме характеристика WAL/POSIX-locking, не проверялась заново на этой
сессии прямым экспериментом] — [established].

Реестр `ktalk-mcp` уже сегодня использует WAL + `busy_timeout=5000` (см. CLAUDE.md, «Конкурентность»)
— это решает конкурентный доступ **локальных** процессов на одной машине; ничего не говорит о
поведении при облачной синхронизации каталога, где лежит БД.

### Что фактически делают соседние Claude Code плагины на этой машине с пользовательскими данными

`~/.claude/plugins/cache/*` — это чек-ауты git-репозиториев маркетплейсов (`nauta`, `gramax`,
`nsmp-plugins`, `es-team`, `claude-plugins-official` и др.) — код и контент плагинов, не
пользовательские данные; ни одного `.db`/`.sqlite*` файла в этом дереве не найдено.

`~/.claude/plugins/data/<plugin-id>-<marketplace-id>/` — существует для 5 официальных плагинов
(`hookify`, `aikido`, `context7`, `hyperpowers`, `superpowers`), но во всех пяти каталогах
**нет ни одного файла** — платформа резервирует место, но ни один установленный на этой машине
плагин его не заполняет. Не удалось найти официальную документацию платформы, описывающую
контракт этого каталога (что туда класть, кто отвечает за очистку, доступен ли он плагину через
переменную окружения аналогично `${CLAUDE_PLUGIN_ROOT}`) — это прямой вопрос к RES-002
(`claude-code-guide`).

Не найдено ни одного примера плагина на этой машине, хранящего SQLite-реестр или аналог
пользовательских данных в централизованном общемашинном каталоге — эталонного prior-art внутри
экосистемы Claude Code plugins нет.

## Тема 3 — механика плагина Claude Code (RES-002)

Собрано агентом `claude-code-guide` по документации code.claude.com в том же заходе.

### Раскладка и манифест

```
plugin-root/
├── .claude-plugin/plugin.json   # только манифест здесь
├── skills/ commands/ agents/    # на КОРНЕ плагина, не внутри .claude-plugin/
├── hooks/hooks.json
├── .mcp.json
├── bin/                         # попадает в PATH при включённом плагине
└── settings.json                # дефолты при включении
```

Обязателен только `name` (kebab-case). Значимо опциональное `version`: без него версия падает на
git SHA/digest, и момент обновления у пользователя становится непредсказуем. Прочее — `description`,
`author`, переопределения путей компонентов, `dependencies`, `defaultEnabled`, `userConfig`.

### MCP-сервер внутри плагина

Объявляется в `.mcp.json` на корне плагина, тип `stdio` (локальный процесс) или `http`.
Подстановки, разрешаемые в runtime в `.mcp.json`/`hooks.json`/`settings.json`:

| Переменная | Значение |
|------------|----------|
| `${CLAUDE_PLUGIN_ROOT}` | каталог установки плагина |
| `${CLAUDE_PLUGIN_DATA}` | персистентный каталог плагина, переживает обновления |
| `${CLAUDE_PROJECT_DIR}` | корень проекта-хозяина |

`${CLAUDE_PLUGIN_DATA}` — прямой ответ на открытый вопрос находки 9: каталог
`~/.claude/plugins/data/<plugin>-<marketplace>/` действительно адресуется плагином через
переменную. Что именно платформа гарантирует при удалении плагина и есть ли квоты — по-прежнему
не подтверждено, а пустота всех пяти каталогов на этой машине остаётся фактом.

Относительные пути в `command`/`hooks` резолвятся от cwd хозяина, а не от корня плагина — типовая
ошибка, описанная в документации отдельно. Автоустановки зависимостей нет: для Python-сервера
`uv` в PATH — требование к пользователю, документируемое в README. Первый запуск stdio-сервера
может упереться в дефолтный таймаут 30 с (`MCP_TIMEOUT`).

### Разрешение имён

- Навыки плагина всегда неймспейсятся `/<plugin>:<skill>` — конфликта между плагинами нет.
- Агенты: проектный `.claude/agents/` **перекрывает** одноимённого агента плагина, дальше
  пользовательский `~/.claude/agents/`, дальше плагин. Прямое следствие для переноса: пока
  `ktalk-processor.md` лежит в vault'е, версия из плагина не действует — переключение обязано
  быть явным удалением файла, а не установкой поверх.
- Hooks и monitors складываются из всех источников.

### Что плагин знает о проекте-хозяине

Доступны cwd, `${CLAUDE_PROJECT_DIR}` и переменные окружения, объявленные в `settings.json` → `env`.
Не подтверждено: может ли плагин читать `.claude/settings.json` хозяина напрямую; существует ли
`${CLAUDE_WORKSPACE_ROOT}`; как плагин узнаёт, включён ли он.

Следствие для волны 3: **конфигурация хозяина не приезжает подстановкой** — её читает сам код
(CLI и MCP-сервер) от cwd. Значит discovery-алгоритм принадлежит пакету `ktalk-mcp`, а не
манифесту плагина, и `vault-config.md` (находка 4) читается кодом, а не промтом.

### Marketplace

`marketplace.json` со списком плагинов и `source` (относительный путь, git-URL, GitHub `owner/repo`
или удалённый URL). Установка `/plugin install <plugin>@<marketplace>`, обновление каталога
`/plugin marketplace update`, кэш — `~/.claude/plugins/cache/`. Прецеденты на этой машине:
`nauta` (git, self-hosted GitLab), `gramax` (github).

Плагин project-scope требует workspace trust до первой загрузки, иначе hooks не поднимаются.
Секреты плагин не получает автоматически — пользователь объявляет их сам.

## Что НЕ удалось выяснить

- Официальный контракт `~/.claude/plugins/data/<plugin>-<marketplace>/`: документирован ли он,
  доступен ли плагину как переменная окружения, что происходит при обновлении/удалении плагина —
  требует RES-002 или прямого запроса платформе.
- Поведение SQLite WAL под iCloud Drive/Dropbox не проверялось прямым экспериментом на этой
  сессии — только справочный факт экосистемы.
- Не проверено, включена ли на других машинах владельца (не только текущей) синхронизация
  «Desktop & Documents» — вывод про `~/Documents/naumen-cto` не обобщается.
- Не найдено содержимое `~/.config` на этой машине — вне задания RES-001, но полезно для полноты
  картины XDG-паттернов, если понадобится SA-002.
- Не оценивался объём/типичный размер транскриптов и БД реестра — важно для решения о лимитах
  хранилища, не входило в задание.
- Права доступа (unix permissions) типичных `~/.local/share/*` каталогов на этой машине не
  сверялись — для NFR по приватности (риск 3 постановки) может понадобиться отдельная проверка.

## Рекомендации для BA/SA

- **BA**: раздел требований к централизованному хранилищу должен явно развести «данные ktalk»
  (реестр, транскрипты, отчёты eval) и «артефакты хозяина» (протоколы, зеркало реестра,
  профили `10_PEOPLE`) — таблица в разделе «Данные vault'а vs код/промты» выше — стартовая точка.
  Учти находку 4 (существующий `vault-config.md`, которым контур сегодня не пользуется) и
  находку 3 (зависимость от `qmd`) — оба должны попасть в объём требования «поведение без
  vault-подобной раскладки»: без `qmd` часть шагов агента `ktalk-processor` не выполнима, это не
  вопрос путей.
- **SA**: `vault-config.md` — прямой prior-art для формата discovery-конфига проекта-хозяина
  (SA-003) — уже есть работающий пример «ключ → путь» с паттернами имён файлов в этом же vault'е.
  Для ADR-013 (хранилище): находка про WAL/облачную синхронизацию — это ограничение на дефолтный
  путь машинного хранилища (не должен молча совпасть с iCloud Drive/Dropbox-каталогом); находка
  про пустой, недокументированный `~/.claude/plugins/data/` — решение спускать секрет/токен
  сессии в централизованное хранилище требует отдельной сверки с риском 3 постановки, а не
  переиспользования недокументированного платформенного каталога без проверки в RES-002.
