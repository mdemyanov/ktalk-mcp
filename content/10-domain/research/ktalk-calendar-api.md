## TL;DR

**П.1 закрыт полностью живыми запросами.** `GET /api/calendar` принимает `start` (обязателен),
`end`, `take`, `roomName`; `startFrom`/`from`/`dateFrom`/`startDate`/`top`/`count`/`limit`/`skip`/
`query` — либо не распознаются, либо принимаются синтаксически, но не влияют на выдачу. Жёсткий
лимит диапазона 7 дней действует только при явном `start`+`end`; при `start`+`take` сервер сам
расширяет окно вперёд без ограничения. `take` формально 1–1000, фактически режется на 100 —
тот же паттерн, что у `top` на `/api/recordings` (см. CLAUDE.md). Пагинации `skip`-подобной нет.
Ответ — `{"items": [...]}`, без курсора, отсортирован по возрастанию времени начала.

**П.2 закрыт документарно, с явной пометкой достоверности.** Прямого пути к схеме `POST /calendar`
нет — в спеке эндпоинта вообще нет. Ближайший документированный аналог — `CreateEmailCalendarEventModel`
для `POST /api/EmailCalendar/{email}` (другой, api-key-only путь). Его состав почти 1:1 покрывает
сигнатуру `create_meeting` из mainpart после перевода snake_case→camelCase — это совпадение по двум
независимым источникам укрепляет доверие к общему подмножеству полей, но не подтверждает их для
`/calendar` напрямую. Схема заметно шире сигнатуры mainpart: там, где mainpart предлагает только
булев `is_recurring`, документированная модель требует полноценный объект `recurrence` (тип
периодичности, интервал, дни недели) — без него неизвестно, что делает `isRecurring: true`.

**Неожиданная находка, меняющая допущение постановки:** ключ без нужных scope (`ktalk auth-status`
сообщает о нехватке `application.applications.read`) получает **200 с реальными данными** на
недокументированном `GET /api/calendar`, при этом 403 — на документированном
`GET /api/EmailCalendar/{email}` и на кандидате «whoami» `GET /api/domain/applications/access-info`.
То есть календарь **частично доступен в api-key-режиме уже сейчас** — вопреки допущению постановки
«ключу не хватает прав вообще ни на что в этой волне». Требует внимания SA при проектировании
`OPERATION_PROFILES` (Ф-34).

**П.3 (идемпотентность повторного `POST /calendar`) не исследовался** — физически не проверяется
GET-запросами, вынесен в боевую приёмку с ведома владельца, как и предписывает постановка.

## §1. `GET /api/calendar` — параметры (проверено живыми GET, session-режим)

### Метод

Все запросы — `env -u KTALK_PERSONAL_API_KEY` + `httpx.get(..., params={..., "sessionToken": <REDACTED>})`,
без заголовка `X-Auth-Token`. Проверено программно на каждый запрос: `sessionToken=` присутствует в
итоговом URL, `X-Auth-Token` в заголовках запроса отсутствует. Значения токена/ключа нигде не
печатались и не попали в этот документ.

### Ф-17. Имя параметра начала окна — `start`

```
GET /api/calendar?start=2026-08-13&sessionToken=<REDACTED>
→ 400 {"errorMessage":"Должна быть задана или дата окончания, или количество запрашиваемых
        элементов; Должна быть задана или дата окончания, или количество запрашиваемых элементов"}
```

Проверенные и отвергнутые варианты имени (все дают тот же 400 «Дата начала является обязательной
для заполнения», что и полное отсутствие параметров — то есть не распознаются вообще):
`startFrom`, `from`, `dateFrom`, `startDate`. Формат — как короткая дата (`2026-08-13`), так и
полный ISO-8601 с `Z` (`2026-08-13T00:00:00.000Z`) принимаются одинаково (200, тот же набор
элементов). [primary] [established]

### Ф-18. Имя параметра конца окна — `end`

```
GET /api/calendar?start=2026-08-13&end=2026-08-14&sessionToken=<REDACTED>
→ 200 {"items":[...10 элементов...]}
```

[primary] [established]

### Ф-19. Имя параметра количества — `take`

`top`, `count`, `limit` не распознаются — с ними сохраняется ошибка «нужен `end` или количество».
`take` — рабочее имя (совпадает с именем параметра у задокументированного аналога
`GET /api/EmailCalendar/{email}`, см. §2). [primary] [established]

### Ф-20. Разное поведение лимита диапазона в зависимости от комбинации параметров

| Комбинация | Поведение |
|---|---|
| `start` + `end`, диапазон ровно 7 дней (`08-01`→`08-08`) | 200, 26 элементов |
| `start` + `end`, диапазон 8 дней (`08-01`→`08-09`) | 400 «Период запроса не должен превышать 7 дней» |
| `start` + `take` (без `end`) | 200 в любом протестированном случае; `take=100` вернул элементы
  с разбросом дат более месяца (`2026-08-03` … `2026-09-07`) — лимит 7 дней здесь **не
  применяется** |

[primary] [established]

### Ф-21. `take` валидируется на 1..1000, фактически режется на 100

```
take=1001 → 400 "The field Take must be between 1 and 1000."
take=0    → 400 "The field Take must be between 1 and 1000."
take=-1   → 400 "The field Take must be between 1 and 1000."
take=101  → 200, count=100
take=1000 → 200, count=100
```

Тот же паттерн, что у `top` на `/api/recordings` (CLAUDE.md: «`top` максимум 100, не 1000»):
валидационная граница схемы и фактический потолок выдачи — разные числа. [primary] [established]

### Ф-22. `skip` принимается, но не работает

```
start=2026-08-01&take=2&skip=0 → первый элемент start=2026-08-03T07:00:00Z
start=2026-08-01&take=2&skip=2 → первый элемент start=2026-08-03T07:00:00Z (тот же!)
```

Нет ошибки валидации, нет и эффекта — способа получить вторую «страницу» сверх первых `take`
элементов через `skip` не существует. [primary] [established]

### Ф-23. `roomName` реально фильтрует (доказано сравнением, не предположено)

Базовая выборка за 7-дневное окно — 26 элементов, 26 различных комнат (1:1). Тест: взят реальный
`roomName` из выборки (не публикуется — внутренний идентификатор), передан фильтром:

```
count без фильтра        = 26
count с реальным roomName = 1, и все вернувшиеся элементы совпадают по этой комнате
count с несуществующим roomName ("definitely-not-a-real-room-xyz") = 0
```

[primary] [established]

### Ф-24. `query` принимается синтаксически, но не фильтрует

```
query=zzz_no_such_meeting_zzz (заведомо не встречающаяся строка) → count=26, то же, что без фильтра
```

В отличие от `roomName`, `query` не даёт эффекта — либо параметр не реализован для этого
эндпоинта, либо ищет не по тем полям, что были протестированы. [primary] [established, в
формулировке «эффекта не обнаружено при тестированном значении», не «доказано, что параметр
всегда игнорируется»]

### Ф-25. `start`/`end` не клэмпятся молча — окно реально применяется в обе стороны

В отличие от `/api/recordings`, где `startFrom`/`startTo` игнорируются (CLAUDE.md), здесь окно
проверено доказательно:

```
start=2020-01-01, end=2020-01-02  → count=0   (окно в прошлом, до появления данных Толка)
start=2020-01-01, take=5          → count=0   (не клэмпится к «сейчас» — иначе вернул бы
                                                ближайшие будущие элементы)
start=2027-06-01, end=2027-06-02  → count=0   (окно в будущем без плановых встреч)
start=2030-01-01, take=5          → count=5, элементы с start в диапазоне 2030-01-02…2030-01-03
                                     (реальные повторяющиеся встречи, запланированные на годы вперёд)
```

[primary] [established]

### Ф-26. Полный набор текстов валидации, собранных зондом

| Условие | `errorMessage` (дословно) |
|---|---|
| нет `start` | «Дата начала является обязательной для заполнения» |
| есть `start`, нет `end` и нет `take` | «Должна быть задана или дата окончания, или количество запрашиваемых элементов» (дублируется дважды подряд в одном сообщении — вероятно, накладываются два правила валидации с одинаковым текстом) |
| `end` - `start` > 7 дней | «Период запроса не должен превышать 7 дней» |
| `end` < `start` | «Дата окончания должна быть больше даты начала» |
| `start` не парсится как дата | «The value '...' is not valid for Start.» (внутреннее имя поля модели — `Start`, с заглавной буквы) |
| `take` вне 1..1000 | «The field Take must be between 1 and 1000.» |

[primary] [established]

### Ф-27. Форма ответа: `{"items": [...]}`, без пагинации

Единственный ключ верхнего уровня — `items`. Нет `total`/`count`/`nextPageToken`/`hasMore`.
Совпадает 1:1 с задокументированной схемой `EmailCalendarResult` (§2). [primary] [established]

### Ф-28. Форма элемента: близка к `EmailCalendarItem`, но не идентична

Ключи, реально встретившиеся хотя бы раз в выборке из 100 элементов (объединение):
`busyType, calendarSource, description, end, id, isRecurring, location, locationAttendee, meetId,
onlineMeetingUrl, onlineUsers, optionalAttendees, organizer, requiredAttendees, room, roomName,
start, stream, subject, urlParams`.

- Два поля отсутствуют в задокументированной `EmailCalendarItem` вовсе: **`meetId`**, **`urlParams`**.
- Среди 100 элементов (74 с `isRecurring: true`) ни разу не встретились документированные поля
  `recurrence`, `isCancelled`, `isAllDayEvent`, `externalMeeting`, `isPrivate`, `onlineUsersCount` —
  даже там, где `isRecurring: true` подразумевает наличие `recurrence` по описанию соседней
  операции (`EmailCalendar_GetRecurrenceEventById`, см. §2).
- `room` внутри элемента — тот же набор полей, что задокументирован для FR-17 («Комната») в
  постановке (`roomName, sessionHalls, stageConferenceId, moderators, ...`), подтверждает связку
  Комната↔Встреча на уровне ответа календаря, не только по имени.

Вывод: внутренний `/api/calendar` — не гарантированно та же реализация, что задокументированный
`/api/EmailCalendar/{email}`, а лишь схожая по форме. [primary] [established по фактам выдачи;
причина расхождения — не то же ли это в бэкенде — не выяснена]

### Ф-29. Сортировка — по возрастанию времени начала

`take=1` → элемент с наименьшим `start` в окне; `take=3` → три элемента строго по возрастанию
`start`. Противоположно `/api/recordings`, где порядок — от новых к старым (Ф-16, прошлая волна).
[primary] [established]

### Ф-30. Семантика выдачи шире, чем «личный календарь вызывающего»

За 7-дневное окно текущая сессия увидела встречи **26 разных организаторов** (не одного — не
похоже на «мой личный календарь»), и ровно 26 разных комнат на 26 элементов (1:1 встреча↔комната).
Правдоподобное прочтение: `/api/calendar` — календарь бронирований комнат Толка в целом (или как
минимум видимых текущей сессии комнат), а не персональный Outlook-календарь вызывающего
пользователя. Проверить с менее привилегированной сессией не удалось — доступен только один
аккаунт для зонда. [primary] [emerging — интерпретация правдоподобна, но не проверена вторым
аккаунтом]

### Ф-31. `calendarSource` — 100% `"ews"` во всей выборке

Подтверждает, что календарь этого пространства Толка интегрирован с Exchange (см. также
`POST /api/Calendar/servers` в §2: «Основным календарем пространства должен быть календарь EWS или
Exchange Online»). [primary] [established]

## §1b. Взаимодействие с режимом авторизации

### Ф-32. Задокументированный аналог `/api/EmailCalendar/{email}` под session-режимом — 401

```
GET /api/EmailCalendar/<self-email>?start=2026-08-13&end=2026-08-14&sessionToken=<REDACTED>
→ 401, пустое тело
```

Подтверждает известный паттерн (CLAUDE.md): интеграторские/задокументированные пути полностью
отвергают sessionToken, а не просто требуют другой scope. [primary] [established]

### Ф-33. Тот же путь под api-key-режимом (недостаточный по правам ключ) — 403

```
GET /api/EmailCalendar/<self-email>?start=2026-08-13&end=2026-08-14
Заголовок: X-Auth-Token: <REDACTED>
→ 403, пустое тело
```

Ожидаемо по спеке (`Разрешения: application.сalendar.read`, см. Ф-36 про опечатку в имени).
[primary] [established]

### Ф-34. Внутренний `/api/calendar` под тем же ключом — 200 (!)

```
GET /api/calendar?start=2026-08-13&end=2026-08-14
Заголовок: X-Auth-Token: <REDACTED>  (тот же ключ, что дал 403 выше)
→ 200, count=10 (то же число элементов, что под сессией для того же окна)
```

Негативные контроли на том же пути и том же окне:

```
X-Auth-Token: 00000000-0000-0000-0000-000000000000 (заведомо неверный) → 401
без заголовка авторизации вовсе                                        → 401
```

То есть путь реально проверяет валидность ключа (невалидный/пустой → 401), но не блокирует
известный по `ktalk auth-status` недостаточный по правам ключ. Значит доступ к недокументированному
`/api/calendar` в api-key-режиме **есть уже сейчас**, несмотря на то, что документированный аналог
и кандидат whoami тем же ключом получают 403. Требуемый (если вообще есть) scope для этого
конкретного пути не выяснен — контраст с Ф-33/Ф-35 показывает, что три родственных операции
проверяют доступ по-разному. [primary] [established сам факт; причина — открытый вопрос]

### Ф-35. Кандидат whoami из прошлой волны под тем же ключом — 403 (пересматривает [emerging] на противоположный установленный факт)

```
GET /api/domain/applications/access-info
Заголовок: X-Auth-Token: <REDACTED>
→ 403, пустое тело
```

RES-001 (`ktalk-integrator-api.md`, находка 8) отмечала этот путь как вероятного «whoami без
scope» — вывод помечался `[emerging — нужна проверка живым запросом]`. Проверка проведена: для
данного ключа эндпоинт **требует** какое-то условие, которого у ключа нет (403, не 200). Прежнюю
гипотезу считать опровергнутой для данного ключа; статус находки RES-001 №8 — пересмотреть на
`[established, отрицательный результат]`. Возможно, дело не в отсутствии scope как такового, а в
каком-то ином необходимом условии (например, типе ключа) — при текущих данных различить нельзя.
[primary] [established]

### Ф-36. Строка разрешения в спеке — не обрезана, а содержит кириллический омоглиф

Постановка со слов владельца утверждала: «у него строка разрешения обрезана до `application.`».
Побайтовая проверка (`unicodedata.name` по каждому символу) показала обратное: строка полная —
`"Разрешения: application.сalendar.write"` (и аналогично `...read` у GET), но 13-й символ слова
`calendar` — `с` (U+0441, CYRILLIC SMALL LETTER ES), не `c` (U+0063, LATIN SMALL LETTER C).
Проверено на обеих операциях (`EmailCalendar_GetAll`, `EmailCalendar_Create`) — опечатка
идентична в обеих. Реальное имя scope в перечислении `TalkScopeType` (RES-001) — `calendar`
(латиницей). Вероятный источник впечатления «обрезано»: ASCII-ориентированный парсер строки
разрешения (например, регэксп с классом `[a-z]` вместо unicode-класса) на кириллическом символе
не матчит остаток слова и визуально даёт «application.» — это гипотеза о причине наблюдения
постановки, не опровержение самого наблюдения владельца. [primary] [established — сам факт
опечатки; гипотеза о причине «обрезанности» — правдоподобное объяснение, не проверено]

## §2. `POST /calendar` — форма тела (документарный анализ, POST на боевой домен не выполнялся)

Красная линия разведки исключает любые пробные записи. Раздел целиком построен на трёх источниках:
1. `talk.public.api-api-2.json` — схема `CreateEmailCalendarEventModel` для **другого** пути
   (`POST /api/EmailCalendar/{email}`, api-key-режим, требует email организатора в пути);
2. `content/10-domain/research/mainpart-ktalk-mcp.md` [secondary] — сигнатура python-функции
   `create_meeting` из чужого MCP-сервера, вызывающей `POST /calendar` (внутренний, session-режим,
   без email в пути) — тот самый путь, который нужен волне;
3. Тексты ошибок валидации `GET /api/calendar` (§1) — не описывают тело POST напрямую, но дают
   независимое подтверждение имён `start`/`end`/`take`/`roomName`, что снижает вероятность
   расхождения именования между чтением и записью в рамках одного и того же внутреннего пути.

Прямого пути к самой схеме `POST /calendar` в спеке нет — это осознанный пробел, а не результат
плохого поиска: раздел «Ф-43» ниже фиксирует, что весь набор Calendar-схем компонентов исчерпан.

### Ф-39. Схема заметно шире сигнатуры mainpart — не покрытые mainpart поля

Минимум 10 задокументированных полей не имеют аналога в python-сигнатуре `create_meeting`:
`allowAnonymous`, `recurrence` (объект), `simultaneousTranslation`, `customMeetingUrl`,
`maskingSettings`, `autoRunDeepFakeDetection`, `isAllDayEvent`, `optionalUserKeys`,
`requiredExternalAttendeesEmails`, `optionExternalAttendeesEmails`, `controlledViaExternalSystem`.

Существеннее всего — **`recurrence`**. `TalkCalendarRecurrence`:

| Поле | Тип |
|---|---|
| `type` | enum `TalkCalendarRecurrencePatternType`: `notSupported, daily, dailyRegeneration, weekly, weeklyRegeneration, monthly, monthlyRegeneration, relativeMonthly, yearly, relativeYearly, yearlyRegeneration` |
| `startDate` | date-time |
| `endDate` | date-time, nullable |
| `numberOfEvents` | int, 1–100, nullable |
| `interval` | int, 1–99, nullable |
| `dayOfMonth` | int, nullable |
| `daysOfTheWeek` | array enum `TalkCalendarDayOfTheWeek` (`sunday`…`saturday`, `day`, `weekday`, `weekendDay`), nullable |
| `month` | enum `TalkCalendarMonth` (`january`…`december`) |
| `dayOfTheWeekIndex` | enum `TalkCalendarDayOfTheWeekIndex` (`first, second, third, fourth, last`) |
| `firstEventId` | string |

`create_meeting` из mainpart предлагает только булев `is_recurring` — флаг «это повторяющаяся
встреча» без единого параметра паттерна повторения. Если `/calendar` действительно использует ту
же по составу модель, что и `/api/EmailCalendar/{email}`, то **`is_recurring=True` без объекта
`recurrence` не может выразить конкретный шаблон повторения** (еженедельно/ежемесячно/по дням
недели) — что произойдёт на практике (ошибка валидации, встреча без реального повторения,
сервер подставляет умолчание) неизвестно и не может быть выяснено без POST. [primary для формы
`recurrence`; вывод о недостаточности `is_recurring` — логическое следствие, не проверено]

### Ф-40. Оговорка про `required`: `start`/`end`/`timezone` не входят в обязательные

`required: ["requiredUserKeys", "roomName", "subject"]` — даты начала/конца и таймзона в этот
список не входят, хотя логически необходимы для назначения времени встречи. Возможные объяснения
(ни одно не проверено): (а) сервер применяет умолчания для не указанных дат; (б) `required` в этой
спеке декларативен и не соответствует фактической серверной валидации (уже наблюдалось для других
операций — CLAUDE.md, «спеке верить нельзя»); (в) поля обязательны фактически, декларация в спеке
неполна. [primary — как факт декларации; причина — открытый вопрос]

### Ф-41. Формат таймзоны подтверждён дважды дословно

Описание поля `timezone` в спеке: «Временная зона в формате GMT+X». Дефолт в сигнатуре mainpart:
`timezone: str = "GMT+3"`. Это единственное поле тела, где совпадение — не только по имени, но и
по формату значения, между двумя независимыми источниками. Самое надёжное поле среди всех
25+ полей тела. [primary + secondary, скрещено] [established формат по документации; фактическое
поведение сервера при других форматах не проверено]

### Ф-42. Прочие типы и границы из документированной модели

`pinCode` — тип `string` (не число), совпадает с `pin_code: str | None` в mainpart. `subject` —
`maxLength: 128`, `minLength: 0` (граница не встречается в сигнатуре mainpart, там просто `str`).
[primary]

### Ф-43. В спеке нет иной Calendar/Meeting-схемы, которая могла бы описывать именно `/calendar`

Полный список схем компонентов с «Calendar» или «Meeting» в имени (21 штука) исчерпывается двумя
семействами: `EmailCalendar*` (создание/чтение/правка встреч по email организатора, см. выше) и
`CalendarServer*`/`TalkCalendarFeatureSettingsModify` (административная настройка интеграции с
внешним календарным сервером — EWS/EWS Office 365/CalDAV, к созданию встреч отношения не имеет).
Нет «осиротевшей» схемы, которая была бы явно про внутренний `/calendar` без пути к ней. [primary]
[established — отрицательный результат поиска]

## §3. Идемпотентность повторного `POST /calendar` (п.3 постановки) — не исследовалась

Постановка (§5, п.3) прямо выносит этот вопрос за периметр разведки: «физически не проверяется без
записи и вынесен в боевую приёмку с ведома владельца». Красная линия разведки запрещает любые
пробные POST на боевой домен без явного разрешения владельца на конкретный запрос. Вопрос
остаётся открытым и должен быть закрыт отдельным, санкционированным владельцем шагом — вероятно,
как часть критерия приёмки «Боевое создание встречи выполнено один раз, в отдельной тестовой
комнате, с ведома владельца» (§6 постановки), а не разведкой.

## Что НЕ удалось выяснить

- **Точные параметры `GET /api/calendar/events`.** Перебраны `id`/`eventId`/`meetId` как query, оба
  варианта как сегмент пути (используя реальные значения `id`/`meetId` из живых элементов
  `/api/calendar`) — во всех случаях либо неизменное `400 «Неверный идентификатор встречи»`, либо
  `404` (путь-сегмент не матчится ни одним маршрутом). Замечено попутно: тело ошибки этого пути
  структурно богаче, чем у `/api/calendar` — содержит `errorSubType: "CalendarBadRequest"`,
  `errorCode: "CommunicationError"`, `errorDetails`, `exception` (все null здесь), тогда как у
  `/api/calendar` — только `errorId/errorType/errorCode:"ValidationError"/errorMessage`. Два разных
  формата ошибки в рамках одного и того же внутреннего контура (Ф-26 vs здесь) — не выяснено, что
  этот путь вообще делает и нужен ли он для FR-18 (сам `/api/calendar` уже отдаёт полные объекты
  встреч, без необходимости в дозапросе за деталями одного события).
- **Причина широты выдачи `/api/calendar` (Ф-30).** Домен-вайд ли это по конструкции, или эффект
  прав конкретного тестового аккаунта — не проверено вторым, менее привилегированным аккаунтом
  (недоступен для зонда).
- **Какой scope (если вообще) реально проверяется на `/api/calendar` под api-key (Ф-34).** Три
  родственных операции под одним и тем же ключом дали три разных результата (200 / 403 / 403) —
  причина расхождения не выяснена ни экспериментом, ни документацией.
- **Всё содержимое §2 не проверено запросом.** Форма тела `POST /calendar` — экстраполяция с
  соседнего пути, не факт. В частности: реагирует ли сервер на `isRecurring: true` без
  `recurrence`; действительно ли `start`/`end`/`timezone` не обязательны на практике, несмотря на
  документированный `required`; принимает ли `/calendar` вообще те же имена полей (camelCase),
  что и `/api/EmailCalendar/{email}`, а не какие-то другие.
- **Идемпотентность повторного POST (п.3 постановки)** — намеренно не исследовалась, см. §3.
