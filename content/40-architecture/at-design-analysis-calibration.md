# AT-design: калибровка рубрики оценки протоколов (ADR-018)

Тест-дизайн для [ADR-018](../00-project/adr/ADR-018-analysis-calibration.md) /
[spec](ADR-018-analysis-calibration-spec.md), контракт с QA-author (spec §5). Правка
рубрики — `skills/ktalk-eval/references/eval-rubric.md` (+ `agents/ktalk-evaluator.md`,
`skills/ktalk-eval/SKILL.md` для NFR-25 AC2), репозиторий `ktalk-plugin`, ветка
`dev-014-analysis-calibration`. Три системных дефекта требования оператор нашёл чтением,
не рубрикой — это то, что закрывает правка ниже.

Периметр: пакет `ktalk-mcp` промт-слоя не касается (ADR-012 §1). Автотеста поведения
промта нет и по границе ADR-012 быть не может — проверка ниже статическая (чтение
текста рубрики/промта) либо прогонная (A/B на записях), не pytest.

## Boundary cases

- Обязательство упомянуто **только** в шапке frontmatter (не в блоке «Формат» и не в
  основном тексте) — §1 Метод п.2 явно включает шапку, не только прозу тела; протокол,
  где шапка противоречит таблице, не может получить Completeness 5.
- Одно и то же третье лицо резолвится в одном месте протокола и не резолвится (кеш
  не сработал) в другом — §3 Schema Consistency чек-лист FR-42 AC4 ловит расхождение
  формы в пределах документа.
- Реплика-акцепт **без** условной конструкции в запросе (обычный прямой запрос, прямое
  согласие) — HIGH правомерен без специального разбора, эталонные пары не единственный
  легитимный путь к HIGH; рубрика не требует буквального совпадения с примерами, только
  наличия акта согласия.
- «Ключевые тезисы» присутствует у `meeting_type: session`, но пустая (нет содержательных
  тезисов без статуса решения в транскрипте) — секция по FR-43 AC2/шаблону всё равно
  опциональна; рубрика не требует непустой секции, только требует **отсутствия** секции
  у не-`session`-типов (см. §3 критерий 4/5 vs 5/5).

## Error cases

**Испорченный/опечатанный ввод (со стороны целевого пользователя — оператора):**
- Оператор запускает `ktalk-eval` без объявленного `routing.eval_report`/`tracker_path` в
  конфигурации проекта-хозяина — SKILL.md шаг 0 уже предписывает явный запрос пути
  пользователю, не угадывание; рубрика этого не проверяет (не её периметр), фиксируется
  здесь как N/A для рубрики, покрыто механикой `SKILL.md`.
- `recording_id`, переданный оценщику, не существует в реестре (опечатка в ID) — вне
  периметра рубрики; обрабатывается `ktalk list`/`ktalk show` (пакет `ktalk-mcp`), не
  промт-слоем анализа. N/A для этой правки.
- Искажённое ASR-имя, которое **не входит** ни в один профиль каталога дословно, но
  частично совпадает с двумя разными профилями (омонимия) — открытый вопрос требования
  (не решён ADR-018, явно оставлен на будущее); рубрика в текущей редакции не даёт
  отдельного критерия для омонимии, попадает под общее правило «не резолвилось →
  `[ASR?]`» без различения причины. Явный **N/A** на разрешение неоднозначности — принято
  требованием, не пробел этой правки.

**Замаскированный отказ (система молча принимает вход / откатывается на дефолт вместо
наблюдаемой ошибки):**
- `commitments_count` совпадает с числом строк таблицы «Договорённости», но обязательство
  осело в прозе — счётчик выглядит «здоровым», маскируя пропуск (сам системный дефект
  FR-40). §1 Completeness Метод п.2 — прямое противоядие: явно требует не доверять
  счётчику как самостоятельному подтверждению полноты.
- Резолвинг третьего лица «молча» пропускается деградацией без объявленного каталога —
  вместо явной пометки всех сомнительных имён система могла бы тихо оставить их как есть
  (что и наблюдалось до ADR-018, §10 `analysis-quality.md` до правки Dev). §2/§3 рубрики
  требуют маркировки при деградации как обязательного исхода, не позволяют «тихому»
  прохождению без пометки остаться незамеченным при оценке.
- HIGH, присвоенный по наличию дословной цитаты реплики-запроса — система не выдаёт
  ошибку и не понижает confidence, а молча использует не тот критерий (наклонение вместо
  акцепта), выглядящий правдоподобно для читателя без сверки с транскриптом. §5
  Confidence Usage, критерий 3/5, называет это явно как отдельный дефект, не растворяет
  в общей формулировке «HIGH для явно выводимого контента».

## Не покрываем (вне scope этой правки)

- Автотест поведения промта (pytest/CI) — не существует и не заводится, граница ADR-012.
- Разрешение омонимии при резолвинге третьих лиц — открытый вопрос требования, будущая
  калибровка.
- Подключение `check-plugin-composition.sh` к CI/pre-commit репозитория `ktalk-plugin` —
  предпосылка DevOps того репозитория, не эта задача.

## Протокол A/B-прогона для оператора

**Записи:** три записи исходного замера (`1-1`, `status`, `session`), те же, что дали
исходные дефекты (`ktalk list --status done --json`, фильтр по `meeting_type`
и дате замера). Если оригинальные записи недоступны (не сохранились/удалены) —
допустимая замена: любая запись того же `meeting_type`, содержащая структурно тот же
класс сценария (обязательство в прозе шапки/«Формата»; пара условный-запрос+акцепт для
confidence). Дополнительно нужна **четвёртая фикстура** — запись (любого типа) с
транскриптом, где третье лицо упомянуто, а `.ktalk.toml` хозяина временно не объявляет
`registry.directories.people` (или каталог профилей физически недоступен) — только так
проверяется FR-42 AC3 (деградация); ни одна из трёх штатных записей это условие не
гарантирует.

**Версии:** «до» — протокол(ы), сгенерированные `ktalk-processor` версии плагина
`1.2.1` (или снятые снапшотом до ветки `dev-014-analysis-calibration`); «после» —
регенерация тех же транскриптов версией `1.3.0` (ветка `dev-014-analysis-calibration`,
коммит `81e09c4`). Рубрика для оценки обеих версий — **одна и та же**, версия из этой
правки (иначе A/B меряет рубрику, не промт).

**Шаги:**
1. `ktalk-eval` A/B режим (`SKILL.md` «A/B режим») на трёх штатных записях +
   отдельный прогон на четвёртой фикстуре (деградация без каталога).
2. Оценить оба протокола (`v1.2.1`, `v1.3.0`) каждой записи откалиброванной рубрикой.
3. Сверить исходы по таблице ниже.

**Ожидаемые исходы (регресс = расхождение с столбцом «Ожидание»):**

| Запись | Проверяемая строка | v1.2.1 (было) | v1.3.0 (ожидание) | Регресс, если |
|---|---|---|---|---|
| status | «интерфейсный трек» — только в блоке «Формат» | нет строки в таблице | строка в таблице «Договорённости» либо явная запись в «Открытых вопросах» | строки нет и причина не зафиксирована |
| status | Запрос 00:46:54 / Акцепт 00:47:09 «Хорошо…Договорились» | HIGH (уже верно) | **остаётся HIGH** | confidence понижен до MEDIUM/LOW — **контроль перекалибровки в обратную сторону**: новое правило не обязано портить уже верную строку |
| session | Запрос 00:57:40 / Акцепт 00:57:51 «Покопать.» | HIGH (дефект) | **становится MEDIUM** | остаётся HIGH — правило §5 не сработало |
| session | `decisions_count`, секция «Ключевые тезисы» | `decisions_count: 0`, тезисы есть | без изменений (регресс-инвариант FR-43) | `decisions_count` изменился без реального решения, либо секция пропала/стала пустой заглушкой |
| 1-1 | Точное имя по каталогу | помечено как неподтверждённое (дефект) | без маркера, исправленная форма | маркер остался |
| 1-1 | Искажённое ASR-имя, не резолвящееся | без маркера (дефект) | `[ASR?]` | маркер отсутствует |
| фикстура (без каталога) | все сомнительные имена | смешанное поведение | все помечены `[ASR?]` | хотя бы одно сомнительное имя без маркера |

Строка «Хорошо…Договорились → остаётся HIGH» и строка «Покопать. → становится MEDIUM» —
обязательная пара контроля: правка нацелена на переход только второй строки, первая —
свидетельство того, что модальность запроса (условная в обеих) не стала новым ложным
триггером понижения confidence.

**Отчёт/трекер:** оба прогона (v1.2.1, v1.3.0) обязаны нести `plugin_version` в отчёте и
строке трекера (NFR-25 AC2) — иначе сравнение A/B неотличимо от одной записи трекера без
даты/версии.
