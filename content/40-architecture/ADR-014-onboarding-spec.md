# ADR-014 spec: контракт онбординг-скрипта плагина ktalk

Companion-спека к [ADR-014](../00-project/adr/ADR-014-sanctioned-onboarding.md). Реализация —
`scripts/ktalk-onboard.sh` в репозитории плагина (`ktalk-plugin`), не в этом репозитории.
Требование-источник: [FR-26…FR-31, NFR-17…NFR-19](../30-requirements/ktalk-plugin-onboarding.md).

## 1. Контракт `ktalk-onboard.sh`

| Команда | Назначение |
|---|---|
| `check` | диагностика: PATH, `uv`, версия |
| `install` | установка/обновление по санкции |
| `grant install\|update` | выдать санкцию (только TTY) |
| `revoke install\|update` | отозвать санкцию |
| `status` | состояние санкций |

Флаг `--json` у `check`, `install`, `status` печатает один JSON-объект в stdout.

| Код | Значение |
|---|---|
| 0 | всё в порядке / операция успешна |
| 10 | `ktalk` не найден в PATH |
| 11 | версия ниже минимально совместимой (или неопределима); у `install` — менеджер отработал, но версия всё ещё ниже минимальной |
| 12 | `uv` не найден в PATH |
| 20 | внутренняя ошибка (нет/битый `compat.json`, неверный аргумент) |
| 30 | нет санкции на установку |
| 31 | установка провалилась |
| 32 | нужно обновление, нет санкции на обновление |
| 33 | `grant` вызван без TTY |

Менеджер один — `uv tool` (ADR-014 §5); подкоманда зависит от ветки:

| Ветка | Команда |
|---|---|
| пакета нет, есть `allow_install` | `uv tool install ktalk-mcp` |
| пакет установлен, версия ниже минимальной, есть `allow_update` | `uv tool upgrade ktalk-mcp` |

Команда установки — та же, что показывается пользователю в совместном режиме (FR-29 AC3);
команда обновления — та же, что скрипт печатает в сообщении кода 11. `uv tool install` на уже
установленном инструменте его не обновляет, поэтому ветка обновления обязана вызывать
`uv tool upgrade`, а не повторять `install`. Ограничение «только `uv tool`» относится к
менеджеру пакетов, а не к подкоманде.

`install` печатает вывод `uv` и код возврата команды (FR-29 AC4), не поглощает их.

**Постусловие `install` (FR-31).** Код возврата менеджера пакетов совместимости не доказывает:
`uv tool upgrade` печатает «Nothing to upgrade» с кодом 0, когда в индексе нет версии новее, а
`uv tool install` завершается успехом, поставив версию ниже минимальной. Поэтому после успешного
запуска команды `install` перечитывает версию (§4) и возвращает **0** только если она не ниже
минимальной; иначе — **11** с тем же статусом (`outdated`) и тем же текстом, что даёт `check` в
этом состоянии. Обе ветки (установка и обновление) подчиняются постусловию одинаково. Сценарий
цепочки в промтах: `check` → (санкция) → `install` → `check`.

`install --json` печатает **один** объект на любом исходе, с полями `report()`
(`status`, `installed_version`, `min_version`, `install_command`, `message`) плюс телеметрия
запуска менеджера: `attempts`, `return_code`, `uv_output` и — только при повторной попытке —
`first_attempt_output`. Экранирование — тем же `json_escape`, что у `report()`.

Приоритет при отсутствии обоих бинарей: если нет ни `ktalk`, ни `uv`, `check` возвращает **12**,
а не 10. Действенная для пользователя причина — отсутствие `uv`: пока его нет, показанная
команда установки невыполнима (FR-27 AC3, ADR-014 §5).

## 2. Схема `onboarding.toml`

Путь: `${XDG_CONFIG_HOME:-$HOME/.config}/ktalk/onboarding.toml`, каталог `0700`, файл `0600`.

```toml
allow_install = true
allow_update = false
granted_at = "2026-08-18"
```

Санкция считается выданной только при точном совпадении строки
`^allow_(install|update)[[:space:]]*=[[:space:]]*true[[:space:]]*$`. Альтернация здесь — схема
формы строки, а не шаблон проверки: в рантайме подставляется **ровно один запрошенный ключ**
(`^allow_<ключ>[[:space:]]*=[[:space:]]*true[[:space:]]*$`), альтернация не используется. Иначе
`allow_update = true` выдал бы санкцию на установку и наоборот, а ключи независимы
(FR-30 AC2, ADR-014 §3). Любое иное содержимое —
санкции нет (fail-closed): отсутствующий файл, `allow_install=maybe`, `allow_install : true`,
закомментированная строка, повреждённый файл читаются одинаково — как отказ. `granted_at` —
информационное поле, на решение не влияет; скрипт его пишет, но не разбирает.

Запись — атомарная: временный файл в том же каталоге, `chmod 600`, затем `mv`. `revoke` не
удаляет файл, а переписывает ключ в `false` — отзыв наблюдаем в `status`.

## 3. Схема `compat.json`

Путь: `compat.json` в корне дерева плагина.

```json
{"ktalk_mcp_min_version": "0.7.0"}
```

Читается `grep` + `sed`, без `jq`: наличие `jq` на машине пользователя не гарантировано.
Файл отсутствует, нечитаем или не содержит ключа — код 20 с сообщением «переустановите
плагин», не молчаливое допущение о версии. README плагина цитирует это число, источник — файл.

## 4. Определение версии

Порядок:

1. `ktalk --version` → строка вида `ktalk-mcp X.Y.Z`, номер извлекается регуляркой
   `[0-9]+\.[0-9]+\.[0-9]+`;
2. fallback `uv tool list` → строка `ktalk-mcp vX.Y.Z` (нужен для версий пакета без флага
   `--version`);
3. обе не сработали → «версия неопределима», трактуется как устаревшая (код 11), не как
   совместимая.

Сравнение версий — покомпонентное на bash (три компонента, недостающие считаются нулём,
суффиксы `-`/`+` отбрасываются), не `sort -V`: на macOS его поведение не гарантировано.

## 5. Классификация ошибок установки

Сетевой класс — регистронезависимое совпадение вывода `uv` с
`failed to fetch|connection|timed out|timeout|temporary failure in name resolution|network|could not resolve`.
Такая ошибка даёт ровно одну повторную попытку той же командой (FR-30 AC4). Всё остальное —
права, конфликт версий, отсутствие пакета в индексе — не повторяется никогда.

Задержка перед повтором — `KTALK_ONBOARD_RETRY_DELAY`, по умолчанию 3 секунды. Переменная
существует ради времени прогона тестов (`KTALK_ONBOARD_RETRY_DELAY=0`), пользовательским
интерфейсом не является и в промтах не упоминается.

Итог обеих веток при неуспехе — код 31 и печать вывода `uv`; система остаётся в состоянии до
попытки (FR-30 AC3) — скрипт сам ничего не откатывает и не доустанавливает частями.

## 6. Текст врезки для промтов

Вставляется дословно в `skills/ktalk-registry/SKILL.md`, `skills/ktalk-eval/SKILL.md`,
`agents/ktalk-processor.md`, `agents/ktalk-evaluator.md` — сразу после frontmatter и заголовка,
идентичным блоком:

```markdown
## Предусловие: пакет ktalk-mcp

Перед первой командой `ktalk` в сессии выполни:

    bash ${CLAUDE_PLUGIN_ROOT}/scripts/ktalk-onboard.sh check --json

Код 0 — работай дальше. Ненулевой код — прочитай `${CLAUDE_PLUGIN_ROOT}/references/onboarding.md`
и действуй по нему; не пропускай шаг молча и не выдумывай результат. Команды установки и выдачи
санкции сам не выполняешь: `install` — только после того как санкция уже выдана пользователем,
`grant` — никогда.
```

Длинные тексты (разбор кодов 10/11/12, инструкция по токену) живут в
`references/onboarding.md` плагина, не во врезке. Значение токена там не запрашивается, не
печатается и не записывается — проверяется только факт настройки (`ktalk auth-status --json`).

## 7. Бриф для Dev

| Задача | Репозиторий | Содержание |
|---|---|---|
| 3 | `ktalk-mcp` | `ktalk --version` (§4, шаг 1) и бамп пакета до 0.7.0 |
| 4 | `ktalk-plugin` | каркас скрипта, `compat.json` (§3), `check` — коды 0/10/11/12/20, `--json` |
| 5 | `ktalk-plugin` | санкция: `status`, `grant` (TTY, код 33), `revoke`, fail-closed чтение (§2) |
| 6 | `ktalk-plugin` | `install`: санкция, идемпотентность, ретрай сетевого класса (§5) |
| 7 | `ktalk-plugin` | `references/onboarding.md`, врезка в четыре промта (§6), правка README |

Порядок обязателен: 4 производит `min_version`, `installed_version`, `version_ge`, `report`;
5 производит `sanction_granted`; 6 их потребляет. Секреты (`KTALK_SESSION_TOKEN`,
`KTALK_PERSONAL_API_KEY`, `KTALK_BASE_URL`) скрипт не читает, не пишет и не печатает.

## 8. Контракт с QA

Автоматически (bash-suite `scripts/test-onboard.sh` в дереве плагина, стабы `ktalk`/`uv` во
временном `PATH`, изолированный `XDG_CONFIG_HOME`):

- `check`: коды 10/11/12/0, fallback на `uv tool list`, валидность JSON при `--json`;
  отдельным кейсом — нет ни `ktalk`, ни `uv` → 12, не 10 (§1);
- санкция: `status` без файла и с файлом, битый файл → fail-closed, `revoke` снимает ключ,
  неверный аргумент `grant`/`revoke` → 20;
- `grant` без TTY → 33 и файл санкции не создан;
- `install`: без санкции → 30 и `uv` не вызывался; с санкцией → 0; уже установлен свежий → 0 и
  `uv` не вызывался; устарел без `allow_update` → 32; устарел при выданном `allow_update` → 0 и
  вызвана именно команда обновления (`uv tool upgrade ktalk-mcp`), не `install` (§1); сетевая
  ошибка → ровно две попытки, код 31; несетевая → одна попытка, код 31; нет `uv` → 12;
- постусловие `install` (FR-31): стаб `uv` отработал успехом, но `ktalk` по-прежнему отдаёт версию
  ниже минимальной → **11**, а не 0; ветка обновления с выводом «Nothing to upgrade» и неизменной
  версией → **11** при том, что вызвана именно `uv tool upgrade`; стаб `uv`, «поставивший»
  совместимую версию → **0** и `status: ok`; `install --json` на коде 11 — один валидный объект со
  `status: outdated`, непустыми `installed_version` и `message`, сохранённым `uv_output`.

Тесты **не** эмулируют TTY через `script` или pty — это обошло бы барьер, который они сами и
проверяют. Автотест ветки «`grant` без TTY» дополнительно подавляет наследование stdin
(`</dev/null`), чтобы отсутствие терминала было детерминированным при любом способе прогона —
из CI, из редактора или из интерактивной оболочки.

Ручная проверка владельца, автоматизации не подлежит:

- ветка записи `grant` в настоящем терминале — файл создан, права `0600`/`0700`, `status`
  показывает санкцию;
- живая установка пакета из публичного индекса (сеть, реальный `uv`);
- FR-31 — после публикации релиза: `check` на машине, где пакет поставлен показанной командой,
  даёт «версия соответствует минимальной». До публикации расхождение фиксируется как открытый
  пункт, а не как провал онбординга.
