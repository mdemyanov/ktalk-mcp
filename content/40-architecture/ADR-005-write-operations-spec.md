# ADR-005 spec: протокол предпросмотра и подтверждения

Companion-спека к [ADR-005](../00-project/adr/ADR-005-write-operations.md). Здесь — детализация,
которую ADR сознательно не несёт: компоненты, форма токена подтверждения, протокол шагов,
валидация состава тела, сценарии отказа, NFR mapping, брифы Dev/DevOps, контракт QA-author.
Источник требований — [«Комнаты, календарь и планирование встреч»](../30-requirements/rooms-calendar-scheduling.md)
(FR-13, NFR-9, «Инварианты и Safeguards»); экстраполяция формы тела и неисследованная
идемпотентность — [RES-003](../10-domain/research/ktalk-calendar-api.md) §2–3.

## Контекст

ADR-005 решает: тело собирает allow-list компоновщик общий для предпросмотра и создания;
подтверждение привязано к содержимому (хеш), не к голому идентификатору; мутирующий вызов
недоступен как MCP-инструмент вообще — только подкомандой CLI за проверкой `isatty()`. Эта спека
не пересматривает решение, только детализирует его до уровня, достаточного Dev и QA-author.

## Компоненты

| Компонент | Ответственность | Входы | Выходы | Зависимости |
|-----------|-----------------|-------|--------|-------------|
| `build_meeting_body` | Allow-list компоновщик тела; единственное место, где параметры превращаются в JSON-тело запроса | именованные параметры (не `**kwargs`) | `dict` тела либо `MissingFieldError` с именем поля | — |
| `PreviewService.preview` | Оркестрирует предпросмотр: строит тело, валидирует NFR-9, считает хеш, выпускает токен | параметры встречи | человекочитаемый текст + `confirmation_id` | `build_meeting_body`, `ConfirmationStore` |
| `ConfirmationStore` | In-memory реестр выданных подтверждений: `id -> {hash, expires_at, consumed}` | `issue(hash)` / `match(id, hash)` / `consume(id)` | `confirmation_id` / `bool` / — | — (живёт в памяти процесса `KTalkClient`-синглтона) |
| CLI `create-meeting confirm` | Единственная точка мутации: проверяет TTY, пересобирает тело, сверяет с хранилищем, вызывает клиент | `--id`, параметры встречи, `sys.stdin`/`sys.stdout` | текст результата, код возврата | `build_meeting_body`, `ConfirmationStore`, `KTalkClient` |
| `KTalkClient.create_meeting` | Ровно одна сетевая попытка `POST /calendar`, без retry | готовое тело | ответ сервера либо сетевое исключение | `httpx`, `OPERATION_PROFILES` (ADR-003) |

## Границы

- Не хранит подтверждения нигде, кроме памяти процесса — перезапуск MCP-сервера/CLI-хоста
  инвалидирует все ожидающие подтверждения молча (нет диска, нет `registry.py` — NFR-8).
- Не реализует retry/backoff для сетевых ошибок мутирующего вызова — решение оператора, не
  автоматика (RES-003 §3: идемпотентность неизвестна).
- Не проверяет существование комнаты/участников по факту (это делает сервер) — валидирует только
  «значение явно передано», не «значение корректно».
- Не даёт обходного пути для неинтерактивной мутации (скрипты, CI, cron) — если такой сценарий
  когда-нибудь понадобится легитимно, это отдельное решение, не тихая правка `isatty()`-проверки.
- Не регистрирует создание/подтверждение встречи как MCP-инструмент — `ktalk_preview_meeting`
  (предпросмотр) в MCP есть, инструмента с сетевым эффектом на запись — нет.

## Форма подтверждения

```python
@dataclass(frozen=True)
class ConfirmationRecord:
    body_hash: str          # sha256 канонического JSON тела (сортированные ключи, ISO-даты)
    expires_at: datetime    # issue_time + TTL; значение TTL -- параметр реализации, не измеренный
                             # факт (сколько минут разумно дать человеку на чтение и решение --
                             # дизайн-выбор, не результат замера)
    consumed: bool = False

class ConfirmationStore:
    def issue(self, body_hash: str) -> str:
        """Непредсказуемый id (secrets.token_urlsafe), не производный от body_hash --
        иначе агент вычислил бы id локально, минуя сам факт вызова предпросмотра."""

    def match(self, confirmation_id: str, body_hash: str) -> bool:
        """False на: id неизвестен, TTL истёк, record.consumed, либо body_hash не совпал --
        любая из причин выдаёт один и тот же отказ вызывающему, не различается в тексте
        (различение впустую подсказывало бы, чем именно управлять для обхода)."""

    def consume(self, confirmation_id: str) -> None:
        """Помечает consumed=True. Вызывается ДО сетевого POST, а не после успешного ответа --
        поэтому сетевая ошибка тоже потребляет токен (см. «Сценарии отказа»)."""
```

## Валидация состава тела (`build_meeting_body`)

- Allow-list полей — ровно то, что назвала постановка, плюс `allowAnonymous`: `subject`, `start`,
  `end`, `timezone`, `roomName`, `requiredUserKeys`, `description`, `enableAutoRecording`,
  `enableSip`, `pinCode`, `allowAnonymous`. Функция не принимает произвольный словарь и не имеет
  параметра для `isRecurring`/`recurrence` — у них физически нет пути в тело.
- Каждый параметр таблицы NFR-9 (участники, комната, время начала/конца, часовой пояс,
  `allowAnonymous`, `pinCode`, `enableSip`, автозапись) по умолчанию `None`; `None` на момент
  валидации => `MissingFieldError(имя_поля)` до обращения к `ConfirmationStore` и тем более к
  сети. `None` — единственный сигнал «не решено»: явный пустой список участников, явная пустая
  строка `pinCode` («без пина»), явные `True`/`False` — валидные решения и проходят.
  Обязательность проверяется по этому списку независимо от `required` документированной схемы
  (`requiredUserKeys`, `roomName`, `subject`) — схема слабее того, что нужно бизнесу (Ф-40), и ей
  нельзя доверять как источнику полноты.
- `description` — единственное поле с тихим дефолтом (`""`), допустимым по NFR-9 явно.
- Канонизация для хеша: `json.dumps(body, sort_keys=True, ensure_ascii=False)`, даты — уже в
  ISO-8601, как их передаёт вызывающий (компоновщик не перекодирует формат даты — вне периметра
  этой волны, см. Ф-41 RES-003: формат `timezone`/`start`/`end` фактическим поведением сервера не
  проверен).

## Сценарии отказа

| Условие | Кто ловит | Сеть? | Сообщение оператору |
|---|---|---|---|
| Поле из NFR-9 не передано явно (`None`) | `build_meeting_body` | нет | имя конкретного отсутствующего поля |
| `isRecurring`/`recurrence`/поле вне состава передано | невозможно на уровне сигнатуры | нет | (структурно недостижимо — не рантайм-ошибка) |
| `create-meeting confirm` вызван не из терминала (пайп/CI) | CLI, до `ConfirmationStore` | нет | «нужен интерактивный терминал» |
| `confirmation_id` неизвестен / TTL истёк / уже `consumed` | `ConfirmationStore.match` | нет | «подтверждение недействительно, повторите предпросмотр» |
| Хеш пересобранного тела не совпал с сохранённым | `ConfirmationStore.match` | нет | тот же текст, что и строкой выше — не различать причину наружу |
| Сетевая ошибка/timeout на `POST /calendar` | `KTalkClient.create_meeting` | да, ровно одна попытка | «исход неизвестен — проверьте календарь (FR-18) перед повторной попыткой»; токен уже `consumed`, повтор требует нового предпросмотра |
| Сервер вернул 4xx/5xx | `KTalkClient.create_meeting` | да | читаемая ошибка API; встреча не создана, токен `consumed` |
| Сервер вернул 2xx | — | да | подтверждение создания, эхо отправленных полей |

## NFR Mapping

- **NFR-9** (нет тихих дефолтов) → `build_meeting_body` валидирует по `None`-сигналу каждое поле
  таблицы независимо от схемы; параметризованный тест на 8 строк таблицы.
- **NFR-6** (10 существующих MCP-инструментов не меняются) → `ktalk_preview_meeting` — новый,
  аддитивный инструмент; мутирующего MCP-инструмента не существует вообще, значит и меняться
  нечему на уровне MCP-контракта записи.
- **NFR-7** (`OPERATION_PROFILES`) → `KTalkClient.create_meeting` идёт через стандартный
  `_call`/`_classify` (ADR-003); недоступность режима диагностируется до того, как протокол
  подтверждения вообще начинает работу с `ConfirmationStore` (точная запись профиля — SA-005).
- **NFR-8** (гейт C13) → компоновщик/хранилище/CLI-обработчик — новые модули; конкретная раскладка
  по файлам и их объём — SA-005, здесь фиксируется только форма контракта.
- **NFR-10** (секреты не в логах) → сообщения об ошибках протокола подтверждения не содержат
  credential; сетевые ошибки `create_meeting` проходят через тот же `redact_secrets`/`KTalkError`,
  что и остальные операции (ADR-003).
- **Р-1 постановки** (трудно для случайного/полностью автоматического вызова) → двухслойная
  защита: привязанный к содержимому токен закрывает случайное/дублирующее создание; исключение
  мутирующего вызова из MCP-поверхности и `isatty()`-барьер в CLI — ответ на «полностью
  автоматического» (см. ADR-005 «Решение», честно назван остаточный риск обхода `isatty()`).
- **RES-003 §3** (идемпотентность не исследована) → потребление токена в момент попытки (не
  исхода) + запрет авто-retry — компенсирующий контроль при неизвестном поведении сервера на
  повтор.

## Контракт с QA-author

**AC (полный список из требования):** FR-13 (7 AC, включая заблокированную боевую проверку),
NFR-9 (1 AC, параметризован таблицей из 8 полей) — полный текст в
[rooms-calendar-scheduling.md](../30-requirements/rooms-calendar-scheduling.md).

**Архитектурный контекст для тестов:**
- Компоненты: `build_meeting_body` (чистая функция), `PreviewService` (оркестрация без сети),
  `ConfirmationStore` (in-memory, чистая логика с инжектируемыми часами), CLI `create-meeting
  confirm` (I/O-граница: TTY, аргументы, вызов клиента), `KTalkClient.create_meeting` (единственная
  точка сетевого эффекта).
- Интеграции: KTalk API (`POST /calendar`, мокируется httpx, живой POST запрещён без санкции
  владельца — RES-003, красная линия разведки); файловая система/TTY — мокируется `pty`/pipes.
- Trust boundaries: параметры вызывающего (агент через MCP либо оператор через CLI) →
  `build_meeting_body` (единственная точка входа в форму тела) → `ConfirmationStore` (единственная
  точка решения «подтверждено ли именно это тело именно сейчас») → `KTalkClient` (единственная
  точка сетевого эффекта, без обратной связи в `ConfirmationStore` кроме `consume`).

**Edge cases / boundary conditions:**
- Предпросмотр с одним отсутствующим полем NFR-9 — сообщение называет именно это поле, не общее
  «неверные параметры» (важно для остальных 7 полей той же таблицы — 8 отдельных тестов).
- Пустой список обязательных участников (валидное явное решение) против отсутствующего параметра
  (невалидно) — оба случая различимы на уровне `None` vs `[]`.
- Явный пустой `pinCode` («без пина») против отсутствующего `pinCode` — то же различение.
- Confirm с телом, отличающимся от преview хотя бы одним полем (например, изменили `roomName`) —
  хеш не совпадает, отказ, сети нет.
- Confirm после истечения TTL — отказ, сети нет, даже если хеш совпал бы.
- Повторный confirm тем же `confirmation_id` после успешного создания — отказ (`consumed`), вторая
  попытка `POST` не выполняется.
- Confirm, вызванный с перенаправленным `stdin`/`stdout` (пайп, тестовый раннер без псевдотерминала)
  — отказ до `ConfirmationStore`, до сети; отдельный позитивный тест — то же самое через `pty`
  (эмулированный терминал) проходит проверку `isatty()`.
- Сетевая ошибка/timeout при `POST /calendar` — ровно одна попытка (без встроенного retry), токен
  помечен `consumed` независимо от исхода, сообщение явно называет неопределённость исхода.
- `isRecurring`/`recurrence` и любое поле вне allow-list — не тестируется как «отклоняется», а
  тестируется как «недостижимо»: у `build_meeting_body` нет параметра для них (проверка сигнатуры,
  не поведения).
- Живой `POST /calendar` и его идемпотентность — вне пирамиды тестов QA-author, заблокировано
  постановкой до санкции владельца (RES-003 §3).

**Test-pyramid рекомендация:**

| AC group | Уровень | Обоснование |
|---|---|---|
| `build_meeting_body` (allow-list, NFR-9 по 8 полям, структурная невозможность recurrence) | unit | чистая функция от параметров, без сети и без I/O |
| `PreviewService.preview` (ноль сетевых вызовов на запись, совпадение полей с create) | unit | мок/spy на транспорт клиента — проверка отсутствия вызывающих запись методов |
| `ConfirmationStore` (issue/match/consume, TTL, single-use, hash-drift) | unit | чистая логика с инжектируемыми часами, без сети |
| CLI `isatty()`-барьер (терминал vs пайп) | integration | требует реального `pty`/pipe на уровне процесса, не мокируется как чистая функция |
| Полный цикл preview → confirm → `POST` (мок-сервер, happy path и сетевая ошибка) | integration | несколько компонентов вместе, мок HTTP-транспорта |
| Ручной боевой AC (санкционированное создание, FR-13 последний AC) | вне пирамиды QA-author | заблокирован постановкой до санкции владельца |

## Бриф для Dev

**Архитектура:** этот файл и [ADR-005](../00-project/adr/ADR-005-write-operations.md).
**Требование:** [rooms-calendar-scheduling.md](../30-requirements/rooms-calendar-scheduling.md), FR-13, NFR-9.
**Фаза:** 0.6.0, первая реализация; боевое создание встречи заблокировано до санкции владельца.

**Реализовать (порядок — fixtures → интерфейсы → реализация → тесты):**
1. `build_meeting_body` — allow-list, `None`-валидация по NFR-9, канонизация для хеша.
2. `ConfirmationStore` + `ConfirmationRecord` — с инжектируемыми часами для тестируемости TTL.
3. `PreviewService.preview` — оркестрация без сети; `ktalk_preview_meeting` как MCP-инструмент
   (тонкая обёртка, по образцу `tools_meetings.py`).
4. CLI `create-meeting preview`/`create-meeting confirm` — `isatty()`-барьер строго в `confirm`,
   не в `preview`; точная раскладка по файлам/подкомандам — предмет SA-005, не додумывать здесь
   архитектурные решения самостоятельно, если раскладка неочевидна — вернуть вопрос SA.
5. `KTalkClient.create_meeting` — регистрация в `OPERATION_PROFILES` по паттерну ADR-003, без
   retry-обёртки.

**Сценарии приёмки:** все AC FR-13 и NFR-9 из требования, кроме отмеченных «заблокирована» —
блокированные не реализуются как боевые тесты, только как задокументированный ручной чек-лист.

  списке MCP-инструментов.
