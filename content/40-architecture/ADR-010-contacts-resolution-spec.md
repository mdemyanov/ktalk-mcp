# ADR-010 spec: Резолюция участника через справочник контактов

Companion-спека к [ADR-010](../00-project/adr/ADR-010-contacts-resolution.md). Раскладка
реализации для DEV-010, брифы Dev/DevOps, контракт QA-author.

## Компоненты

| Компонент | Ответственность | Входы | Выходы | Зависимости |
|-----------|-----------------|-------|--------|-------------|
| `OPERATION_PROFILES["search_contacts"]` (`auth.py`) | путь + режим для операции чтения справочника | — | `EndpointProfile` или `None` | `AuthMode` |
| `search_contacts` (новый, вне `client.py`, гейт C13 — свободная функция по образцу `rooms.get_room`/`calendar_reader`) | один GET-запрос, нормализация ответа в список кандидатов | `client: KTalkClient`, `query: str` | `list[dict]` (кандидаты) | `client._profile_for`, `client._classify` |
| CLI `ktalk search-contacts` (новая подкоманда, по образцу `create-meeting-preview`) | текстовый ввод → печать списка кандидатов; сам `key` в тело не подставляет | `--query` | markdown/`--json`-список кандидатов | `search_contacts` |
| MCP tool `ktalk_search_contacts` (новый, читающий — не входит в реестр мутирующих) | тот же поиск для вызывающего агента | `query: str`, `format` | `raw`/`markdown` | `search_contacts` |
| `build_meeting_body`/`build_required_attendees` (`meeting_body.py`) | **не меняется** — по-прежнему принимает готовые числовые `key` | `required_attendee_keys: list[str]` | тело запроса | — |

## Границы

- Резолюция НЕ встроена в `create-meeting-preview`/`create-meeting-confirm` — оператор вызывает
  поиск отдельно, значение `key` передаёт вручную тем же флагом `--required-attendee-key`, что и
  сегодня (ADR-009 §5).
- `search_contacts` НЕ автовыбирает кандидата ни при 0, ни при >1 совпадении — только печатает
  список/отказ, решение остаётся за оператором.
- `search_contacts` НЕ проверяет и НЕ поддерживает логин как значение `query` — контракт заявляет
  только текст имени/фамилии; попытка передать логин не валидируется отдельно (не запрещена, но и
  не гарантирована), исход не специфицирован.
- Api-key-режим НЕ получает рабочую запись в этой волне — `None` в `OPERATION_PROFILES`, вызов до
  сети отклоняется тем же `OperationNotAvailableError`, что и `get_room`/`get_calendar` в
  api-key-режиме сегодня.

## Поток данных

1. Оператор/агент вызывает `search-contacts --query "<текст>"` (CLI) или `ktalk_search_contacts`
   (MCP).
2. `search_contacts(client, query)` шлёт `GET /api/contacts?query=<query>&top=25&
   fillInMeetingStatus=false&includeKiosks=true`, парсит `{"contacts": [...]}`.
3. Нормализатор возвращает список объектов `{key, name, post}` (`name` — та же функция
   `_display_name`, что уже используется в `auth.py::normalize_participant`, для единообразия ФИО
   по проекту).
4. Вывод: 0 → сообщение «ничего не найдено по запросу «...»», код возврата 1 (CLI) / текст (MCP);
   1 → карточка кандидата с `key` явным текстом, без автоподстановки в какую-либо форму;
   >1 → таблица кандидатов (`key`, ФИО, `post`), без ранжирования, порядок — как в ответе сервера.
5. Оператор запускает `create-meeting-preview`/`confirm` отдельным вызовом с выбранным
   `--required-attendee-key`.

## Интеграционные точки

| Точка | Протокол | Контракт | Auth | Rate limit | Error handling |
|-------|----------|----------|------|------------|-----------------|
| `GET /api/contacts` | HTTPS, session-режим (`?sessionToken=`, стандартный read-путь — НЕ mutating, query не убирается) | `query`, `top=25` (фиксировано компоновщиком запроса, не параметр вызывающего в этой волне), `fillInMeetingStatus=false`, `includeKiosks=true` → `{"contacts": [...]}` | `AuthMode.SESSION` только; `AuthMode.API_KEY` — `None`, `OperationNotAvailableError` до сети | не измерялся, N/A — не было живого объёма запросов для оценки | 401/403 — стандартная `classify_response` (ADR-003); незнакомый код — не обёрнуто корреляционной диагностикой ADR-004 (операция читающая, не mutating, тот же класс, что `get_room`) |

## NFR Mapping

- `### NFR-9 — Нет тихих дефолтов у полей, влияющих на приглашения и доступ` → числовой `key`
  участника по-прежнему не имеет тихого дефолта: резолюция добавляет способ его *найти*, не способ
  его *подставить без явного решения* — компоновщик тела не принимает ничего, кроме явно переданного
  `key`; контракт §3 ADR-010 (таблица «0/1/>1 совпадений») делает решение оператора обязательным
  шагом при любом числе кандидатов.
- `### NFR-7 — Новые операции живут в OPERATION_PROFILES` (rooms-calendar-scheduling.md) →
  `search_contacts` регистрируется записью в таблице, не условием внутри метода клиента; отсутствие
  записи для api-key-режима — управляемый отказ до сети, тот же паттерн, что у `get_room`/
  `get_calendar`.
- `### NFR-10 — Секреты не попадают в логи, трейсбеки и вывод CLI` → `search_contacts` использует
  тот же `KTalkClient`/`redact_secrets`, новых мест логирования секретов не вводит.

## Anti-fabrication (количественные поля)

- Rate limit `/api/contacts` — N/A, не измерялся живым объёмом запросов.
- Поведение при `top` вне диапазона (аналог Ф-21 для `/api/calendar`) — N/A, не проверено; до
  проверки компоновщик запроса фиксирует `top=25` константой, не параметром вызывающего.
- Приём логина в `query` — N/A, отдельный непроверенный замер (см. ADR-010 §4 «Decision»).
- Стабильность порядка кандидатов при повторном запросе с тем же `query` — N/A, не проверялось.

## Бриф для Dev

**Архитектура:** этот файл. **Требование:** [ADR-010](../00-project/adr/ADR-010-contacts-resolution.md).
**Фаза:** DEV-010.
**Реализовать:**
- `OPERATION_PROFILES["search_contacts"]` в `auth.py` (session: `EndpointProfile("/api/contacts",
  None)`; api-key: `None`).
- `search_contacts(client, query)` — свободная функция вне `client.py` (по образцу `rooms.get_room`),
  нормализатор кандидата (`key`, ФИО через переиспользуемую `_display_name`-логику, `post`).
- CLI-подкоманда `search-contacts --query` (по образцу `create-meeting-preview`, без TTY-барьера —
  чтение, не запись).
- MCP tool `ktalk_search_contacts(query, format)` — читающий, без побочных эффектов.
- Вывод для 0/1/>1 совпадений — три разных ветки форматтера (`formatters.py`), явно
  различимые оператором/агентом текстом, не только кодом возврата.
**Порядок:** fixtures (сэмпл ответа `/api/contacts` по форме Ф-53, обезличенный) → профиль → 
`search_contacts` → CLI/MCP → форматтер → тесты.
**Сценарии приёмки:** см. «Контракт с QA-author» ниже.

## Бриф для DevOps

**Архитектура:** этот файл.
**Подготовить:** ничего нового по инфраструктуре — операция читающая, использует существующий

## Контракт с QA-author

**Сценарии приёмки (полный список, формулируются QA-author по этому контракту — capability-спека
для DEV-010 ещё не заведена BA отдельно, это ADR-контракт напрямую, аналог DEV-009 в проекте):**
- Given `query` даёт 0 совпадений, When вызван поиск, Then печатается явный факт «ничего не
  найдено» с текстом запроса, код возврата ненулевой (CLI).
- Given `query` даёт ровно 1 совпадение, When вызван поиск, Then выводится карточка с `key`, ФИО,
  `post`, без автоматической подстановки в тело встречи.
- Given `query` даёт >1 совпадения, When вызван поиск, Then выводится полный список кандидатов без
  ранжирования, `key` виден по каждому, автовыбора нет.
- Given `AuthMode.API_KEY` активен, When вызван `search_contacts`, Then операция отклоняется до
  сетевого вызова (`OperationNotAvailableError`), сеть не используется — тест на моке, без
  реального запроса.
- Given секрет в контексте (session token / api key), When любая из веток (0/1/>1/api-key-отказ)
  печатает вывод, Then секрет не появляется в тексте.

**Архитектурный контекст для тестов:** компоненты — `auth.py::OPERATION_PROFILES`, новая функция
`search_contacts`, CLI-подкоманда, MCP tool, форматтер. Интеграция — `GET /api/contacts`,
session-режим, `KTalkClient`. Trust boundary — оператор вводит текст → `search_contacts` (без
интерпретации, без эвристики) → форматтер (человекочитаемый вывод) → отдельный явный шаг
`--required-attendee-key`.

**Edge cases / boundary conditions:**
- `query` пустая строка — поведение сервера не проверено, N/A; тест должен фиксировать фактическое
  поведение реализации (валидация до сети либо пропуск), не гадать про сервер.
- `query`, совпадающая с логином, а не ФИО — N/A по контракту, тест не должен полагаться на
  конкретный результат (0 или совпадение) как на гарантию.
- Ровно 25 кандидатов (`top`) — граница отображения списка, не потолок сервера (не проверялся);
  тест — на форматтер (список из 25 не обрезается и не переполняет вывод нечитаемо), не на сервер.
- Api-key-режим — только unit (мок), живой запрос невозможен (нет выданных scope, Р-4).

**Test-pyramid рекомендация:**

| Группа | Уровень | Обоснование |
|---|---|---|
| 0/1/>1 совпадений, форматтер | unit | чистая логика ветвления и рендера, без сети |
| Профиль api-key → `OperationNotAvailableError` | unit | тот же паттерн, что тест на `get_room`/`get_calendar` в api-key-режиме |
| `search_contacts` формирует правильный GET (путь, query-параметры, session-транспорт) | integration (мок HTTP-транспорта, не реальный сервер) | проверка контракта запроса без боевого домена |
| Секреты не в выводе по всем веткам | unit | тот же тест-паттерн NFR-5/NFR-10 волны 1/2 |
| Живой `GET /api/contacts` на реальном домене | НЕ автоматизируется этой волной | красная линия SA-010 — боевых запросов не делать; при появлении живой санкции — отдельная задача, аналог RES-003 §5 |
