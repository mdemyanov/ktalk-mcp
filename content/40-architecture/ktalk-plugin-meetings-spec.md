# Промт-слой плагина ktalk для встреч — состав, FR-карта, handoff-тексты

Companion-спека (SA-006) к [ktalk-plugin-meetings.md](../30-requirements/ktalk-plugin-meetings.md)
(FR-32…FR-38, NFR-20…NFR-23), [ADR-015](../00-project/adr/ADR-015-cli-authority-and-write-handoff.md)
+ [ADR-015-spec](ADR-015-cli-authority-and-write-handoff-spec.md) (контракт handoff, здесь —
финальная формулировка), [ADR-012](../00-project/adr/ADR-012-plugin-boundary.md) +
[ktalk-plugin-spec.md](ktalk-plugin-spec.md) (три дома, `.ktalk.toml`), [ADR-006](../00-project/adr/ADR-006-get-room-side-effect.md)
(побочный эффект `get-room`). Значимого нового решения владельца сверх уже принятых в ADR-006/012/015
нет: требование прямо оставляет SA выбор состава навыка/команды/агента (`ktalk-plugin-meetings.md`,
«Вне рамок») — эта спека раскладывает его, тем же приёмом, что `ktalk-plugin-spec.md` для `.ktalk.toml`
(companion без нового ADR). Прочитано перед написанием: пакет `ktalk-mcp` 0.7.0 —
`src/ktalk_mcp/cli_meetings_read.py`, `cli_meeting.py`, `cli_contacts.py`, `cli.py`, `formatters.py`;
дерево плагина `ktalk-plugin` — `skills/ktalk-registry/`, `skills/ktalk-eval/`, `agents/`,
`scripts/check-plugin-composition.sh`, `references/onboarding.md`, `compat.json`, `plugin.json`.

## Развилки и решения

| Развилка | Решение | Обоснование |
|---|---|---|
| Расширить `ktalk-registry` или завести новый навык | **Новый навык `ktalk-meetings`** | Триггеры `description` не пересекаются («записи/транскрипты/реестр» vs «расписание/встреча/участник/комната») — description-based роутинг навыков полагается на непересекающиеся фразы, смешивание ухудшает и то, и другое. Компоненты разные: `ktalk-registry` — SQLite + фоновые агенты-обработчики; встречи — синхронный CLI-запрос/ответ без записи в реестр. Один файл на оба домена раздул бы `SKILL.md` (сейчас 253 строки) до состояния, где Dev/оператору сложнее найти нужный workflow |
| Сколько новых навыков | **Один** (`ktalk-meetings`), не по одному на FR | FR-32…FR-38 — не последовательный pipeline (как `ktalk-registry`: sync→dashboard→select→context→launch→export), а набор из 5 независимых сценариев с общим доменом (встречи/комнаты/участники) и общей эскалацией (FR-38) — естественно живут секциями одного файла, как `ktalk-eval` держит основной workflow и режим A/B в одном `SKILL.md` |
| Нужна ли новая команда `commands/*.md` | **Нет** | Прецедент `ktalk-eval`: нет команды, работает только через description-триггер. Сценарии FR-32…FR-38 — разовые ad hoc запросы («покажи расписание», «найди участника»), не повторяющаяся рутина, как `/ktalk-registry` (синхронизация по расписанию с фоновыми агентами) — обоснование заведения команды для реестра сюда не переносится. Имя `/ktalk:ktalk-registry` уже занято другим навыком, не мешает — команда просто не нужна. Открыто для Dev: завести `/ktalk-meetings` позже, если операторы не находят навык через авто-роутинг — не решение этой спеки |
| Нужен ли новый агент | **Нет** | Все операции FR-32…FR-38 — один синхронный вызов CLI без долгой обработки; `Agent(..., run_in_background=true)` в `ktalk-registry` оправдан минутами анализа транскрипта, здесь такой работы нет |
| Дублировать блок «Предусловие: пакет ktalk-mcp» или выносить в общий файл | **Дублировать** (как уже сделано 4 раза: `ktalk-registry/SKILL.md`, `ktalk-eval/SKILL.md`, `agents/ktalk-processor.md`, `agents/ktalk-evaluator.md`) | Механизма include/вставки для `SKILL.md`/`agents/*.md` не существует (обычный markdown, не шаблонизатор) — извлечение потребовало бы нового инструмента подстановки, не решения этой спеки. Дублирование — уже принятая конвенция дерева, не новая |
| Новые ключи `.ktalk.toml` для маршрутизации артефактов встреч | **Не нужны** | FR-32…FR-38 не производят файлов в проекте-хозяине: результат — текст в диалоге (расписание, предпросмотр, диагностика) и текст команды `*-confirm`, которую оператор выполняет сам в своём терминале. `routing.*` в `.ktalk.toml` существует для маршрутов **сохраняемых** артефактов (протокол, отчёт eval) — здесь сохраняемого артефакта нет ни на одном из FR |
| Номер версии плагина | **1.1.0** (было `1.0.0`) | Аддитивная новая возможность (новый навык), без изменения контракта существующих `ktalk-registry`/`ktalk-eval` — minor по семверу |
| `compat.json` | **Не меняется** (`ktalk_mcp_min_version` остаётся `0.7.0`) | Все нужные CLI-подкоманды (`list-calendar`, `create-meeting-preview/-confirm`, `cancel-meeting-preview/-confirm`, `search-contacts`, `get-room`, `auth-status`, `config show`) уже в 0.7.0 (см. требование, врезка) |

## Границы

- `ktalk-meetings` не открывает и не трогает SQLite-реестр `ktalk-registry` — не пересекается по данным.
- Навык не вызывает `create-meeting-confirm`/`cancel-meeting-confirm` программно ни при каком исходе
  (NFR-23) — граница совпадает с ADR-015 «Решение» п.2.
- Навык не реализует альтернативную проверку занятости имени комнаты — `get-room` не описывается как
  такой инструмент (FR-36 AC2).
- Навык не хранит `.ktalk.toml`-ключи для встреч — они не заводятся (см. «Развилки»).

## Карта FR → CLI-команда → элемент плагина

### FR-32 — просмотр расписания

| | |
|---|---|
| CLI | `ktalk list-calendar --start <ISO-дата> --end <ISO-дата> [--room-name <имя>] --json` |
| Флаги | `--start`/`--end` обязательны, ISO `YYYY-MM-DD`; `--room-name` опционален (без `--json` — markdown) |
| `--json` | Да; печатает `{"items": [...], "incomplete_segments": [[start,end], ...]}` |
| Коды возврата | `0` — успех (включая пустой `items`); `1` — сетевая/авторизационная ошибка (`Ошибка: ...` в stderr) |
| Действие навыка | Given оператор назвал даты — вызывает с явными `--start`/`--end` (не подставляет период сам, FR-32 AC1). При непустом `incomplete_segments` — переносит предупреждение в свой ответ дословно, не отбрасывает (FR-32 AC2). Код `1` → «расписание не получено: <текст CLI>» + эскалация FR-38, никогда не «встреч нет» (FR-32 AC3) |
| Элемент | `skills/ktalk-meetings/SKILL.md`, секция «Расписание» |

### FR-33 — создание встречи

| | |
|---|---|
| CLI (шаг агента) | `ktalk create-meeting-preview --subject "..." --start ... --end ... --timezone ... [--room-name ...] [--required-attendee-key ... ]* \| --no-required-attendees [--description ...] [--enable-auto-recording true\|false] [--pin-code ... \| --no-pin-code] [--allow-anonymous true\|false [--anonymous-access-expiration ...]]` |
| `--json` | **Нет флага `--json` у этой команды** — вывод всегда markdown (`format_meeting_preview`); навык парсит markdown-вывод, не JSON |
| Коды возврата | `0` — предпросмотр построен; `1` — `MissingFieldError` (не хватает обязательного поля) |
| CLI (текст для оператора, не вызывается агентом) | `ktalk create-meeting-confirm` с теми же флагами — см. «Handoff-сообщение» |
| Действие навыка | Given не хватает поля из перечня NFR-9 — не подставляет дефолт, либо переспрашивает оператора, либо передаёт `create-meeting-preview` без поля и показывает отказ CLI как есть (FR-33 AC3). Given предпросмотр построен — формирует handoff-сообщение (три части, см. ниже) и останавливается; не вызывает и не предлагает subprocess/скрипт для `create-meeting-confirm` (FR-33 AC1, NFR-23) |
| Элемент | `skills/ktalk-meetings/SKILL.md`, секция «Создание встречи» |

### FR-34 — отмена встречи

| | |
|---|---|
| CLI (шаг агента) | `ktalk cancel-meeting-preview --id <base64-id> [--reason "..."]` |
| `--json` | Нет флага — вывод всегда markdown (`format_cancel_preview`) |
| Коды возврата | Всегда `0` (компоновка без сети и без обязательных полей сверх `--id`, которое обеспечивает argparse) |
| CLI (текст для оператора) | `ktalk cancel-meeting-confirm --id <тот же id> [--reason "тот же текст"]` |
| Действие навыка | Given нет `id` — предлагает получить его из `list-calendar` (FR-32) или из вывода `create-meeting-confirm`, не изобретает и не запрашивает как произвольную строку без пояснения формата (FR-34 AC2). Given предпросмотр показан — формирует handoff-сообщение, не вызывает `cancel-meeting-confirm` (FR-34 AC1, NFR-23) |
| Элемент | `skills/ktalk-meetings/SKILL.md`, секция «Отмена встречи» |

### FR-35 — поиск участника

| | |
|---|---|
| CLI | `ktalk search-contacts --query "<имя/фамилия>"` |
| `--json` | **Нет флага `--json`** — только markdown (`format_search_contacts`) |
| Коды возврата | `0` — ровно один кандидат; `1` — **и** «0 кандидатов» (текст `Ничего не найдено по запросу «…»` на **stdout**), **и** сетевая/авторизационная ошибка (`Ошибка: ...` на **stderr**) — код одинаковый, различение по каналу и тексту, не по коду возврата |
| Действие навыка | При `1` проверяет: если stdout содержит «Ничего не найдено» — «участник не найден по запросу», не путает с ошибкой (FR-35 AC3); если текст в stderr — ошибка сети/авторизации, эскалация FR-38. При `>1` кандидатов (multi-строка markdown-таблица) — показывает всех (`key`, ФИО, должность), явно просит оператора выбрать, не берёт первого (FR-35 AC1). При ровно одном кандидате (код `0`) — показывает, чей `key` подставлен, **до** передачи в `--required-attendee-key` дальнейшего сценария создания встречи (FR-35 AC2) |
| Элемент | `skills/ktalk-meetings/SKILL.md`, секция «Поиск участника» |

### FR-36 — диагностика комнаты

| | |
|---|---|
| CLI | `ktalk get-room <room_name> --json` |
| `--json` | Да |
| Коды возврата | `0` — успех; `1` — сетевая/авторизационная ошибка |
| Действие навыка | Каждый вызов — предупреждение о побочном эффекте, безусловно (текст ниже), плюс данные комнаты. Запрос «проверь, свободно ли имя» — не вызывает `get-room`, объясняет отсутствие такой проверки в контуре (FR-36 AC2) |
| Элемент | `skills/ktalk-meetings/SKILL.md`, секция «Диагностика комнаты» |

### FR-37/FR-38 — деградация и эскалация (сквозные, не отдельная CLI-команда)

| | |
|---|---|
| CLI (эскалация) | `ktalk auth-status --json`, при подозрении на конфигурацию хозяина — `ktalk config show --json` |
| Действие навыка | Текст отказа любой из команд FR-32/FR-33/FR-34/FR-35/FR-36 передаётся оператору без искажения (FR-37 AC1) — не подменяется на «что-то пошло не так», не намекает на вероятный успех для неподтверждённого профиля (FR-37 AC2). При отказе — предлагает `auth-status --json` (выполняет с согласия оператора); если похоже на раскладку хозяина — дополнительно `config show --json`; не единственная гипотеза при не-авторизационной ошибке — корреляционная диагностика CLI (если сработала) передаётся как есть (FR-38 AC1/AC2) |
| Элемент | Общая секция «Диагностика при отказе» в `SKILL.md`, на неё ссылаются все секции FR-32/33/34/35/36 (не дублируется 5 раз) |

## Handoff-сообщение — точный текст (FR-33/FR-34, ADR-015 «Решение» п.2)

Три части одним сообщением, без сокращений.

### FR-33 (создание)

```
{вывод create-meeting-preview как есть, без сокращения полей}

Команда для запуска лично вами, в вашем терминале:

    ktalk create-meeting-confirm --subject "<то же значение>" --start <то же> --end <то же> \
      --timezone <то же> [--room-name <то же>] [--required-attendee-key <то же>]... \
      [--no-required-attendees] [--description <то же>] \
      [--enable-auto-recording <то же>] [--pin-code <то же> | --no-pin-code] \
      [--allow-anonymous <то же> [--anonymous-access-expiration <то же>]]

Выполните эту команду сами в своём терминале — я не подтверждаю и не создаю встречу
за вас: без реального интерактивного терминала (isatty()) команда откажет. Так устроено
намеренно (ADR-005 §3) — подтверждение пишущей операции остаётся вашим осознанным
действием, не шагом, который может выполнить агент.
```

Квадратные скобки — опциональность флага (передаётся, только если был передан в
`create-meeting-preview`); значения — буквально те же, не значения по умолчанию, не
пересчитанные заново (ADR-015 «Решение» п.2).

### FR-34 (отмена)

```
{вывод cancel-meeting-preview как есть}

Команда для запуска лично вами, в вашем терминале:

    ktalk cancel-meeting-confirm --id <тот же id> [--reason "<та же причина>"]

Выполните эту команду сами в своём терминале — я не подтверждаю и не отменяю встречу
за вас: без реального интерактивного терминала (isatty()) команда откажет. Так устроено
намеренно (ADR-005 §3) — подтверждение пишущей операции остаётся вашим осознанным
действием, не шагом, который может выполнить агент.
```

## Предупреждение `get-room` — точный текст (FR-36 AC1, ADR-006 п.2)

Безусловное, одинаковое при любом входном имени — условного варианта не существует физически
(ADR-006 п.2: сервер не различает существовавшую и созданную этим вызовом комнату).

```
⚠️ Обращение к get-room может создать комнату как побочный эффект, если это имя раньше
не встречалось в контуре — сервер не отличает существовавшую комнату от только что
созданной этим вызовом, и созданный объект нельзя удалить средствами проекта (ADR-006
п.2). Это предупреждение показывается при каждом вызове, для любого имени — контур не
даёт сигнала «имя новое» заранее. get-room нельзя использовать, чтобы проверить,
свободно ли имя комнаты, — такой проверки в контуре не существует (ADR-006 п.5).
```

## Расширение `scripts/check-plugin-composition.sh`

Один новый `check` (тот же вид, что 4 существующих), к уже проверяемым утечкам раскладки
хозяина/абсолютных путей/секретов/домена добавляется утечка канала MCP для операций встреч (NFR-20):

```bash
# MCP-имена операций встреч — промт-поверхность обязана называть только CLI-команды
# (ADR-012 §2а, ADR-015 «Решение» п.1: MCP заморожен для этой поверхности, FR-32…FR-36).
check "MCP-имя операции встреч вместо CLI" \
  'ktalk_list_calendar|ktalk_get_room|ktalk_search_contacts|ktalk_preview_meeting|ktalk_preview_cancel_meeting'
```

Имена — точные имена MCP-инструментов пакета (`tools_meetings.py`, `tools_rooms.py`,
`tools_contacts.py`, `tools_scheduling.py`, `tools_meeting_cancel.py`), не предположение.

**NFR-22/NFR-23 (отсутствие программного вызова `*-confirm`) в этот скрипт не входит.** Существующие
4 проверки — простой негативный grep содержимого (значение утекло в текст плагина или нет, бинарный
факт). Различить «`create-meeting-confirm` упомянута как текст для оператора» (обязательное
поведение, FR-33 AC1) от «`create-meeting-confirm` вызвана агентом программно» (запрещённое, NFR-23)
по одному grep-паттерну без семантики контекста нельзя — эта проверка требует того же приёма, что
`ADR-015-spec` уже назначила QA-author («текстовый снимок дерева промта»), не блайнд-grep сборочного
скрипта. Остаётся контрактом QA-author (`ADR-015-spec`, «Test-pyramid рекомендация»), не переносится
сюда.

## NFR Mapping

- `### Requirement: NFR-20` (только CLI) → карта FR→команда выше не называет MCP-инструмент ни в одной
  секции; новый `check` в `check-plugin-composition.sh` — автоматическая проверка того же факта.
- `### Requirement: NFR-21` (секреты не в промтах) → навык не читает `KTALK_SESSION_TOKEN`/
  `KTALK_PERSONAL_API_KEY` напрямую — только вывод CLI, уже прошедший `redact_secrets`; навык не
  добавляет значение секрета повторно из окружения.
- `### Requirement: NFR-22` (без авто-повтора `*-confirm`) → навык не вызывает `*-confirm`
  программно вовсе (ни при каком исходе — handoff останавливает автономный участок), значит и
  повторного вызова после сбоя нет структурно, не только по соглашению.
- `### Requirement: NFR-23` (подтверждение — действие человека) → handoff-сообщение (FR-33/FR-34) —
  единственный выход из автономного участка; текст явно называет причину (TTY-барьер) и то, что
  выполняет оператор лично.

**Сценарии приёмки (полный список из capability-спеки, `ktalk-plugin-meetings.md`):**

- FR-33 AC1/AC2/AC3

- FR-35 AC1/AC2/AC3
- FR-36 AC1/AC2
- FR-37 AC1/AC2
- FR-38 AC1/AC2
- NFR-20 AC, NFR-21 AC, NFR-22 AC, NFR-23 AC

**Архитектурный контекст для тестов:**
- Компоненты: `skills/ktalk-meetings/SKILL.md` (новый, единственный элемент, реализующий FR-32…FR-38);
  без новых `commands/`/`agents/`/`.mcp.json`-записей.
- Интеграции: только CLI `ktalk` (Bash tool) — `list-calendar`, `create-meeting-preview`/`-confirm`,
  `cancel-meeting-preview`/`-confirm`, `search-contacts`, `get-room`, `auth-status`, `config show`.
- Trust boundary: навык (недоверенный источник действия) → handoff-сообщение → терминал оператора
  (доверенный источник) → `*-confirm` — тот же контур, что `ADR-015-spec`, применён к конкретному
  новому файлу.

**Edge cases / boundary conditions:**
- `search-contacts` код `1` без stderr, только stdout «Ничего не найдено» — навык обязан не
  путать это с кодом `1` из сетевой ошибки (stderr непустой); текст-снимок обоих путей нужен отдельно.
- `create-meeting-preview`/`cancel-meeting-preview`/`search-contacts` не поддерживают `--json` —
  навык обязан парсить markdown-вывод этих трёх команд, не пытаться передать им `--json` (снимок
  промта: отсутствие `--json` в этих трёх вызовах).
- `cancel-meeting-preview` не имеет ошибочной ветки вовсе (всегда код `0`) — сценарий «нет `id`»
  обрабатывается **до** вызова CLI (навык не находит `id` у оператора), не как код возврата команды.
- Флаги в напечатанной команде `*-confirm`, не совпадающие буквально с флагами `*-preview` —
  покрыто `ADR-015-spec` (edge case уже описан там), не дублируется тестом здесь повторно.

**Test-pyramid рекомендация:**

| Группа AC | Уровень | Обоснование |
|---|---|---|
| FR-33 AC1/AC2, FR-34 AC1, NFR-22/NFR-23 (отсутствие программного `*-confirm`, текст handoff) | статическая проверка/снимок промта (плагин) | grep + текстовый снимок `skills/ktalk-meetings/SKILL.md` |

| FR-35 (0/1/>1 кандидатов, различение источника кода `1`) | integration | замоканный `search-contacts` с тремя фикстурами вывода (пусто/один/много) + фикстура ошибки в stderr |
| CLI-команды сами по себе (`PreviewService`, `search_contacts`, `get_room`, `get_calendar_window`) | не входит в эту волну | уже покрыты тестами пакета `ktalk-mcp` (0.6.0/0.7.0) |

Фреймворк для статических/integration-проверок в дереве плагина — выбор QA-author под стек плагина,
