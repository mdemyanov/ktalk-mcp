# ADR-004 spec: подтверждённость путей, каталог ошибок, механизм детекции деградации

Companion-спека к [ADR-004](../00-project/adr/ADR-004-undocumented-contour.md). Здесь —
детализация, которую ADR сознательно не несёт: таблица подтверждённости по путям, каталог известных
текстов ошибок недокументированного контура, механизм различения причины сбоя, слои проверки
(unit/живой прогон), ориентир для SA-005, бриф для SA-005/DevOps, контракт с QA-author. Источник
требований — [«Комнаты, календарь и планирование встреч»](../30-requirements/rooms-calendar-scheduling.md)
(FR-17, FR-18, FR-13, NFR-7); источник фактов — [RES-003](../10-domain/research/ktalk-calendar-api.md).

## Контекст

Три операции волны 2 живут вне спеки целиком или частично (см. ADR-004 «Контекст»). Ключевая
асимметрия — Ф-33/Ф-34/Ф-35 RES-003: под одним и тем же api-key-ключом `GET /api/calendar` даёт
200, а родственные `GET /api/EmailCalendar/{email}` и `GET /api/domain/applications/access-info` —
403; негативные контроли (неверный ключ, отсутствие заголовка) на `/api/calendar` дают 401, то есть
путь проверяет валидность ключа, но не блокирует известную по `auth-status` нехватку scope.
Причина не установлена ни экспериментом, ни документацией.

## Таблица подтверждённости по путям

Столбец «Принцип профиля» — не литерал кода: следствие применения решения ADR-004 п.2 к каждой
строке. Конкретную запись `OPERATION_PROFILES` (структура `EndpointProfile`, точные пути,
квотирование параметров) кладёт SA-005.

| Операция | Режим | Живой исход | Причина доступа | Принцип профиля этой волны | Источник |
|---|---|---|---|---|---|
| Чтение комнаты | session | 200 | обычный доступ по сессии (нет понятия scope) | рабочий | постановка §5 |
| Чтение комнаты | api-key | не проверено вовсе | — | без записи (untested), отказ до сети (FR-17 AC3) | RES-003, не тестировался |
| Чтение календаря | session | 200 | обычный доступ по сессии | рабочий | RES-003 Ф-17–Ф-31 |
| Чтение календаря | api-key | 200 | **не объяснена** — расходится с 403 у документированного аналога и у кандидата whoami тем же ключом | без записи (принцип ADR-004 п.2) — 200 не переносится в «рабочий» профиль этой волной | RES-003 Ф-33–Ф-35 |
| Планирование встречи (POST) | session | санкционированный боевой POST дал 404 (ADR-007); встреча не создана, доказано отдельным чтением | путь `/api/calendar` с префиксом `/api`, согласован с обоими подтверждёнными путями контура (ADR-007 п.1) — сама попытка результата не подтвердила, исходный путь без `/api` был ошибкой прочтения источника | реализуется по документарной экстраполяции формы тела (FR-13/NFR-9, Ф-37–Ф-38) и по исправленному прочтению пути (ADR-007); статус «путь неверифицирован живым ответом» сохраняется до новой санкционированной боевой проверки | RES-003 §2, mainpart, ADR-007 |
| Планирование встречи (POST) | api-key | не проверено вовсе, ни одного сигнала ни за, ни против | — | без записи (untested) — тот же принцип, что и чтение комнаты api-key | RES-003 §3 |

## Каталог известных текстов ошибок недокументированного контура

Единственный путь с исчерпывающим каталогом на дату волны — `GET /api/calendar` (Ф-26 RES-003,
собран систематическим перебором read-only запросов). У чтения комнаты и у `POST /calendar` такого
каталога нет — известен только положительный случай (комната) либо вовсе ничего (POST). Это
асимметрия покрытия детекции, не пробел составления документа: у POST не может быть каталога без
нарушения красной линии разведки.

| Условие | `errorMessage` (дословно) |
|---|---|
| нет `start` | «Дата начала является обязательной для заполнения» |
| есть `start`, нет `end` и нет `take` | «Должна быть задана или дата окончания, или количество запрашиваемых элементов» (дублируется дважды в одном сообщении) |
| `end - start` > 7 дней | «Период запроса не должен превышать 7 дней» |
| `end` < `start` | «Дата окончания должна быть больше даты начала» |
| `start` не парсится как дата | «The value '...' is not valid for Start.» |
| `take` вне 1..1000 | «The field Take must be between 1 and 1000.» |

Любой другой текст 400 у уже знакомого запроса к `/api/calendar` — сам по себе сигнал дрейфа
контракта (см. «Механизм детекции»), не повод расширять этот каталог молча.

## Механизм детекции деградации

<mermaid path="./ADR-004-drift-detection.mermaid" width="900px" height="620px"/>

Псевдокод (иллюстративный, не нормативная сигнатура — точное размещение и имена SA-005):

```python
def diagnose_undocumented_failure(op, response_or_exc, auth_context):
    control_op = CONTROL_OPERATION[auth_context.mode]  # уже подтверждённая, дешёвая операция
    control_result = call(control_op)                  # тот же режим, отдельный сетевой вызов
    if control_result.failed_the_same_way(response_or_exc):
        return classify(response_or_exc, auth_context)  # существующий классификатор ADR-003
    return ContourDriftError(op, response_or_exc)        # новый класс: явный, не тихий откат
```

Правила:
- Контрольный вызов выполняется **только** при уже подозрительном исходе недокументированного пути
  — не на каждый штатный вызов; иначе цена корреляции ложится на весь обычный трафик, а не только
  на диагностику сбоя.
- Контрольная операция обязана быть уже подтверждённой (есть рабочая запись профиля для активного
  режима) и дешёвой по побочным эффектам — не сам проверяемый путь и не другой недокументированный
  путь; конкретный выбор (`list_recordings` для session, `get_recording` для api-key — оба уже
  рабочие по ADR-003) — раскладка SA-005, здесь фиксируется только требование к её свойствам.
- Деградация формы при сохранённом коде 200 (пропажа `items`/`roomName`/`start`) обрабатывается той
  же дисциплиной: явный `ContourDriftError`-класс, не `KeyError`/`None`/пустой список.
- `create_meeting` подключена к тому же корреляционному вызову, что чтение календаря (ADR-007):
  сетевые исключения и исключения `_classify` на `POST /api/calendar` идут через
  `diagnose_undocumented_failure` с контрольным вызовом `list_recordings(top=1)` для session.
  Санкционированная боевая проверка (постановка §6) остаётся единственным источником правды о
  фактическом состоянии пути — корреляция локализует причину сбоя (контур vs токен/сеть) в момент
  этой проверки, не заменяет её.

## Слои проверки: что доказывает мок, что требует живого прогона

| Сценарий | Слой | Обоснование |
|---|---|---|
| Fail-closed для операции без записи профиля (room/api-key, calendar/api-key, POST/api-key) | unit | spy на транспорте: ноль исходящих HTTP-вызовов до `OperationNotAvailableError` — проверяем свой код, не сервер |
| Корреляционная диагностика: комбинации (недокументированный ответ × контрольный ответ) → вердикт | unit | оба ответа мокируются; матрица минимум: недок=404/контроль=200, недок=401/контроль=401, недок=неизвестный 400/контроль=200, недок=сетевая ошибка/контроль=200 |
| Маппер календаря терпим к отсутствию документированных полей, сохраняет недокументированные (`meetId`, `urlParams`) | unit на фикстурах из Ф-28 | чистая функция `dict → DTO`, без сети |
| Явная опознаваемая ошибка при пропаже поля контракта (`items`, `roomName`, `start`) на коде 200 | unit | фикстура «200 с усечённым телом» |
| Каталог известных текстов 400 (Ф-26) распознаётся по имени условия; незнакомый текст даёт `ContourDriftError`, не общий `400` | unit | по фикстуре на строку каталога + одна фикстура «неизвестный текст» |
| Фактическое состояние контракта на боевом домене (путь ещё существует, форма ещё та же) | **вне пирамиды — живой прогон** | мок по определению воспроизводит заданное, не видит реальный сервер; требует боевых учётных данных, которых в CI нет |

## Ориентир для SA-005 (иллюстративно, не нормативно)

Как отразить «наблюдался 200, но профиль не подтверждён» так, чтобы решение было видно в коде, а
не только в этом документе, — открытый вопрос раскладки. Не предписывается, для затравки:
- **Вариант А.** Оставить `AuthMode.API_KEY: None` для `get_calendar`, как для любой неподтверждённой
  операции — простейший, ничего не меняет в модели данных; факт «200 наблюдался эмпирически» живёт
  только в RES-003 и здесь.
- **Вариант Б.** Тот же `None`, но с комментарием в коде, ссылающимся на ADR-004 — минимальная
  связность код↔решение без изменения модели `EndpointProfile`.
- **Вариант В (отклонён ADR-004, «Альтернативы»).** Третье состояние доверия в `EndpointProfile` —
  избыточно ради одной записи с невыясненной причиной.

Оба совместимых варианта (А/Б) реализуют решение ADR-004 п.2 корректно; выбор между ними не влияет
на архитектуру, только на читаемость кода — решает SA-005.

## Границы

- Не решает раскладку кода и точные записи `OPERATION_PROFILES` — предмет SA-005.
- Не решает сегментацию 7-дневного окна `GET /api/calendar` на укладывающиеся в лимит запросы —
  отдельное архитектурное решение (FR-18 постановка), не предмет этого документа.
- Не выполняет и не санкционирует боевой `POST /calendar` — красная линия разведки и критерий
  приёмки постановки §6 остаются в силе; этот документ не заменяет санкцию владельца.
- Не вводит автоматический мониторинг/алертинг как систему — фиксирует только принцип «мок не
  заменяет живой прогон»; кто и когда прогоняет зонд — операционная процедура DevOps, не архитектура.

## NFR Mapping

- **NFR-7** (новые операции живут в `OPERATION_PROFILES`, отказ до сети для операции без записи) →
  механизм ADR-003 переиспользуется без изменений архитектуры; принцип ADR-004 п.2 сужает, какие
  наблюдения вообще дают право на запись, но не меняет сам механизм отказа.
- **NFR-10** (секреты не в логах/трейсбеках/выводе CLI) → `ContourDriftError` и сообщения
  корреляционной диагностики строятся из статичных текстов, кода ответа и имени операции — никогда
  из `str(request.url)`/заголовков (тот же барьер, что `SecretRedactor` ADR-003).
- **Р-3 постановки** (внутренний контур без контракта — как заметим деградацию) → закрыт целиком
  этим документом: корреляционная диагностика причины + явная ошибка формы при 200 + разделение
  unit/живой прогон.

## Бриф для SA-005

**Архитектура:** этот файл и [ADR-004](../00-project/adr/ADR-004-undocumented-contour.md).
**Подготовить:** конкретные записи `OPERATION_PROFILES` для трёх операций волны по принципам
таблицы «Подтверждённость по путям» выше; реализацию корреляционной диагностики как переиспользуемый
компонент (не по копии на операцию); выбор контрольных операций по режиму; маппер календаря,
терпимый к составу полей (Ф-28); маппер комнаты по 18 полям FR-17.
**Порядок:** fixtures (каталог Ф-26 + сценарии деградации формы) → интерфейсы (профиль/классификатор/
маппер) → реализация → тесты.
**Учесть отдельно:** статус `get_calendar`/api-key и `create_meeting`/api-key остаётся «без записи»
до отдельного обоснования (ADR-004 п.2) — не переносить в рабочие по факту одного наблюдения 200.

## Бриф для DevOps

**Архитектура:** этот файл.
**Подготовить:** runbook «живой смоук-прогон недокументированного контура» — неразрушающий (только
GET) повтор зонда RES-003 по комнате и календарю в обоих режимах, где применимо, как ручная/полу-
ручная практика перед релизом волны и при первом появлении `ContourDriftError` в выводе.
Периодичность и владелец процедуры этим документом не фиксируются числом (не измерялось,
каденция — операционное решение вне архитектуры). Боевые учётные данные для прогона не хранятся в
CI — прогон выполняется вручную оператором, тем же способом, что и разведка RES-003.
**NFR:** NFR-10 — вывод смоук-прогона проходит через тот же санитайзер, что штатный CLI/MCP вывод.

## Контракт с QA-author

**Архитектурный контекст для тестов:** три недокументированных пути (комната, календарь, создание
встречи), корреляционная диагностика причины сбоя (`diagnose_undocumented_failure`), `ContourDriftError`
как отдельный класс ошибки, маппер календаря терпимый к составу полей (Ф-28), fail-closed поведение
для операций без записи профиля (тот же механизм ADR-003, распространённый на три новые операции).

**Сценарии приёмки, которые этот документ затрагивает:**
- FR-17 AC3 (api-key-режим без подтверждённого профиля отказывает до сетевого вызова) — тот же
  принцип теперь явно распространён на `get_calendar`/api-key и `create_meeting`/api-key.
- FR-18 (чтение календаря) — корректность полей результата зависит от терпимого маппера (Ф-28), не
  от буквального следования документированной `EmailCalendarItem`.
- FR-13 (планирование встречи) AC про сетевую ошибку/таймаут при создании — смежный, но отдельный
  от детекции контура механизм (нет авто-повтора записи); `create_meeting` подключена к
  корреляционной диагностике этого документа (ADR-007), детали обёртки — в
  [ADR-007 spec](ADR-007-create-meeting-path-correction-spec.md).

**Edge cases / boundary conditions:**
- Комбинаторная матрица (недокументированный ответ × контрольный ответ): 404/200, 401/401,
  неизвестный-400/200, сетевая-ошибка/200, 403/403 — каждая пара даёт свой, детерминированный вердикт.
- 200 с телом, из которого пропало поле, на которое опирается контракт (`items`, `roomName`,
  `start`) — должно давать `ContourDriftError`, не пустой/усечённый, но «валидный на вид» результат.
- Текст 400 у `/api/calendar`, не входящий в каталог Ф-26, — отдельный сигнал, не общий 400.
- Элемент календаря без документированных `recurrence`/`isCancelled`/`isAllDayEvent`/
  `externalMeeting`/`isPrivate`/`onlineUsersCount` — валиден, не ошибка маппера.
- Элемент календаря с `meetId`/`urlParams` (вне спеки) — поля сохраняются в результате, не
  отбрасываются как «неизвестные для схемы».
- Корреляционный вызов не выполняется на штатном успешном ответе недокументированного пути — только
  при уже подозрительном исходе (проверка отсутствия лишнего сетевого вызова в счастливом пути).

**Test-pyramid рекомендация:** таблица «Слои проверки» выше — дословно переиспользуется как
test-pyramid рекомендация для QA-author; последняя строка («живой прогон») — вне автоматизируемой
пирамиды, фиксируется как ручной чеклист DevOps/оператора, не как тест QA-author.
