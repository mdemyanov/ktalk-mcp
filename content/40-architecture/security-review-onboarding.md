# Security review: волна 4, санкционированный онбординг плагина (SEC-004)

DevSecOps-ревью первого исполняемого файла в дереве плагина, умеющего менять состояние машины.
Скоуп: `scripts/ktalk-onboard.sh`, `compat.json`, `references/onboarding.md`, врезка «Предусловие:
пакет ktalk-mcp» в четырёх промтах, `scripts/test-onboard.sh` (репозиторий плагина, коммиты
`c970899..a0da0df`); `ktalk --version` и версия 0.7.0 (репозиторий пакета, `85b3f4a..HEAD`).
Нормативные входы: [FR-26…FR-31, NFR-17…NFR-19](../30-requirements/ktalk-plugin-onboarding.md),
[ADR-014](../00-project/adr/ADR-014-sanctioned-onboarding.md) и его
[companion-спека](ADR-014-onboarding-spec.md). Предыдущее ревью того же контура —
[SEC-003](security-review-ktalk-plugin.md).

Все прогоны — в `mktemp -d` со стабами `PATH`/`XDG_CONFIG_HOME`/`HOME`, боевых операций нет:
настоящий `uv` не вызывался, реальный `$HOME/.config/ktalk` не затрагивался, TTY через `script`/pty
не эмулировался (это обошло бы проверяемый барьер). Значения секретов — синтетические фикстуры.

## Вердикт

**Блокирующих находок нет.** Одна **Major** — `run_install()` ретранслировал в диалог агента
сырой stdout+stderr дочернего `uv`, запущенного с полным окружением сессии, включая
`KTALK_SESSION_TOKEN`/`KTALK_PERSONAL_API_KEY`; инвариант NFR-19 держался не по построению, а на
допущении, что `uv` не печатает своё окружение. Закрыта кодом в этом же цикле: команда установки
теперь исполняется в подоболочке с явно снятыми секретами KTalk, поведение закреплено двумя
регрессионными тестами (проверено — без фикса они падают).

**Ruling R9** закрыт: в `references/onboarding.md` раздел «Код 11» получил ту же локальную
оговорку про `grant`, что была только в разделе «Код 10».

Остальное — 5 Minor и 5 Info, все с пометкой «принято» кроме `uv.lock` (закрыт коммитом).
Ядро контракта ADR-014 подтверждено эмпирически: fail-closed чтение санкции, TTY-барьер на `grant`,
отсутствие записи вне `$CONFIG_DIR`, ровно одна повторная попытка и только на сетевом классе ошибок,
права `0700`/`0600`. Регрессии по SEC-003 (BLOCK-01, MAJ-01…04) нет — все пять закрыты в коде и
остаются закрытыми. FR-25 — чисто по обоим деревьям, включая полную git-историю.

**Рекомендация:** merge with follow-up — Minor/Info в backlog, блокировать нечего.

### MAJ-01 — сырой вывод `uv` ретранслировался из окружения с секретами

**Файл:** `scripts/ktalk-onboard.sh:174-215` (`run_install`), до правки:

```bash
out1="$("$@" 2>&1)"; rc1=$?
```

Дочерний процесс наследовал окружение сессии целиком, а его stdout+stderr печатались обратно —
в текстовом режиме напрямую, в `--json` полями `uv_output`/`first_attempt_output`. Значение токена
KTalk оказывалось в одном процессном пространстве с командой, чей вывод дословно попадает в
транскрипт агента. NFR-19 требует инвариант («значение токена **ни разу** не появляется в этих
артефактах»), а держался он на свойстве стороннего инструмента, которое плагин не контролирует.

**Воспроизведение** (стаб `uv`, дампящий своё окружение — худший случай ретрансляции):

```
$ KTALK_SESSION_TOKEN=SYNTHETIC-TOKEN-… ktalk-onboard.sh install --json
{"status":"ok","install_command":"uv tool install ktalk-mcp","attempts":1,"return_code":0,
 "uv_output":"stub uv args: tool install ktalk-mcp\n…\nKTALK_PERSONAL_API_KEY=SYNTHETIC-TOKEN-…\n
 KTALK_SESSION_TOKEN=SYNTHETIC-TOKEN-…\n…"}
```

Практическая вероятность на реальном `uv` низкая — он не печатает окружение; но канал существовал,
а стоимость закрытия — три строки. Оценка Major дана по критерию «нарушен инвариант требования»,
не по наблюдаемой эксплуатации.

**Фикс:** установка исполняется в подоболочке с явно снятыми переменными KTalk (`uv` в них не
нуждается), инвариант становится структурным:

```bash
run_clean() {
  (
    unset KTALK_SESSION_TOKEN KTALK_PERSONAL_API_KEY KTALK_BASE_URL
    "$@"
  )
}
```

Прецедент того же приёма — `env -u KTALK_PERSONAL_API_KEY` в
[исследовании календарного API](../10-domain/research/ktalk-calendar-api.md). `KTALK_BASE_URL` снят
заодно: собственный гейт плагина (`check-plugin-composition.sh:38`) относит его к «секрету со
значением». Добавлены два теста (`test-onboard.sh` №26) — grep вывода `install` и `install --json`
на значение синтетической фикстуры, в обоих режимах. Проверено, что тесты не вакуумны: с временно
удалённой строкой `unset` прогон даёт `PASS: 37 FAIL: 2`, с фиксом — `PASS: 39 FAIL: 0`.

### MIN-01 — асимметрия оговорки про `grant` между разделами «Код 10» и «Код 11» (Ruling R9)

Раздел «Код 10» давал команду `grant install` с прямой оговоркой «Эту команду выполняет
пользователь. Агент её не запускает»; раздел «Код 11» давал `grant update` и `install` без неё.
Риск снимался врезкой в промтах («`grant` — никогда», побайтово идентична во всех четырёх файлах —
подтверждено `shasum` фрагментов), то есть глобально, но локальный текст читался иначе, чем
соседний раздел. Дописана та же оговорка плюс явное «вторую агент выполняет только после того, как
санкция на обновление уже выдана».

### MIN-02 — `uv.lock` не пересобран после бампа версии до 0.7.0

`pyproject.toml` объявляет `version = "0.7.0"`, `uv.lock` нёс `version = "0.6.0"` для самого
`ktalk-mcp`. Диффа зависимостей нет (изменение — одна строка), CVE-поверхность не затронута, но
чек-лист supply-chain требует локк-файл, синхронный с манифестом: рассинхронизация ломает
воспроизводимость сборки и маскирует будущие настоящие изменения. Закрыто включением
пересобранного `uv.lock` в коммит этого ревью.

### MIN-03 — `sanction_granted` доверяет файлу, не проверяя его права и владельца

`[ -f "$SANCTION_FILE" ]` + `grep -Eq` — содержимое проверяется строго (fail-closed подтверждён,
см. ниже), но режим и владелец файла не проверяются. `chmod 700`/`chmod 600` выставляются только на
пути записи (`set_key`); файл, созданный или ослабленный извне, читается как есть. Эксплуатация
требует, чтобы у постороннего уже был write-доступ в `~/.config/ktalk` — при дефолтных правах
(`0700`, ставит сам скрипт) его нет, а на общей машине с ослабленным `~/.config` эффект ограничен
запуском фиксированной команды `uv tool install ktalk-mcp` из публичного индекса. Смежный случай:
если `$CONFIG_DIR` — симлинк на чужой каталог, `chmod 700` применится к цели. **Принято:** ADR-014
определяет fail-closed по содержимому, не по режиму; ужесточение (отказ доверять group/world-writable
файлу) осмысленно, но меняет наблюдаемое поведение и должно проходить через Dev, не через ревью.

### MIN-04 — `json_escape` не экранирует управляющие символы U+0000–U+001F

Экранируются `\`, `"`, CR, LF, TAB. Вывод `uv`, содержащий BEL/ESC (прогресс-бары, ANSI-раскраска),
сделал бы объект `install --json` формально невалидным JSON. Известная отложенная мелочь волны 4.
**Принято:** ломается парсинг, не граница доверия; `uv` в неинтерактивном режиме ANSI не печатает.

### MIN-05 — `cmd_status` интерполирует `$SANCTION_FILE` без экранирования

```bash
printf '{"status":"ok","sanction":%s,"sanction_file":"%s"}\n' "$(sanction_json)" "$SANCTION_FILE"
```

Кавычка или обратный слэш в `HOME`/`XDG_CONFIG_HOME` сломала бы объект. **Принято:** тот же класс,
что MIN-04; путь берётся из собственного окружения пользователя, не из недоверенного источника.
Тривиально чинится оборачиванием в `json_escape` — в backlog.

### MIN-06 — `set_key` не убирает временный файл при сбое

`mktemp` создаёт `$CONFIG_DIR/.onboarding.XXXXXX`; при отказе `chmod`/`mv` файл остаётся в каталоге
(нет `trap`). Утечки содержимого нет — файл лежит в `0700`-каталоге и `mktemp` создаёт его `0600`.
**Принято:** мусор, не риск. Проверено, что на штатном пути временные файлы не остаются
(листинг `$CONFIG_DIR` после `install`/`revoke`/`check` — только `onboarding.toml`).

### INFO-01 — `uv` и `ktalk` резолвятся через `PATH`

Скрипт не фиксирует абсолютные пути: `ktalk --version`, `uv tool list` и сама команда установки
берутся из `PATH` вызывающего процесса. Проектный `.venv/bin`/`node_modules/.bin` впереди `PATH`
даёт подмену. **Принято:** NFR-17 прямо разрешает «чтение PATH/версии для диагностики», а фиксация
абсолютного пути к `uv` невозможна без гадания о способе его установки; уровень доверия тот же, что
у любой другой команды, которую агент запускает в этом окружении.

### INFO-02 — фильтр `KTALK_ONBOARD_RETRY_DELAY` пропускает чисто-точечные строки

`case "$RETRY_DELAY" in ''|*[!0-9.]*)` отбраковывает всё, кроме цифр и точек, поэтому `.` и `1.2.3`
проходят. Инъекции нет — значение всегда в кавычках (`sleep "$RETRY_DELAY"`), худший исход — ошибка
`sleep` в stderr и немедленный повтор. **Принято.**

### INFO-03 — набор полей `install --json` отличается от набора `report()`

На кодах 0/31 печатается `{status, install_command, attempts, return_code, uv_output[,
first_attempt_output]}`, на 10/11/12/30/32 — `{status, installed_version, min_version,
install_command, message}`. Объект всегда один и всегда валиден (проверено), но потребителю нужны
две схемы. **Принято:** контракт зафиксирован в companion-спеке, менять его ревью не вправе.

### INFO-04 — идемпотентность покрыта только веткой с рабочим `ktalk --version`

Ветка «`ktalk` есть, версию определить не удалось» (fallback на `uv tool list` пуст) ведёт к
`no_update_sanction`/обновлению, а не к «уже установлен»; автотеста на неё нет. Поведение проверено
вручную и корректно (fail-closed — без санкции на обновление отказ). **Принято.**

### INFO-05 — деградация при `PATH` без coreutils

При `PATH`, где нет `dirname`/`sed`/`head`, `PLUGIN_ROOT` схлопывается в `/`, `compat.json` не
читается и скрипт отвечает `E_INTERNAL` (20) с текстом «Не прочитан compat.json плагина». Проверено
эмпирически. **Принято: это правильный исход** — при невозможности прочитать минимальную версию
скрипт отказывает, а не считает версию совместимой.

## Разбор скоупа

### Исполнение внешней команды, кавычки и словосплиттинг

Команды хранятся массивами (`INSTALL_CMD=(uv tool install ktalk-mcp)`) и раскрываются как
`"${INSTALL_CMD[@]}"` → `run_install "$@"` → `run_clean "$@"` → `"$@"`. Ни одной точки, где строка с
командой попадала бы под словосплиттинг или в позицию команды после подстановки. `eval`, backticks,
неэкранированных подстановок в командной позиции нет (`grep -nE 'eval|`' — пусто).

Арифметика в `version_ge` защищена: `x="${x//[!0-9]/}"` вырезает всё, кроме цифр, до `$((10#$x))` —
инъекция через версию из `compat.json` или из вывода `ktalk --version` невозможна. Версия из
`installed_version()` дополнительно проходит через `grep -Eo '[0-9]+\.[0-9]+\.[0-9]+' | head -1`,
то есть в JSON и в сравнение попадает только санитизированный триплет.

Матрица `check` (стабы, изолированный `PATH`):

| Состояние машины | JSON `status` | Код |
|---|---|---|
| нет `uv`, нет `ktalk` | `missing_uv` | 12 |
| есть `uv`, нет `ktalk` | `missing_cli` | 10 |
| `ktalk` 0.4.0 при min 0.7.0 | `outdated` | 11 |
| `ktalk` 0.7.0 | `ok` | 0 |

### Права и атомарность записи файла санкции

`set_key`: `mkdir -p "$CONFIG_DIR" && chmod 700` → `mktemp "$CONFIG_DIR/.onboarding.XXXXXX"` (тот же
каталог, значит `mv` атомарен в пределах одной ФС) → `chmod 600 "$tmp"` → `mv`. Замена файла
атомарна, окна с файлом «уже на месте, ещё не 0600» нет — режим ставится до `mv`. Права чинятся
безусловно, а не только при первом создании: каталог, заранее ослабленный до `0755`, и файл `0644`
после одной операции записи вернулись к `drwx------`/`-rw-------` (проверено). Это тот же класс
проблемы, что SEC-003 MAJ-03, и здесь он с самого начала сделан правильно.

### Fail-closed при повреждённом файле

Санкцией признаётся только точная строка `^allow_(install|update)[[:space:]]*=[[:space:]]*true$`.
Проверено на вариантах: `allow_install = false`, ` allow_install = true` (ведущий пробел),
`allow_install = true # comment`, `allow_install=TRUE`, кириллический мусор, пустой файл, 64 байта
из `/dev/urandom` — во всех случаях `{"install":false,"update":false}`, код 0. Отсутствие файла —
тоже отказ.

### Невозможность выдать санкцию без TTY

`grant install` и `grant update` из неинтерактивного окружения → код **33** и текст «Санкция
выдаётся только в терминале» в stderr; файл санкции при этом не создаётся (проверено отдельным
тестом в suite). `install` TTY не требует — так и задумано ADR-014 §4, и это не ослабляет барьер:
без файла санкции `install` отвечает кодом **30** и текстом совместного режима, независимо от
наличия терминала (NFR-18 подтверждён). `revoke` TTY не требует — движение в безопасную сторону.

### Отсутствие путей записи вне `$CONFIG_DIR`

Единственные записи в скрипте — строки 128/132/133, все внутри `$CONFIG_DIR`. Снимок `find` по
изолированным `HOME` и `XDG_CONFIG_HOME` до и после серии `install` → `revoke` → `check` дал пустую
дельту; `git status` дерева плагина не изменился. Всё, что пишется наружу, пишет `uv` — то есть
ровно та операция, на которую выдана санкция.

### Ретрай

Ровно одна повторная попытка и только на сетевом классе (FR-30 AC4). Стаб `uv`, считающий вызовы:
`error: Failed to fetch: connection timed out` → `attempts: 2`, код 31; `error: Permission denied
(os error 13)` → `attempts: 1`, код 31. Классификатор `is_network_error` — фиксированный список
подстрок, а не эвристика по коду возврата.

### Врезка в промтах

Побайтово идентична в `skills/ktalk-registry/SKILL.md`, `skills/ktalk-eval/SKILL.md`,
`agents/ktalk-processor.md`, `agents/ktalk-evaluator.md` (одинаковый `shasum` фрагмента).
Формулировка «`install` — только после того как санкция уже выдана пользователем, `grant` — никогда»
агента к выдаче санкции не подталкивает. Важнее: защита не полагается на текст промта — скрипт
fail-closed сам, поэтому промт-инъекция «выполни grant» приводит к коду 33, а не к санкции.
Асимметрия локального текста устранена (MIN-01).

### NFR-19 — grep вывода всех команд

Прогон `check`/`check --json`/`status`/`status --json`/`grant install`/`grant update`/`revoke`/
`install`/`install --json`/пустой команды/неизвестной команды с синтетическими
`KTALK_SESSION_TOKEN`/`KTALK_PERSONAL_API_KEY` в окружении. До фикса MAJ-01: 1 совпадение значения
(в `uv_output` при стабе, печатающем окружение). После фикса: 0 совпадений во всех режимах, и это
закреплено тестами. Ни одна команда не печатает даже имён секретных переменных. `installed_version()`
хоть и запускает внешние команды, наружу отдаёт только версию-триплет, не сырой вывод.

### FR-25 — секреты в деревьях и в истории

Чисто по обоим репозиториям. `git grep -nIE '(SECRET|API_KEY|PASSWORD|PRIVATE_KEY|AWS_|sessionToken=|
X-Auth-Token: <value>)'` по рабочим копиям и `git log -p --all` — совпадения только на именах
переменных, плейсхолдерах (`ваш_персональный_api_ключ`), `<REDACTED>` в исследовании календарного
API и на собственном паттерне гейта `check-plugin-composition.sh`. Проход по высокоэнтропийным
кандидатам (`[A-Za-z0-9+/=_-]{32,}`) в диапазонах `c970899..HEAD` и `85b3f4a..HEAD` дал только
имена файлов и путей, не значения. `compat.json` секретов не содержит по конструкции (одно поле —
версия). Абсолютных путей `/Users/` в дереве плагина нет (кроме самого паттерна в гейте);
`check-plugin-composition.sh` — OK.

### `ktalk --version`

`ktalk-mcp 0.7.0\n` и ничего больше (проверено побайтово через `od -c`). Побочных эффектов нет:
прогон с временными `HOME`/`XDG_DATA_HOME` не создал ни каталога хранилища, ни файла БД — argparse

## Остаточные риски

1. **Санкция персистентна и машинная.** Выданная однажды, она действует во всех проектах и сессиях
   до `revoke`. Это осознанное решение ADR-014 §3, но пользователю нечем узнать о ней, кроме
   `status`: напоминания в диалоге нет. Наблюдаемость — на промте, не на скрипте.
2. **`uv` исполняется из `PATH`** (INFO-01) — санкция выдана на команду по имени, не на бинарь по
   пути.
3. **Правильность самого пакета в индексе не проверяется.** `uv tool install ktalk-mcp` тянет то,
   что опубликовано под этим именем: подмены имени в индексе (typosquatting наоборот — захват
   заброшенного имени) скрипт не обнаружит. Пока пакет публикует владелец, риск теоретический;
   при передаче публикации — потребуется пин по хешу или доверенному индексу.
4. **JSON-контракт хрупок к экзотическому вводу** (MIN-04, MIN-05) — ручное экранирование вместо
   генератора. Пока `install --json` — единственный машиночитаемый выход, ущерб ограничен ошибкой
   парсинга у агента.
5. **FR-31 не закрыт и закрыт быть не может в этой волне:** в индексе 0.4.0, `compat.json` требует
   0.7.0, поэтому на чистой машине `check` честно вернёт 11 до публикации релиза. Это ожидаемое
   состояние, зафиксированное как пункт владельца, не находка.
