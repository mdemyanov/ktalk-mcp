# ADR-015 spec: контракт передачи пишущей операции оператору

Companion-спека к [ADR-015](../00-project/adr/ADR-015-cli-authority-and-write-handoff.md). Не
решение — детализация: состав и текст handoff-сообщения, разбор отказов, брифы Dev/DevOps, контракт
QA-author для SA-006. Имена навыков/файлов/шагов workflow — решение SA-006, здесь не выбираются.

## Компоненты

| Компонент | Ответственность | Входы | Выходы | Зависимости |
|-----------|-----------------|-------|--------|-------------|
| Промт-слой плагина (SA-006, не спроектирован здесь) | Формирует handoff-сообщение, вызывает `*-preview`, не вызывает `*-confirm` | Запрос оператора, параметры встречи/отмены | Текст handoff (превью + команда + пояснение TTY) | `ktalk create-meeting-preview`/`cancel-meeting-preview --json` |
| `PreviewService`/`CancelPreviewService` (существует, `meeting_scheduling.py`/`meeting_cancel.py`) | Allow-list компоновщик тела, канонический хеш, выдача `confirmation_id` в рамках процесса `*-preview` | Флаги CLI | `(body/payload, confirmation_id)` | `ConfirmationStore` |
| `ConfirmationStore` (существует, `confirmation.py`) | TTL 10 мин, single-use, привязка к хешу тела — **в рамках одного процесса** | `body_hash` | `confirmation_id` / `match()` | in-memory, не переживает границу процессов |
| `cmd_*_confirm` (существует, `cli_meeting.py`) | TTY-барьер → пересборка тела теми же флагами → собственный `confirmation_id` → подтверждение словом → один сетевой вызов без retry | Флаги CLI (те же, что `*-preview`), слово подтверждения с терминала | Результат операции / «исход неизвестен» | `isatty()`, сеть |

## Границы

- Промт-слой не реализует альтернативный TTY-барьер и не эмулирует терминал — обход `isatty()`
  вне контура этого решения (ADR-005 §3).
- Промт-слой не хранит и не передаёт `confirmation_id` между вызовами разных процессов — он
  бесполезен вне процесса, породившего его (`ConfirmationStore` не синглтон, `confirmation.py`).
- Промт-слой не реализует retry-цикл вокруг `*-confirm` ни в каком виде — ни автоматический, ни
  «предложенный по умолчанию» (NFR-22).

## Поток данных

1. Оператор формулирует намерение агенту.
2. Агент вызывает `*-preview --json`, парсит `body`/`payload` и `confirmation_id` (последний
   используется только для показа в предпросмотре — не переносится дальше).
3. Агент рендерит предпросмотр оператору и рядом печатает точный текст команды `*-confirm` с теми
   же значениями флагов, что были переданы в `*-preview` — не значениями по умолчанию, не
   пересчитанными заново.
4. Агент добавляет пояснение: команда выполняется лично оператором в его терминале; без TTY
   отклоняется.
5. Ход передан — агент не выполняет шаг 6 ни при каких условиях.
6. Оператор запускает `*-confirm` в своём терминале, вводит слово подтверждения на предложенный
   CLI предпросмотр (CLI строит его заново тем же компоновщиком — операторский предпросмотр может
   визуально отличаться от агентского только при расхождении версий CLI, не по данным).
7а. Успех — оператор видит результат, возвращается к диалогу с агентом при желании.
7б. Отказ с «исход неизвестен» — оператор видит текст CLI с предложением проверить
`list-calendar`; если оператор возвращается к агенту с этим текстом, агент передаёт диагностику
дальше (FR-38), не запускает `*-confirm` повторно и не предлагает это как готовое действие.

## Handoff-сообщение — обязательный состав

Три части, одним сообщением (ADR-015, «Решение», п.2):

1. **Предпросмотр** — вывод `render_tool_output(..., format_meeting_preview | format_cancel_preview)`
   как есть, без сокращения полей.
2. **Команда** — `ktalk create-meeting-confirm --subject "..." --start ... [все флаги, переданные в
   preview]` (аналогично `cancel-meeting-confirm --id <id> --reason "..."`) — строка, готовая к
   копированию в терминал, не описание параметров прозой.
3. **Пояснение** — фиксированный смысл (точный текст — SA-006): «Выполните эту команду сами в своём
   терминале — агент не может и не должен подтверждать создание/отмену встречи за вас; без реального
   терминала (`isatty()`) команда откажет».

Формулировка п.3 — не решение этой спеки (это уже промт-текст, домен SA-006), но обязательный
смысл, который любая формулировка SA-006 обязана нести: (а) действие выполняет оператор лично,
(б) причина — TTY-барьер, (в) команда именно та, что показана в п.2.

## Разбор отказов

| Момент отказа | Кто видит | Действие агента | Действие оператора |
|---|---|---|---|
| `*-preview`: `MissingFieldError` (NFR-9) | Агент (сам вызывал) | Переспрашивает недостающее поле, повторяет `*-preview` | Не участвует |
| `*-preview`: сеть/CLI недоступен | Агент | FR-38: предлагает `auth-status`/`config show` | Не участвует |
| `*-confirm`: не введено слово подтверждения | Только оператор | Не видит (не его процесс) | Останавливается сам, ход не завершён |
| `*-confirm`: `store.match()` = False (TTL/дрейф) | Только оператор | Не видит; если оператор сообщит — агент строит новый `*-preview` с нуля | Начинает заново с `*-preview` |
| `*-confirm`: сетевая ошибка/таймаут («исход неизвестен») | Только оператор, текст называет `list-calendar` | Не инициирует retry; при обращении оператора передаёт FR-38-эскалацию | Проверяет `list-calendar` лично, решает о повторе сам |

Инвариант NFR-22 в терминах этой таблицы: ни одна строка «Действие агента» не содержит повторного
вызова `*-confirm`.

## NFR Mapping

- **NFR-20** (промт-поверхность только CLI) → компоненты выше не называют MCP-инструмент;
  ADR-015 фиксирует, что MCP-путь для этой поверхности не существует архитектурно, а не только по
  соглашению промта.
- **NFR-22** (без автоматического повтора) → раздел «Разбор отказов»: ни одна строка агента не
  инициирует повторный `*-confirm`; текст CLI («исход неизвестен... проверьте list-calendar»)
  передаётся оператору как есть (FR-37 AC1), не переформулируется в «агент попробует снова».
  Тест: text-снимок дерева промта на отсутствие цикла вокруг пишущих команд.
- **NFR-23** (подтверждение — действие человека) → «Поток данных» шаг 5: агент не выполняет `*-confirm`
  ни при каком исходе шагов 1–4; handoff-сообщение — единственный выход из автономного участка.

## Контракт с QA-author

**Сценарии приёмки (полный список из capability-спеки требования):**
- FR-32 AC (просмотр расписания: явные даты, предупреждение о неполном сегменте, различение
  пустого/ошибки)
- FR-33 AC1/AC2/AC3 (создание: только preview, точная команда confirm, отсутствие дефолтов NFR-9)
- FR-34 AC1/AC2 (отмена: только preview, получение id без изобретения)
- FR-35 AC1/AC2/AC3 (поиск участника: без автовыбора, явная подстановка key, различение «не найден»
  от ошибки)
- FR-36 AC1/AC2 (get-room: безусловное предупреждение, не используется как проверка занятости)
- FR-37 AC1/AC2 (деградация по режиму: текст CLI не искажается, нет угадывания успеха)
- FR-38 AC1/AC2 (эскалация к auth-status/config show, не единственная гипотеза при не-авторизационной ошибке)

**Архитектурный контекст для тестов:**
- Компоненты: промт-слой плагина (SA-006, вне этого пакета) как вызывающая сторона;
  `PreviewService`/`CancelPreviewService`/`ConfirmationStore`/`cmd_*_confirm` — существующий,
  протестированный код пакета, регрессии этой волны не требует.
- Trust boundary этого решения: агент (недоверенный источник действия) → handoff-сообщение → терминал
  оператора (доверенный источник действия) → `*-confirm`. Тестируется форма сообщения на стороне
  промта плагина (текстовый снимок), не поведение CLI повторно.

**Edge cases / boundary conditions:**
- Флаги, переданные в `*-preview`, не совпадают буквально с флагами в напечатанной команде
  `*-confirm` (например, агент забыл `--no-pin-code` при явном «без PIN») — источник рассинхрона на
  уровне промта, не пакета; должен быть покрыт снимком промта в SA-006/тестах плагина, не здесь.
- Оператор редактирует напечатанную команду `*-confirm` вручную перед запуском — вне контроля
  контракта; `*-confirm` валидирует независимо тем же allow-list-компоновщиком (ADR-005) — regression
  не нужен, уже покрыт существующими тестами пакета.
- Оператор запускает `*-confirm` спустя >10 минут после показанного предпросмотра — TTL истёк на
  стороне `*-confirm`, CLI выдаёт «подтверждение истекло», уже покрыто существующим тестом пакета.

**Test-pyramid рекомендация:**

| Группа AC | Уровень | Обоснование |
|-----------|---------|-------------|

| NFR-22 AC (нет retry-цикла) | статическая проверка/снимок промта | тот же grep-класс, что NFR-23 |
| NFR-20 AC (нет имён MCP-инструментов в промте) | статическая проверка | grep дерева плагина на `ktalk_create_meeting`/`ktalk_cancel_meeting` и т.п. |
| FR-32/FR-35/FR-36/FR-37/FR-38 (обработка вывода CLI агентом) | integration (в дереве плагина, не пакета) | нужен реальный/замоканный вывод `ktalk ... --json`, проверка того, что текст не теряется и не переформулируется при показе оператору |
