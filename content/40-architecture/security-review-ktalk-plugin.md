# Security review: волна 3, плагин ktalk перед сборкой (SEC-003)

DevSecOps-ревью перед сборкой плагина ktalk (DEV-003). Скоуп: централизованное хранилище
(`store.py`, `store_migration.py`, `host_config.py`), точки его подключения (`config.py::resolve_db_path`,
`cli.py::main`), новые CLI-обёртки волны 3 (`cli_content.py`, `cli_meetings_read.py`), дерево плагина
`/Users/mdemyanov/Devel/ktalk-plugin` (отдельный git-репозиторий, собран DEV-002) и дерево пакета
`/Users/mdemyanov/Devel/ktalk-mcp`. Вход: [ADR-012](../00-project/adr/ADR-012-plugin-boundary.md) +
[companion-спека](ADR-012-plugin-boundary-spec.md), [ADR-013](../00-project/adr/ADR-013-central-transcript-store.md) +
[companion-спека](ADR-013-central-transcript-store-spec.md), [ktalk-plugin.md](../30-requirements/ktalk-plugin.md)
(FR-25, NFR-14, NFR-15), [ktalk-plugin-spec.md](ktalk-plugin-spec.md),
[dev-001](../60-implementation/dev-001-host-config-and-store.md), dev-002 (плагин, отдельный репозиторий).
Vault хозяина `naumen-cto` — только чтение, не менялся.

На момент ревью: `uv run pytest` — 420 passed. `uvx pip-audit --local` — известных CVE в зависимостях
нет. Находки ниже получены статическим чтением кода и точечными эмпирическими прогонами
(permission-бенчмарки на временных каталогах, вне рабочего дерева) — не боевыми операциями.

## Вердикт

**Одна block-находка** — миграция в централизованное хранилище (`store_migration.py`) не
устанавливает NFR-15-права на цели независимо от источника: `shutil.copy2` переносит permission bits
исходного файла как есть, значит обычный (0644/0755) исходный `.registry.db` из vault даёт обычный
(не 0700/0600) централизованный файл. Команда сегодня нигде не вызывается из `cli.py` — риска
сегодняшней эксплуатации нет, но это и есть сама находка: команда для NFR-12 не реализована до конца,
а модуль, который должен быть последним рубежом NFR-15 для миграции, прав не проставляет. Закрыть
до появления CLI-обвязки миграции (не обязательно до сборки плагина как таковой, plugin-дерево кода
не содержит — но до того, как эта функция станет достижимой пользователем).

**Major** — 4 находки: (1) реальный wiring-разрыв между `.ktalk.toml`/`discover_host_config()` и
`main()` — приоритет источников из FR-23/спеки не действует в проде, третий источник мёртв; (2)
процессная мутация `umask` в `resolve_store_root()` не восстанавливается — структурная хрупкость с
конкретным путём исправления без правки `registry.py`; (3) NFR-15 не выполняется для уже
существующего корня хранилища с ослабленными правами — `mkdir(exist_ok=True)` под новым `umask` не
трогает права существующего каталога; (4) отсутствует CLI-обвязка для `migrate_to_central_store`
(NFR-12 требует отдельную явную команду — её нет).

Secrets-sweep (FR-25) — **чисто** по обоим деревьям (рабочие копии и `git log -p`), включая проверку
известного факта про `.mcp.json` хозяина (не просачивается ни в плагин, ни в пакет, ни в хранилище).
Supply-chain — чисто (`pip-audit`, локфайл присутствует и закоммичен, новых зависимостей волна не
добавила).

## Тема 1 — режим доступа к хранилищу

**Вердикт: в основном соответствует NFR-15/NFR-14 для пути "с нуля", но гарантия не тотальна.**

- `resolve_store_root()` резолвит `${XDG_DATA_HOME:-$HOME/.local/share}/ktalk`, создаёт каталог с
  `os.umask(0o077)` перед `mkdir`. Проверено эмпирически на чистом `XDG_DATA_HOME`: свежесозданный
  каталог получает `0700`, файлы, создаваемые тем же процессом позже (включая `registry.db` через
  голый `sqlite3.connect` в замороженном `registry.py`), получают `0600`. NFR-15 "без окна между
  созданием и ограничением прав" для этого сценария выполнено.
- На реальной машине ревьюера каталог уже существует и имеет права `drwx------` (`0700`) — корректно.
- `detect_sync_dir`/`warn_if_sync_dir` (NFR-14) — сегментированная проверка по границе каталога
  (`Dropbox`, `Google Drive`, `OneDrive`, `Nextcloud`, `ownCloud`, `Library/Mobile Documents`,
  `Library/CloudStorage`), не substring — код и тесты (`tests/test_host_config.py`,
  `tests/test_config.py`) подтверждают защиту от ложного совпадения на `MyDropboxBackup/`.
  Предупреждение печатается в stderr, работа не блокируется — соответствует AC-2.
- Гарантия **не покрывает** два случая — см. находки MAJ-03 (существующий корень с ослабленными
  правами) и BLOCK-01 (миграция) ниже: NFR-15 в этих случаях фактически не проверяется и не
  обеспечивается кодом, только "новый чистый каталог, созданный этим кодом впервые".

## Тема 2 — поведение при чужом umask (особое внимание)

Пункты (а)–(г) из задания — каждый с отдельным вердиктом.

**(а) Файлы вне хранилища, созданные после мутации umask.**
Эмпирически подтверждено: после вызова `resolve_store_root()` внутри того же процесса файл,
записанный в произвольном другом каталоге (`vault/registry.md` и т.п.) через обычный `open()`/
`Path.write_text()`, тоже получает `0600` (каталог — `0700`), а не обычные права окружения. Это
прямое следствие процессной, а не точечной мутации `umask`.
Проверка call-графа сегодняшнего кода (`grep` по `resolve_db_path`/`resolve_store_root` во всех
модулях) показывает, что на практике сегодня это не эксплуатируется: единственная точка вызова
машинного дефолта — `resolve_db_path()` внутри короткоживущего процесса `ktalk`
(`cli.py::main`), и всё, что этот же процесс пишет после открытия `Registry` (в частности,
`_cmd_export` → `registry.md`), при **явном `--db`** не задевает `resolve_store_root()` вовсе (первый
приоритет возвращает путь до какого-либо вызова `resolve_store_root`), а без `--db`/`KTALK_REGISTRY_DB`
`out_path.parent` совпадает с корнем централизованного хранилища, то есть `registry.md` в этом случае
и так пишется внутрь хранилища, не наружу в vault. MCP-сервер (`server.py`) вообще не импортирует
`resolve_db_path`/`resolve_store_root`. **Практической утечки прав на файлы вне хранилища сегодня не
найдено** — но это счастливое стечение сегодняшнего call-графа, не структурная гарантия: см. MAJ-02.

**(б) Поведение при уже существующем корне хранилища с ослабленными правами.**
Эмпирически подтверждено: `root.mkdir(parents=True, exist_ok=True)` под `umask 0o077` **не меняет**
режим уже существующего каталога. Тест: каталог создан заранее с `0755`, после вызова
`resolve_store_root()` (с активной мутацией `umask`) режим каталога остался `0755`. NFR-15 для этого
случая не выполняется, и код не пытается его чинить (ни `os.chmod`, ни явной проверки режима перед
использованием каталога нет). Правдоподобный сценарий появления такого каталога: более ранняя версия
`ktalk-mcp` до этой волны, ручное создание, восстановление из бэкапа без сохранения прав, шаринг
`$HOME` с другим инструментом, который создаёт `~/.local/share/ktalk` раньше `ktalk`.

**(в) Более строгий/более слабый `umask` хозяина.**
Не влияет на итоговый результат для новых объектов — `os.umask(0o077)` — абсолютное присваивание, не
модификация существующего значения; чем бы ни был `umask` хозяина до вызова (`022`, `002`, `077`,
даже `000`), после первого вызова `resolve_store_root()` в процессе он гарантированно `0o077` для
всех последующих `mkdir`/`open` этого процесса. Единственный побочный эффект — прежнее значение
безвозвратно потеряно для остатка жизни процесса (см. (а)/MAJ-02): более слабый исходный `umask`
хозяина (например, `002`, обычный для групповых Unix-окружений) означал бы, что без этого кода
файлы создавались бы `0664`/`0775` — конкретно для хранилища это *желаемое* ужесточение, но
распространяется дальше периметра хранилища на весь процесс.

**(г) Решение без правки замороженного `registry.py`.**
Да, есть, и оно не требует трогать `registry.py`. Сегодняшняя мутация происходит внутри
`resolve_store_root()` (`store.py`) и никогда не восстанавливается. Альтернатива — сузить окно
мутации до места вызова в `cli.py::main()`, а не внутри самого резолвера пути:

```python
# cli.py::main(), вместо голого `Registry(resolve_db_path(args.db))`
old_umask = os.umask(0o077)
try:
    db_path = resolve_db_path(args.db)      # может внутри снова выставить 0o077 — идемпотентно
    with Registry(db_path) as reg:          # sqlite3.connect создаёт файл здесь, под ограничением
        return handler(reg, args)
finally:
    os.umask(old_umask)                     # возвращает umask хозяина сразу после открытия БД
```

Это даёт то же самое "без окна между созданием и ограничением прав" для `registry.db`/`-wal`/`-shm`
(момент их создания строго внутри `try`), но перестаёт протекать в код, исполняющийся впоследствии
в том же процессе (`_cmd_export`, будущие хендлеры) — окно сужено ровно до конструктора `Registry`.
Правки нужны только в `cli.py` (не заморожен) и, возможно, в докстроке `resolve_store_root()` (снять
формулировку "не восстанавливается" как обязательное свойство — сделать восстановление
ответственностью вызывающей стороны). `store.py` может оставить сегодняшнее поведение по умолчанию
для вызывающих, которые не оборачивают вызов сами (обратная совместимость), но `cli.py::main` должен
быть тем местом, где реальное присваивание временное.

## Тема 3 — отсутствие секретов (FR-25)

**Вердикт: чисто на всех проверенных поверхностях.**

- Дерево плагина `/Users/mdemyanov/Devel/ktalk-plugin`, рабочая копия: `grep -rnE
  '(SECRET|API_KEY|PASSWORD|PRIVATE_KEY|AWS_|sessionToken=|X-Auth-Token:)'` по всем `.md` — 0
  совпадений с реальным значением (только упоминания имён переменных как документации).
- Дерево плагина, `git log -p` (весь, 2 коммита) — тот же grep плюс отдельный проход
  high-entropy-кандидатов (`[A-Za-z0-9+/=]{32,}`) — единственные совпадения это git-хэши самих
  коммитов, не секреты. Коммит `e4a4b12` ("анонимизация примеров") убрал реальные ФИО из примера
  markdown-зеркала — это PII-гигиена, не секрет-утечка, и она уже закрыта.
- `.gitignore` плагина: только `.DS_Store` — секретных файлов, которые нужно было бы игнорировать, в
  дереве плагина по конструкции нет (плагин — только промты/скиллы/агенты, не хранит `.env`/ключи).
- Формат `.ktalk.toml` (ktalk-plugin-spec.md, «Схема»): четыре секции —
  `registry.db_path` (строка-путь), `directories.*` (строки-пути), `routing.*` (строки-шаблоны с
  плейсхолдерами), `integrations.qmd` (bool). Ни одно поле контрактом не предназначено для секрета;
  `host_config.py::_validate_string_map` проверяет только тип (`str`), не содержимое — если хозяин
  всё же положит токен в `routing.*` по ошибке, код это не отловит и не остановит (нет проверки на
  content), но и не спровоцирует утечку сам — значения используются только для построения путей/
  показа в `ktalk config show`, не уходят в сеть. Оценено как **info** (см. ниже), не как находка
  уровня выше: контракт схемы сам по себе не создаёт секретного канала.
- Централизованное хранилище (`~/.local/share/ktalk` на машине ревьюера): проверено содержимое —
  только `registry.db*` (создаётся тестами волны 3, см. dev-001 "побочный эффект"), никаких
  экспортированных markdown/токенов. `KTALK_SESSION_TOKEN`/`KTALK_PERSONAL_API_KEY` никогда не
  записываются в SQLite (реестр хранит только метаданные записей, не credentials — подтверждено
  структурой `registry.py`/`formatters.py`, не изменённой этой волной).
- Пакет `ktalk-mcp`, рабочая копия и `git log -p` (весь): та же связка grep — совпадения только на
  плейсхолдерах/тестовых значениях (`KTALK_SESSION_TOKEN=test`, `KTALK_SESSION_TOKEN=invalid-token-broken`,
  `KTALK_SESSION_TOKEN=SECRET` — последнее буквально строка `SECRET`, использованная в тексте ADR как
  плейсхолдер для примера, не значение). `.gitignore` пакета покрывает `.env`, бинарники БД
  (упомянуты в CLAUDE.md как gitignored в vault — не в самом пакете, где путь к БД параметризован и
  не коммитится), снимки DevTools (`docs/*-recording.json`, `docs/calendar`, `docs/*.har`) —
  осознанно исключены с явным комментарием "содержат живые токены".
- Известный факт из RES-002: `.mcp.json` хозяина (`/Users/mdemyanov/Documents/naumen-cto/.mcp.json`)
  несёт `KTALK_SESSION_TOKEN`/`KTALK_BASE_URL` открытым текстом. Подтверждено присутствие файла
  (только листинг, содержимое не читалось — не нужно для вывода). Это артефакт хозяина, не плагина:
  ни один файл дерева плагина, дерева пакета или централизованного хранилища на него не ссылается и
  не копирует его содержимое (`grep -rn "\.mcp\.json"` по обоим деревьям — 0 совпадений). Просачивания
  не найдено.

- TOCTOU в `store_migration.py::migrate_to_central_store`: см. MIN-01 ниже.
- Отдельно от path traversal в `.ktalk.toml`: обнаружен риск для будущей фичи маршрутизации

### BLOCK-01 — миграция не проставляет NFR-15-права на целевой файл/каталог

**Файл:** `src/ktalk_mcp/store_migration.py:57-58`.

```python
target.parent.mkdir(parents=True, exist_ok=True)
shutil.copy2(source, target)
```

`target.parent.mkdir()` вызывается **без** предварительного `os.umask(0o077)` — эта функция не
использует `store.resolve_store_root()` и не устанавливает никакого ограничивающего `umask` сама.
`shutil.copy2` явно копирует метаданные источника, включая биты прав (`copystat`), — целевой файл
получает **те же права, что и исходный** `.registry.db` в vault хозяина (типично `0644`/родительский
каталог `0755` при обычном `umask 022`), а не `0600`/`0700`, требуемые NFR-15 для централизованного
хранилища.

**Воспроизведение (эмпирически подтверждено):**
```python
os.umask(0o022)  # ambient, resolve_store_root() не вызывается
migrate_to_central_store(source="/tmp/vault/.registry.db", target="/tmp/central/ktalk/registry.db")
# target dir mode: 0o755, target file mode: 0o644 — не 0700/0600
```

**Риск:** централизованное хранилище по факту вводится именно ADR-013 ради консолидации
транскриптов/реестра между проектами вне периметра одного git-репозитория — единственный явный путь
попадания данных в это хранилище "централизованно, из старого места" — эта функция. Если она
станет достижимой (см. MAJ-04) без исправления, первая же реальная миграция создаст закрытый по
названию, но фактически групповой/мирочитаемый каталог с реестром встреч (потенциально с PII
участников).

**Почему не поднято до критичности "уже эксплуатируется"**: сегодня `migrate_to_central_store` не
вызывается ни из одной точки `cli.py`/argparse — грепом по `src/` подтверждено, что имя функции
встречается только в определении и в тестах. Функция физически недостижима из `ktalk`-CLI сегодня.

**Рекомендация:** внутри `migrate_to_central_store` (не в вызывающей стороне, чтобы не полагаться на
дисциплину каждого будущего вызывающего) — либо (a) вызвать `store.resolve_store_root()`-подобную
установку `umask(0o077)` перед `mkdir`/`copy2` и явный `os.chmod(target, 0o600)` /
`os.chmod(target.parent, 0o700)` сразу после копирования (не полагаться только на `umask`, раз
`copy2` всё равно переносит режим источника поверх созданного файла), либо (b) заменить `copy2` на
`copy` (не переносит метаданные) в паре с корректным `umask`. Явный `chmod` после копирования —
более надёжный вариант, т.к. не зависит от того, вызывался ли `resolve_store_root()` раньше в этом
же процессе.

### MAJ-01 — приоритет источников FR-23 не работает в проде: `.ktalk.toml`→`resolve_db_path` не подключены

**Файл:** `src/ktalk_mcp/cli.py:343` (`main()`).

```python
with Registry(resolve_db_path(args.db)) as reg:
```

`resolve_db_path` вызывается без параметра `host_config` — третий источник приоритета
(`host_config.registry.db_path`, заявленный в ktalk-plugin-spec.md §"Приоритет источников" и
FR-23) **никогда не передаётся** в проде. Нигде в `main()` не вызывается `discover_host_config()`.
`server.py` (MCP) тоже не вызывает `resolve_db_path`/`discover_host_config` вовсе. Единственные
места, где `host_config`-параметр реально используется — юнит-тесты `tests/test_config.py`, которые
вызывают `resolve_db_path(..., host_config=...)` напрямую.

Отдельно, `discover_host_config()` **вызывается** в `cli.py:253` — но только внутри `_cmd_config`
(`ktalk config show`), результат используется исключительно для вывода, не передаётся в
`resolve_db_path`.

**Риск для безопасности:** сегодня это работает "в безопасную сторону" — раз третий источник мёртв,
хозяйский `.ktalk.toml` не может тихо перенаправить путь реестра куда-то ещё, путь падает на
`KTALK_REGISTRY_DB`/машинный дефолт. Но это прямое расхождение со спекой (FR-23 AC1-AC3 подразумевают
рабочий приоритет с `.ktalk.toml` на третьей позиции) и с NFR-11 (миграция vault'а `naumen-cto`,
описанная в спеке §"Миграция vault'а", предполагает, что `db_path` из `.ktalk.toml` реально
подхватывается — сегодня не подхватится, и переход останется незамеченным до первого расхождения
данных между ожидаемым и фактическим файлом реестра).

**Рекомендация:** в `main()` перед строкой 343 вызвать `host_config = discover_host_config()`
(с той же обработкой `HostConfigError`, что уже есть в `_cmd_config`, только не гасить, а дать
общему `try/except` обработать так же, как сейчас) и передать `host_config=host_config` в
`resolve_db_path`. Не требует правки `registry.py`.

### MAJ-02 — мутация `umask` в `resolve_store_root()` не сужена до момента реальной необходимости

Разобрано полностью в теме 2, пункт (г). Ссылка на конкретный код: `src/ktalk_mcp/store.py:54`.
Рекомендация — перенести временную мутацию в `cli.py::main()` вокруг `Registry(...)`, восстанавливать
`umask` сразу после открытия БД через `try/finally`. Сегодня это не эксплуатируется (см. тему 2 (а)),
но является структурным долгом: любая новая фича, которая пишет что-то в том же процессе после
разрешения машинного дефолта пути реестра, немедленно унаследует непредсказуемые (слишком
рестриктивные, что ломает ожидания, например, для файлов, которые должны быть читаемы другими
инструментами в vault'е) права без явного решения автора этой фичи.

### MAJ-03 — существующий корень хранилища с ослабленными правами не выправляется

Разобрано в теме 2, пункт (б); эмпирическое подтверждение там же. `src/ktalk_mcp/store.py:55`.
**Рекомендация:** после `root.mkdir(parents=True, exist_ok=True)` явно проверить/выставить режим
каталога: `if stat.S_IMODE(root.stat().st_mode) != 0o700: os.chmod(root, 0o700)` (безусловно, не
только при первом создании) — закрывает NFR-15 для случая "каталог существовал раньше этого кода".
Не требует правки `registry.py` — весь код в `store.py`.

### MAJ-04 — нет CLI-команды для `migrate_to_central_store` (NFR-12)

ADR-013-spec §"Контракт команды миграции" явно требует: "Команда не запускается неявно... только
явным вызовом" и "Рабочее имя команды уточняет Dev при реализации". Функция реализована и покрыта
юнит-тестами (`tests/test_store_migration.py`), но ни один subparser в `cli.py` её не вызывает —
grep по `migrate_to_central_store` во всём `src/` даёт только определение функции. Пользователь
не может выполнить эту миграцию через `ktalk` сегодня.

**Риск:** это функциональный, не чисто security-дефект сам по себе, но напрямую влияет на security-
поверхность: пока команда не подключена, BLOCK-01 недостижим — но именно поэтому подключение этой
команды **обязано** сопровождаться фиксом BLOCK-01 в том же PR, не после. Фиксирую здесь явно, чтобы
Dev не подключил CLI-обвязку отдельным более поздним изменением, забыв про права.

**Рекомендация:** добавить subparser (например, `ktalk migrate-to-central-store` или другое имя,
не пересекающееся с существующим `ktalk migrate <vault>` — тот уже занят импортом markdown-архивов
по ADR-002, спека прямо предупреждает об этом), в `_REGISTRY_FREE_COMMANDS` не добавлять (команда
сама открывает и путь-источник, и путь-цель вручную, не через стандартный `Registry(resolve_db_path(...))`).
Реализация — Dev, вместе с BLOCK-01.

### MIN-01 — TOCTOU между `target.exists()` и `shutil.copy2`

**Файл:** `src/ktalk_mcp/store_migration.py:51-58`. Проверка `target.exists()` и последующий
`shutil.copy2` не атомарны: два параллельных вызова `migrate_to_central_store` с одним и тем же
`target` могут оба пройти проверку `not target.exists()` до того, как любой из них начнёт копировать,
и оба начать копирование — второй завершившийся копированием молча перезапишет результат первого
(`shutil.copy2` не использует `O_EXCL`), в обход инварианта "повторная миграция не перезаписывает
данные, добавленные после первой" (docstring `MigrationTargetExistsError`).

**Риск:** низкий — это explicit, редко запускаемая административная команда (сегодня даже не
подключена к CLI, см. MAJ-04), не сетевой endpoint под контролем недоверенной стороны; конкурентный
запуск требует, чтобы один и тот же оператор/автоматизация запустила её дважды почти одновременно.

**Рекомендация:** заменить check-then-act на атомарную попытку создания через `target.open("xb")`
(режим exclusive-create) до `shutil.copy2`, либо использовать lock-файл рядом с `target` на время
операции. Не блокирует сборку плагина — можно закрыть вместе с MAJ-04/BLOCK-01.

### MIN-02 — прерывание между сверкой дампа и `rename` оставляет невозобновляемое состояние

**Файл:** `src/ktalk_mcp/store_migration.py:60-68`. Если процесс прерван (kill/сбой машины) **после**
успешной сверки дампа, но **до** `source.rename(backup)` — целевой файл (`target`) уже содержит
верную копию данных, но источник (`source`) остаётся под старым именем непереименованным. Повторный
запуск команды немедленно получит `MigrationTargetExistsError` (`target` уже существует) и
завершится ошибкой, не пытаясь довести до конца только оставшийся шаг `rename`. Функция не идемпотентна
в этом промежуточном состоянии — требуется ручное вмешательство (переименовать `source` вручную или
удалить `target` и мигрировать заново).

**Риск:** низкий, тот же класс "explicit, редкая административная операция", но стоит явно
задокументировать в runbook (DevOps, OPS-001), а не оставлять как неявную ловушку.

**Рекомендация:** либо сделать команду устойчивой к этому промежуточному состоянию (при
`MigrationTargetExistsError` дополнительно сверять дамп существующего `target` с `source` и, если
совпадает, доводить до конца только `rename`, не копирование заново), либо явно описать шаг
восстановления в runbook DevOps. Решение — на Dev/DevOps, не блокирует сборку плагина.

### INFO-01 — схема `.ktalk.toml` не рассчитана на секреты, контент-проверки нет

`host_config.py::_validate_string_map` (строки 42-47) проверяет только тип значения (`str`), не
его содержимое. Если хозяин по ошибке положит токен в `routing.*`/`directories.*` (контракту это не
противоречит формально — там просто строка), код это не отловит. Риска утечки это не создаёт
сегодня: значения используются только для локальной сборки путей и вывода в `ktalk config show`
(локальный процесс, не сеть) — не логируются на внешний сервис, не отправляются в API KTalk.
**Рекомендация (не блокирует):** можно по желанию Dev добавить soft-предупреждение в
`load_host_config`, если значение секции похоже на токен (высокая энтропия/длина), но это blue-sky
улучшение, не находка, требующая фикса.

### INFO-02 — будущая фича маршрутизации: несанитизированный `{title}` в путях (промты плагина)

`routing.transcript_archive`/`routing.committee` и т.д. (ktalk-plugin-spec.md, "Маршрутизация как
конфигурация") подставляют плейсхолдер `{title}`, который в итоге происходит из заголовка встречи
KTalk API — данных, которые может создать любой участник организации, имеющий право создавать
встречи. Подстановка сегодня выполняется не Python-кодом пакета, а промтом/скиллом плагина
(`/Users/mdemyanov/Devel/ktalk-plugin/skills/ktalk-registry/`) через LLM-агента, вызывающего Bash
tool — санитизации `../`/абсолютных путей в найденных инструкциях skill'а не описано. Не находка
кода этого пакета (вне периметра ktalk-mcp, вне периметра, ревьюируемого DevSecOps по коду), но
стоит зафиксировать для SA/BA как открытый вопрос перед реализацией маршрутизации как рабочей
фичи: заголовок встречи, содержащий `../../../etc/`, теоретически может увести Write-путь агента
за пределы каталога маршрутизации. **Рекомендация:** явно прописать в `ktalk-plugin-spec.md` или в
самом skill'е правило санитизации `{title}` (запрет `/`, `..`, ограничение на алфавит/длину) до
того, как маршрутизация из конфигурации станет активной механикой, а не просто провалидированной
схемой.
