# AT-design: переименование `ktalk-mcp` → `ktalk-cli`

[ADR-022](../00-project/adr/ADR-022-ktalk-cli-rename.md) + companion
[ADR-022-ktalk-cli-rename-spec.md](ADR-022-ktalk-cli-rename-spec.md) (§7 порядок работ, §8

`content/30-requirements/` под это решение не заведено (решение владельца, не производное от
BA-требования этого дерева, companion §NFR mapping) — приёмочный контракт исчерпывается
companion-спекой, не отдельной capability-спекой `openspec/`.

собственный тест-дизайн границы интеграции:

## Мутации, доказывающие небутафорность тестов

- **QA-1.** Прогнана scratch-симуляция (не правка отслеживаемого `src/`, инструмент этой
  задачи не редактирует код Dev): `fake_pkg_correct.py` читает имя через
  `importlib.metadata.metadata(...)["Name"]` — под патчем `importlib.metadata.metadata`,
  печатает подменённое имя, тест бы прошёл. `fake_pkg_wrong_relabel.py` — та же ловушка, что
  нашёл SA-001: Dev просто переписывает литерал на новый («ktalk-cli») вместо чтения
  метаданных — печатает `ktalk-cli`, НЕ подменённое имя, тест остаётся красным. Оба прогнаны
  через `run_mutation_proof.py` (тот же приём: патч `importlib.metadata.metadata`, наблюдение
  первого токена stdout). Результат: `fake_pkg_correct` → PASS, `fake_pkg_wrong_relabel` →
  FAIL — тест отличает «читает метаданные» от «переписал литерал на новый», это и есть его
  предмет.
- **QA-2/QA-3.** Уже красные на неизменённом дереве по реальной причине (12 литералов вместо
  8; сотни хитов `ktalk_mcp` вместо нуля) — не нуждаются в отдельном мутационном доказательстве
  вида «а что, если бы Dev ничего не сделал»: это и есть текущее состояние, воспроизведённое
  прогоном (`uv run pytest tests/test_adr022_ktalk_cli_rename.py -q`, 3 failed).

## Boundary cases

- Литеральный бюджет QA-2 — двусторонняя граница, не потолок: тест падает и при неполном
  переименовании (сегодня, 12 > 8), и при избыточном (гипотетически, наивный global
  find-replace случайно задевает один из шести путей конфига или одну из двух чужих ссылок —
  бюджет по конкретному файлу увеличился бы не туда, где ожидается, `dict(per_file) !=
  expected` ловит это так же строго).
- QA-1 не зависит от того, ГДЕ Dev разместит чтение метаданных (`__init__.py` на уровне
  модуля, как сегодня `__version__`, или лениво внутри `main()`) — тест форсирует
  переимпорт пакета после патча метаданных именно для устойчивости к обоим вариантам.

## Error cases (два обязательных класса)

**Malformed/mistyped input:** не применимо ни к одному из трёх стабов этого файла — ни один
не принимает пользовательский/операторский ввод; предмет — состав дерева `src/`/`tests/` и
поведение `importlib.metadata` под контролем теста, не внешний ввод. **N/A**.

**Masked failure:** QA-1 целиком — это и есть класс masked failure (напечатанное имя
«тихо» остаётся прежним литералом вместо явной реакции на смену метаданных, без падения,
без сообщения об ошибке — то же самое молчаливое поведение, которое уже ударило версию в
0.8.0). QA-2/QA-3 — тоже: неполный рефакторинг не роняет сборку и не печатает предупреждение
сам по себе, только этот тест делает молчаливый остаток литералов/идентификаторов
наблюдаемым.

## Не покрыто исполнимым стабом

**QA-6 (пакет-указатель `ktalk-mcp` 0.11.0).** Companion-спека §7 п.3 прямо говорит: указатель
— «отдельный релизный артефакт вне этого репозитория… публикуется из последнего коммита
истории, где пакет ещё назывался `ktalk-mcp`, либо из отдельной ветки/тега». После коммита 2
(§7) `src/ktalk_mcp/` переименован в `src/ktalk_cli/` — пакет `ktalk_mcp` в союз с полным
CLI физически не сосуществует с урезанным пакетом-указателем `ktalk_mcp` (тот же модульный
путь, взаимоисключающие состояния) в ОДНОМ рабочем дереве. Стаб, импортирующий `ktalk_mcp` в
ЭТОМ дереве ПОСЛЕ переименования, упал бы на `ImportError` — ровно тот класс дефекта («падает
на компиляции/импорте, не на ассерте»), который контракт QA-author прямо запрещает. Не
выдумывается тест ради галочки: пункт остаётся design-only здесь, со следующими обязательными
ассертами для АВТОРА собственного лёгкого тестового набора указателя (заводится при подготовке
отдельной ветки/тега §7 п.3, роль DevOps/Dev той задачи, companion §Brief for DevOps):
- `main()` возвращает ненулевой код на каждом вызове;
- сообщение о переименовании и точная команда `uv tool install ktalk-cli` — в **stderr**, не
  stdout;
- `warnings.warn(..., DeprecationWarning)` поднимается;
- `pyproject.toml` указателя не содержит `[project.scripts] ktalk = ...` — статическая
  проверка файла, не тест на реальном `uv` (тяжёлый для CI, companion §Тест-пирамида).

**QA-4/QA-5** — см. таблицу выше: не нуждаются в отдельном красном стабе ПЕРЕД реализацией
(удаление кода закрывается прогоном оставшегося набора; снятие зависимости — однозначный
статический факт, защищать мутацией нечего до первого прохода).

## Расхождение, унаследованное сиблинг-репозиторием (зафиксировано там, не решается здесь)

`ktalk-plugin`, `at-design.md` требования `2026-08-31-package-rename-transition`, раздел
«Расхождение, требующее реконсиляции BA/SA»: BA-спека плагина требует, чтобы пакет `ktalk-mcp`
после ретирмента продолжал предоставлять команду `ktalk` без изменения поведения/кода
возврата («SHALL NOT otherwise change the command's existing behaviour or exit code») — прямо
противоположно решению ADR-022 §6 этого дерева (указатель НЕ объявляет `ktalk` вовсе,
единственная команда `ktalk-mcp` завершается ненулевым кодом). Тело и статус ADR-022 не
редактируются этой задачей (задача — QA-author, не SA/владелец); расхождение зафиксировано в
обоих деревьях для координатора, ADR-022 сохраняет статус «принято владельцем, не
пересматривается» до явного нового решения.

## Не покрыто (out of scope, помимо QA-6)

- Бесконфликтность `uv tool install` в обоих безопасных порядках (companion §5) — тяжёлая
  e2e-проверка внешнего инструмента, ручной раздел QA-отчёта (companion §Тест-пирамида, уже
  сама архитектура относит это к ручному прогону, не CI).
- Реакция сиблинг-плагина (`ktalk-onboard.sh`) на факт идентичности `ktalk-mcp`/`ktalk-cli` —
  тестируется в дереве плагина, не здесь (граница проведена companion §Contract with
  QA-author: «компонент дерева пакета… вне контракта того QA-author» — и симметрично, детали
  реализации `ktalk-onboard.sh` вне контракта этого).
