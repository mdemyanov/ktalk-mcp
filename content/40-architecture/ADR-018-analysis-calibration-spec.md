# ADR-018 spec: целевые редакции промт-фрагментов калибровки анализа

Companion-спека к [ADR-018](../00-project/adr/ADR-018-analysis-calibration.md). Требование-источник:
[FR-40…FR-43, NFR-25](../30-requirements/ktalk-plugin-analysis-calibration.md). Реализация — промт-
слой репозитория `ktalk-plugin` (Dev), вне пакета `ktalk-mcp` (ADR-012 §1). Пути ниже —
относительные внутри репозитория `ktalk-plugin`, без URL и абсолютных путей.

## 1. Целевые редакции по файлам

### 1.1 `agents/ktalk-processor.md` — новый шаг 4.5

Между текущим шагом сборки черновика протокола и шагом определения места сохранения вставляется:

```
### Шаг 4.5. Финальная сверка прозы с таблицей «Договорённости»

Для каждого предложения черновика, описывающего обязательство одного участника
(включая шапку и блок «Формат», не только основной текст) — найди соответствующую
строку таблицы «Договорённости».

Не нашёл строку → сделай одно из двух, не пропускай молча:
  - добавь строку в таблицу «Договорённости»;
  - добавь запись в «Открытые вопросы» с текстом причины, почему строки нет
    (например: «неполная информация о сроке», «не обязательство, а констатация факта»).

Диалог вида «реплика-запрос — реплика явного согласия в пределах одного обмена» —
кандидат на строку таблицы независимо от того, в каком разделе черновика обязательство
упомянуто впервые (шапка, «Формат», основной текст).

Этот шаг выполняется один раз, над уже собранным черновиком целиком — не повторяет
извлечение из транскрипта (шаг 3), сверяет черновик сам с собой.
```

Место вставки — после шага сборки черновика, до шага определения пути сохранения (текущая
нумерация шагов файла на момент правки — уточняется Dev по факту, «4.5» — рабочее имя,
допустимо иное целочисленное соответствие месту в последовательности).

### 1.2 `agents/references/protocol-template.md` — синтаксис маркера и секция «Ключевые тезисы»

Объявление маркера (новый абзац, рядом с существующим объявлением `[UNCLEAR]` для открытых
вопросов, с явным разграничением):

```
**Маркер неопределённого имени:** `[ASR?]`, вплотную после имени без пробела перед
скобкой — например, `Дмитрий Иванов[ASR?]`. Означает: имя не резолвилось однозначно
через каталог профилей (участник или третье лицо). Не совпадает и не заменяет `[UNCLEAR]`
(открытые вопросы встречи, отдельная секция и отдельный счётчик `unclear_count`) — два
разных смысла, два разных токена. `[ASR?]` не входит в `unclear_count`.
```

Фиксированный порядок секций дополняется восьмой, опциональной:

```
Порядок секций протокола: Участники, Ключевые решения, Договорённости, Обновления
статуса, Открытые вопросы, Флаги для владельца проекта, Заметки, **Ключевые тезисы**
(только для `meeting_type: session`; отсутствует у прочих типов встречи — не пустая
секция с заглушкой, а полностью опущена).
```

### 1.3 `skills/ktalk-registry/references/analysis-quality.md`

**§1 «Context-first»** — распространить предписание Grep на третьих лиц, добавить абзац:

```
Поиск профиля через каталог применяется не только к участникам встречи, но и к
третьим лицам, упомянутым в речи, если имя встречается в тексте, уже отнесённом к
разделам «Договорённости», «Ключевые решения» или «Обновления статуса» (не в
проходной речи вне этих категорий). Механика пакетного поиска — §1а ниже.
```

Новый подраздел **§1а «Пакетный резолвинг третьих лиц»**:

```
Список уникальных имён третьих лиц собирается после структурированного извлечения
(проход 1, `two-pass-analysis.md`, разделы A–E) — не по ходу чтения транскрипта.
Grep выполняется пакетно по собранному списку, не на каждое упоминание в отдельности.
Имя, уже резолвленное или уже помеченное `[ASR?]` в рамках текущего прогона, повторно
не ищется — результат кешируется на весь прогон.
```

**§3 «Двухпроходный анализ»** — заменить тело раздела ссылкой (нормативный текст переезжает в
`two-pass-analysis.md`):

```
Алгоритм двух проходов и чек-лист структурированного извлечения — нормативно в
`agents/references/two-pass-analysis.md` (разделы A–E). Здесь не дублируется.
```

**§4 «Темпоральные маркеры»** — без изменения текста правила (уже верно, замер это подтверждает);
добавляется одна ссылка на калибровочные примеры ниже:

```
Правило калибровки confidence по факту согласия, не по наклонению запроса — см.
Примеры 3а/3б в приложении.
```

**§6 «Защита от галлюцинаций и шкала confidence»** — остаётся нормативным телом (без переноса) —
файл `two-pass-analysis.md` для confidence получает встречную ссылку (см. 1.4 ниже), текст шкалы
не дублируется во втором файле.

**Приложение — замена Примера 3.**

Было (отклонённая редакция, помечена GOOD ошибочно):

```
Пример 3 [GOOD]:
Реплика: «Может быть, мне либо там обдумать надо… Давай я на завтра всё в
голове уложу»
| Обдумать вопрос | завтра | HIGH |
```

Целевая редакция — пара, оба примера GOOD, различающий признак — реплика-акцепт:

```
Пример 3а [GOOD] — условный запрос, явный акцепт → HIGH:
Запрос: «А ты можешь вот это вот, может быть, следующий понедельник здесь
рассказать?»
Акцепт: «Хорошо. […] Договорились.»
| Рассказать интерфейсный трек | следующий понедельник | HIGH |
Наклонение запроса условное — на исход не влияет: акцепт явный, поэтому HIGH.

Пример 3б [GOOD] — условный запрос, односложная реакция → MEDIUM:
Запрос: «Если вдруг ты найдёшь способ… может быть, даже просто по КЦП…
Подумаю дополнительно»
Акцепт: «Покопать.»
| Покопать по КЦП | не задан | MEDIUM |
Различает пары не наклонение запроса (условное в обоих), а сила акцепта:
однословная реакция без акта согласия → MEDIUM, не HIGH.
```

## 4. Механика резолвинга третьих лиц (детализация решения 6)

1. После прохода 1 (структурированное извлечение, `two-pass-analysis.md` A–E) собран список
   говорящих и упомянутых третьих лиц.
2. Фильтр: третье лицо попадает в список кандидатов на резолвинг, только если его имя встречается
   в тексте, уже отнесённом к «Договорённости»/«Ключевые решения»/«Обновления статуса» — не в
   тексте, отнесённом к прочей прозе или мелким репликам.
3. Список дедуплицируется (одно имя — одна запись независимо от числа упоминаний).
4. Grep по каталогу профилей выполняется пакетно на дедуплицированный список (один вызов
   инструмента на список, не на упоминание).
5. Результат (резолвлено / не резолвлено) кешируется на весь прогон — повторное упоминание имени
   в протоколе не порождает повторный вызов.
6. Не резолвившееся имя из списка — маркер `[ASR?]` на каждое место употребления в готовом тексте
   (кеш определяет решение «резолвлено/нет», не отменяет разметку в тексте).

Порог фильтра (шаг 2) — ручка Dev: если будущий замер найдёт третье лицо, упомянутое вне трёх
перечисленных категорий, но требующее резолвинга (например, в «Открытых вопросах»), список
категорий расширяется правкой этого раздела, не переписыванием механики целиком.

## 5. Контракт с QA-author

**Сценарии приёмки (полный список из требования):**
- FR-40 AC1–AC3 (финальная сверка: строка есть либо явная причина в «Открытых вопросах»; связка
  запрос-акцепт — кандидат независимо от места в черновике).
- FR-41 AC1–AC3 (HIGH по явному акцепту; MEDIUM по односложной реакции; ни один GOOD-пример не
  противоречит правилу).
- FR-42 AC1–AC4 (резолвленное имя без маркера; нерезолвленное — с единым маркером; деградация без
  каталога маркирует все сомнительные имена; согласованность маркировки в пределах документа).
- FR-43 AC1–AC2 (регрессия пустых секций; «Ключевые тезисы» как часть шаблона для `session`).
- NFR-25 AC1–AC2 (подъём minor-версии при правке промт-слоя; версия плагина в отчёте `ktalk-eval`).

**Архитектурный контекст для тестов:**
- Компоненты промт-слоя: `ktalk-processor.md` (ядро, новый шаг 4.5), `protocol-template.md`
  (синтаксис маркера, порядок секций), `analysis-quality.md` (§1/§1а/§4/§6, приложение),
  `two-pass-analysis.md` (алгоритм A–E, ссылка на confidence).
- Границы: пакет `ktalk-mcp` не участвует в этом решении вовсе — все правки в репозитории
  `ktalk-plugin` (ADR-012). Верификация промта — либо чтение текста, либо прогон навыка оценки
  `ktalk-eval` на записях замера, не pytest.
- Trust boundary: транскрипт — untrusted вход для резолвинга имён; каталог профилей —
  доверенный источник коррекции (уже валидированный проектом-хозяином).

**Edge cases / boundary conditions:**
- Третье лицо упомянуто и в «Договорённостях», и в проходной речи — резолвится один раз (кеш),
  маркер/коррекция одинаковы в обоих местах (FR-42 AC4).
- Обязательство в шапке протокола, не имеющее явной реплики-акцепта в транскрипте (например,
  формулировка ведущего без ответной реплики) — шаг 4.5 обязан пометить его в «Открытых вопросах»,
  не пропустить и не выдумать акцепт.
- `meeting_type: session` без содержательных тезисов — секция «Ключевые тезисы» опущена полностью,
  не выведена пустой (симметрично `decisions_count: 0`, FR-43 AC1).
- Каталог профилей объявлен, но конкретное третье лицо не входит ни в один профиль (полное
  совпадение по имени, а не омонимия) — маркер `[ASR?]`, не молчаливый пропуск.

**Test-pyramid рекомендация:**

| Группа AC | Уровень | Обоснование |
|---|---|---|
| FR-40 AC1–AC3, FR-41 AC1–AC2, FR-42 AC1–AC3 | e2e (прогон `ktalk-eval` на записях замера) | поведение промта целиком — не разложимо на unit/integration вне LLM-вызова |
| FR-41 AC3 | статический текстовый снимок (не e2e) | сверка приложения `analysis-quality.md` с правилом §4 — текстовое сравнение, не требует прогона |
| FR-42 AC4 | e2e на протоколе с повторным упоминанием (та же запись, что AC2) | согласованность — свойство одного прогона, не требует отдельной записи |
| FR-43 AC1–AC2 | e2e (регрессия на session-записи) | инвариант уже верифицирован текущим прогоном — тест ловит регресс, не новое поведение |
| NFR-25 AC1 | статическая проверка (diff-скрипт `check-plugin-composition.sh`) | git-уровень, не поведение промта |
| NFR-25 AC2 | контракт поля в рубрике `eval-rubric.md` — задача QA-author, не тест на промт | вне периметра этой спеки |
