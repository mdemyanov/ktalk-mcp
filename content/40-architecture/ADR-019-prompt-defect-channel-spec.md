# ADR-019 spec: контракт канала дефектов промта

Companion-спека к [ADR-019](../00-project/adr/ADR-019-prompt-defect-channel.md).
Требование-источник: [FR-44…FR-47, NFR-26,
NFR-27](../30-requirements/ktalk-prompt-defect-channel.md). Реализация целиком — репозиторий
плагина (`ktalk-plugin`): промты навыка `ktalk-eval`, агента `ktalk-evaluator`,
`CONTRIBUTING.md`, каталог классов дефекта. Пакет `ktalk-mcp` не затронут. Урезанный объём
(решение владельца, 2026-08-19): скрипта `ktalk-defect-issue.sh`, санкции, журнала, кодов
возврата в этой волне нет — см. ADR-019 «Решение» п.1 и «Альтернативы» (условие возврата).

## 1. Каталог классов дефекта

Новый файл `skills/ktalk-eval/references/defect-classes.md` в репозитории плагина —
контролируемый расширяемый перечень: таблица `id | название | пример`. Стартовые три записи —
классы волны 8 (обязательство в прозе не в таблице; confidence по наклонению запроса; маркер
ASR-имени непоследователен). Агент `ktalk-evaluator`, найдя дефект, обязан взять `id` из каталога;
не найдя подходящего — предлагает новую строку тем же коммитом, в котором фиксирует первый
случай (append, не свободный текст поверх каталога). Единственная часть решения, для которой
сохраняется код: файл — данные, читаемые и промтом, и оператором, без исполняемой логики поверх.

## 2. Секция «Дефекты промта» отчёта (FR-44)

Заменяет секцию «Рекомендации» агента `ktalk-evaluator.md` (сейчас — свободный список 1–3
пунктов). Новый формат — таблица, одна строка на найденный дефект:

```markdown
## Дефекты промта

| Класс (id) | Тип встречи | Измерение | Цитата транскрипта | Цитата протокола | Предложенное правило |
|---|---|---|---|---|---|
| completeness-prose-not-table | status | Completeness | «...» (таймкод) | «...» (строка/секция) | ... |
```

Промт агента при формировании таблицы применяет два правила текстом инструкции (не кодом,
ADR-019 п.4): включать класс в таблицу только если он уже встречался на другой записи по
таблице `Defects` трекера (§3) — иначе строка остаётся в трекере, в секцию отчёта, готовую к
issue, не попадает; включать случай только с обеими цитатами. Поле «Класс» — только `id` из
каталога §1, не произвольный текст.

## 3. Трекер качества — таблица «Defects» (FR-45, FR-46)

Тот же файл `tracker_path`, что уже несёт таблицу «Evaluations» (ADR-018, NFR-25) — новое
хранилище не заводится (NFR-27). Вторая таблица:

```markdown
## Defects

| Дата | Recording (short) | Класс (id) | Тип встречи | Измерение | Цитата транскрипта | Цитата протокола | Issue |
|---|---|---|---|---|---|---|---|
```

Шаг «Обновить трекер» агента `ktalk-evaluator.md` (сейчас — п.10, только таблица Evaluations)
дописывает по одной строке на каждый найденный дефект — независимо от того, попал ли он в
секцию «Дефекты промта» отчёта: трекер накапливает всё, отчёт показывает только готовое к
issue (порог, пара цитат). Столбец `Issue` пуст до заведения, после — номер/URL, который
оператор вписывает вручную после того, как завёл issue в GitLab (§7).

**Порог и пара цитат — проверка чтением, не кодом.** Оператор (или промт при формировании
секции отчёта) сверяет число различных `Recording (short)` с тем же классом в таблице
`Defects` и полноту обеих колонок цитат. Ни один шаг этой сверки не имеет кода возврата —
корректность контракта опирается на текст `CONTRIBUTING.md` (§4) и дисциплину чтения.

## 4. `CONTRIBUTING.md` репозитория плагина

Новый файл в корне `ktalk-plugin` (сегодня отсутствует, замер требования). Раздел «Дефекты
промта»:

```markdown
## Заведение issue по дефекту промта

Issue заводится только для класса дефекта, встретившегося в таблице `Defects` трекера
качества `ktalk-eval` на 2+ разных записях. Класс, встретившийся один раз, остаётся строкой
трекера — issue не заводи.

Обязательные поля тела issue (перенос из секции «Дефекты промта» отчёта 1:1, без
переформулирования): класс (id из `skills/ktalk-eval/references/defect-classes.md`), тип
встречи, измерение рубрики, цитата транскрипта, цитата протокола, предложенное правило — по
каждому подтверждающему случаю.

Issue без пары цитат (транскрипт + протокол) хотя бы для одного случая — не заводи, дефект
остаётся строкой трекера до появления полной пары.

Перед заведением: замени в цитатах имена сотрудников на роль/обезличенный идентификатор,
удали или замени плейсхолдером названия клиентов и внутренние суммы. Прочитай собранное тело
целиком перед публикацией — репозиторий плагина читается анонимно, без авторизации, откатить
опубликованный текст нельзя.
```

Это правило без проверки, названное так прямо (ADR-019 п.3): файл делает контракт видимым в
момент заведения issue, не обеспечивает его исполнение кодом. Нарушение (issue без пары цитат,
issue ниже порога, неочищенные данные) не блокируется — обнаруживается постфактум чтением
самого issue или трекера.

## 5. Обезличивание (NFR-26) — целиком человеческий барьер

Навык `ktalk-eval` при формировании секции «Дефекты промта» (§2) несёт инструкцию промта:
заменить в цитатах имена сотрудников на роль, суммы — на плейсхолдер, названия клиентов —
удалить или заменить плейсхолдером, прежде чем показать секцию оператору. Автоматической
подстановки (regex, каталог участников/профилей) нет ни в промте, ни где-либо ещё — решение
ADR-019 п.5 распространяет на весь барьер вывод, к которому первая редакция уже пришла для
класса «клиент»: проверяемого признака для естественного языка нет, барьер — предпросмотр.

Оператор обязан прочитать полное тело issue (не только диф с шаблоном) непосредственно перед
тем, как скопировать его в интерфейс GitLab, — `CONTRIBUTING.md` (§4) называет это прямо.
Других линий защиты нет: пропуск в предпросмотре — реализованный риск, не гипотетический,
назван в ADR-019 «Последствия» без смягчения формулировкой.

## 7. Обратный путь

Столбец `Issue` таблицы `Defects` (§3) несёт номер/URL после того, как оператор вручную завёл
issue и вписал ссылку в трекер, — единственная связка «дефект → issue». Закрытие issue после
правки промта и подъёма версии (ADR-018 §7, NFR-25) — ручное действие оператора со ссылкой на
коммит/версию в комментарии issue. Требование → ADR → правка промта → A/B (цикл волны 8) не
пересматривается; issue — вход в этот цикл, не замена ни одного его шага.

## Контракт с QA-author

**Acceptance-сценарии:** полный список `#### Scenario:` капабилити, объявленной строкой
`**Capability:**` требования `ktalk-prompt-defect-channel.md` — FR-44…FR-47, NFR-26, NFR-27.
Часть AC (FR-45, FR-46, FR-47, NFR-26) в этой волне не имеет кодовой реализации для проверки —
таблица переноса верификации в ADR-019 передана BA для правки текста требования.

**Архитектурный контекст:** компоненты — `ktalk-evaluator.md` (секция §2, шаг трекера §3),
`CONTRIBUTING.md` (§4), файл каталога классов (§1). Внешних вызовов, файловой санкции, журнала —
нет. Граница доверия: единственная — предпросмотр оператором полного тела issue перед ручным
заведением (§5); всё, что до него, — данные, всё, что после, — вне контроля этого решения
(GitLab, ручное действие).

**Edge cases:**
- Класс дефекта встретился 2 раза на **одной и той же** записи (не на разных) — не считается
  повторяемостью (§2/§3 требуют различных `Recording (short)`); это правило, не код — при QA
  можно проверить только фиксацией сценария в тексте промта, не тестом на реальном отказе.
- Оператор находит новый класс дефекта без подходящего `id` в каталоге — агент обязан
  предложить новую строку тем же коммитом (§1); дефект без `id` из каталога не должен появиться
  ни в отчёте, ни в трекере.
- Тело issue правится оператором после предпросмотра, но до вставки в GitLab, — привязки
  тела к показанному варианту нет (отличие от тяжёлого варианта, где был хеш): ручная правка
  легитимна, риск (внесение неочищенных данных руками) покрывается только повторным прочтением
  перед вставкой.
- `CONTRIBUTING.md` устаревает относительно каталога классов (например, порог меняется, файл —
  нет) — расхождение не детектируется автоматически; регулярная сверка — операционная
  обязанность, не эта спека.

**Test-pyramid:**

| Группа AC | Уровень | Обоснование |
|---|---|---|
| FR-44 (шесть полей, перенос 1:1) | unit (fixture-отчёт → секция) | детерминированное форматирование текста промта, проверяется на фикстурах без сети |
| FR-45, FR-46 (порог, пара цитат) | вручную / текстовый снимок промта | правило — текст инструкции, не код; автоматический тест ловит только наличие формулировки в промте и `CONTRIBUTING.md`, не факт соблюдения оператором |
| FR-47 | не применимо — нет операции, которую можно тестировать (человек действует вне контролируемого интерфейса) |
| NFR-26 | вручную / текстовый снимок промта | тот же довод, что FR-45/FR-46: код не гейтирует, проверяется наличие инструкции и явного шага предпросмотра |
