# ADR-021 spec: восемь capability и материализация `openspec/`

Companion-спека к [ADR-021](../00-project/adr/ADR-021-requirement-capability-pairing.md).
Детализация, не решение: таблица восьми capability, правило появления каталога, брифы для
задачи, пишущей спеки, контракт с QA-author этой же задачи.

## 1. Восемь capability — состав и граница

| Требование | Capability | Что покрывает контракт |
|---|---|---|
| `personal-api-key.md` | `talk-api-auth-modes` | Режимы авторизации (session / `X-Auth-Token`), профиль эндпоинтов по режиму, диагностика протухшего ключа/токена (FR-1…FR-6, FR-11 — включая FR-19 `auth-status` без реестра, слитое сюда решением SA) |
| `personal-api-key.md` | `recording-data-access` | Скачивание видео, полный состав участников, архив встреч, чат встречи (FR-7…FR-10) |
| `personal-api-key.md` | `registry-sync-window` | Границы `top`/пагинация через `skip`, сверка идентификаторов перед первым api-key sync, клиентское окно дат (FR-14…FR-16) |
| `rooms-calendar-scheduling.md` | `room-diagnostics` | Диагностика комнаты, побочный эффект `get_room` (FR-17, ADR-006) |
| `rooms-calendar-scheduling.md` | `calendar-window-reading` | Чтение календаря, включительная правая граница окна (FR-18, FR-39, ADR-017) |
| `rooms-calendar-scheduling.md` | `meeting-scheduling` | Планирование встречи, предпросмотр/подтверждение, формат `--timezone` (FR-13, FR-40, ADR-005, ADR-020) |
| `ktalk-plugin.md` | `host-project-config-discovery` | Discovery раскладки проекта-хозяина, `.ktalk.toml`, приоритет разрешения пути (ADR-012 §1 «Пакет Python») |
| `ktalk-plugin.md` | `centralized-machine-storage` | Резолюция пути централизованного хранилища, конкурентный доступ, права (ADR-013) |

Дискриминатор границы — **независимая проверяемость**, не файл-носитель: `talk-api-auth-modes`
и `recording-data-access` живут в одном файле требования, потому что режим авторизации и
доступ к данным записи — разные контракты (первый проверяем без сети реальной записи, второй
требует её), и они уже разошлись один раз в истории пакета (ADR-003 против ADR-006/ADR-007
корректировали разные поверхности одного файла требования независимо).

FR-19 (`auth-status` не обязан открывать реестр) слит в `talk-api-auth-modes`, а не выделен в
собственную capability — решение SA этой задачи, не BA: диагностика режима авторизации и
диагностика доступности реестра проверяются одним и тем же вызовом `auth-status`, разделение
дало бы два контракта над одной командой без независимого пути отказа.

## 2. Материализация каталога — порядок для задачи, пишущей спеки

1. Первый файл `openspec/specs/<capability>/spec.md` создаёт каталог `openspec/specs/`
   неявно — mkdir отдельной командой не нужен и не делается заранее.
2. `.nauta-ids.yaml` уже объявляет `scenario` (`home: openspec/specs/*/spec.md`,
   `populated: false`) — флаг остаётся `false` навсегда, снимать его не нужно ни при первой
   спеке, ни при восьмой. Это не тот же протокол, что у `adr`: пустой `prefix` при
   `allocation: derived` структурно исключает `populated: true` (`id-check.sh` §4.1a) —
   пространству нечего нумеровать (ключ сценария — текст заголовка `#### Scenario:`), и
   `populated: true` здесь гейт читает как повреждённый реестр (`ERROR`), не как «корпус
   пуст». Проверено прогоном: `populated: true` при восьми существующих спеках даёт
   `ERROR: реестр повреждён…`, `populated: false` — чисто (`bash scripts/id-check.sh`).
3. Каждая capability-спека объявляет себя строкой `## Purpose` и разделом `## Requirements` с
   `### Requirement: <имя>` и `#### Scenario: <имя>` — формат нормативного языка (SHALL/SHALL
   NOT) без AC-нумерации: машинно-проверяемый контракт живёт как текст сценария, номер ему не
   нужен (та же конвенция, что у сестринского репозитория плагина, `openspec/specs/*/spec.md`
   там же).
4. Строка `**Capability:**` вписывается в шапку требования **тем же коммитом**, что и первая
   спека соответствующей capability, не раньше — раннее объявление красит дерево (форма
   проверяется до существования файла).

## 3. Брифы

### Брифа для задачи «написать восемь capability-спек»
**Архитектура:** этот файл + [ADR-021](../00-project/adr/ADR-021-requirement-capability-pairing.md).
**Реализовать:** восемь файлов `openspec/specs/<capability>/spec.md` по таблице §1, каждый —
`## Purpose` + `## Requirements` с нормативными `### Requirement:`/`#### Scenario:`, источник
текста — соответствующие FR/NFR трёх требований пакета (не пересказ, перенос нормативных
пунктов в форму Scenario).
**Порядок:** capability одного требования — одним заходом (не вперемешку по трём файлам), чтобы
строка `**Capability:**` вписывалась в шапку требования сразу полным списком, не по одной.
**После спек:** DEV-задача добавляет строки `**Capability:**` в шапки трёх требований — по
одной строке на requirement-файл, перечисляя все capability этого файла (пример: у
`personal-api-key.md` — три значения в одной строке или три строки, форма — на усмотрение
исполнителя, валидатор принимает оба варианта, `_declared_capability_paths` разбирает список).

### DevOps
Нет: решение не меняет инфраструктуру, деплой или мониторинг. `openspec/specs/` — файлы в том
же git-репозитории, тот же цикл релиза, что и `content/`.

## Контракт с QA-author

Эта задача (ADR-021) не вводит новое проверяемое поведение кода — она проектирует, где живёт
контракт. Acceptance-сценарии для QA-author появляются вместе с восемью capability-спеками
(следующая задача): `#### Scenario:` каждой спеки — полный список для теста этой capability.
До их появления у QA-author нет предмета теста по этому ADR; фиксируется здесь, чтобы следующая
задача не собирала контекст заново:

**Архитектурный контекст будущих тестов:** контракт живёт в тексте (`openspec/specs/`), не в
коде валидатора — тестируется чтением сценария против поведения кода пакета (`src/ktalk_mcp/`),
не самого механизма пары `**Capability:**` (это тестирует сьют донора `nauta`,
`test-validate-content.sh`, не пакета).

**Test-pyramid по умолчанию** (уточняется при написании каждой спеки): контракты
`talk-api-auth-modes`/`recording-data-access` — unit/integration поверх существующих fixtures
`tests/`; `meeting-scheduling`/`calendar-window-reading` — integration (сетевые моки уже
приняты решением ADR-005/ADR-017); `centralized-machine-storage` — integration (конкурентный
доступ, ADR-013 уже несёт контракт теста).
