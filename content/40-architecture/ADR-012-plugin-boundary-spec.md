## `.mcp.json` плагина — контракт

Плагин объявляет ровно один stdio-сервер, без секретов и без пути внутри `${CLAUDE_PLUGIN_ROOT}`
(код не вендорится):

```json
{
  "mcpServers": {
    "ktalk": {
      "type": "stdio",
      "command": "ktalk-mcp"
    }
  }
}
```

Переменные окружения (`KTALK_SESSION_TOKEN`/`KTALK_PERSONAL_API_KEY`/`KTALK_BASE_URL`) сюда не
попадают — их источник: shell-окружение процесса Claude Code или `.mcp.json`/`settings.json`
хозяина, если хозяин решает их объявить сам (override того же ключа `ktalk` перекрывает
плагинное объявление сервера целиком, включая `command` — это существующий механизм разрешения
имён Claude Code, не специфика ktalk).

## `plugin.json` — обязательные поля

| Поле | Значение | Комментарий |
|------|----------|-------------|
| `name` | `ktalk` | kebab-case, неймспейс `/ktalk:*` для навыков |
| `version` | semver плагина (напр. `1.0.0`) | обязателен де-факто — без него версия падает на git SHA (RES-002) |
| `description` | краткое описание контура | — |
| `author` | владелец | — |

`dependencies` на пакет `ktalk-mcp` в манифест не выносится — RES-002 не подтвердил, что это
поле способно выразить внешнюю Python-зависимость с версией; предусловие документируется текстом
в `README` плагина плюс командой проверки (`which ktalk-mcp` / `uv tool list | grep ktalk-mcp`).

## Cutover-процедура (детализация для OPS-001)

1. Владелец устанавливает пакет (уже установлен: `~/.local/share/uv/tools/ktalk-mcp/`) и
   проверяет `ktalk-mcp`/`ktalk` доступны в PATH.
2. Владелец устанавливает и включает плагин `ktalk` в проекте-хозяине (`/plugin install`).
3. Владелец создаёт файл конфигурации раскладки хозяина (формат — SA-003), эквивалентный
   сегодняшней раскладке vault'а — NFR-11 требует, чтобы пути результата не изменились.
4. Владелец **вручную** удаляет из vault'а: `agents/ktalk-processor.md`,
   `agents/ktalk-evaluator.md`, `skills/ktalk-registry/`, `skills/ktalk-eval/`,
   `commands/ktalk-registry.md` — отдельным коммитом с сообщением, ссылающимся на переход на
   плагин. Не выполняется автоматически установкой плагина (ADR-012, отклонённая альтернатива).
5. Регрессия: полный сценарий (`sync` → обработка встречи → `mark-done`) даёт те же пути
   результата, что до перехода (NFR-11 AC) — проверяется до удаления файлов шага 4 и после.
6. Миграция реестра на централизованное хранилище (ADR-013) — отдельный шаг, не входит в этот
   cutover (NFR-12): реестр продолжает жить на `95_TRANSCRIPTS/.registry.db`, пока не вызвана
   команда миграции явно.

Откат: до выполнения шага 4 — деинсталляция плагина без последствий (копии в vault'е снова
действуют). После шага 4 — восстановление удалённых файлов из git-истории vault'а; реестр не
затронут cutover'ом агентов вовсе.

## `qmd` — варианты (детализация к §5 ADR-012)

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| (a) Опциональная интеграция в плагине — **рекомендация SA** | не дублирует логику по хозяевам; шаг деградирует явно (FR-24) без выноса кода | плагин несёт зависимость от специфичного стороннего MCP даже там, где он не нужен |
| (b) Вынос шага из плагина в отдельный навык хозяина | контур ktalk не знает о `qmd` вовсе | каждый хозяин, которому нужно сопоставление профиля, переизобретает шаг; риск дрейфа копий, который волна и устраняет |

Решение принадлежит владельцу (FR-24, открытый вопрос требования). При выборе (a): агент на
старте шага сопоставления проверяет доступность `qmd` (наличие MCP-инструмента в текущей сессии)
и каталога профилей независимо друг от друга (FR-24 AC — недоступность одной не останавливает
шаг целиком), помечает недоступную явно в отчёте.

## Контракт с QA-author

**Сценарии приёмки (AC требования, сгруппированные по FR):**
- FR-20 AC (discovery: файл есть / файла нет / файл повреждён)
- FR-21 AC (проект без vault-раскладки: registry-команды работают / MCP read-инструменты работают)
- FR-23 AC (приоритет `--db > env > конфиг хозяина > дефолт`, регрессия трёх существующих +
  новый источник)
- FR-25 AC (секреты не в централизованном хранилище; два проекта — два независимых значения)

**Архитектурный контекст для тестов:**
- Компоненты: конфиг-слой пакета (discovery), `.mcp.json`/`plugin.json` плагина, cutover-процедура
  (не автоматизируется — вне периметра юнит/интеграционных тестов, ручная проверка по runbook)
- Границы: плагин не содержит исполняемого кода — тестировать код discovery/резолюции пути в
  пакете (`ktalk-mcp`), не в дереве плагина; плагинные артефакты (`plugin.json`, `.mcp.json`,
  промты) — статическая проверка состава (нет абсолютных путей, нет `95_TRANSCRIPTS`/
  `20_MEETINGS` в теле — GO-критерий 3 постановки), не поведенческий тест

**Edge cases / boundary conditions:**
- `.mcp.json` хозяина переопределяет объявление сервера плагина целиком — тест на то, что
  секреты хозяина не просачиваются в объявление плагина (grep дерева плагина)
- Cutover до шага 4 (копия в vault'е ещё жива) — проектный агент выигрывает у плагинного молча;
  это ожидаемое поведение платформы (RES-002), не баг — фиксировать регрессионным тестом
  отсутствия обратного (плагин не должен пытаться перекрыть проектную копию)
- `qmd` доступен частично (сервер есть, каталога профилей нет, или наоборот) — FR-24 AC уже
  покрыт QA-010/at-design для контура обработки встречи; здесь не дублируется

**Test-pyramid рекомендация:**

| Группа AC | Уровень | Обоснование |
|-----------|---------|-------------|
| FR-20 (discovery: есть/нет/повреждён файл) | unit | чтение файла конфигурации, чистая функция от пути |
| FR-21 (команды без vault-раскладки) | integration | CLI/MCP-инструмент end-to-end во временном проекте без конфига |
| FR-23 (приоритет источников) | unit | резолюция пути — чистая функция от набора входов |
| FR-25 (секреты не в хранилище) | integration | grep реального дерева хранилища после серии операций на фикстуре |
| Состав плагина (нет абсолютных путей/`95_TRANSCRIPTS` в теле) | статическая проверка (не тест кода) | grep дерева плагина, часть CI сборки плагина, не pytest пакета |
