# ADR-022 spec: снятие MCP-слоя и переименование `ktalk-mcp` → `ktalk-cli`

Companion-спека к [ADR-022](../00-project/adr/ADR-022-ktalk-cli-rename.md). Детализация,
брифы Dev/DevOps, контракт QA-author.

## 1. Инвентарь: что снимается

| Модуль | Роль | Единственный вызывающий |
|---|---|---|
| `src/ktalk_mcp/server.py` | Регистрация MCP-сервера | — |
| `src/ktalk_mcp/tools_contacts.py` | MCP-обёртка `search_contacts` | `server.py` |
| `src/ktalk_mcp/tools_meeting_cancel.py` | MCP-обёртка отмены встречи | `server.py` |

| `src/ktalk_mcp/tools_recordings.py` | MCP-инструменты записи (5 существующих + скачивание) | `server.py` |
| `src/ktalk_mcp/tools_rooms.py` | MCP-обёртка диагностики комнаты | `server.py` |
| `src/ktalk_mcp/tools_scheduling.py` | MCP-обёртка планирования | `server.py` |

Все семь — единственные во всём дереве потребители `fastmcp` (проверено `grep -rl fastmcp

переехал).

## 3. Entry points: было / стало

| Пакет | Команда | До | После |
|---|---|---|---|
| `ktalk-mcp` (текущий, 0.10.0) | `ktalk-mcp` | `ktalk_mcp.server:main` | — (пакет переименован) |
| `ktalk-mcp` (текущий, 0.10.0) | `ktalk` | `ktalk_mcp.cli:main` | — (переезжает в `ktalk-cli`) |
| `ktalk-cli` (новый, 1.0.0) | `ktalk` | — | `ktalk_cli.cli:main` |
| `ktalk-mcp` (указатель, 0.11.0, финальный) | `ktalk-mcp` | — | `ktalk_mcp:main` (стаб) |

`ktalk-cli` не объявляет `ktalk-mcp`; пакет-указатель не объявляет `ktalk` — пересечения имён
команд между двумя пакетами нет ни на одном шаге после завершения перехода.

## 4. Пакет-указатель `ktalk-mcp` 0.11.0 — состав

- `pyproject.toml`: `dependencies = []`; `classifiers` дополняются `Development Status :: 7 -
  Inactive`; `description` называет замену прямо («Deprecated — renamed to ktalk-cli; install
  ktalk-cli instead»). Дев-группа тестов и вся раскладка `src/ktalk_mcp/{client,cli,tools_*,
  server,...}.py` удаляется — пакету нечего защищать регрессией, кроме самого стаба.
- `src/ktalk_mcp/__init__.py` — единственный оставшийся файл пакета: функция `main()`,
  вызываемая entry point'ом `ktalk-mcp`. Поведение: печатает в stderr сообщение о переименовании
  и точную команду `uv tool install ktalk-cli`; поднимает `DeprecationWarning`; возвращает
  ненулевой код — тот же контракт, что у прочих ошибок CLI (`CLAUDE.md`, «ошибки — в stderr с
  ненулевым кодом возврата»).
- Релиз объявлен финальным: дальнейших версий `ktalk-mcp` после `0.11.0` не планируется
  (последствие решения ADR-022 п.6, не отдельное обязательство README — текст README/классификатор
  фиксируют это на момент публикации).

## 5. Эмпирика `uv tool`: почему указатель не должен объявлять `ktalk`

Проверено локально (`uv 0.12.5`, две тестовые пары пакетов с общим именем команды):

1. Пакет A устанавливает команду `demo`. Пакет B, объявляющий ту же команду `demo`, получает при
   установке отказ: `error: Executable already exists: demo (use --force to overwrite)` — установка
   B **не завершается**, `uv tool list` не показывает B вовсе. Второй пакет не «побеждает тихо» и
   не выполняется частично — весь `uv tool install` для него падает.
2. Апгрейд пакета A **на месте** (то же имя пакета, новая версия, entry point `demo` снят в новой
   версии) корректно убирает старый shim `demo` — команда освобождается для другого владельца без
   дополнительных действий пользователя.

Следствие для миграции машины пользователя (уже стоит `ktalk-mcp` версии до 0.11.0, владеющей
и `ktalk`, и `ktalk-mcp` — подтверждено `uv-receipt.toml` боевой машины): `uv tool install
ktalk-cli` **до** апгрейда/удаления старого `ktalk-mcp` откажет по пункту 1. Безопасный порядок —
любой из двух: (a) `uv tool install ktalk-mcp==0.11.0` (апгрейд на месте снимает `ktalk`-shim по
пункту 2), затем `uv tool install ktalk-cli`; (b) `uv tool uninstall ktalk-mcp`, затем `uv tool
install ktalk-cli`. Обратный порядок (`ktalk-cli` уже стоит, следом ставится указатель) всегда
бесконфликтен — указатель не заявляет `ktalk` ни в каком виде.

| `openspec/specs/talk-api-auth-modes/spec.md` (строка 20) | `~/.config/ktalk-mcp/token` | **не менять** — литеральный путь конфига остаётся (ADR-022 п.5); спека продолжает называть фактический путь |

## 7. Порядок работ (дерево остаётся зелёным на каждом шаге)

Три коммита, каждый зелёный самостоятельно (`bash scripts/check.sh --full` exit 0 после каждого):

1. **Снятие MCP-слоя.** Удалить семь модулей (§1), 12 тестовых функций и файл
   `test_public_interface.py` целиком (§2), убрать `fastmcp` из `dependencies` и entry point
   `ktalk-mcp` из `pyproject.toml`. Прогон: 573 → 561, все зелёные. `check.sh --full` зелёный:
   C13 (грандфазер `registry.py`) не тронут; C11 не тронут — ADR-022 и эта companion-спека уже
   в дереве (результат задачи SA, предшествующей Dev), пара «ADR/спека» полна с первого коммита.
2. **Переименование модуля и дистрибутива.** `src/ktalk_mcp/` → `src/ktalk_cli/`, замена
   `ktalk_mcp` → `ktalk_cli` во всех оставшихся файлах `src/`/`tests/` (75 файлов до вычета семи
   удалённых на шаге 1 — фактическое число правки шага 2 меньше на объём удалённого), `name =
   "ktalk-cli"`, `version = "1.0.0"`, entry point `ktalk = "ktalk_cli.cli:main"`. Той же правкой —
   идентичность пакета в рантайме по §8: замена литералов `ktalk-mcp` в `__init__.py`/`cli.py` на
   чтение из метаданных, обновление `tests/test_cli.py::test_version_flag` (перестаёт быть
   хардкод-снимком имени) и добавление аналога `test_version_matches_pyproject` для имени.
   Правка двух прозаических строк в capability-спеках (§6) — тем же коммитом, раз они называют
   имя пакета, которое меняется этим коммитом. Полный прогон тестов подтверждает 561/561 после
   переименования (импорт-пути обновлены, поведение не меняется, кроме печатаемого имени).
3. **Пакет-указатель `ktalk-mcp` 0.11.0.** Отдельный релизный артефакт вне этого репозитория (уже
   переименованного в `ktalk-cli`) — публикуется из последнего коммита истории, где пакет ещё
   назывался `ktalk-mcp`, либо из отдельной ветки/тега, урезанной до состава §4. Способ выпуска
   (тег, отдельная ветка, отдельный пустой репозиторий-обёртка) — операционное решение DevOps, не
   архитектурное; инвариант — версия `0.11.0` строго больше `0.10.0` и `pyproject.toml`
   указателя содержит только состав §4.

## 8. Идентичность пакета в рантайме: полный перечень литералов `ktalk-mcp` в `src/`

Находка SA-001, подтверждена (`grep -rn "ktalk-mcp" src/` — 12 совпадений в 6 файлах). Ни одно из
них не задевается механической заменой `ktalk_mcp` → `ktalk_cli` из §7 п.2: в дефисной форме нет
идентификатора модуля, только текст.

| Файл:строка | Что это | Судьба |
|---|---|---|
| `config.py:95` | докстринг, наш путь `~/.config/ktalk-mcp/token` | не менять — путь не переименовывается (ADR-022 п.5) |
| `token_file.py:9` | докстринг, наш каталог `ktalk-mcp/` | не менять — то же (п.5) |
| `token_file.py:26` | комментарий, ссылка на файл-исследование `mainpart-ktalk-mcp.md` | не менять — это имя **чужого** продукта (сторонний MCP-сервер, разобранный как прецедент, RES-002), не нашего |
| `token_file.py:33-34` | докстринг, наш путь `~/.config/ktalk-mcp/token` | не менять — то же (п.5) |
| `token_file.py:40` | код, `root / "ktalk-mcp" / "token"` — функциональный литерал каталога | не менять — то же (п.5); риск для Dev: наивный global find-replace может задеть эту строку по ошибке, регресс ловит существующий `tests/test_token_file.py:38` |
| `__init__.py:12` | код, `_installed_version("ktalk-mcp")` — аргумент лукапа версии | **менять** — `_installed_version(__package__)` (ADR-022 п.7) |
| `cli.py:59` | код, текст `--help` для `--version` | **менять** — читает экспортированное имя, не набирает заново |
| `cli.py:381` | код, `print(f"ktalk-mcp {__version__}")` — печатаемая идентичность | **менять** — находка SA-001, читает экспортированное имя (ADR-022 п.7) |
| `endpoints.py:120` | комментарий, ссылка на `mainpart-ktalk-mcp.md` | не менять — то же, что `token_file.py:26` |
| `CLAUDE.md:1` (`src/ktalk_mcp/CLAUDE.md`) | заголовок документа | менять — документация, не код; низкий риск, но переезжает вместе с переименованием модуля (заголовок называет модуль, который переименовывается) |
| `CLAUDE.md:11` | тот же путь конфига | не менять — то же (п.5) |

Итог: 12 находок, 4 меняются (`__init__.py:12`, `cli.py:59`, `cli.py:381`, `CLAUDE.md:1`), 8
остаются как есть (6 — наш неизменяемый путь конфига по п.5, 2 — ссылка на чужой продукт).

**Реализация меняющихся четырёх.** `ktalk_cli/__init__.py` — единственная точка, где пакет узнаёт
себя: `_installed_version(__package__)` вместо `_installed_version("ktalk-cli")` (аргумент —
имя реального Python-пакета, не набранная заново строка; подтверждено эмпирически — `importlib.
metadata` нормализует `-`/`_`/регистр ключа поиска, `version("ktalk_mcp")` и `version(
"ktalk-mcp")` на этой машине разрешаются в один установленный дистрибутив). Туда же добавляется
экспорт зарегистрированного имени через `importlib.metadata.metadata(__package__)["Name"]`
(подтверждено — возвращает исходную строку `Name` из `pyproject.toml`, здесь и сейчас `ktalk-mcp`,
после переименования — `ktalk-cli`, без правки этой строки кода). Ветка `except
PackageNotFoundError` (исходное дерево без установки) — единственное место, где имя остаётся
литералом: метаданных для чтения нет физически. `cli.py:59`/`cli.py:381` импортируют оба значения
из `ktalk_cli`, не набирают строку заново.

**Регрессия для имени, симметричная существующей регрессии для версии.**
`tests/test_cli.py::test_version_matches_pyproject` уже ловит расхождение версии с
`pyproject.toml` (добавлен после инцидента 0.8.0). У имени такого теста нет —
`test_version_flag` сегодня лишь фиксирует ожидаемую подстроку (`assert out.startswith(
"ktalk-mcp ")`), не сверяет её с `pyproject.toml` динамически. Fix для §8 переиспользует
`test_version_matches_pyproject` как образец: assert печатаемое имя == `pyproject.toml`
`[project].name`, тем же приёмом (`tomllib`, без сети). `test_version_flag` обновляется на
литерал `"ktalk-cli "` тем же коммитом (снимок текущего состояния, не тест на будущее).

## NFR mapping

Формального FR/NFR в `content/30-requirements/` этого дерева под это решение не заведено —
решение владельца, не производное от BA-требования пакета (ADR-022 п.6.3, «Related articles»).
Применимый внешний контракт — `openspec/specs/cli-only-boundary/spec.md` репозитория
`ktalk-plugin`:

- Requirement «Default `ktalk-mcp` install excludes the MCP-only dependency» → превышено полным
  снятием: зависимости не требуется ни по умолчанию, ни через extra, потому что кода-потребителя
  не остаётся.
- Requirement «The plugin declares no MCP interface surface» → выполняется на стороне пакета
  тем, что MCP-сервера, который можно было бы объявить, больше не существует.
- Scenario «Contributor test run is unaffected... every test file covering the MCP layer SHALL
  run exactly as before» → **не выполняется** этим решением (файлы/функции снимаются, не
  сохраняются) — прямое следствие решения владельца «MCP-слой снимается целиком», зафиксировано
  как отклонение от плана плагинного ADR-022 (ADR-022 «Контекст»/«Alternatives Considered»).

## Brief for Dev

**Architecture:** этот файл, [ADR-022](../00-project/adr/ADR-022-ktalk-cli-rename.md)
**Phase:** Production
**Implement:** три коммита по §7 в указанном порядке; состав §1–§6, идентичность в рантайме по §8 (обязательна внутри коммита 2, не отдельным шагом).
**Order:** снятие MCP-слоя → переименование модуля/дистрибутива → пакет-указатель (отдельный
релизный процесс, после того как основной репозиторий уже переименован).
**Acceptance scenarios:** нет локального `#### Scenario:` (см. NFR mapping) — приёмка по

двух коммитов; `ktalk --version` печатает имя, равное `pyproject.toml[project].name` (§8, не
хардкод-снимку); `uv tool install ktalk-cli` бесконфликтен на чистой машине и на машине с уже
установленным указателем `ktalk-mcp==0.11.0` (не бесконфликтен на машине со старым `ktalk-mcp`
до апгрейда/удаления — задокументированный, не случайный, исход, §5).

## Brief for DevOps

**Architecture:** этот файл
**Prepare:**
- релизный процесс для двух артефактов вместо одного: `ktalk-cli` (этот репозиторий, дальше по
  обычному циклу) и `ktalk-mcp==0.11.0` (разовый финальный тег/ветка, §7 п.3);

  — тоже требует правки на стороне плагина под новое имя пакета и порядок §5;
- явный текст миграции для уже настроенных машин (порядок (a)/(b) из §5) — кандидат для README

**NFRs:** холодный старт установки без `fastmcp` укладывается в интерактивный таймаут 120 с
(измерено — 23,1 с), что было явным требованием сиблинг-эпика; это решение сохраняет его с
запасом (зависимостей меньше, чем в измеренном случае «default without MCP extra»).

## Contract with QA-author

**Архитектурный контекст:** удаление модулей — не рефакторинг с сохранением поведения для семи
файлов `tools_*`/`server` (поведение исчезает целиком), но чистый рефакторинг для 75 файлов
переименования (поведение не меняется, меняются только имена). Два разных класса риска требуют
разных проверок.

**Edge cases / граничные условия:**
- после снятия семи модулей ни один тест не должен искать `fastmcp`/`ktalk_mcp.server` даже
  косвенно (импорт в `try/except ImportError` тоже недопустим — решение снимает зависимость без
  остатка, не переводит в опциональную);
- переименование модуля — риск неполной замены: путь `src/ktalk_mcp/` → `src/ktalk_cli/`,
  строковые упоминания в докстрингах/`CLAUDE.md`/`README.md`, entry points в `pyproject.toml`,
  ссылки в `content/`/`openspec/`, путь `token_file.py` (см. следующий пункт — этот путь НЕ
  переименовывается, регрессия на это — баг);
- `~/.config/ktalk-mcp/token` обязан остаться литералом после переименования модуля — тест на
  «путь не изменился» защищает от случайной find-replace правки по всему дереву
  (`tests/test_token_file.py:38` уже это делает — регресс на этом пункте будет пойман);
- печатаемая идентичность (`ktalk --version`) обязана совпадать с `pyproject.toml`
  `[project].name`, не просто с ожидаемой строкой снимка (§8) — источник для этого теста
  динамический (`tomllib`), не хардкод, тем же приёмом, что уже защищает версию;
  ADR-024 (`ktalk-plugin`) читает именно этот вывод при откате — тест на это поле не опция;
- пакет-указатель: вызов `ktalk-mcp` — ненулевой код возврata, сообщение в stderr (не stdout),
  `DeprecationWarning` поднят; `uv tool install` пакета-указателя никогда не запрашивает `ktalk`
  (проверяется по `pyproject.toml` указателя — entry point отсутствует, не тестом на реальном
  `uv`, тяжёлым для CI).

**Тест-пирамида:**

| Группа | Уровень | Обоснование |
|---|---|---|
| Отсутствие `fastmcp` в графе зависимостей после снятия | unit (проверка `pyproject.toml`/`uv.lock`, не сеть) | статический факт конфигурации |
| Полнота переименования модуля (grep-инвариант «`ktalk_mcp` встречается только в перечисленных легитимных местах: путь конфига, история ADR») | unit | текстовая проверка дерева, не поведение |
| Печатаемая идентичность == `pyproject.toml[project].name` (§8, аналог `test_version_matches_pyproject`) | unit | чистая функция, без сети, тот же приём, что уже защищает версию |
| CLI-команды пакета работают после переименования (`ktalk <subcommand>`, включая сетевую) | integration | реальный HTTP-мок или снимок, как у существующих CLI-тестов |
| Поведение пакета-указателя (код возврата, сообщение, `DeprecationWarning`) | unit | чистая функция `main()` без сети |
| Бесконфликтность `uv tool install` в обоих порядках (§5) | e2e / ручной прогон (не автоматизируется дешево — требует реальных `uv tool install`/`uninstall` на подготовленном окружении) | тяжёлая проверка внешнего инструмента, не CI по умолчанию — ручной раздел QA-отчёта, как экспирация реестра в существующей практике пакета |
