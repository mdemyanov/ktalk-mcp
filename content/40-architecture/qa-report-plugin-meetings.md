### Два места, где контракт менялся (не добавлялся)

**Код возврата `search-contacts`: 1 → 2 при нуле совпадений (DEV-009).**

Было: `rc == 1` — общий для «0 найдено» и для сетевого/авторизационного отказа, различимо
только каналом (at-design «Замаскированный отказ», находка №2). Стало: `0` — найден кандидат,
`1` — отказ, `2` — 0 кандидатов без отказа. Кто ещё мог читать старый код:

- `tests/test_search_contacts.py::test_ac_10_1_zero_matches_cli_message_names_the_query_and_nonzero_exit`
  — проверяет `rc != 0`, не конкретное значение `1`; правка не требуется, тест зелёный при `rc==2`.
  Подтверждено этим прогоном (`test_search_contacts.py` — все тесты в наборе passed).
- MCP-инструмент `ktalk_search_contacts` (`tools_contacts.py`) — код возврата CLI не читает
  вовсе, отдельный процесс.
- Промт-слой плагина (`skills/ktalk-meetings/SKILL.md`, `_meta.md`) — уже описывает новый
  контракт (`--json`, различение `search-contacts`) на момент этого прогона, не старый.
  Проверено `grep` по дереву `ktalk-plugin`.
- Два стаба QA-005, кодировавших старое ожидание (`test_ac_34_1c_...`,
  `test_search_contacts_rejects_json_flag`, третий — `test_ac_35_3_...`, переименован) —
  единственные потребители старого контракта в этом дереве, переписаны DEV-009 (дев-заметка
  `content/60-implementation/dev-009-cli-json-and-exit-codes.md`, раздел «Судьба перевёрнутых
  стабов»). Грепом по `content/`, `tests/`, `scripts/` DEV-009 других жёстких зависимостей от
  `rc==1` на «0 найдено» не нашёл — заявление дев-заметки, этим прогоном не переверифицировано
  повторным полнотекстовым поиском за пределами уже указанных мест (избыточно: та же команда
  дала бы тот же результат, дерево не менялось между DEV-009 и этим прогоном кроме DEV-010,
  который `src/` не трогал).
- **Вывод: изменение безопасно, все известные потребители на новом контракте, покрытие теста
  прямое (`test_dev009_search_contacts_json_zero_matches_shape`,
  `test_ac_35_3_zero_matches_vs_network_error_are_distinguishable_by_exit_code_and_channel`).**

**Постусловие `install` выровнено на предикат `check` (DEV-007).**

Было: `install` мог вернуть `0` (успех операции) при бинаре, всё ещё недостижимом из `PATH`
(рассинхрон предиката). Стало: постусловие `install` — тот же `command -v ktalk`, что и у
`check`; несовпадение → код `10`, текст называет `PATH`. Цепочка `check → install → check`
покрыта явным тестом `install→check: одинаковый предикат, одинаковый код` (зелёный, подтверждено
прогоном 3). Дополнительно закрыт второй дефект той же задачи: `install --json` теперь печатает
`attempts`/`return_code`/`uv_output` на любом исходе (5 тестов на телеметрию, все зелёные) —
раньше поле могло отсутствовать на отказе, скрывая диагностику от потребителя, парсящего JSON.
Тесты герметичны (стаб `uv`, не реальный бинарный менеджер) — граница покрытия ниже, в разделе
«Вне автотестов».

## Вне автотестов этой волны — чек-лист живых проверок владельца

Три класса поведения физически не покрываются герметичным прогоном (TTY-барьер ADR-005,
стаб `uv` вместо реального менеджера, отсутствие сетевого доступа к боевому KTalk в CI).
Ниже — точные команды для владельца, не для агента; красная линия задачи запрещает агенту их
выполнять.

1. **Боевое создание и отмена встречи (TTY-барьер, ADR-005).**
   `*-confirm`-команды физически требуют реального терминала — под pytest `isatty()` всегда
   `False`, барьер проверен только на отказе (rc!=0, ноль сети), не на позитивном сценарии.
   ```
   ktalk create-meeting-preview --title "тест QA-006" --start <ISO> --end <ISO>
   # прочитать предпросмотр, затем — если устраивает —
   ktalk create-meeting-confirm --title "тест QA-006" --start <ISO> --end <ISO>
   # затем отменить тем же способом:
   ktalk cancel-meeting-preview --id <id из ответа> --reason "QA-006 живая проверка"
   ktalk cancel-meeting-confirm --id <id> --reason "QA-006 живая проверка"
   ```
   Критерий: `-confirm` запрашивает подтверждение интерактивно (не молча выполняет), встреча
   реально создаётся/отменяется в боевом KTalk, повторный запуск `-confirm` после сетевого сбоя
   не отправляет второй `POST` (NFR-22, механика проверена под `pty` в тестах — сам факт
   доведения до боевого сервера нет).

2. **`~/.local/bin` вне `PATH` на настоящей машине.** Запарковано с DEV-007
   (`ktalk-onboard-parked-defects`, auto-memory) — тесты `test-onboard.sh` герметичны, стаб `uv`
   не создаёт реального бинаря вне `PATH`.
   ```
   # временно убрать ~/.local/bin из PATH в новой оболочке:
   env PATH="$(echo "$PATH" | tr ':' '\n' | grep -v '\.local/bin' | paste -sd: -)" \
     bash scripts/ktalk-onboard.sh check --json
   # ожидается ненулевой код с текстом про PATH, не молчаливый 0
   env PATH="$(echo "$PATH" | tr ':' '\n' | grep -v '\.local/bin' | paste -sd: -)" \
     bash scripts/ktalk-onboard.sh install --json
   # ожидается код 10 (постусловие install==check), не 0
   ```

3. **Навык `ktalk-meetings` против боевого контура после публикации пакета 0.8.0 в PyPI.**
   Плагин требует `ktalk_mcp_min_version: 0.8.0` (`compat.json`); пакет в `pyproject.toml` уже
   `0.8.0`, но публикация в PyPI — отдельный шаг (ADR по механике релиза через `gh`,
   `ktalk-mcp-pypi-lags-repo`, auto-memory).
   ```
   # проверить, что 0.8.0 действительно на PyPI (не только в репозитории):
   pip index versions ktalk-mcp
   # после подтверждения публикации — живой прогон онбординга плагина с реальным uv:
   bash scripts/ktalk-onboard.sh check --json
   bash scripts/ktalk-onboard.sh install --json   # только после явной санкции владельца
   bash scripts/ktalk-onboard.sh check --json      # повторно — постусловие DEV-007
   # затем — сессия с навыком ktalk-meetings, боевой список расписания:
   ktalk list-calendar --start <сегодня ISO> --end <сегодня+1 ISO> --json
   ```
   Критерий: `install` подтягивает именно `0.8.0` (не более раннюю кэшированную версию),
   `search-contacts --json`/`list-calendar --json` дают реальные данные, коды возврата
   совпадают с зафиксированными в DEV-009 (`0`/`1`/`2` для `search-contacts`).
