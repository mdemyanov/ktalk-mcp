# Раскладка модулей и карта API-контрактов

## Контекст

Эпик [«Персональный API-ключ и расширение возможностей»](../30-requirements/personal-api-key.md)
(0.5.0) добавляет ≈6-8 методов клиента, 5 MCP-инструментов, 1-2 CLI-команды, 5 форматтеров и два
новых алгоритма (дообогащение участников, сверка id). Это SA-002: **где что лежит и кто кого
вызывает**. Auth-заголовки, приоритет режима, профиль эндпоинтов по режиму (таблица FR-6),
нормализация ответов между режимами и диагностика 401/403 (FR-5) — зона параллельного
[ADR-003-auth-modes](../00-project/adr/ADR-003-auth-modes.md) (в работе на момент письма; ссылка
станет рабочей, когда тот SA его создаст). Здесь эти механизмы **используются как внешняя
зависимость**, не проектируются заново.

## Границы этой спеки

Не описано здесь (см. ADR-003 и его companion-спеку):
- откуда клиент берёт заголовок `X-Auth-Token` vs `sessionToken`;
- какой конкретно путь вызывается в какой момент (профиль FR-6 как решение "если режим X, то
  путь Y" — сама таблица уже дана BA, её реализация как переключателя — ADR-003);
- как ответы `Domain/recordings/v2` (`entities[]`) и внутреннего `/api/recordings`
  (`recordings[]`) сводятся к одной форме для последующей обработки;
- текст диагностических сообщений на 401/403 (FR-5).

Описано здесь: физическое расположение кода, сигнатуры методов клиента, какой MCP-инструмент/
CLI-команда что вызывает, единый итератор пагинации (FR-14/FR-9), куда встраивается
дообогащение участников (FR-8), нейминг нового API.

## 3. Нейминг нового API

### MCP-инструменты (контент)

| Имя | Обоснование конвенции |
|---|---|
| `ktalk_get_participants` | Сущность + действие, как у пяти существующих; `get_` — единичный объект (список участников одной записи), не `list_` |
| `ktalk_download_recording` | Единственное отступление от `ktalk_<verb>_<noun>` — здесь `<verb>` не read-действие; имя намеренно совпадает с mainpart (`download_recording`, RES-002) для узнаваемости, но с нашим префиксом `ktalk_` |
| `ktalk_list_archive` | `list_` — множественный результат с пагинацией, как `ktalk_list_recordings` |
| `ktalk_get_chat_messages` | Совпадает по смыслу с mainpart `get_chat_messages`, префикс наш |
| `ktalk_auth_status` | В отличие от mainpart (`auth_status` без объекта) явный noun сохранён для единообразия префикса |

NFR-1 закрыт: ни одно из пяти существующих имён/обязательных параметров не меняется — новые
инструменты только добавляются, старые пять физически переезжают в `tools_recordings.py` без
изменения кода.

### CLI-команды (механика)

| Команда | Тип | Обоснование |
|---|---|---|
| `ktalk sync --dry-run` | новый флаг на существующей команде | Повторяет уже принятый в проекте паттерн `migrate --dry-run` — не плодит команду ради одного сценария |
| `ktalk auth-status` | новая команда | Операционная предпроверка перед `sync` (тот же `client.get_auth_status()`, что и MCP-инструмент); не «контент», но и не чисто registry-механика — решение объяснено ниже |

### Решение: что из нового — в MCP, что — в CLI

CLI = механика реестра (sync/дедуп/статусы/экспорт, CLAUDE.md). Участники, скачивание, архив,
чат — это **контент**, потребитель — агент через MCP, не оператор реестра. Поэтому:
`ktalk_get_participants`, `ktalk_download_recording`, `ktalk_list_archive`,
`ktalk_get_chat_messages` — **только MCP**, дублирующих CLI-команд нет.

`auth-status` — пограничный случай, решён в пользу CLI **тоже**: диагностика ключа нужна
оператору/скрипту-автоматизации ДО запуска `sync` (аналогично тому, зачем `mark-*` команды
существуют отдельно от MCP) — не контент про встречу, а предпроверка перед механикой. Реализация
не дублируется: оба потребителя вызывают один и тот же `client.get_auth_status()` и один и тот же
`format_auth_status`.

Осознанно **не сделано**: опциональный параметр `enrich_participants` на существующем
`ktalk_list_recordings` (рассматривался и отклонён — расширяет уже застабилизированный NFR-1
инструмент ради того, что закрывает отдельный `ktalk_get_participants`; N+1 по каждому элементу
списка на каждый вызов списка — не тот компромисс по стоимости, см. §6).

### `ktalk_download_recording`: параметры, поведение, риски

```
ktalk_download_recording(
    recording_key: str,
    target_path: str,
    quality: str | None = None,   # None -> см. открытый вопрос ниже
    format: str = "markdown",     # как у остальных инструментов — раз о метаданных, не о файле
) -> str
```

- **`target_path`** — конвенция как у mainpart (RES-002): директория/путь с `os.sep` в конце →
  имя файла из URL; конкретный путь → пишется туда, родительские каталоги создаются. Заимствуем
  этот один механизм осознанно (проверен на практике), явно НЕ заимствуя остальное решение
  mainpart про хранение токена (вне рамок эпика, BA «Вне рамок»).
- **Возврат** — только метаданные (`{path, bytes, quality}` в духе mainpart), никогда не
  содержимое файла: инструмент не отдаёт файл через текстовый канал MCP.
- **Большие файлы** — потоковая запись (`httpx.AsyncClient.stream()` + `aiter_bytes()`), без
  буферизации в памяти — прямое требование FR-7 AC4. Таймаут на чтение отдельный от базового 30 с
  клиента (у mainpart — 600 с, RES-002) — точное число для этого домена не откалибровано (файлы
  этого пространства не измерялись), берём прецедент mainpart как отправную точку, Dev
  перепроверяет на боевом домене.
- **Ошибка "качества нет в списке"** (FR-7 AC3) — `download.py` сверяет запрошенное `quality`
  со списком доступных, полученным от `get_recording()` (session) или... — здесь открытый вопрос:
  api-key-режим не даёт `qualities[]` в ответе деталей (`TalkDomainConferenceRecording` не несёт
  этого поля, RES-001) — список доступных качеств под ключом взять неоткуда, кроме рекомендованного
  спекой значения `900 p`. Решение остаётся за ADR-003/Dev на боевом домене — здесь зафиксировано
  как факт асимметрии между режимами, не решено произвольно.
- **Безопасность записи на диск** — `target_path` приходит от вызывающего агента без валидации
  пути в этой спеке (не входит в её рамки: SA не формулирует политику песочницы). Рекомендация:
  DevSecOps-ревью перед релизом — MCP-инструмент даёт запись в произвольный путь файловой системы
  тому, кто управляет MCP-клиентом.

## 4. Куда встраивается FR-8 (полный состав участников)

### Решение

Дообогащение **условное**, не всегда: только когда `len(participants) < participantsCount`
(прямое соответствие AC). Всегда — означало бы ~1316 лишних запросов на полный sync вместо ~300
(экстраполяция из зонда: 23 из 100 записей выборки требовали дообогащения, не факт для всего
домена — BA зонд явно это не утверждает как измеренное число для 1316).

### Кто вызывает

- **`ktalk sync`** — единственный обязательный потребитель. `cli.py::_cmd_sync` вызывает
  `enrichment.enrich_batch(records, client, concurrency=N)` **после** того, как все страницы
  списка собраны через `pagination.py` (последовательно — пагинация курсорная/офсетная,
  распараллелить нечем), затем — фан-аут с ограниченной конкурентностью по записям, требующим
  дообогащения.
- **`ktalk_get_participants`** (MCP) — по требованию, одна запись за вызов, не пакетный сценарий.
- **`ktalk_get_recording`/`ktalk_list_recordings`** — дообогащением НЕ занимаются (решение,
  не забывчивость): `ktalk_get_recording` уже возвращает полный состав в session-режиме (зонд
  Ф-4: детали отдают 8 из 8 при списке 6 из 6), а для случаев `participantsCount > 10`
  (не проверено зондом ни в одном режиме) агент должен явно позвать `ktalk_get_participants`.

### Параллелизм и отказоустойчивость

```
async def enrich_batch(
    records: list[dict],
    client: KTalkClient,
    *,
    concurrency: int = 5,
) -> dict[str, list[dict]]:
    """Возвращает {recording_id: participants[]} только для записей, где
    len(participants) < participantsCount. Остальные не трогает.

    concurrency=5 — консервативный дефолт, а не измеренный безопасный порог:
    RES-001 явно фиксирует "Пределы rate limiting (429) — нигде не
    задокументированы числом" — при отсутствии данных выбран малый параллелизм,
    настраиваемый, не выведенный из замера пропускной способности.

    Отказ по одной записи не прерывает sync целиком: лог предупреждения,
    запись остаётся с усечённым participants[] этого прохода (согласуется с
    общей веротерпимостью sync к частичным данным — ср. `expire_new`).
    """
```

Реализация — `asyncio.Semaphore(concurrency)` вокруг задач `asyncio.gather(..., return_exceptions=True)`,
не голый `asyncio.gather` без ограничения (упёрлось бы в 429 на полном sync 1316 записей разом).

### Участники с анонимами: новый маппер вместо `registry.py`

`registry.py::participants_from_api` (существующий, замороженный) требует `userInfo` и молча
пропускает анонимов — менять нельзя (грандфазер). `enrichment.py` вводит собственный маппер
(другое имя, не путать с замороженным):

```
def map_participants(raw: list[dict]) -> list[dict]:
    """Замена participants_from_api для новых вызовов: не роняет анонимов.
    Аноним -> {"ktalk_id": anonymousId, "name": anonymousName or "Аноним"}.
    Именованный -> та же схема id/name, что у participants_from_api (без
    изменения формата строки participants в SQLite — участники по-прежнему
    (recording_id, ktalk_id) PK, схема registry.py не меняется).
    """
```

`cli.py::_cmd_sync` вызывает `map_participants`, не `participants_from_api`, для записей,
дошедших до `upsert_recording`. Старая функция в `registry.py` становится недостижимой с этого
call site — не удаляется этой спекой (SA не пишет код), но Dev может убрать её как мёртвый код
отдельным маленьким PR, если она больше нигде не используется — это уменьшит `registry.py`,
разрешено (гейт блокирует рост, не уменьшение).

## 5. Единый итератор пагинации

### Проблема, которую закрывает (Ф-3, FR-14)

`/api/recordings` не содержит `nextPageToken` — текущий цикл `while page_token` обрывается после
первой страницы всегда. `Domain/recordings/v2` (api-key) — курсор `pageTokenString`/`nextPageToken`
реально существует. `domain/conferencesHistory` (архив, FR-9) — `skip`/`take`, без курсора вовсе.
Три разных формы "продолжение есть/нет" — нужен один алгоритм, не три копии одного бага.

### Форма

```
async def paginate_pages(
    fetch_page: Callable[[Cursor | None], Awaitable[tuple[list[dict], Cursor | None]]],
) -> AsyncIterator[list[dict]]:
    """Условие остановки: items пуст ИЛИ next_cursor ложный — оба варианта,
    какой сработает раньше. Не полагается на наличие поля токена в ответе
    (Ф-3: этого поля физически нет в session-ответах) — источник истины
    "продолжать ли" всегда пара (items, next_cursor), которую строит адаптер,
    а не сырое поле ответа API.
    """
    cursor: Cursor | None = None
    while True:
        items, next_cursor = await fetch_page(cursor)
        if not items:
            return
        yield items
        if not next_cursor:
            return
        cursor = next_cursor
```

Два адаптера строят пару `(items, next_cursor)` из разных API-форм:

- **`skip_pages(fetch, page_size=100)`** — session и archive. `cursor` — целое смещение
  (стартует с `0`). `next_cursor = cursor + len(items)`, но только если `len(items) == page_size`
  (полная страница) — короткая или пустая страница = последняя, конец пагинации без доверия
  какому-либо полю ответа. `page_size` жёстко клэмпится в `[1, 100]` внутри адаптера — это и есть
  системное закрытие дефекта FR-14 (`top=1000` больше физически недостижим ни из одного call site,
  клэмп в одном месте, не в каждом вызывающем).
- **`token_pages(fetch)`** — api-key список записей. `cursor` — непрозрачная строка
  `pageTokenString`. `next_cursor = response.get("nextPageToken")` — чтение конкретного поля уже
  нормализованного ответа (форма ответа — забота ADR-003, `token_pages` получает на вход
  уже единообразную пару `(entities_или_recordings, next_token)`, не сырой JSON).

### Потребители

| Потребитель | Адаптер | Зачем |
|---|---|---|
| `cli.py::_cmd_sync` (FR-14) | `skip_pages` (session) / `token_pages` (api-key, через ADR-003) | Полный обход окна дат |
| `client.py::list_archive` (FR-9) | `skip_pages` | `domain/conferencesHistory` — только skip/take, курсора нет вообще |
| `client.py::get_full_participants` (FR-8, api-key) | `skip_pages` | `Domain/recordings/{key}/participants` — тоже skip/top |
| `reconciliation.py` (FR-15) | тот же `skip_pages`/`token_pages`, что и sync | Сверка должна смотреть на то же множество, что реально заберёт боевой sync |
| `tools_meetings.py::ktalk_list_archive` (MCP) | обход `paginate_pages` до исчерпания, с потолком страниц (по прецеденту `_fetch_recordings`: `range(20)`) | FR-9 AC2 требует все встречи окна за один вызов инструмента, не постранично как `ktalk_list_recordings` |

ADR-003.

**AC из этой зоны:**

- FR-8: все три AC (дообогащение по условию, анонимы не пропадают, состав > 10).

- FR-14: все три AC (границы 1-100, `skip`-пагинация до пустой страницы, окно > 100 записей).
- FR-15: все три AC (сверка id, блокировка боевого прогона при расхождении, продолжение при совпадении).

**Архитектурный контекст:**
- Компоненты: `pagination.py` (общий для 5 потребителей), `enrichment.py` (fan-out с
  семафором), `download.py` (потоковая запись), `reconciliation.py` (guard).
- Интеграции: KTalk API (реальные HTTP-вызовы для ручных AC — большинство FR-7..FR-15 AC
  помечены BA как "ручная проверка на боевом домене", т.к. api-key на момент BA-работы не
  проверен ни разу; часть AC на моках/фикстурах — автоматическая).
- Trust boundary: MCP/CLI вход → `tools_*.py`/`cli.py` (тонкие) → `client.py` +
  специализированные модули → `httpx` наружу.

**Edge cases / boundary conditions:**
- Пустая страница на первой же попытке (записей 0 в окне) — `paginate_pages` должен вернуть 0
  страниц, а не упасть.
- Полная последняя страница (`len(items) == page_size` на последней реальной странице) — адаптер
  `skip_pages` в этом случае сделает ОДИН лишний запрос (страница окажется пустой) — по дизайну,
  не баг; тест должен подтвердить, что лишний запрос происходит и корректно завершает цикл.
- `participantsCount == len(participants)` ровно (граница дообогащения) — НЕ должно вызывать
  дообогащение (строгое `<`, не `<=`).
- Конкурентный fan-out: одна из N записей отдаёт 500/timeout — остальные N-1 должны успешно
  дозавершиться, sync не падает целиком.
- `quality` с пробелом и без (`"900p"` vs `"900 p"`) не должны давать разный результат сравнения
  в `download.py`.
- `ktalk sync --dry-run` на пустом реестре (первый sync вообще, не только первый api-key) —
  сверивать не с чем; должен явно сообщить "нет данных для сравнения", не молчаливый "OK".
