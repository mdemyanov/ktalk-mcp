# OPS-001: Откат миграции реестра в централизованное хранилище

## Purpose

Использовать, когда `ktalk migrate-to-central-store` (NFR-12, [ADR-013](../00-project/adr/ADR-013-central-transcript-store.md))
завершилась, но результат нужно отменить: централизованный файл повреждён, содержит не те данные,
или решение о переходе пересмотрено. Не путать с `ktalk migrate <vault>` — тот импортирует
markdown-архивы (ADR-002), у него нет отношения к этой процедуре.

Каждый шаг ниже исполнен на синтетическом дереве перед публикацией этого рунбука (issue
[mdemyanov/ktalk-cli#7](https://github.com/mdemyanov/ktalk-cli/issues/7)) — фактический вывод
команд приведён под каждым шагом, не выдуман. Прогон: 3 сентября 2026, пакет `ktalk-cli` 1.0.0,
ветка `epic-cli-open-issues`. Синтетические `recording_id`/имена участников — не данные владельца.

## Preconditions

- `ktalk` доступен в PATH (`which ktalk` или `uv run ktalk --version`).
- Известен путь-источник (vault, из которого мигрировали) и путь-цель (централизованный корень,
  по умолчанию `${XDG_DATA_HOME:-$HOME/.local/share}/ktalk/registry.db` —
  [ADR-013 §1](../00-project/adr/ADR-013-central-transcript-store.md)).
- Рядом с путём-источником существует файл вида `<имя>.pre-migration-<дата>` — миграция создаёт
  его сама (NFR-12), удаления не делает. Без этого файла шаги 1–2 ниже неисполнимы — см.
  «Известное ограничение» и «Что делать, если откат не удался».
- `sqlite3` в PATH для проверки целостности (шаг 3) — либо `python3` с модулем `sqlite3`
  (стандартная библиотека, всегда доступен там же, где `ktalk`).
- Доступ к машине, где физически лежит централизованный файл (локальная операция, не сетевая).

## Шаги миграции (контекст, кратко)

Полный контракт — [ADR-013-spec §«Контракт команды миграции»](../40-architecture/ADR-013-central-transcript-store-spec.md).
Коротко, что уже произошло к моменту, когда нужен откат:

1. `ktalk migrate-to-central-store <source> [--target <path>]` скопировал `<source>` в целевой
   путь, построчно сверил дамп источник↔копия, и только после совпадения переименовал источник в
   `<source>.pre-migration-<YYYY-MM-DD>` (не удалил).
2. С этого момента команды реестра открывают целевой путь (приоритет источников —
   [ADR-013-spec §«Поток данных»](../40-architecture/ADR-013-central-transcript-store-spec.md)).

Фактический прогон на синтетических данных (3 записи, синтетические `recording_id`
`synthetic-rec-001..003`):

```
$ uv run ktalk migrate-to-central-store /path/to/vault/.registry.db --json
{"source": ".../vault/.registry.db", "target": ".../xdg-data/ktalk/registry.db"}
```

Права после миграции — каталог `0700`, файл `0600` (NFR-15), проверено `stat -f "%OLp %N"`:
```
700 .../xdg-data/ktalk
600 .../xdg-data/ktalk/registry.db
```
Источник на месте, переименован — `.registry.db` → `.registry.db.pre-migration-2026-09-03`.

## Шаги отката

### 1. Остановить всё, что пишет в централизованный файл

UI-шаг, нет CLI-эквивалента: закрыть все запущенные обработчики/скрипты, использующие `ktalk` с
этим путём БД, прежде чем трогать файлы ниже — не команда, а организационное условие (проверено
2026-09-03: в пакете нет команды «показать активные подключения к SQLite-файлу»).

### 2. Переименовать backup обратно на канонический путь

```
mv "<source>.pre-migration-<дата>" "<source>"
```

Фактический прогон:
```
$ mv .../vault/.registry.db.pre-migration-2026-09-03 .../vault/.registry.db
$ echo $?
0
```

### 3. Проверить целостность восстановленного файла

```
sqlite3 "<source>" "PRAGMA integrity_check;"
```

Фактический вывод:
```
$ sqlite3 .../vault/.registry.db "PRAGMA integrity_check;"
ok
```
Любой другой вывод (не `ok`) — файл повреждён, откат не завершать восстановлением по этому пути;
см. «Что делать, если откат не удался».

### 4. Указать восстановленный путь явно — до следующего запуска

Приоритет разрешения ([ADR-013 §3](../00-project/adr/ADR-013-central-transcript-store.md)):
`--db` > `KTALK_REGISTRY_DB` > `.ktalk.toml` (`[registry] db_path`) > машинный дефолт. Пока
источник не удалён из машинного дефолта, следующий голый запуск `ktalk` без одного из трёх
явных указателей снова адресует централизованный (потенциально проблемный) файл — откат должен
зафиксировать один из трёх способов:

**а) Флагом на каждый вызов** — не персистентно, годится для разовой проверки:
```
ktalk --db "<source>" dashboard --json
```

**б) Переменной окружения** — персистентно на сессию/процесс:
```
export KTALK_REGISTRY_DB="<source>"
ktalk dashboard --json
```

**в) Конфигом проекта-хозяина** (`.ktalk.toml`, `[registry] db_path = "<source>"`) — персистентно
для проекта. **Не прогнано в этом рунбуке**: discovery конфига — компонент SA-003
(`host_config.py`), отдельный от прямого разрешения пути через `--db`/env, проверенного здесь;
формат ключа подтверждён чтением кода (`registry = data.get("registry", {})`,
`registry["db_path"]`), но сквозной прогон discovery не выполнялся — если варианты (а)/(б) не
подходят организационно, выбор (в) требует отдельной проверки перед тем, как полагаться на неё.

Фактический прогон варианта (б):
```
$ KTALK_REGISTRY_DB=".../vault/.registry.db" uv run ktalk dashboard --json
{
  "new": [ {"recording_id": "synthetic-rec-003", ...}, {"recording_id": "synthetic-rec-002", ...},
           {"recording_id": "synthetic-rec-001", ...} ],
  "stats": {"new": 3, "processing": 0, "done": 0, "skipped": 0, "partial": 0},
  "last_synced": "2026-09-01"
}
```
Три исходные записи на месте, `last_synced` восстановлен как был.

## Проверка успешности отката

- `PRAGMA integrity_check` (шаг 3) вернул `ok`.
- `ktalk --db "<source>" dashboard --json` (или с `KTALK_REGISTRY_DB`) отдаёт код возврата `0` и
  число записей, совпадающее с состоянием до миграции (сверить со снятым до миграции `dashboard
  --json`, если он был снят — иначе сверка невозможна, откат считать частичным).
- Ни одна команда реестра (`list`, `show`, `dashboard`) не падает с ошибкой открытия БД.

## Известное ограничение (кросс-проектный случай, ADR-013 §7)

Если после миграции в централизованный файл успели добавиться записи от **другого** проекта
(тот же файл, другой проект-хозяин, продолжавший писать в общее хранилище всё то время, пока этот
проект уже мигрировал) — откат на файл-backup их не переносит: backup — снимок состояния ДО
миграции этого проекта, новые записи другого проекта существуют только в централизованном файле,
не в backup.

Прогнано и подтверждено фактическим выводом (синтетика): после миграции в централизованный файл
добавлена запись `synthetic-rec-004-other-project` (имитация активности другого проекта),
`dashboard --json` на централизованном файле показывает 4 записи (`"new": 4`). После отката (шаги
1–4 выше, восстановление backup) `dashboard --json` на восстановленном `<source>` показывает
снова 3 записи — `synthetic-rec-004-other-project` в восстановленном файле нет: он остаётся только
в централизованном файле, который после отката больше не адресуется этим проектом.

**NFR-12 AC3 требует наличие и выполнимость шагов отката, не отсутствие потерь в этом
кросс-проектном случае** (дословно капабилити-спека, сценарий «A documented, verifiable rollback
path exists», [openspec/specs/centralized-machine-storage/spec.md](../../openspec/specs/centralized-machine-storage/spec.md)).
Если кросс-проектная потеря неприемлема — перед откатом вручную выгрузить записи-кандидаты на
потерю из централизованного файла (`ktalk show <recording_id> --db <централизованный путь>` для
каждой) и внести их в восстановленный файл отдельным шагом; автоматизации для этого шага в пакете
нет.

## Что делать, если откат не удался

| Симптом | Причина | Действие |
|---|---|---|
| Файла `<source>.pre-migration-<дата>` нет | Миграция чистила/переименовывала его вручную, либо это не первая миграция и файл уже был использован предыдущим откатом | Восстановления средствами пакета нет — только внешний бэкап файловой системы (машинный, не git: `.registry.db` в `.gitignore`, ADR-002/CLAUDE.md). Без внешнего бэкапа записи восстановимы только из централизованного файла вручную, построчно |
| `PRAGMA integrity_check` вернул не `ok` | Backup сам повреждён (диск, прерванная запись до переименования) | Не использовать backup как есть; обратиться к внешнему бэкапу файловой системы. Централизованный файл (если не тронут) остаётся рабочим источником — откат не обязателен, если проблема только в backup |
| Повторный `migrate-to-central-store` на тот же `--target` падает с "Целевой файл уже существует" | Ожидаемое поведение (`MigrationTargetExistsError`) — вторая миграция не перезаписывает данные, которые могли добавиться в централизованный файл после первой | Не обходить удалением целевого файла вручную без проверки, что в нём нет данных другого проекта (см. «Известное ограничение» выше) — прочитать целевой файл (`dashboard --json --db <target>`) перед удалением |
| После шага 4 команды реестра всё равно открывают централизованный файл | Указатель (`--db`/env/`.ktalk.toml`) не применился — опечатка в пути или конфиг хозяина переопределяет его на более высоком приоритете | Проверить фактически применённый путь: `ktalk config show` (если используется `.ktalk.toml`) и приоритет `--db > KTALK_REGISTRY_DB > .ktalk.toml > дефолт` — источник с более высоким приоритетом побеждает молча |

Фактический вывод повторной миграции на существующую цель (прогнано):
```
$ uv run ktalk migrate-to-central-store .../vault/.registry.db --json
Ошибка: Целевой файл уже существует: .../xdg-data/ktalk/registry.db — повторная миграция не
перезаписывает данные, добавленные после предыдущей миграции
$ echo $?
1
```

## Monitoring

Нет рантайм-метрик — CLI-инструмент, не сервис ([ADR-013-spec §«Бриф для DevOps»](../40-architecture/ADR-013-central-transcript-store-spec.md)).
- Проверка: `PRAGMA integrity_check` — после каждой миграции и после инцидента конкурентного
  доступа (NFR-13); норма — `ok`, любой другой вывод — повод остановить запись и обратиться к
  этому рунбуку.
- Проверка: `ktalk dashboard --json` → `last_synced` — `null` после свежей установки без единого
  `sync`, дата — после успешной синхронизации; не метрика с порогом, диагностический признак.
- Секреты в централизованном хранилище — вне ответственности этого рунбука; политика хранения
  секретов — DevSecOps (при активации этой роли для пакета).

## Escalation

- On-call — оператор, инициировавший миграцию/откат (пакет — локальный CLI-инструмент одного
  владельца, не сервис с дежурством).
- Эскалировать, если: `PRAGMA integrity_check` не проходит ни на централизованном файле, ни на
  backup — оба источника подозрительны, восстановление только из внешнего бэкапа файловой
  системы (см. таблицу выше).

## Known problems

- **Кросс-проектная потеря при откате** — см. «Известное ограничение» выше. Не баг, задокументированное
  ограничение ADR-013 §7.
- **`.ktalk.toml`-вариант отката не прогнан живым тестом** — см. пункт (в) шага 4; формат
  подтверждён чтением кода `host_config.py`, не исполнением.
- **Нет команды «кто сейчас держит открытым файл БД»** — шаг 1 отката организационный, не
  проверяемый инструментом пакета.
