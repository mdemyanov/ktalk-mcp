# DEV-015: канал дефектов промта (ADR-019)

Реализация [ADR-019](../00-project/adr/ADR-019-prompt-defect-channel.md) и
[ADR-019 spec](../40-architecture/ADR-019-prompt-defect-channel-spec.md) по
[требованию FR-44…FR-47, NFR-26, NFR-27](../30-requirements/ktalk-prompt-defect-channel.md).
Правки — целиком в репозитории плагина `ktalk-plugin`, ветка `dev-014-analysis-calibration`
(отдельным коммитом поверх волны 8, HEAD на момент начала `eca1f62`). Пакет `ktalk-mcp` не
тронут — вне периметра решения (ADR-012 §1). Объём урезан решением владельца, ADR-019
«Решение» п.1: транспорт-скрипта, санкции, журнала, кодов возврата нет — задача целиком
промт-текст и один новый файл-каталог без исполняемой логики.

## Что сделано (по файлам репозитория плагина)

- `CONTRIBUTING.md` — новый файл в корне репозитория (отсутствовал совсем, замер PM
  подтверждён). Раздел «Заведение issue по дефекту промта» — текст спеки §4 дословно.
- `skills/ktalk-eval/references/defect-classes.md` — новый файл, append-only каталог
  `id | название | пример`. Три стартовые записи волны 8:
  `completeness-prose-not-table`, `confidence-high-by-request-mood`,
  `asr-name-marking-inconsistent`. Названия и примеры не придуманы — свёрнуты из
  формулировок `eval-rubric.md` (критерий 3/5 Completeness, критерий 3/5 Confidence
  Usage, метод резолвинга ASR-имён), а не из прозы ADR — так они совпадают буквально с
  тем, что оценщик уже опознаёт при чтении рубрики.
- `agents/ktalk-evaluator.md`:
  - секция после «Детальные findings», ранее только `## Рекомендации` со списком
    1–3 пунктов — теперь несёт `## Дефекты промта` (таблица шести полей §2 спеки) перед
    прежним `## Рекомендации`, список которого остался как есть (спека §6: «список 1–3
    „улучшений“ без класса дефекта остаётся текстом ниже таблицы как есть»).
  - шаг 10 «Обновить трекер» получил абзац: строка таблицы `Defects` пишется по каждому
    найденному дефекту независимо от попадания в секцию отчёта, плюс шаблон строки и
    шаблон заголовка таблицы (на случай, если трекер её ещё не несёт).
- `skills/ktalk-eval/SKILL.md`, шаг 4 «Показать результат» — абзац: если отчёт несёт
  секцию «Дефекты промта», показать её оператору отдельно от таблицы оценок и сослаться
  на `CONTRIBUTING.md` репозитория плагина; явная фраза «Этот навык issue не заводит и
  не публикует» — чтобы промт не домысливал автоматизацию, которой нет.

Версия плагина (`1.3.0`) не поднята повторно — минорный рост в этой же ветке уже выполнен
задачей DEV-014 (`1.2.1 → 1.3.0`), условие гейта NFR-25 (`agents/`, `skills/ktalk-registry/`
изменены при выросшем minor) выполнено этим же ростом; NFR-25 не смотрит
`skills/ktalk-eval/` — правка `agents/ktalk-evaluator.md` этой задачи достаточна сама по
себе, чтобы гейт сработал против уже поднятой версии.

## Расхождения со спекой (не молчаливые)

**1. Таблица `Defects` — шаблон заголовка добавлен в промт агента, не только в спеку.**
Спека §3 описывает формат таблицы как факт контракта, не как инструкцию агенту. Трекер
качества на момент этой правки уже несёт таблицу `Evaluations` (DEV-014), но не факт, что
несёт `Defects` — первый прогон `ktalk-evaluator` после этой правки на существующем
трекере не найдёт заголовка. Добавил в шаг 10 явную инструкцию «если таблицы ещё нет —
создать её с этим заголовком», иначе агент на живом трекере либо придумает свой формат
заголовка, либо пропустит запись молча. Решение поддаётся эмуляции — сгенерировать первый
прогон нельзя без реального вызова LLM-агента (см. «Что осталось непроверенным»).

**2. Место таблицы «Дефекты промта» в отчёте — перед `## Рекомендации`, не вместо неё.**
Спека §6 буквально: «список 1–3 „улучшений“ без класса дефекта остаётся текстом ниже
таблицы как есть». Прочитал «ниже таблицы» как «`## Рекомендации` остаётся отдельным
заголовком после новой секции», не «текст без заголовка внутри новой секции» — второе
чтение потеряло бы разницу между «дефект с классом» и «улучшение без класса», которую
явно проводит спека («список… без класса дефекта»). Оставил оба заголовка.

## Довесок: недостающий артефакт — шаблон issue (2026-08-19)

`CONTRIBUTING.md` и каталог классов ссылаются на заведение issue в GitLab по шаблону, но
самого файла шаблона не было: `find . -iname "*issue*"` в репозитории `ktalk-plugin` до
этой правки — пусто. ADR-019 «Решение» п.4 и spec §2/§4 описывают структуру тела (шесть
обязательных полей), но не файл — упущение того же типа, что в самом решении названо про
`CONTRIBUTING.md` до этой задачи: контракт был виден в спеке, но не материализован там, где
его действительно читают (форма создания issue в GitLab).

Добавлен `.gitlab/issue_templates/Дефект промта.md` — GitLab подхватывает шаблоны из
`.gitlab/issue_templates/<Имя>.md`, имя файла становится подписью в выпадающем списке при
создании issue. Шесть полей — секции markdown (не таблица, в отличие от отчёта
`ktalk-evaluator.md`: тело issue заполняется человеком по одному полю за раз, таблица здесь
только мешала бы редактированию в форме GitLab), плюс HTML-комментарий сверху с условием
порога 2+ и требованием пары цитат (перечитывается в момент заведения, не изучается заранее)
и явное напоминание об обезличивании перед вставкой.

## Что осталось непроверенным

- **Реальный прогон `ktalk-evaluator` с найденным дефектом** — не выполнен. Проверка
  того, что промт действительно применяет порог 2+ и правило пары цитат при формировании
  секции отчёта (не только несёт текст инструкции), требует вызова LLM-агента на
  фикстурах записей — вне периметра статической правки текста. Test-pyramid спеки §
  «Контракт с QA-author» прямо называет это «вручную / текстовый снимок промта»: автотест
  ловит наличие формулировки, не факт соблюдения — граница не эта задача её сдвигает.
- **Обезличивание (NFR-26) на реальной цитате с именем/суммой/клиентом** — не проверено
  живым прогоном по той же причине; инструкция промта и требование предпросмотра внесены
  текстом (`CONTRIBUTING.md` §, `SKILL.md` шаг 4), факт применения оператором — вне
  контроля кода по решению ADR-019 п.5.
- **Расхождение каталога классов с последующими находками** — три стартовые записи
  покрывают волну 8; новые классы дефектов появятся только по мере находок агента при
  оценке, append-only правило проверено только чтением файла, не тестом (в файле нет
  исполняемой логики, тестировать нечего — FR-47/NFR-27 таблица трассировки спеки).
- **`ktalk-mcp`: `bash scripts/check.sh --fast`** — прогнан после правок в `ktalk-plugin`,
  не должен был измениться (реализация вне пакета). Результат ниже.
