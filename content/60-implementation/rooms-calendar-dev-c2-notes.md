# Разбор боевого 404 на create-meeting-confirm (DEV-002, приёмка 0.6.0)

Задача DEV-002 (разбор) из
[postanovka-wave-2.1-boevaya-priyomka.md](../../docs/postanovka-wave-2.1-boevaya-priyomka.md).
Только чтение — код не менялся, второй POST не выполнялся (красная линия постановки: первая
попытка провалилась с неизвестным исходом, условие на повторный POST не выполнено).

Тело запроса, тема, слот и комната — из
[rooms-calendar-dev-c1-notes.md](rooms-calendar-dev-c1-notes.md) (DEV-001, предпросмотр той же
команды). `create-meeting-confirm` выполнен человеком в TTY, ответ — `KTalkNotFoundError`
(«Ресурс не найден.») из `client.py::_classify`, то есть сервер вернул HTTP 404 на `POST`.

## 1. Исход: встреча не создана

Живой `GET` календаря (`ktalk_mcp.calendar_reader.get_calendar_window`,
`KTalkClient.from_settings(Settings())`, session-режим) на окне 2026-08-15…2026-08-22 (8 дней,
покрывает слот 2026-08-18T14:00–14:15+03:00 с запасом в обе стороны против таймзонных сдвигов):
16 элементов, ни один сегмент не `incomplete`. Ни по теме (`[ТЕСТ приёмки 0.6.0] Проверка
планирования встреч`), ни по `roomName` (`probe-fresh-7d2a4860aac4a5b7`) совпадений нет.
В 14:00 2026-08-18 в выдаче есть **другая** встреча («Карта рисков ИИ», `roomName:
bp5kpfn7hwvt») — совпадение времени случайно, не наша.

Выдача домен-вайд, не отфильтрована по вызывающей сессии (Ф-30/Ф-48 §4
[ktalk-calendar-api.md](../10-domain/research/ktalk-calendar-api.md)) — то есть будь встреча
создана хоть от чужого имени, она попала бы в эту выдачу. Её нет.

**Вывод: встреча не создана.** Доказано отрицательным результатом широкого (не персонального)
чтения календаря, не предположением по коду ошибки.

## 2. Точный запрос, давший 404

`meeting_scheduling.py::create_meeting`:

```python
profile = client._profile_for("create_meeting")
response = await client._client.post(profile.path_template, json=body)
```

`auth.py::OPERATION_PROFILES["create_meeting"][AuthMode.SESSION]` → `EndpointProfile("/calendar",
None)`. `client._client` — `httpx.AsyncClient(base_url=settings.ktalk_base_url, ...)`, и
`ktalk_base_url` (`config.py`) — это корень домена (`https://<space>.ktalk.ru`), **без** суффикса
`/api`.

**Фактический абсолютный запрос: `POST https://<space>.ktalk.ru/calendar`.**

Это единственная операция в `OPERATION_PROFILES` с путём без префикса `/api` — все остальные
подтверждённые внутренние пути (`get_room`: `/api/rooms/{room_name}`, `get_calendar`:
`/api/calendar`) префикс несут.

## 3. Объявлен ли путь в спеке

Нет. Перебор всех путей `talk.public.api-api-2.json` — ни `/calendar`, ни `/api/calendar` не
встречаются. Ближайшие документированные кандидаты с «calendar» в имени:

| Путь | Метод | Режим | Почему не совпадает |
|---|---|---|---|
| `/api/EmailCalendar/{email}` | GET, POST | api-key-only | требует `{email}` организатора в пути — другая модель адресации, не `roomName` |
| `/api/EmailCalendar/{email}/{eventId}` | PUT, DELETE | api-key-only | правка/удаление существующего события, не создание |
| `/api/EmailCalendar/{email}/{eventId}/attendees` | POST | api-key-only | добавление участников к уже созданному событию |
| `/api/Calendar/servers` | GET, POST | api-key-only | регистрация календарного сервера пространства (EWS/etc.), не встречи |

Ни один путь спеки не создаёт встречу в session-режиме без адресации по email.

### Источник экстраполяции: путь скопирован без поправки на префикс

Форма тела `/calendar` получена сопоставлением с `create_meeting` стороннего проекта mainpart
(`content/10-domain/research/mainpart-ktalk-mcp.md`, Ф-38 в `ktalk-calendar-api.md` §2). В этом же
исследовании прямо зафиксировано (mainpart-ktalk-mcp.md, раздел «HTTP-эндпоинты Толка»):

> Все пути — относительно `base_url = f"{space_url}/api"`, то есть реальный HTTP-путь всегда с
> префиксом `/api`.

То есть у mainpart относительный путь `POST /calendar` **уже подразумевает** `/api` — mainpart
шлёт `POST {space_url}/api/calendar`, не `POST {space_url}/calendar`. Комментарий в `auth.py`
(строки 130–135) фиксирует обратное — «путь БЕЗ префикса `/api` (mainpart, Ф-38) — намеренно
отличается от get_room/get_calendar, не опечатка» — и это прочтение расходится с тем, что
зафиксировано про сам источник экстраполяции в исследовании: относительный путь у mainpart взят
буквально, без применения его собственного правила базового URL. Ф-38 в момент написания честно
пометил вывод как `[emerging]`, не `[established]`, и отдельно отметил «пути физически разные» —
но эта оговорка не помешала `auth.py` закрепить путь без `/api` как решение, а не как гипотезу к
проверке.

## 4. «Нет пути» vs «нет объекта» — различить не удалось

По самому ответу — нет. `client.py::_classify` на 404 поднимает `KTalkNotFoundError("Ресурс не
найден.")` безусловно, не читая `response.text`/`response.json()` — тело ответа (если оно вообще
было) нигде не сохранено и не логировалось. `create_meeting` также не оборачивает вызов в
`contour_diagnostics.diagnose_undocumented_failure` (ADR-004) — в отличие от
`calendar_reader._fetch_segment`, которая на ошибке недокументированного `get_calendar` делает
контрольный `list_recordings(top=1)` и по нему различает «сеть/права в порядке, путь дрейфует» от
«общий сбой». В `create_meeting` этой корреляции нет вовсе — механизм ADR-004 существует в
проекте, но не подключён к этой операции. Задним числом её не восстановить: контрольный вызов
что-то доказывает только выполненный в момент исходной ошибки, не постфактum.

Второй POST для получения диагностируемого тела ответа запрещён постановкой (красная линия) —
единственный легальный способ отличить два исхода сейчас недоступен.

Косвенно, без нового POST: обе сущности, которые мог бы не найти обработчик (комната
`probe-fresh-7d2a4860aac4a5b7`, участник `vkuznetsov`), существуют и подтверждены живым чтением —
комната создана побочным эффектом `GET /api/rooms/{roomName}` ещё в RES-001 (Ф-49), `vkuznetsov`
— реальный ключ пользователя, владелец санкции. Это делает версию «объект не найден» менее
правдоподобной, чем версию «путь не существует» (маршрутизация 404 до обработчика, который вообще
не смотрит на тело) — но это довод по правдоподобию, не доказательство: сопоставление с чтением
не то же самое, что чтение самого 404.

**Чем это различалось бы, если бы было можно:** повторным `POST` на `/api/calendar` (с префиксом)
с тем же телом — если 404 даёт уже `/calendar`, а `/api/calendar` отвечает иначе (200/400/403),
это подтверждает версию «путь не существует». Это и есть решение о новом пути — не в компетенции
этой задачи (Р-2 постановки, решение за SA).

## 5. Читаемые кандидаты без новых запросов

Кроме таблицы в п.3 — других путей создания встречи в спеке нет. Внутренний контур (пути без
`/api`, как `/calendar`, `/api/calendar`) вообще не описан спекой ни для одной операции; всё, что
о нём известно, получено живыми `GET`-запросами прошлых волн, не документарным чтением. Прямого
недокументированного кандидата на «создание встречи» с методом, отличным от уже опробованного,
в проекте и в спеке не найдено — единственная содержательная правка, которую можно предложить без
сети, это добавление `/api` к уже используемому пути, а это и есть непроверенная гипотеза п.3/4,
не факт.

## Что осталось неизвестным

- Верна ли гипотеза «не хватает `/api`» — не проверено, второй POST запрещён без выполнения
  условия постановки (комната удалена + новое «да» владельца).
- Идемпотентность повторного `POST` (открытый вопрос волны 2, §3 `ktalk-calendar-api.md`) —
  всё ещё не исследована, независимо от исхода этой попытки.
- Тело ответа сервера на этот конкретный 404 — не сохранено нигде, `_classify` его не читает.

## Не входит в эту задачу

Решение по правке `auth.py::OPERATION_PROFILES["create_meeting"]` (путь, возможно и логика
`_classify` — доносить тело 404 до диагностики) — предмет SA-001, код здесь не менялся.
