# Разбор боевого 401 на create-meeting-confirm после правки пути (DEV-005, приёмка 0.6.0)

Задача DEV-005 (разбор) из
[postanovka-wave-2.1-boevaya-priyomka.md](../../docs/postanovka-wave-2.1-boevaya-priyomka.md).
Только чтение — код не менялся, третий боевой POST не выполнялся (красная линия постановки:
лимит в один плюс один на идемпотентность исчерпан после [rooms-calendar-dev-c2-notes.md](
rooms-calendar-dev-c2-notes.md)).

Хронология: первый боевой POST на `/calendar` (без `/api`) дал 404, встреча не создана
([c2-notes](rooms-calendar-dev-c2-notes.md)). Путь исправлен на `/api/calendar` (ADR-007,
`4409f78`). Второй боевой POST, тем же телом, в TTY человеком — **401**, сообщение
пользователю: «Токен сессии истёк или невалиден. Обновите KTALK_SESSION_TOKEN».

## 1. Исход: встреча не создана

Живой `GET` календаря (`ktalk_mcp.calendar_reader.get_calendar_window`,
`KTalkClient.from_settings(Settings())`, session-режим) на том же окне 2026-08-15…2026-08-22
(8 дней), выполнен заново в рамках этой задачи:

```
n_items 16
incomplete_segments []
rooms: [... без 'probe-fresh-7d2a4860aac4a5b7' ...]
```

Ровно те же 16 элементов, что и после первого POST ([c2-notes](rooms-calendar-dev-c2-notes.md)
§1) — ни по теме (`[ТЕСТ приёмки 0.6.0] Проверка планирования встреч`), ни по `roomName`
(`probe-fresh-7d2a4860aac4a5b7`) совпадений по-прежнему нет. Выдача домен-вайд (Ф-30/Ф-48),
довод «нет в выдаче — значит не создана» тот же, что в c2.

**Вывод: встреча не создана.** Совпадает с ожиданием от кода ошибки (401 — отказ до создания
объекта, не частичный успех), но доказано отдельным чтением, не выведено из кода ответа.

## 2. GET на тот же путь тем же токеном — работает

`get_calendar` (`AuthMode.SESSION`) ходит на тот же `/api/calendar`
(`OPERATION_PROFILES["get_calendar"][AuthMode.SESSION]`, `auth.py:123`), что и `create_meeting`
после ADR-007 (`auth.py:135`). GET из п.1 этой задачи — **200**, отдал 16 элементов, ни один
сегмент не `incomplete`. Тем же процессом (`KTalkClient.from_settings(Settings())`, тот же
`KTALK_SESSION_TOKEN` из окружения) прогнан и живой `list_recordings(top=1)` — тоже успешен,
что подтверждает `uv run ktalk auth-status` → `alive: True`.

**Факт: один и тот же путь `/api/calendar`, один и тот же токен — GET успешен, POST даёт 401.**
Значит объяснение не в правах на ресурс `/api/calendar` как таковой — иначе GET отказал бы тоже.
Различие — в методе или в том, как для этого метода интерпретируется credential.

## 3. Что реально уходит на POST

`meeting_scheduling.py::create_meeting`: `client._client.post(profile.path_template, json=body)`
— вызов через тот же `self._client` (`httpx.AsyncClient`), что и все GET-запросы клиента,
никакого отдельного пути авторизации для записи в коде нет. Клиент сконструирован в
`client.py::__init__` (session-ветка):

```python
self._client = httpx.AsyncClient(
    base_url=base_url,
    params={"sessionToken": self._auth.credential},
    timeout=30.0,
)
```

`params=` на уровне `httpx.AsyncClient` — это client-level query-параметры, которые httpx
подмешивает в **каждый** запрос через `build_request`, независимо от метода. Проверено
воспроизведением на локальном `httpx.AsyncClient` с тем же паттерном конструирования (без
сети, без токена — синтетическое значение):

```python
c = httpx.AsyncClient(base_url="https://x.example", params={"sessionToken": "abc"})
req = c.build_request("POST", "/api/calendar", json={"a": 1})
# req.url    == "https://x.example/api/calendar?sessionToken=abc"
# req.headers содержит: host, accept, accept-encoding, connection, user-agent,
#                        content-length, content-type — Authorization отсутствует
```

Инспекция боевого клиента (`KTalkClient.from_settings(Settings())`, без выполнения запроса)
подтверждает то же на реальном объекте: `client._client.params` содержит ключ `sessionToken`
(значение не читалось, проверялось только наличие ключа), `client._client.headers` — только
стандартный набор httpx (`accept`, `accept-encoding`, `connection`, `user-agent`), заголовка
`Authorization` нет ни в каком виде.

**Вывод: `sessionToken` не теряется при смене метода.** Он уходит в query POST-запроса так же,
как в query GET-запроса — это механическое свойство `httpx.AsyncClient(params=...)`, не
специфика конкретного вызова. Версия «токен потерялся между GET и POST» — опровергнута,
не подтверждена.

## 4. Тело 401 — не сохранено, но почти наверняка было напечатано в терминал в момент прогона

`client.py::_classify` на 401 в session-режиме:

```python
raise KTalkAuthError(
    "Токен сессии истёк или невалиден. Обновите KTALK_SESSION_TOKEN (см. README)."
)
```

— поднимает исключение с фиксированным текстом безусловно, `response.text`/`response.json()`
не читает и никуда не пишет. Это точка, где формулировка перестаёт зависеть от того, что
реально ответил сервер.

Но **до** `_classify`, в `meeting_scheduling.py::create_meeting` (добавлено DEV-004,
`4409f78`, то есть уже действовало на момент этого POST):

```python
if response.status_code >= 400:
    logger.warning("create_meeting: HTTP %s, тело: %s", response.status_code, response.text)
```

Эта строка на 401-ответе выполнилась бы. В проекте нет ни одной настройки `logging`
(`logging.basicConfig`, `FileHandler`, `dictConfig` — не найдено ни в `src/`, ни в
`pyproject.toml`) — при отсутствии обработчиков Python по умолчанию использует
`logging.lastResort`, который для уровня `WARNING` и выше пишет в `sys.stderr` без
форматирования сверх стандартного `LEVEL:logger.name:message`. `create-meeting-confirm`
выполнялся в TTY человеком напрямую (не через перенаправление в файл, судя по постановке) —
значит эта строка **скорее всего появилась на экране** в момент прогона, следом за ней —
результат `_print_error(str(exc))` из `cli_meeting.py` с уже подменённым текстом «Токен сессии
истёк».

**Проверить нельзя, потому что не сохранено.** Ни один файл лога в репозитории не появился
(`find` по `.log`, новее `pyproject.toml`, пусто), в постановке и в этой задаче текст
терминала не зафиксирован. Тело конкретно этого 401 потеряно для разбора — не потому что
код его не производил, а потому что вывод логгера никуда не персистится и никем не был
скопирован в момент прогона.

**Минимальная правка, которая бы это сохранила:** не полагаться на `logging.lastResort` —
либо настроить `FileHandler` на модуль `ktalk_mcp` при старте CLI (`cli.py::main`), либо
(проще и без риска зацепить другие команды) в `cli_meeting.py::cmd_create_meeting_confirm`
явно писать `response.text`/тело ошибки в `_print_error` при неудаче, а не только
`str(exc)` — тогда тело будет в том же месте, что и остальной вывод команды, без зависимости
от того, куда смотрит `logging`.

## 5. Гипотеза о причине — уровень доказанности explicit

По п.2–3: GET тем же токеном и тем же путём работает, query-параметр `sessionToken` уходит
на POST так же, как на GET, `Authorization`-заголовка нет вовсе. Значит либо (a) сервер
принимает `sessionToken` в query только для чтения и требует другой способ передачи
credential для записи, либо (b) 401 вызван чем-то, не связанным с транспортом credential
(например, CSRF-защитой на мутирующих методах, которая ожидает заголовок или cookie, которых
здесь нет никаких — `httpx.AsyncClient` без `cookies=` не хранит и не шлёт cookie).

Единственный конкретный источник, на который можно опереться без нового запроса —
`content/10-domain/research/mainpart-ktalk-mcp.md` (Ф-2 в разделе «Ключевые находки», раздел
«Авторизация — механика целиком» п.1): у стороннего проекта mainpart авторизация **всех**
запросов (не только записи) идёт заголовком `Authorization: Session <token>`, а не query
`?sessionToken=` — то есть mainpart вообще не использует наш механизм передачи, ни для чтения,
ни для записи. Токен там другого происхождения (браузерная сессия из `localStorage`,
переиздаётся через `/api/authorize/session`, которого наш проект не вызывает) — это другой
токен и другой канал, не альтернативная кодировка того же значения.

**[ГИПОТЕЗА, не проверено]** — сервер Толка может принимать `?sessionToken=` в query как
облегчённый механизм только для чтения (наблюдаемо: `get_room`, `get_calendar`,
`list_recordings` — все GET, все успешны с этим механизмом), а мутирующие эндпоинты
внутреннего контура — требовать то же, что "настоящий" браузерный клиент шлёт при записи:
заголовок `Authorization: Session <token>` и/или CSRF-подтверждение, которых наш `POST`
структурно не может послать текущим кодом (заголовка `Authorization` в клиенте нет вовсе,
см. п.3). Довод по правдоподобию (у GET и POST разное поведение при одном токене и одном
пути, у другого проекта запись требует заголовок) — не подтверждение: не проверено, что смена
транспорта credential (заголовок вместо query) на POST даст другой код ответа. Единственная
проверка — новый боевой POST с заголовком `Authorization: Session <token>` вместо/вместе с
query, что запрещено этой задачей (лимит POST исчерпан) и является предметом решения SA
(следующий боевой шаг по новой санкции — вне DEV-005).

Альтернативная гипотеза (b), CSRF/cookie, — той же степени недоказанности; не найдено
источника (ни в спеке, ни в mainpart, ни в проекте), который бы её подтвердил или опроверг.
Различить (a) и (b) без нового запроса нельзя.

## 6. Дефект модели ошибок сообщения

По CLAUDE.md модель предусматривает два случая для session-режима: 401 — «токен
истёк/невалиден», 403 — «доступ запрещён, токен рабочий». Здесь наблюдается третий случай,
для которого модели нет: **401 на конкретной операции при токене, который в ту же секунду
(и до, и после) подтверждён живым GET-запросом на тот же путь и живым `list_recordings`**.
Формулировка «обновите KTALK_SESSION_TOKEN» в этом случае объективно ложна — обновление
токена не решит проблему, потому что токен не истёк; она отправляет владельца санкции по
неверному следу (проверять/менять переменную окружения) вместо реального — проверять
механизм передачи credential для этой конкретной операции или права на запись как таковую.

Что должно говориться вместо этого — постановка проблемы, не готовое решение (решает SA):
сообщение для 401, полученного на операции, отличной от `get_auth_status`, не должно
безусловно утверждать «токен истёк» — эта причина не единственная и, как показано в п.2,
не подтверждена независимой проверкой того же токена. Точная формулировка и то, стоит ли
эта проверка сетевого вызова на каждый 401 (издержка) — решение SA-001, не этой задачи.

## Что осталось неизвестным

- Верна ли гипотеза (a) «query работает только для чтения, запись требует заголовок» —
  не проверено, третий POST запрещён.
- Верна ли гипотеза (b) CSRF/cookie — не проверено, тем же ограничением.
- Дословное тело ответа 401 — не сохранено нигде, восстановить нельзя.
- Идемпотентность повторного `POST` (открытый вопрос волны 2) — по-прежнему не исследована.

## Не входит в эту задачу

Решение о правке `client.py` (передача `Authorization`-заголовка для мутирующих операций,
чтение тела 4xx до `_classify`, правка модели сообщений на 401) — предмет SA-001, код здесь
не менялся.
