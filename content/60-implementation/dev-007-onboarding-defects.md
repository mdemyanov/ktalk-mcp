# DEV-007 (волна 5): два запаркованных дефекта онбординга

Найдены финальным ревью волны 4 (dev-005, раздел «Финальное ревью волны»), не отражены ни там,
ни в [SEC-004](../40-architecture/security-review-onboarding.md) — обнаружены позже написания
обоих. Оба закрыты в `scripts/ktalk-onboard.sh` (репозиторий плагина, отдельный git).

## Дефект 1 — `install` и `check` проверяли разные предикаты

**Подтверждено кодом.** `cmd_check` первым гейтом требует `command -v ktalk`; постусловие
`finish_install` (FR-31) проверяло только `installed_version()` — она резолвит версию через
`ktalk --version`, а при неудаче — через fallback `uv tool list`. Fallback может дать версию,
даже когда `ktalk` не резолвится через `PATH` (типовой случай — `uv` ставит бинарь в
`~/.local/bin`, не входящий в `PATH` процесса): `uv tool install` подтверждает установку с
кодом 0, `finish_install` перечитывает версию через тот же fallback, видит совместимую версию и
возвращает 0 — при том что `command -v ktalk` в этот момент уже фейлится. Цепочка `check →
install → check`, обязательная в промтах (ADR-014-onboarding-spec §6), давала 10 → 0 → 10:
`install` заявлял успех, немедленно опровергаемый следующим `check`.

**Правка:** `finish_install` теперь сначала требует `command -v ktalk`, тем же порядком, что
`cmd_check`. Если бинарь не резолвится, а `uv tool list` при этом видит пакет — возвращается
**10** (`missing_cli`), не 0, с текстом, называющим причину явно: не «пакет не установлен», а
«команда ktalk не резолвится через PATH», плюс совет добавить каталог инструментов `uv` в
`PATH`. Постусловие выровнено на предикат `check`, не наоборот — так, как просил владелец: `check`
остаётся источником истины о работоспособности CLI, `install` не имеет права заявлять успех,
который `check` тут же отменит.

`references/onboarding.md` (раздел «Код 10») получил абзац: `install` может вернуть 10 даже после
безошибочного запуска менеджера, если это `PATH`, а не отсутствие пакета — с инструкцией поправить
`PATH` и повторить `check`.

Companion-спека `ADR-014-onboarding-spec.md` §1 дополнена абзацем: постусловие `install` обязано
использовать тот же предикат, что первый гейт `check`.

## Дефект 2 — `install --json` не нёс телеметрию на исходах без запуска менеджера

**Подтверждено кодом.** Спека §1 обещает поля `attempts`/`return_code`/`uv_output` «на любом
исходе». Фактически их печатал только `install_report()` — вызывался из веток, где менеджер
пакетов (`run_install`/`finish_install`) реально запускался. Ветки без санкции (30), без
`allow_update` (32), без `uv` (12), с битым `compat.json` (20) и «пакет уже свежий» (0) шли через
`report()` — тот же набор полей, что у `check` (`status`, `installed_version`, `min_version`,
`install_command`, `message`), без телеметрии. Объект был валиден всегда (оба вывода — валидный
JSON), но парсер, читающий контракт спеки буквально, ожидал бы поля безусловно и падал бы на
`KeyError` на этих пяти кодах.

**Решение — код выровнен на спеку** (рекомендация задачи; альтернатива — сузить спеку — цены не
нашлось: добавить три поля с честными нейтральными значениями дешевле, чем менять опубликованный
контракт и переучивать промты, которые уже читают по нему).

`install_report()` теперь печатает `attempts`/`return_code`/`uv_output` всегда: если менеджер не
запускался (`RI_RAN=0`), `attempts: 0`, `return_code: null`, `uv_output: ""` — честные значения
«запуска не было», не выдуманные и не пропущенные поля. `return_code` — единственное поле, где
понадобился `null`: числовой код возврата процесса, который не был запущен, не выразить как
осмысленное число (0 читался бы как «менеджер отработал успешно», что неверно).

`cmd_install()` переведён на `install_report()` целиком: все её выходы (внутренняя ошибка
`compat.json`, нет `uv`, уже свежий, нет санкции на обновление, нет санкции на установку) теперь
идут через неё, не через `report()`. Явный сброс `RI_RAN=0; RI_RC=0; RI_OUT=''; RI_FIRST_OUT=''`
в начале `cmd_install()` — гигиена состояния, не строго обязательна (скрипт завершается после
одной команды), но делает функцию самодостаточной, если её вызовут повторно в одном процессе
(тесты).

Companion-спека дополнена: телеметрия печатается на любом исходе с нейтральными значениями при
отсутствии запуска менеджера; SEC-004 INFO-03 («набор полей различается по коду») этим снят —
принятое там решение было верным на момент ревью, спека тогда не фиксировала унификацию явно.

## Что осталось незакрытым

- Живая проверка ветки `~/.local/bin` не в `PATH` на настоящей машине владельца — тест
  герметичен (стаб `uv`), реального `uv tool install` не запускался.
- Прежние открытые пункты волны 4 (публикация 0.7.0 в PyPI, `git push` в обоих репозиториях,
  ветка `grant` в настоящем терминале) — не в скоупе этой задачи, см. dev-005.
- `content/60-implementation/dev-005-onboarding.md` не переписан задним числом — по инструкции
  задачи оба дефекта фиксируются здесь, а не задним числом в уже написанной заметке.
