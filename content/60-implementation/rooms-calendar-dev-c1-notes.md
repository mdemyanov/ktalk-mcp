# Заметки реализации: предпросмотр боевой встречи без сети (DEV-001, приёмка 0.6.0)

Задача DEV-001 из
[postanovka-wave-2.1-boevaya-приёмка.md](../../docs/postanovka-wave-2.1-boevaya-priyomka.md).
Продолжает [rooms-calendar-dev-b-notes.md](rooms-calendar-dev-b-notes.md) (реализация FR-13):
здесь новый код не писался — задача проверить существующий `create-meeting-preview` на боевом
запросе, который пойдёт в DEV-002. Комната по решению владельца — уже существующий
`probe-fresh-7d2a4860aac4a5b7` (созданный зондом RES-001), не новое имя: предусловие постановки
«GET подтвердил отсутствие» невыполнимо, `GET /api/rooms/{roomName}` создаёт комнату побочным
эффектом (Ф-44…Ф-49, `content/10-domain/research/ktalk-calendar-api.md` §4).

## Команда

```
uv run ktalk create-meeting-preview \
  --subject "[ТЕСТ приёмки 0.6.0] Проверка планирования встреч" \
  --start "2026-08-18T14:00:00+03:00" \
  --end "2026-08-18T14:15:00+03:00" \
  --timezone "GMT+3" \
  --room-name "probe-fresh-7d2a4860aac4a5b7" \
  --required-user-key vkuznetsov \
  --enable-auto-recording false \
  --enable-sip false \
  --allow-anonymous false \
  --pin-code ""
```

15-минутный слот, 18.08.2026 14:00–14:15 MSK (день после текущей даты 17.08.2026, дневное
время). Тема несёт явную пометку `[ТЕСТ приёмки 0.6.0]`. `timezone` — формат `GMT+X` (Ф-41: то
же значение и формат, что у соседнего документированного пути mainpart, единственное поле тела,
где спека и код совпадают не только по имени).

### Обоснование булевых (минимально-инвазивный выбор)

- `--enable-auto-recording false` — запись боевого тестового прогона не нужна, лишний
  артефакт с содержимым (даже пустой встречи) не создаём.
- `--enable-sip false` — участник один (`vkuznetsov`), телефонный вход не требуется.
- `--allow-anonymous false` — единственный обязательный участник поимённый; анонимный вход
  расширяет поверхность (Р-2 постановки — тот же класс риска, что и `PUT` в существующую
  комнату) без надобности.
- `--pin-code ""` — явный пустой PIN, не отсутствие флага: NFR-9 требует явного решения по
  каждому полю `_REQUIRED`, `pinCode` в их числе (см. `meeting_body.py` `_REQUIRED`); пустая
  строка — валидное явное «без PIN».
- Участники — `--required-user-key vkuznetsov`, не `--no-required-users`: единственный
  обязательный участник по санкции владельца и Р-3 постановки (приглашения необратимы,
  участник = владелец санкции).

## Доказательство 1 — ноль сетевых вызовов

Наблюдение, не утверждение: monkeypatch `httpx.AsyncClient.send` считает вызовы, плюс второй
прогон с заведомо невалидным `KTALK_SESSION_TOKEN` — предпросмотр обязан отработать одинаково
в обоих случаях, если сети действительно нет.

Прогон с валидным токеном:

```
[PROBE] сетевых вызовов httpx.AsyncClient.send: 0
# Встреча: [ТЕСТ приёмки 0.6.0] Проверка планирования встреч (ещё не создана)
...
EXIT=0
```

Прогон с `KTALK_SESSION_TOKEN=invalid-token-broken`:

```
[PROBE] сетевых вызовов httpx.AsyncClient.send: 0
# Встреча: [ТЕСТ приёмки 0.6.0] Проверка планирования встреч (ещё не создана)
...
EXIT=0
```

Вывод идентичен по форме (меняется только `confirmation_id` — он случаен по построению,
`confirmation.py` `secrets.token_urlsafe`), код возврата `0` в обоих случаях. Структурное
объяснение того же факта: `cmd_create_meeting_preview` → `PreviewService.preview` →
`build_meeting_body`/`canonical_body_hash`/`store.issue` — ни один из этих вызовов не получает
`KTalkClient` как параметр (`meeting_scheduling.py`), значит сетевой вызов физически недостижим
на этом пути, а не просто отсутствует в текущей ветке кода.

## Доказательство 2 — состав полей тела

`build_meeting_body` с ровно перечисленными выше значениями напечатал:

```json
{
  "allowAnonymous": false,
  "description": "",
  "enableAutoRecording": false,
  "enableSip": false,
  "end": "2026-08-18T14:15:00+03:00",
  "pinCode": "",
  "requiredUserKeys": ["vkuznetsov"],
  "roomName": "probe-fresh-7d2a4860aac4a5b7",
  "start": "2026-08-18T14:00:00+03:00",
  "subject": "[ТЕСТ приёмки 0.6.0] Проверка планирования встреч",
  "timezone": "GMT+3"
}
```

11 полей = 10 из `_REQUIRED` (`meeting_body.py`) + `description` (единственное поле с
разрешённым тихим дефолтом по NFR-9, здесь передано явно пустым `--description` не задавался,
дефолт `""`). Сверка множеств ключей — точное совпадение, лишних полей нет, ни одно из
`_REQUIRED` не подставлено молча (все переданы явно флагами CLI).

## Доказательство 3 — confirmation_id

Пример из боевого прогона: `r_v1AdhpCxqZp4Ij5Y_mXK_ZpYP17k5a` (24 байта, `secrets.token_urlsafe`,
не производный от хеша тела — `confirmation.py`). Срок жизни: `CONFIRMATION_TTL = 10 минут` от
момента `issue()`, single-use (`consume()` вызывается до сетевой попытки). Действителен только
внутри одного вызова `create-meeting-confirm` — межпроцессной связки между `preview` и
`confirm` физически нет (§6.3 спеки, зафиксировано в DEV-B заметках); `confirmation_id`,
напечатанный здесь в `create-meeting-preview`, для DEV-002 не переносим — DEV-002 запускает
`create-meeting-confirm` с теми же аргументами, тот построит собственный `confirmation_id`
внутри своего TTY-вызова.

## Не входит в эту задачу

`create-meeting-confirm` не запускался — красная линия постановки, боевой POST выполняется
отдельно в DEV-002 после явного «да» владельца в TTY.
