## Расхождения со спекой ADR-014 (с причиной)

- **R4 — install/upgrade разными командами.** План выполнял `install` в обеих ветках (первичная
  установка и обновление устаревшего пакета). `uv tool install` на уже установленном пакете не
  обновил бы его — код 32 и FR-30 AC2 остались бы декларативными. Реализовано: `uv tool install
  ktalk-mcp` при отсутствии пакета, `uv tool upgrade ktalk-mcp` при устаревшей версии и выданном
  `allow_update`. Спека §1 приведена в соответствие в этой же волне (`b286caa`).
- **R5 — код 12 при отсутствии одновременно `ktalk` и `uv`.** `check` возвращает 12, не 10:
  действенная для пользователя причина в этом случае — отсутствие `uv`, без него ни установка,
  ни диагностика невозможны (FR-27 AC3).
- **R6 — регекс санкции без альтернации в рантайме.** Спека формулирует форму строки как
  `allow_(install|update)`; в скрипте на каждый ключ подставляется отдельный якорный паттерн
  (`^allow_install[[:space:]]*=[[:space:]]*true[[:space:]]*$`, аналогично для `update`).
  Буквальная альтернация в одном регексе матчила бы `allow_update = true` и на проверку
  `allow_install`, санкция на обновление выдавала бы санкцию на установку — независимость
  ключей (FR-30 AC2) была бы нарушена.
- **R1 — подавление stdin в автотесте ветки «`grant` без TTY».** Тест перенаправляет
  `</dev/null`. Без этого при прогоне suite владельцем из интерактивного терминала stdin
  оказался бы TTY, автотест упал бы и попутно записал файл санкции — сайд-эффект в среде
  разработчика. Эмуляция TTY через `script`/pty для проверки самого барьера не использована —
  это обошло бы то, что проверяется.
- **R7 — добавлен автотест независимости ключей.** `allow_update = true` без `allow_install` →
  `install` возвращает 30, `uv` не вызывается. В исходном плане такого теста не было.
- **R8 — найдено и закрыто ревью Task 6.** `install --json` печатал не-JSON на кодах 0 и 31
  (спека §1 требует единый JSON-объект на любом исходе); починено вместе с четырьмя минорными
  правками в тех же строках, коммит `2013b22`.

## `KTALK_ONBOARD_RETRY_DELAY`

Переменная окружения, задержка в секундах перед единственным повтором сетевого сбоя (§5
спеки). По умолчанию 3. Существует ради времени прогона тестов —
`KTALK_ONBOARD_RETRY_DELAY=0` убирает реальную паузу из suite. Не пользовательская настройка.

## Известные отложенные мелочи

- `json_escape` в `scripts/ktalk-onboard.sh` не экранирует управляющие символы
  U+0000–U+001F, кроме CR/LF/TAB: вывод `uv` с BEL/ESC сделал бы объект невалидным JSON. Риск
  низкий — `uv` в command substitution не раскрашивает вывод.
- Фильтр `KTALK_ONBOARD_RETRY_DELAY` пропускает чисто-точечные строки (`.`, `1.2.3`) —
  `sleep` ругается в stderr и ретраит немедленно вместо ожидания.
- Набор полей `install --json` на кодах 0/31 отличается от набора `report()` (нет `message`);
  спека полей не фиксирует.
- В `references/onboarding.md` раздел «Код 11» даёт `grant update` + `install` без локальной
  оговорки «эту команду выполняет пользователь», в отличие от раздела «Код 10» — глобально
  закрыто врезкой во все 4 промта, но локальная асимметрия текста осталась.
- `cmd_status()` печатает `SANCTION_FILE` (поле `sanction_file`) в JSON без `json_escape` —
  кавычка в `XDG_CONFIG_HOME`/`HOME` сделала бы объект невалидным. `report()` после правки
  задачи 6 экранирует все поля, включая `min_version`; `sanction_json()` печатает только
  литералы `true`/`false` и строк не интерполирует.
- Тест идемпотентности покрывает только ветку с рабочим `ktalk --version`.

## Что не покрыто и остаётся владельцу

- Публикация 0.7.0 в PyPI (в индексе сейчас 0.4.0 — до публикации `check` честно сообщает
  «версия ниже минимальной», это и есть FR-31).
- `uv tool upgrade ktalk-mcp` на машине владельца.
- Живая проверка на vault'е.
- `git push` в обоих репозиториях.
- Ветка записи `grant` в настоящем терминале (ручная проверка владельца — автотестом покрыта
  быть не может по построению, см. R1).
- CI репозитория плагина и `ktalk doctor` — вне волны.
