# DEV-018: файл session-токена как третий источник авторизации

Короткий путь по решению владельца: без цикла BA→SA, ADR не заводился. Основание для
этого — не экономия, а то, что единственный вопрос, ради которого нужен был цикл,
закрыт замером в той же сессии (ниже). Расширение ADR-003 фиксируется здесь.

## Что установлено живой проверкой (2026-08-21)

| Факт | Как получен | Итог |
|---|---|---|
| `JSON.parse(localStorage.session).data.token` — то же значение, что рабочий `KTALK_SESSION_TOKEN` | `sha256` файла и переменной окружения, сравнение первых 12 символов хеша | совпало побайтово, 20 символов, `^[A-Za-z0-9]{16,40}$` |
| Читающий транспорт (query `sessionToken`) авторизуется этим значением | `KTALK_SESSION_TOKEN=$(cat ~/.config/ktalk-mcp/token) uv run ktalk auth-status` | `alive: True` — реальный `list_recordings(top=1)` |
| То же на боевом чтении календаря | `ktalk list-calendar --start 2026-08-21 --end 2026-08-21` | 4 встречи |
| Файл сам по себе НЕ подхватывался (дефект, ради которого задача) | `env -u KTALK_SESSION_TOKEN uv run ktalk auth-status` | отказ конфигурации, код возврата 1 |

Пишущий транспорт (`Authorization: Session`, ADR-009) этим значением **не проверен** —
живой POST требует санкции записи и отдельного решения владельца. Заявление README
относится только к чтению.

## Реализация

- `token_file.py` — `token_path()` (`KTALK_TOKEN_FILE` > `$XDG_CONFIG_HOME/ktalk-mcp/token`
  > `~/.config/ktalk-mcp/token`), `read_token()`, `write_token()` (запись через временный
  файл и `os.replace`, права выставляются до переименования), `file_mode()`.
- `config.py` — `@model_validator(mode="after")` подставляет токен из файла, когда пусты
  **обе** переменные. Точка входа одна: `auth_mode`, `auth_credential` и барьер
  маскирования `redact_secrets` о файле не знают и продолжают читать одно поле.
- `cli_token.py` — `ktalk token set <значение|->` и `ktalk token status [--json]`,
  команда в `_REGISTRY_FREE_COMMANDS` (секрет к реестру отношения не имеет).
- Каталог `ktalk-mcp/`, не `ktalk/`: в `ktalk/` живёт санкция записи (ADR-016) с другим
  жизненным циклом.

**Приоритет: `KTALK_PERSONAL_API_KEY` > `KTALK_SESSION_TOKEN` > файл.** Окружение сильнее
диска намеренно — иначе протухший файл молча перебивал бы токен, переданный явно.

Права шире `0600` читаются как «файла нет» — тот же fail-closed барьер, что у санкции
записи (SEC-006).

## Находка живой проверки: `token set` принимал что угодно

`pbpaste | ktalk token set -` с устаревшим буфером записал в файл путь к markdown-файлу и
отрапортовал успехом; единственным сигналом об ошибке стал бы отказ авторизации минутами
позже. Добавлена проверка формата `^[A-Za-z0-9]{16,64}$` до записи (наблюдаемый токен — 20
символов; прецедент mainpart проверяет `{16,40}`, верхняя граница поднята с запасом).
Текст отказа называет длину и правило, но не значение: в буфере мог быть чужой секрет.

Класс ошибки тот же, что у волны 6 (`confirmation_id` с дефиса) и волны 10 (формат
`timezone`): свойство значения, безразличное на одной границе, становится дефектом при
переносе на другую.

## Проверки

- `uv run --with pytest-xdist --with pytest pytest tests/ -q -n 8` → `569 passed`
  (`tests/test_token_file.py` — 19 тестов, все красные до реализации).
- `bash scripts/check.sh --fast` → `Errors: 0 | Warnings: 3` (грандфазеры, не задеты).
- Боевой сценарий после реализации: `env -u KTALK_SESSION_TOKEN ktalk auth-status` →
  `alive: True`, `ktalk token status` → `present: True, права 0600`, `usable: True`.

## Что осталось

- Пишущий транспорт живым POST не проверен (см. выше).
- Формат JSON `{token, expiresAt}` из прецедента mainpart не поддержан: срок жизни от
  сервера мы не получаем, хранить нечего.
- README переписан (раздел «Session token», таблица источников, таблица CLI); текст
  ошибки 401 в `auth.py` больше не советует единственный путь через переменную окружения.
