# Заметки реализации: планирование встречи FR-13 (DEV-B, волна 2)

Реализована пишущая часть эпика «Комнаты, календарь, планирование» по
[rooms-calendar-spec.md](../40-architecture/rooms-calendar-spec.md) §6: `meeting_body.py`,
`confirmation.py`, `meeting_scheduling.py`, `cli_meeting.py`, `tools_scheduling.py`, профиль
`create_meeting` в `auth.py`, регистрация подкоманд в `cli.py`, регистрация
`ktalk_preview_meeting` в `server.py`. Продолжает [заметки DEV-A](rooms-calendar-dev-a-notes.md)
(чтение комнаты/календаря, FR-19).

## Открытый вопрос 1 — слово подтверждения: подтверждаю "да"

QA-author закодировал рабочую гипотезу `"да"` (регистронезависимо) в позитивном TTY-сценарии
`test_cli_create_meeting_confirm_over_real_tty_creates_exactly_once`. Оставлено как есть —
короткое, однозначное, не пересекается с `"нет"`/пустой строкой/Ctrl+D (EOF даёт `""`, тоже
отклоняется). Альтернативы («yes», «confirm», «create») не рассматривались отдельно — нет
довода предпочесть их русскоязычному CLI без явного требования владельца.

## Открытый вопрос 2 — оценка `ConfirmationStore`

Несёт реальную нагрузку, но только одну: **защиту от истёкшего TTL, пока оператор читает
предпросмотр в терминале и печатает ответ** (`store.match`/`consume` внутри одного вызова
`create-meeting-confirm`, см. §6.3 спеки). Между шагами предпросмотра и подтверждения
межпроцессной связки нет физически (`confirmation_id`, показанный MCP-инструментом, — справочный
для человека, не проверяемый CLI), так что хеш-сверка содержимого в рамках одного вызова CLI
проверяет только «то же ли тело, что secs назад построил тот же `build_meeting_body`» — при
одинаковых аргументах CLI это тавтология (тело детерминировано аргументами, хеш всегда совпадёт,
кроме случая истечения TTL). Единственный сценарий, где `match` реально может вернуть `False`
внутри `create-meeting-confirm`, — TTL истёк, пока оператор печатал ответ на достаточно медленном
терминале (10 минут).

Итог: ~57 строк + ~130 строк тестов ради одной содержательной проверки (TTL) в
единственном практическом месте вызова. Это не церемония в смысле «делает вид, но не работает»
— TTL-логика реальна и покрыта тестами с инжектируемыми часами — но incremental value над
альтернативой «просто держать `expires_at` как локальную переменную функции без выделенного
класса» тонкий. Оправдание существования отдельного класса, а не инлайна, — тестируемость
(issue/match/consume как отдельные предикаты, параметризуемые часы) и симметрия с `PreviewService`
API, которую МCP-инструмент тоже использует (там TTL-проверка не тавтологична: между
`ktalk_preview_meeting` и гипотетической будущей мутацией в MCP реально мог бы пройти час — но
такой мутации нет и не будет). Решение об упрощении — не моё; я оставляю оценку явной, а не
скрытой в коде.

## Ловушка среды: буфер вывода псевдотерминала ограничивает объём предпросмотра

Позитивный TTY-тест (`test_cli_create_meeting_confirm_over_real_tty_creates_exactly_once`) не
дренирует `master_fd` пары `pty.openpty()` ни разу — только пишет входную строку один раз при
настройке. На этой машине (macOS) кернел-буфер slave-стороны псевдотерминала — ровно **1024
байта** (проверено эмпирически: `os.write` в цикле блокируется без ошибки ровно на 1024-м байте).
Любой `print()` в `cmd_create_meeting_confirm`, суммарно превышающий этот порог (предпросмотр +
приглашение + финальное сообщение), **вешает тест навсегда** — не падает, не таймаутит на уровне
pytest, блокируется в системном вызове `write()`.

Первая версия `format_meeting_preview` (полный markdown с двумя абзацами-сносками про
§6.3 ADR-005) давала 1094 байта только на предпросмотр реалистичного тела — этого уже достаточно
для зависания при добавлении строки приглашения. Сокращена до однострочных полей без сносок
(≈564 байта на тот же ввод) — вместе с приглашением и финальным сообщением укладывается в разумный
запас под порогом. Формат используется общим — и `ktalk_preview_meeting` (MCP, порог не
актуален), и `create-meeting-preview`/`create-meeting-confirm` (CLI, порог актуален для второй
подкоманды) — компактность не теряет содержательных полей, только избыточные пояснения из markdown
(текстовое объяснение §6.3 осталось в докстроке MCP-инструмента и в этой заметке, не в каждом
выводе).

## Не расхождение: профиль `create_meeting` (уточнение PM)

DEV-B изначально записал `SESSION`-профиль `create_meeting` себе в расхождения. **Это не так** —
спека предписывает его дословно (`rooms-calendar-spec.md` §2):
`AuthMode.SESSION: EndpointProfile("/calendar", None)`, путь без префикса `/api`, с комментарием,
что «рабочая» запись означает «код готов слать по этому пути», а не «подтверждено живым ответом».
`AuthMode.API_KEY: None` — fail-closed, тоже по спеке.

Содержательная часть наблюдения верна и остаётся в силе: статус «непроверено живым POST»
(RES-003 §3) наличием записи **не снимается** и снимается только боевой приёмкой с санкции
владельца. Реализация спеке соответствует.
