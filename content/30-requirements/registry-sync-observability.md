# Наблюдаемость момента последней синхронизации реестра

Источник: [issue #6, mdemyanov/ktalk-cli](https://github.com/mdemyanov/ktalk-cli/issues/6) —
перенесено из внутреннего трекера плагина-обёртки.

**Capability:** `openspec/specs/registry-sync-window/spec.md`

## JTBD

Когда автоматическая проверка «все ли записи разобраны» строится поверх операционного реестра, а
момент его последней синхронизации нигде не отдаётся машиночитаемо, я (потребитель пакета
`ktalk-cli`, строящий предикат полноты разбора поверх читающих команд реестра) хочу получать
момент последней синхронизации в ответе читающей команды, чтобы отличать «ноль необработанных
записей» от «ноль по данным, которые не обновлялись неделю».

## Контекст

`ktalk sync` пишет момент своего завершения в таблицу `meta` реестра (`reg.set_meta("last_synced",
...)`, `src/ktalk_cli/cli_sync.py:126`), но не возвращает его в собственном `--json`-ответе —
только счётчики (`synced`, `inserted`, `updated`, `expired`, `stats`). Читатель значения уже
существует (`Registry.get_meta`, `src/ktalk_cli/registry.py:378`), но ни одна читающая команда его
не вызывает: `_cmd_dashboard` (`src/ktalk_cli/cli.py`) печатает только `{"new": new, "stats":
stats}`. Значение технически хранится, но снаружи недоступно ни одной командой.

Обойти это вызовом `sync` нельзя: `sync` мутирует бизнес-данные — переводит записи `new` старше
срока экспирации (по умолчанию 7 дней) в `skipped`. Потребителю, которому нужен только момент
последней синхронизации, недопустимо получать его ценой побочной мутации статусов чужих записей.

## Почему это критично именно для предиката полноты

Без момента синхронизации предикат «все записи разобраны» считает по данным, которые могли не
обновляться сколь угодно долго, и молча отдаёт **зелёный ноль на устаревших данных**: записи,
появившиеся в Толке после последней синхронизации, физически отсутствуют в реестре и в проверку не
попадают. Зелёный результат на устаревших данных хуже взведённого — потребитель считает, что
разобрал всё, хотя реестр не видел последних записей вовсе.

## Функциональные требования

### FR-41 — Момент последней синхронизации в ответе читающей команды

Хотя бы одна документированная читающая команда с `--json` отдаёт момент последней завершённой
синхронизации реестра, не требуя вызова мутирующей команды `sync` для его получения. Выбор
конкретной команды, имени и расположения поля в структуре JSON-ответа не фиксируется этим
требованием — это решение SA.

**AC:**
- Given реестр прошёл хотя бы одну синхронизацию, When вызывается документированная читающая
  команда с `--json`, Then в ответе присутствует момент последней синхронизации, совпадающий со
  значением, записанным этой синхронизацией — автоматическая проверка (сравнение значения из
  `--json`-ответа со значением `Registry.get_meta("last_synced")` после `sync`).
- Given реестр ещё ни разу не синхронизировался, When вызывается та же читающая команда с
  `--json`, Then ответ явно сообщает отсутствие синхронизации — не молчаливый пропуск поля и не
  падение с ошибкой — автоматическая проверка (свежий реестр без единого `sync`).
- Given читающая команда с `--json`, отдающая момент синхронизации, вызвана любое число раз
  подряд, When статусы записей реестра сравниваются до и после серии вызовов, Then ни одна запись
  не меняет статус — вызов не является скрытой мутацией — автоматическая проверка (регрессия:
  чтение не должно приобретать побочный эффект `sync`).

## Инварианты и Safeguards

**Содержательные:**
- Получение момента последней синхронизации не переводит ни одной записи реестра в `skipped` и не
  меняет никакое другое поле записи (FR-41) — закрывает риск того, что диагностическое чтение
  приобретёт побочный эффект мутирующей команды.
- Отсутствие когда-либо выполненной синхронизации выражается явным значением, а не пропуском поля
  или падением команды (FR-41) — молчаливое отсутствие поля неотличимо потребителем от дефекта
  сериализации.

**Sensitive content:** N/A — момент синхронизации не несёт персональных данных и содержимого
встреч, это временная метка операции.

## Вне рамок

- Формат самого значения (эпоха, ISO 8601, локальная дата), имя JSON-поля и то, в какой блок
  ответа (`stats` или иначе) оно попадает, — решение SA, не фиксируется этим требованием.
- Изменение поведения `sync` (частоты, порога экспирации, набора возвращаемых счётчиков) — вне
  рамок, `sync` меняется только в части не затрагиваемой этим требованием.
- Реализация самого предиката «все записи разобраны» на стороне потребителя — вне рамок пакета
  `ktalk-cli`, это ответственность вызывающего плагина/агента.
