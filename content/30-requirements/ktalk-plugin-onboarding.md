# Онбординг плагина ktalk — обнаружение зависимости и санкционированная установка

Продолжение волны 3 поверх [«Плагин ktalk в произвольном проекте»](ktalk-plugin.md) (FR-20…FR-25,
NFR-11…NFR-16) и [ADR-012](../00-project/adr/ADR-012-plugin-boundary.md). Источник — запрос
владельца от 2026-08-18: плагин обязан обнаруживать отсутствие установленного пакета, помогать
пользователю его установить и получить токен авторизации, а при явной санкции — устанавливать
пакет самостоятельно.

## JTBD

Когда я (владелец) устанавливаю плагин `ktalk` в проект, где пакет `ktalk-mcp` ещё не установлен,
я хочу узнать об этом сразу и получить готовую к выполнению команду установки и инструкцию по
токену авторизации, чтобы не выяснять причину неработающих навыков методом проб.

Когда я готов доверить плагину установку пакета без своего участия, я хочу явно это разрешить и
быть уверен, что без такого разрешения плагин ничего не устанавливает сам, чтобы граница между
«плагин подсказывает» и «плагин действует» не размывалась молчаливым поведением.

## Контекст

ADR-012 §2 фиксирует сегодняшнее решение: плагин — тонкая обёртка, пакет `ktalk-mcp` в дерево
плагина не вендорится, зависимость документируется в README текстом плюс командой проверки
(`which ktalk-mcp`, `uv tool list | grep ktalk-mcp`, `ktalk --help`), а не устанавливается плагином.
ADR-012 (Контекст, RES-002) прямо называет это ограничением платформы: «Плагины не устанавливают
зависимости автоматически; `uv` в PATH — требование к пользователю». Опубликованный состав плагина
(`dev-004-plugin-assembly.md`) подтверждает: хука «после установки» в дереве нет, установка
пакета — операция пользователя.

Запрос владельца расширяет это поведение: обнаружение отсутствия CLI остаётся обязательным
(совместимо с ADR-012), но реакция на него — не только текст README, прочитанный заранее, а
активная помощь в момент обнаружения, и при явной санкции — самостоятельное выполнение установки.
Второе прямо расходится с формулировкой ADR-012 «плагин не проверяет и не чинит это автоматически»
— расхождение зафиксировано отдельным разделом ниже, не растворяется в тексте требований.

Приоритетный интерфейс контура — CLI, не MCP (ADR-012 §2а): наблюдаемая точка обнаружения
отсутствия зависимости — попытка выполнить команду `ktalk …` из навыка или агента плагина, не
запуск stdio MCP-сервера. Механика обнаружения (где именно в коде навыка/агента размещена
проверка, как санкция передаётся и хранится) — решение SA, здесь фиксируется наблюдаемое
поведение на границах, тем же приёмом, что FR-20/FR-24 в `ktalk-plugin.md`.

## Функциональные требования

### FR-26 — Обнаружение отсутствия установленного пакета

Плагин не полагается на хук «после установки» — состав плагина (dev-004) его не имеет.
Обнаружение происходит на первой попытке выполнить операцию контура в текущей сессии.

**AC:**
- Given плагин установлен и включён, но команда `ktalk` не резолвится через PATH, When навык или
  агент плагина впервые в сессии пытается выполнить операцию контура, Then пользователь получает
  явное сообщение об отсутствии зависимости, не молчаливый пропуск шага и не выдуманный
  результат — ручная проверка (первый вызов в чистом окружении без пакета).
- Given хука «после установки» в составе плагина нет, When оценивается момент обнаружения, Then
  он наступает не позже первой попытки выполнить операцию контура в сессии, не откладывается на
  непредсказуемый момент — ручная проверка.
- Given пакет установлен, но версия ниже минимально совместимой, объявленной машинночитаемым
  файлом `compat.json` в дереве плагина (README цитирует этот файл, не наоборот), When выполняется
  первая операция контура, Then несовместимость версии также распознаётся и сообщается, не только
  полное отсутствие бинаря — точный механизм проверки версии — решение SA/Dev.

### FR-27 — Совместный режим: помощь в установке пакета

**AC:**
- Given пакет `ktalk-mcp` не установлен и автоматическая установка не санкционирована (FR-29),
  When обнаружено отсутствие CLI (FR-26), Then плагин показывает пользователю команду установки
  дословно (текст README ADR-012 §2, `uv tool install ktalk-mcp`), готовую к копированию, и не
  выполняет её сам.
- Given пользователь выполнил показанную команду самостоятельно, When он хочет подтвердить успех,
  Then плагин предлагает команду проверки (`which ktalk-mcp` / `ktalk --help`) и по её результату
  сообщает, устранена зависимость или нет — ручная проверка.
- Given инструмент `uv` тоже отсутствует в PATH (предусловие самого предусловия), When обнаружено
  отсутствие CLI, Then сообщение называет отсутствующим именно `uv`, не `ktalk-mcp`, чтобы
  пользователь не пытался установить несуществующий шаг вместо инструмента.

### FR-28 — Инструкция по получению и размещению токена авторизации

Два поддерживаемых режима авторизации (CLAUDE.md, «API Reference»): `KTALK_PERSONAL_API_KEY` →
заголовок `X-Auth-Token`; `KTALK_SESSION_TOKEN` → query `sessionToken`; ключ побеждает при обоих
заданных.

**AC:**
- Given CLI пакета установлена (или устанавливается в рамках FR-27/FR-29), When плагин выдаёт
  инструкцию по авторизации, Then текст называет оба способа и правило приоритета при обоих
  заданных — ручная проверка текста инструкции.
- Given пользователь читает инструкцию, When он ищет, откуда взять значение, Then инструкция
  указывает источник в интерфейсе Толка (личный API-ключ или сессионный токен), не подставляет и
  не выдаёт реальное значение секрета ни в каком виде.
- Given пользователь читает инструкцию, When он ищет, куда положить значение, Then инструкция
  называет два допустимых места — переменную окружения процесса либо `.mcp.json`/`settings.json`
  проекта-хозяина, — не файл внутри дерева плагина.
- Given плагин выдал инструкцию, When проверяется его собственное поведение, Then он не
  записывает значение токена ни в один файл сам и не печатает значение токена в вывод или лог ни
  при каких условиях (совместимо с FR-25) — автоматическая проверка (grep вывода команд онбординга
  на паттерн значения тестового токена в фикстуре).

### FR-29 — Автоматическая установка по явной санкции

Санкция — предварительное явное разрешение пользователя, не выводится из молчания или
неоднозначного ответа. Форма хранения санкции (разовая в диалоге, сохранённая конфигурация) —
решение SA.

**AC:**
- Given пользователь явно и предварительно разрешил автоматическую установку, When плагин
  обнаруживает отсутствие CLI (FR-26), Then он вправе выполнить команду установки пакета
  самостоятельно, не запрашивая разрешение заново в рамках той же сессии.
- Given явной санкции не было, When плагин обнаруживает отсутствие CLI, Then он не выполняет
  установку сам ни при каких условиях — переходит в совместный режим (FR-27); молчание
  пользователя санкцией не считается.
- Given санкция получена, When плагин выполняет установку, Then используется та же команда, что
  была бы показана в совместном режиме (FR-27), не альтернативный путь, неизвестный пользователю.
- Given установка выполняется автоматически, When она завершается (успешно или с ошибкой), Then
  результат сообщается пользователю явно — код возврата команды и её вывод, не тихий переход к
  следующему шагу.

### FR-30 — Идемпотентность и границы автоматической установки

**AC:**
- Given пакет уже установлен и соответствует минимально совместимой версии, When плагин
  обнаруживает CLI перед выполнением операции, Then он не запускает установку повторно ни в
  совместном, ни в автоматическом режиме — повторный запуск на настроенной машине эффекта не
  имеет.
- Given пакет установлен, но версия ниже минимально совместимой, и санкция на автоматическую
  установку отсутствующего пакета получена, When требуется обновить установленный пакет, Then
  обновление существующей версии требует отдельной санкции — санкция «установить при отсутствии»
  молча не расширяется на «обновить при устаревании».
- Given автоматическая установка завершилась ошибкой (сеть, права, конфликт версий), When плагин
  сообщает результат, Then система остаётся в состоянии, предшествовавшем попытке — не частично
  установленным, необнаружимым состоянием пакета — ручная проверка по факту.
- Given автоматическая установка провалилась с ошибкой сетевого класса (недоступность индекса,
  таймаут, отказ DNS), When плагин обрабатывает ошибку, Then он делает ровно одну повторную
  попытку той же командой; ошибки прав, конфликта версий и отсутствия пакета в индексе не
  повторяются никогда — автоматическая проверка (стаб `uv`, возвращающий сетевой и несетевой
  текст ошибки).

### FR-31 — Установка приводит к работоспособному контуру

Команда установки, которую плагин показывает (FR-27) и выполняет (FR-29), обязана давать версию
пакета не ниже минимально совместимой. На 2026-08-18 в индексе опубликована 0.4.0, в репозитории
пакета — 0.6.0; ни одна из них не несёт конфиг-слоя волны 3 в объявленном виде.

**AC:**
- Given пакет установлен показанной командой из публичного индекса, When выполняется `check`
  (FR-26), Then результат — «версия соответствует минимальной», не «ниже минимальной»; расхождение
  означает, что релиз не выпущен, и фиксируется как открытый пункт, а не как успех онбординга —
  ручная проверка владельцем после публикации.

## Нефункциональные требования

### NFR-17 — Граница доверия: без санкции плагин не изменяет систему

**AC:** Given явной санкции на автоматическую установку нет, When плагин действует в совместном
режиме, Then единственные операции, которые он выполняет сам, — чтение PATH/версии для
диагностики (FR-26) и вывод текста инструкций (FR-27, FR-28); ни одна команда, устанавливающая
или изменяющая пакеты в системе, не выполняется без санкции — инвариант, проверяется на каждом
AC режима FR-27, не разово.

### NFR-18 — Поведение в неинтерактивной сессии

Прецедент — TTY-барьер ADR-005 для боевой пишущей операции (`create-meeting-confirm`): отсутствие
TTY не заменяется допущением о согласии.

**AC:** Given сессия не имеет TTY, When требуется получить санкцию на автоматическую установку,
Then плагин не запрашивает её интерактивно и не трактует невозможность спросить как санкцию —
он переходит в совместный режим (FR-27), тем же путём, что при отсутствии санкции (FR-29) —
ручная проверка (прогон онбординга в неинтерактивном окружении).

### NFR-19 — Секреты токена не появляются в диалоге онбординга (уточнение FR-25)

**AC:** Given плагин ведёт диалог онбординга (обнаружение CLI, инструкция по установке,
инструкция по токену), When любой шаг протоколируется (лог сессии, история команд), Then значение
токена ни разу не появляется в этих артефактах — плагин запрашивает и проверяет только факт
настройки («переменная задана?»), не её значение — автоматическая проверка (grep протокола
диалога на значение тестового токена в фикстуре).

## Конфликт с ADR-012

ADR-012 §2 и его раздел «Контекст» (со ссылкой на RES-002) фиксируют текущее решение: **плагин не
устанавливает и не обновляет пакет сам**, предусловие — текст README плюс команда проверки;
раздел «Негативные» последствия называет это прямо — «пользователь обязан вручную поддерживать
`uv` в PATH и актуальную версию пакета — плагин не проверяет и не чинит это автоматически».
Раздел «Альтернативы» отклоняет автоматизацию соседнего рода (cutover агентов при установке) тем
же аргументом: «install-хук плагина не имеет санкции на запись вне своего дерева».

FR-29 и FR-30 этого требования **прямо отменяют** формулировку «плагин не проверяет и не чинит
это автоматически» в части «не чинит»: при явной санкции пользователя плагин обязан уметь
выполнить установку пакета самостоятельно. FR-26 расширяет ту же формулировку в части «не
проверяет»: обнаружение отсутствия/устаревания CLI становится обязанностью плагина, а не
допущением, разрешённым, но не предписанным.

Это решение принадлежит SA, не этому документу. ADR-012 требует ревизии (новый раздел §2б или
явная правка §2/«Негативные последствия») либо отдельного нового ADR, разбирающего: чем
санкционированная установка отличается от отклонённого варианта «автоматический cutover при
установке плагина» с точки зрения «install-хук не имеет санкции на запись вне своего дерева»
(различие в том, что здесь санкция — явное действие пользователя в моменте, а не встроенная в
install-хук автоматика без спроса); какой командой/API выполняется установка, если в составе
плагина нет install-хука (dev-004) — то есть где физически исполняется команда установки;
как санкция передаётся между сессиями и куда записывается её факт, если не в централизованное
хранилище (FR-25 это запрещает для секретов, но не описывает хранение самой санкции).

**FR-25 (секреты авторизации не централизуются) этим требованием не отменяется.** FR-28/NFR-19
формулируют инструкцию по получению и размещению токена как текст, который плагин показывает
пользователю, — не как запись секрета плагином. Ни один AC этого документа не предполагает, что
плагин сохраняет, передаёт между проектами или логирует значение токена; там, где текст касается
токена, он явно требует обратного (FR-28 AC4, NFR-19).

## Риски

**Требуют решения SA/владельца, не этого документа:**
- Механика обнаружения отсутствия CLI без install-хука (dev-004 подтверждает его отсутствие в
  составе) — где именно в навыке/агенте размещается проверка.
- Форма и хранение санкции на автоматическую установку — разовая в диалоге сессии или
  сохраняемая конфигурация, и если сохраняемая, то где (не в централизованном хранилище — оно для
  данных пакета, ADR-013, не для конфигурации плагина).
- Ревизия ADR-012 или новый ADR, разбирающий отмену формулировки «плагин не чинит зависимость
  автоматически» — раздел «Конфликт с ADR-012» выше.

**Не проверено эмпирически на момент написания:**
- Поведение обнаружения в реальной установленной копии плагина (текущий состав, dev-004, не
  содержит кода онбординга) — все AC этого документа сформулированы как контракт для будущей
  реализации, не регрессия существующего поведения.

## Вне рамок

- Механика обнаружения (код навыка/агента, момент проверки внутри цепочки вызовов) — решение SA.
- Формат хранения санкции — решение SA.
- Ревизия или замена ADR-012 — решение SA/владельца, не этого документа.
- Пользовательский интерфейс диалога санкции (текст промпта, язык подтверждения) — решение SA/Dev
  в пределах инвариантов NFR-17/NFR-18.

## Инварианты и Safeguards

**Содержательные:**
- Без явной предварительной санкции плагин не выполняет ни одной команды, устанавливающей или
  изменяющей пакеты в системе (NFR-17).
- Отсутствие TTY никогда не трактуется как санкция (NFR-18).
- Санкция «установить отсутствующий пакет» никогда не расширяется молча на «обновить
  установленный» (FR-30).
- Значение токена авторизации никогда не появляется в выводе, логе или файле, которые пишет сам
  плагин (FR-28 AC4, NFR-19) — наследует FR-25 `ktalk-plugin.md`.
- Неудачная автоматическая установка не оставляет систему в состоянии частично установленного,
  необнаружимого пакета (FR-30).

**Sensitive content:**
- Тестовые фикстуры проверки логов/вывода на утечку токена (FR-28, NFR-19) используют
  синтетическое значение, не реальный `KTALK_SESSION_TOKEN`/`KTALK_PERSONAL_API_KEY`.
- Команда установки, показываемая пользователю (FR-27, FR-29), не содержит значений секретов —
  только имя пакета и флаги `uv tool install`.
