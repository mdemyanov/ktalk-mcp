# ADR-011: Контракт отмены встречи и отложенное решение по правке

**Дата:** 2026-08-18

## Context

Пятая боевая попытка (2026-08-18, `ktalk-calendar-api.md` §6, Ф-55/Ф-56) создала встречу в боевом
контуре владельца, участник приглашён; снятие сегодня — вручную в UI (`roadmap.md`). Операции
отмены в коде нет. Браузерный HAR (§5 того же документа) даёт два факта: **Ф-50** —
`POST /api/calendar/{id}/cancel`, тело `{"reason": ""}` → 200; **Ф-51** — `PUT /api/calendar/{id}`
→ 200, форма тела не разобрана. **Ф-56** — `{id}` несёт `+`, `/`, `=` (base64 Exchange-идентификатор),
требует `quote_path_param` при подстановке в путь — без него путь отмены собьётся молча.

Отмена — вторая мутирующая операция проекта после `create_meeting` (ADR-005/007/008/009) и не
менее опасна: письма об отмене уходят реальным людям, эффект необратим (создание события отзывом
не компенсируется, ADR-005 «Context»). Барьер обязан быть не слабее барьера создания. У операции
всего два параметра (`id`, `reason`) — привязка подтверждения к «содержимому» ADR-005 нуждается в
уточнении: голого `reason` недостаточно, чтобы удержать подтверждение от переиспользования на
другой `id`.

Правка (Ф-51) заявлена задачей отдельно, но тело не разобрано ни живым трафиком, ни документацией
(`ktalk-calendar-api.md` §2 не содержит аналога для `PUT`) — решать её форму сейчас значило бы
проектировать по домыслу, что запрещено правилом anti-fabrication.

## Decision

**1. `cancel_meeting` — профиль `OPERATION_PROFILES`, симметричный `create_meeting`.**
`AuthMode.SESSION: EndpointProfile("/api/calendar/{id}/cancel", None, mutating=True)`,
`AuthMode.API_KEY: None` (fail-closed — как и `create_meeting`, api-key-режим для мутаций
календаря не проверен ни разу). `mutating=True` даёт тот же транспорт, что ADR-009 подтвердил
живым POST: заголовки `Authorization: Session <token>` + `X-Platform: web`, без query
`sessionToken`. `{id}` — обязательный `quote_path_param` перед подстановкой в путь (Ф-56); без
квотирования `+`/`/`/`=` меняют фактический путь запроса тем же классом риска, что SEC-001 уже
закрыл для `recording_key`/`conference_key`.

**2. Подтверждение привязано к тройке (операция, `id`, `reason`), не к голому телу запроса.**
Тело на проводе — `{"reason": reason}`, но `id` — часть пути, не тела; хешировать только тело
означало бы, что подтверждение, выданное для одной встречи, матчится для любой другой с тем же
`reason` (в предельном случае — `reason=""`, единственный наблюдённый образец, для которого
совпадение произошло бы всегда). Хеш строится над отдельным словарём
`{"operation": "cancel_meeting", "id": id, "reason": reason}` тем же `canonical_body_hash`
(sha256 канонического JSON), что и создание — функция уже общая, не специфична для тела встречи.
`operation` — дискриминатор против путаницы с будущим подтверждением правки на том же `id`.
Инфраструктура ADR-005 (`ConfirmationStore`, TTL 10 мин, single-use, `isatty()`-барьер CLI,
отсутствие мутирующего MCP-инструмента) переиспользуется без изменений — расширяется предметом
хеширования, не протоколом.

**3. `{id}` — явный ввод оператора, без нового хранилища.** У проекта нет реестра встреч
(`registry.py` — про записи, не про календарь; расширение его схемы упёрлось бы в заморозку 562
строк грандфазером). Источник — уже существующие каналы чтения: поле `id` в ответе `create_meeting`
или в элементах `ktalk_list_calendar`/`get_calendar_window` (оба несут `id`, `calendar_reader.py`,
Ф-28). Оператор копирует значение вручную в `--id`; ktalk-mcp его нигде не сохраняет и не
резолвит по имени/дате — то же решение, каким ADR-009 п.3 оставил резолюцию логина участника
оператору, не эвристике.

**4. `reason` — опциональная строка, дефолт `""`.** Единственный наблюдённый образец (Ф-50) —
пустая строка, 200. **N/A — обязательность непустого `reason` не проверялась** ни на одном живом
запросе; сервер мог бы как принимать пустую строку всегда, так и требовать содержательный текст
для части сценариев (например, отмены с уведомлением участников) — недостаточно данных, чтобы
решить. Безопасный контракт: `reason` не входит в обязательные поля NFR-9 (в отличие от полей
создания), дефолт `""` воспроизводит единственную подтверждённую рабочую конфигурацию; оператор
может передать непустой текст явно.

**5. Правка (`PUT /api/calendar/{id}`) — не проектируется, не реализуется этой волной.**
Известно: путь, метод, код ответа 200 (Ф-51). Неизвестно: форма тела целиком — ни документарного
аналога (в отличие от создания, `ktalk-calendar-api.md` §2 констатирует отсутствие Calendar/Meeting
схемы для `/calendar` вообще), ни живого образца тела запроса (только факт успешного ответа без
разбора трафика). Экстраполяция с тела создания недопустима: `PUT` может быть частичным
(patch-семантикой) или полным (replace), различить без образца нельзя. Закрывается тем же
методом, каким ADR-009 закрыл форму создания — снимком DevTools живого редактирования встречи в
UI Толка, обезличенным владельцем тем же способом, что и предыдущий снимок (`docs/`, не в git).
До этого измерения `update_meeting` не входит в `OPERATION_PROFILES`, не имеет компоновщика тела и
не входит в объём DEV-010.

## Consequences

**Positive:** отмена доступна той же по строгости конструкцией, что создание — оператор не
получает более слабый барьер для операции, которая тоже рассылает письма; привязка хеша к `id`
закрывает конкретный сценарий переиспользования подтверждения между встречами, который голый хеш
тела не закрыл бы; правка не проектируется по догадке — pending-статус зафиксирован явно, а не
подразумевается отсутствием упоминания.

**Negative:** оператору по-прежнему нужен `id` из внешнего наблюдения (ответ создания или чтение
календаря) — без реестра это ручной шаг, тот же класс трения, что уже принят для числового `key`
участника (ADR-009 п.3); отмена не проверена ни одним боевым POST — статус `ГИПОТЕЗА` до
санкционированной попытки, тем же приёмом, что ADR-007/008/009; отсутствие `update_meeting` оставляет
владельца без программной правки встречи до отдельного измерения — до тех пор правка остаётся
ручной операцией в UI, как и отмена сегодня.

**Mitigations:** транспорт (`mutating=True`, заголовки, отсутствие query) уже подтверждён живым
POST создания (Ф-55) — на отмену переносится тот же подтверждённый механизм, не новая гипотеза;
`ГИПОТЕЗА`-статус снимается тем же протоколом маркировки, что и предыдущие три ADR; PUT — открытая
задача с явным способом закрытия (снимок DevTools), не забытый пробел.

## Alternatives Considered

- **Хешировать только тело `{"reason": reason}`, без `id`.** Отклонено: `id` — единственный
  параметр, идентифицирующий цель разрушительного действия, и он не входит в тело запроса
  (часть пути) — хеш без него не привязывает подтверждение к конкретной встрече.
- **Отмена — облегчённая операция без барьера ADR-005 (один шаг, без TTY).** Отклонено:
  последствие то же по типу, что создание (письма реальным людям), необратимо — упрощать барьер
  для операции с сопоставимым ущербом непоследовательно.
- **Хранить `id` во внутреннем реестре (SQLite) для последующей отмены по номеру записи.**
  Отклонено: `registry.py` — про записи разговоров, не про календарные события; смешение доменов
  не обосновано этой задачей, класс `Registry` к тому же заморожен грандфазером на 562 строках.
- **Спроектировать тело `PUT` по аналогии с телом создания (замена набора полей).** Отклонено
  напрямую anti-fabrication правилом ADR-шаблона: ни одного живого образца тела `PUT` нет,
  аналогия — правдоподобное предположение, не факт.
