# ADR-006: `get_room` — эмпирически мутирующий read, контракт предупреждения

**Дата:** 2026-08-17

## Контекст

Живая разведка боевой приёмки (RES-001, `ktalk-calendar-api.md` §4, Ф-44/45/49) и независимая
сверка QA-001 (`qa-report-rooms-calendar.md`, п.2) установили: `GET /api/rooms/{roomName}` под
session-режимом отдаёт **200 на любое имя, включая гарантированно свежее случайное — 404 не
отдаёт никогда** (4 независимых зонда, два свежих случайных имени). Форма ответа на несуществующее
имя неотличима от существующей комнаты (18/18 полей). Первый GET на не встречавшееся имя **создаёт
или персистентно кеширует объект комнаты**: `anonymousAccessModifiedDate`/
`anonymousAccessExpirationDate` фиксируются в момент первого запроса и не пересчитываются при
повторном GET спустя ≥65 с (Ф-49, три независимые проверки, три объекта оставлены в контуре).
Коллекционного пути листинга комнат нет — все 8 путей `*room*` в спеке параметризованы
`{roomName}` (Ф-49 п.4) — подтвердить существование комнаты чтением, не создав её, нечем.

ADR-004 этот класс не покрывает. Его механизмы (`diagnose_undocumented_failure`,
`require_contract_field`) реагируют на не-2xx или на пропажу якорного поля при 200 — здесь код 200,
`roomName` присутствует, форма полная и валидная. Наблюдаемое — не деградация контракта и не отказ,
а **успешный read-ответ с побочным эффектом записи**, категория, для которой ADR-004 не
проектировался (документ целиком про пути, переставшие отвечать ожидаемо, не про read-эндпоинты,
тихо мутирующие состояние при штатном ответе).

`rooms-calendar-spec.md` §4.2 и FR-17 AC2 держали этот исход как непроверенную гипотезу («поведение
для несуществующей комнаты не проверено», консервативная стратегия — любой отказ уходит в
корреляционную диагностику). Формально гипотеза не была неверной декларацией — она честно
признавала пробел. По существу она не адресует найденный случай: отказа нет вовсе, диагностика по
коду ответа структурно не может сработать.

Тест `test_get_room_any_non_2xx_with_working_control_raises_contour_drift_not_not_found` мокирует
404, которого сервер не отдаёт ни разу на четырёх зондах. Тест зелёный на код, который живьём не
воспроизводим, — не опровержение корректности кода, но повод для QA-author пересмотреть, что этот
тест доказывает.

Это третье подряд расхождение спеки с боевым контуром в проекте: ADR-003 (набор путей по режиму),
ADR-004 (форма/текст ошибок, омоглиф в спеке), теперь — контракт операции целиком (read → read+write).
Устойчивая тенденция: гипотезы о недокументированном контуре, отмеченные как «непроверено» в спеке,
регулярно расходятся с реальностью сильнее, чем закладывалось на этапе проектирования — повод для
привычки закрывать такие гипотезы живым зондом раньше, а не откладывать до боевой приёмки.

## Решение

**1. `get_room` переклассифицируется как read-с-побочным-эффектом-записи, а не pure read.** Это
архитектурный факт контракта операции, фиксируемый в спеке и в докстринге/описании MCP-инструмента,
а не деталь реализации.

**2. Условного предупреждения (только когда объект реально создан) не будет — оно физически
невозможно.** Форма ответа не содержит ни одного поля, различающего «существовало» и «создано этим
вызовом» (Ф-45) — детектор такого поля не существует, писать его на основе несуществующего сигнала
означало бы делать вид, что различение есть. Вместо условного — **безусловное статическое
предупреждение**: в описании инструмента (`ktalk_get_room`) и в докстринге `rooms.py::get_room`
явно зафиксировано, что вызов с именем, ранее не читанным в этом контуре, создаёт объект комнаты
как побочный эффект, необратимый средствами проекта (инструмента удаления нет), и что операцию
нельзя использовать для проверки занятости/свободности имени.

**3. Гейта подтверждения (по образцу ADR-005) для `get_room` не вводится.** Различить «новое имя»
от «уже читанного» нечем (п.2) — гейт срабатывал бы на каждый вызов без разбора, включая штатное
чтение уже существующих комнат, что превращает read-инструмент в пишущий по процедуре без пользы:
ADR-005 требует подтверждения там, где создание — цель вызова и опознаваемо заранее; здесь создание
— непреднамеренный, неопознаваемый побочный эффект. Правильный барьер — не рантайм-гейт, а осознание
вызывающим до вызова (докстрайн/описание инструмента), т.е. п.2.

**4. Предпосылка DEV-002 «новая комната — только после `GET`, подтвердившего отсутствие имени»
невыполнима буквально и снимается.** Подтверждающий `GET` — то самое действие, которое делает имя
существующим (Ф-49). Замена для боевой приёмки: имя тестовой комнаты выбирается заведомо уникальным
(например, с меткой теста и меткой времени) без предварительного проверочного `GET`; единственный
вызов чтения в этой цепочке — тот, что уже неявно происходит при создании (если создание вообще
требует чтения) либо не выполняется вовсе, если `POST /calendar` создаёт комнату по имени без
отдельного `GET`. Это не новая санкция и не расширение границ владельца (число разрешённых `POST`
не меняется) — это снятие невыполнимого технического условия внутри уже данной санкции; итоговая
формулировка шага для рантайма — решение PM-001/DEV-002.

**5. FR-17 AC2 не может быть закрыт положительно** — сервер не имеет сигнала «комната не найдена»,
сообщать вызывающему нечего. Разметка этого AC («заблокирована» → «опровергнута») — решение BA-001,
не переписывается здесь.

## Последствия

**Позитивные:** контракт `get_room` описан честно — агенты и разработчики знают о побочном эффекте до
вызова, а не узнают из инцидента; снят несуществующий барьер DEV-002; тенденция расхождений спеки с
контуром зафиксирована явно, а не растворена в третьем отдельном инциденте.

**Негативные:** предупреждение показывается на каждый вызов, включая безвредное чтение давно
существующих комнат — шум для частого пользователя инструмента; в контуре уже остались минимум три
созданных зондом объекта (`vkuznetsov-nonexistent-probe-0001`,
`probe-fresh-7d2a4860aac4a5b7`, `probe-fresh2-cf44d841c9aa6fb7`), удалить которые проектными
средствами нельзя.

**Смягчения:** предупреждение — одна статичная строка, не блокирует и не замедляет вызов;
оставленные зондом объекты имеют `anonymousAccessExpirationDate` в пределах суток от создания —
естественное истечение доступа не проверено, но не требует действия сейчас; решение ревизуемо —
если в контуре появится путь листинга/подтверждения существования, п.2–3 пересматриваются.

## Альтернативы

- **Условное предупреждение «этот вызов создал новую комнату».** Отклонено: нет сигнала в ответе
  для такого различения (Ф-45) — потребовало бы либо ложного вывода, либо отдельного состояния вне
  контура (например, локального реестра всех когда-либо читанных имён), что выходит за рамки задачи
  и не решает случай первого запуска инструмента на чистом окружении.
- **Гейт подтверждения по образцу ADR-005 (предпросмотр + токен перед вызовом `get_room`).**
  Отклонено: сработал бы на каждый вызов без разбора (п.3), превращая read-операцию в
  пишущую-по-процедуре без реальной пользы — не решает то, что должен решать: неведение вызывающего
  о конкретном побочном эффекте конкретного имени.
- **Расширить ADR-004 (`diagnose_undocumented_failure`) для покрытия этого случая.** Отклонено:
  механизм строится на сравнении с контрольным вызовом при подозрительном ответе — здесь ответ не
  подозрителен ни по коду, ни по форме (200, полный набор полей), классифицировать нечего.
- **Молчание — оставить как есть, полагаясь на общую честность документации проекта.** Отклонено:
  прямо нарушает Р-2 боевой приёмки («ценность имеет журнал расхождений, а не зелёный вид») и
  оставляет агентов создающими боевые артефакты без предупреждения.
