# ADR-012: Границы плагина ktalk

**Дата:** 2026-08-18

## Контекст

Контур ktalk сегодня живёт в двух несвязанных местах: пакет `ktalk-mcp` (этот репозиторий,
установлен на машине владельца через `uv tool` в `~/.local/share/uv/tools/ktalk-mcp/`) и 11
файлов `.claude/` в vault'е `naumen-cto` (агенты, навыки, команда) с 27 вхождениями
`95_TRANSCRIPTS`, 2 абсолютными путями, зависимостью от чужого MCP `qmd` и захардкоженными
адресатами дайджеста (RES-001). Требование [FR-20…FR-25, NFR-11…NFR-16](../../30-requirements/ktalk-plugin.md)
фиксирует наблюдаемое поведение — discovery, машинный дефолт хранилища, явную деградацию,
несовместимость с миграцией секретов — но прямо оставляет SA решение о границах: что уезжает в
плагин, что остаётся у хозяина, как плагин соотносится с пакетом Python.

RES-002 установил два факта, сужающих пространство решений. Конфигурация хозяина не приезжает
подстановкой манифеста плагина — discovery принадлежит коду пакета, читающему cwd (FR-20).
Проектный `.claude/agents/` перекрывает одноимённого агента плагина без предупреждения —
переключение обязано быть явным удалением файла-копии, не установкой поверх (RES-001 риск 5).
Плагины не устанавливают зависимости автоматически; `uv` в PATH — требование к пользователю.

## Решение

### 1. Три дома артефактов

| Дом | Что туда попадает | Критерий |
|-----|--------------------|----------|
| **Плагин** `ktalk` | `skills/ktalk-registry/**`, `skills/ktalk-eval/**`, `agents/ktalk-processor.md`, `agents/ktalk-evaluator.md`, `commands/ktalk-registry.md`, `.mcp.json` (объявление сервера, без секретов), `.claude-plugin/plugin.json` — код/промты контура, без встроенных путей хозяина (депараметризация — DEV-002) | Артефакт переносим между проектами без правки после подстановки конфигурации хозяина |
| **Проект-хозяин** | файл конфигурации раскладки (формат — SA-003), протоколы встреч, `registry.md`-зеркало, профили участников (`10_PEOPLE`-подобное), `.mcp.json`/env хозяина с секретами (`KTALK_SESSION_TOKEN`/`KTALK_PERSONAL_API_KEY`) | Данные и конфигурация специфичны для одного проекта, не годятся другому без переосмысления |
| **Пакет Python** `ktalk-mcp` | `config.py`/discovery-слой (FR-20), резолюция пути реестра (FR-22/23, ADR-013), CLI/MCP tools как сегодня | Логика, а не декларация — устанавливается и версионируется отдельно от плагина |

Скилл `news-digest` и захардкоженные адресаты (`amuratov`/`drubin`) **не входят** ни в один из
трёх домов контура ktalk — постановка прямо выносит их за границу волны (RES-001 находка,
«Граница волны»); остаются артефактом vault'а как есть — решение владельца зафиксировано в §6.

Централизованное хранилище (реестр, сырые транскрипты, отчёты качества — ADR-013) — данные
пакета, не плагина: плагин не хранит пользовательских данных, только код/промты и объявление
MCP-сервера.

### 2. Плагин — тонкая обёртка, не вендоринг

Плагин **не вендорит** код пакета. `.mcp.json` плагина объявляет stdio-сервер командой `ktalk-mcp`
(bare, разрешается через PATH пользователя), не путём внутри `${CLAUDE_PLUGIN_ROOT}` — потому что
исполняемого кода в дереве плагина нет. Зависимость документируется в `README` плагина как
предусловие: пакет установлен (`uv tool install ktalk-mcp`), `uv`/шимы `uv tool` в PATH. Секреты
(`KTALK_SESSION_TOKEN`/`KTALK_PERSONAL_API_KEY`/`KTALK_BASE_URL`) в `.mcp.json` плагина не
объявляются — по FR-25 они остаются конфигурацией окружения хозяина (env или `.mcp.json`/`.env`
хозяина, если хозяин переопределяет объявление сервера).

Отклонено: вендоринг пакета внутрь плагина (дублирует source of truth, ломает независимый релиз
пакета через PyPI/`uv tool`) и объявление сервера через `${CLAUDE_PLUGIN_ROOT}/bin/...`
(осмысленно только при вендоринге).

### 2а. Приоритетный интерфейс контура — CLI, не MCP

Решение владельца (2026-08-18, после первой редакции этого ADR): **в плагине приоритетна работа
через CLI `ktalk`, а не через MCP-сервер.** Навыки и агенты плагина обращаются к контуру
командами `ktalk <подкоманда> --json` через Bash; `--json` уже сегодня контракт машинного чтения
для всех команд (CLAUDE.md, «CLI / реестр»), ошибки — в stderr с ненулевым кодом возврата.

Следствия, обязательные для DEV-002 и SA-003:

- депараметризация навыков ориентируется на CLI-вызовы, не на имена MCP-инструментов;
- discovery конфигурации хозяина попадает на тот же путь исполнения, что и всё остальное
  (код пакета от cwd, FR-20) — MCP-транспорт из этой цепочки исключён, а не продублирован;
- предусловие «пакет установлен и `ktalk` в PATH» становится жёстким: без него не работает
  ничего, а не только часть инструментов;
- MCP-сервер остаётся объявленным в `.mcp.json` плагина как **вторичный** путь для чтения
  контента (транскрипты, саммари) и не является обязательным для работы навыков; отказ MCP не
  обязан ломать реестровые сценарии.

Обоснование владельца в ADR не реконструируется. Наблюдаемые факты, которые решение снимает:
таймаут первого запуска stdio-сервера (RES-002), необходимость передавать секреты в объявление
MCP-сервера плагина, и разнесение одной операции по двум транспортам с разной диагностикой.

Не проверено: полнота покрытия CLI-командами всех сценариев навыков — сегодня 13 MCP-инструментов
против набора подкоманд `ktalk`, и соответствие не сверялось. Сверка — задача DEV-002; пробел,
если он есть, закрывается новыми подкомандами, а не возвратом к MCP.

### 3. Агенты: миграция + явный cutover

`ktalk-processor.md` (436 строк) и `ktalk-evaluator.md` (180 строк) переносятся в
`agents/` плагина депараметризованными (DEV-002: абсолютный путь vault'а, `95_TRANSCRIPTS`,
`20_MEETINGS/*` — из промта в конфигурацию, читаемую кодом или передаваемую через reference-файл).
Промт `ktalk-processor` режется на ядро + reference-файлы под тем же плагинным неймспейсом —
объём 436 строк не переносится в плагин одним файлом без ревизии.

Поскольку проектный `.claude/agents/` перекрывает плагинного агента (RES-002), сосуществование
копии в vault'е и плагина даёт вводящий в заблуждение результат: копия в vault'е молча выигрывает,
правка плагина не действует, пока копия не удалена. Решение: переключение — двухшаговая
процедура, обе части обязательны и выполняются владельцем (не автоматизируются установкой
плагина — тот же принцип, что миграция реестра, NFR-12):
1. Установить и включить плагин `ktalk` в проекте-хозяине.
2. Явно удалить `.claude/agents/ktalk-processor.md` и `.claude/agents/ktalk-evaluator.md` (и
   каталоги `skills/ktalk-registry/`, `skills/ktalk-eval/`, `commands/ktalk-registry.md`) из
   vault'а — коммитом, не побочным эффектом.

Процедура и её порядок — runbook OPS-001 (companion-спека, не тело этого ADR).

### 4. Версионирование и репозиторий

`plugin.json` **обязан** объявлять `version` явно (иначе версия падает на git SHA — RES-002).
Плагин живёт в **отдельном git-репозитории**, не подкаталоге `ktalk-mcp`: пакет релизится через
`uv tool`/PyPI-подобный канал на своём цикле, плагин — через marketplace Claude Code на своём;
смешивание в одном репозитории синхронизирует циклы релиза искусственно и не даёт откатить
плагин независимо от пакета. Marketplace — git-источник по прецеденту `nauta`/`gramax` на этой
машине; выбор self-hosted vs GitHub для конкретного репозитория плагина — операционное решение
владельца, не архитектурное (обе формы поддержаны платформой одинаково).

Версия плагина не обязана совпадать с версией пакета (0.7.0) — они меняются независимо; плагин
объявляет минимально совместимую версию пакета в `README`, не в `dependencies` manifest (RES-002
не подтвердил, что `dependencies` в `plugin.json` способен выразить внешнюю Python-зависимость).

### 5. Зависимость от `qmd` — опциональная интеграция по факту наличия

Решение владельца (2026-08-18): вариант **(a)** — шаг сопоставления профиля остаётся в
`ktalk-processor` как **опциональная** интеграция, и работает **только если `qmd` уже используется
в проекте-хозяине**. Плагин не требует `qmd`, не устанавливает его и не считает его наличие
нормой: активация шага — следствие обнаруженного факта, отсутствие — штатная ветка с явной
пометкой (FR-24).

Из этого следуют границы, обязательные для DEV-002 и SA-003:

- `integrations.qmd` в `.ktalk.toml` — заявление хозяина о факте, а не переключатель функции
  плагина; заявленное `true` не заменяет фактическую проверку доступности инструмента на старте
  шага (уже зафиксировано спекой SA-003);
- проект, где `qmd` нет, не получает ни ошибки, ни предупреждения об отсутствующей зависимости —
  только пометку в результате шага о том, что сопоставление не выполнялось;
- обратная связка запрещена: наличие `qmd` в проекте не делает шаг обязательным, если хозяин
  его не объявил.

Отклонён вариант (b) (вынос шага из плагина целиком): дублирует логику в каждом хозяине, которому
функция нужна, и противоречит цели волны — один рабочий контур вместо копий.

### 6. `news-digest` — вне текущего плагина

Решение владельца (2026-08-18): скилл `news-digest` и его захардкоженные адресаты
(`amuratov`/`drubin`, RES-001) **в текущий плагин не переносятся** и в объём волны 3 не входят.
Остаются артефактом vault'а как есть; ни один шаг плагина на них не опирается. Пункт закрыт как
решение, а не как отложенный вопрос.

## Последствия

**Позитивные:** плагин переносим между проектами без хардкода путей; пакет и плагин релизятся
независимо; секреты никогда не входят в состав плагина; переключение vault'а — контролируемое
действие, не тихая подмена поведения.

**Негативные:** приоритет CLI (§2а) делает предусловие «`ktalk` в PATH» жёстким — без пакета не
работает ни один сценарий навыка, а не часть; пользователь обязан вручную поддерживать `uv` в PATH и актуальную версию пакета —
плагин не проверяет и не чинит это автоматически; двухшаговый cutover агентов — ещё один ручной
шаг, который легко пропустить (риск дрейфа копий сохраняется до явного удаления); разные
репозитории пакета и плагина — двойной релизный процесс вместо одного.

**Смягчения:** README плагина явно называет предусловие (`uv tool install ktalk-mcp` + PATH) и
даёт команду проверки; runbook OPS-001 делает cutover пошаговым чек-листом, не устной
договорённостью; риск дрейфа копий снижается тем же способом, что миграция реестра (NFR-12) —
явный шаг вместо автоматики, задокументированный, а не более сложной синхронизацией.

## Альтернативы

- **Вендоринг пакета внутрь плагина.** Отклонено: дублирует source of truth кода, ломает
  независимый релиз пакета через `uv tool`/PyPI, плагин перестаёт быть тонким.
- **Один репозиторий на пакет и плагин.** Отклонено: разные циклы релиза (Python-пакет vs
  Claude Code plugin marketplace), разная структура каталогов верхнего уровня (`src/` vs
  `skills/`/`agents/`/`commands/` на корне) — совмещение усложняет оба процесса без выгоды.
- **Автоматический cutover при установке плагина (удаление файлов vault'а инсталлятором).**
  Отклонено: install-хук плагина не имеет санкции на запись вне своего дерева, и тихое удаление
  чужих файлов противоречит принципу «явное действие владельца», уже принятому для миграции
  реестра (NFR-12).
- **Вынос шага `qmd` из плагина по умолчанию (вариант b как решение, не альтернатива).**
  Не отклонено — оставлено открытым вопросом владельцу, не решено этим ADR.
