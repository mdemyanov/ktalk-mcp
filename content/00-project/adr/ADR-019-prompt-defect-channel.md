# ADR-019: Канал дефектов промта

**Дата:** 2026-08-19

## Контекст

[FR-44…FR-47, NFR-26, NFR-27](../../30-requirements/ktalk-prompt-defect-channel.md) требуют
перенос секции «Рекомендации» отчёта `ktalk-eval` в issue репозитория плагина без устной
передачи — три системных дефекта волны 8 дошли до промт-слоя только пересказом в чате (ADR-018).
Ограничивают решение: ADR-012 §1 (плагин — код/промты, пакет `ktalk-mcp` не знает о GitLab);
ADR-016 (запись во внешний контур — по санкции, не свободным действием агента); требование прямо
называет асимметрию — issue доступен анонимно, без авторизации, и не отзывается фактом прочтения.

Решение владельца (2026-08-19): канал строится в урезанном объёме. На сегодня — один пользователь
плагина, ноль заведённых issue, три дефекта за всю историю наблюдений (волна 8, устная передача).
Первая редакция этого ADR (скрипт `ktalk-defect-issue.sh`, санкция `file_defect_issue`, коды
возврата, журнал операций — механика по образцу ADR-016) при этой нагрузке дороже дефекта,
который ловит. Дополнительно: собственный разбор первой редакции признал, что барьер обезличивания
названий клиента не автоматизируется в принципе и держится на человеческом предпросмотре — один из
двух аргументов в пользу кода (проверяемость барьера целиком) для этого класса данных не работал
уже там. Решение ниже — сознательный размен: код не пишется, контракт держит текст и дисциплина.

## Решение

**1. Транспорта-скрипта нет. Заведение issue — операция человека в интерфейсе GitLab.** Навык
`ktalk-eval` формирует готовое тело issue (шаблон — п.2) и показывает его оператору; оператор
копирует тело и заводит issue руками. Нет `ktalk-defect-issue.sh`, нет санкции
`file_defect_issue`, нет журнала операций, нет привязки тела хешем, нет кодов возврата
40/41/42 — предыдущая механика этой ADR отменяется целиком, не переносится в спеку черновиком.
Третья персистентная сущность на машине оператора (после `onboarding.toml`, `write-sanction.toml`)
не заводится. Пакет `ktalk-mcp` по-прежнему не участвует и не получает зависимости на GitLab.

**2. Шаблон issue — таблица «Дефекты промта» отчёта переносится в тело 1:1.** Секция отчёта
`ktalk-evaluator.md` (заменяет «Рекомендации») несёт шесть полей на дефект: класс, тип встречи,
измерение рубрики, цитата транскрипта, цитата протокола, предложенное правило (FR-44). Оператор
переносит поля в тело issue без переформулирования — решение сохраняется целиком, меняется только
исполнитель переноса: человек вместо кода `prepare`.

**3. `CONTRIBUTING.md` репозитория плагина — носитель контракта вместо гейтов кода.** Новый файл
называет: куда заводить issue дефекта промта, что обязательно приложить (шесть полей шаблона),
порог 2+ записей на класс, обязательность пары цитат, правило обезличивания. Это прямая замена
кодовых проверок `prepare` (коды 40/41/42) — **правило без проверки**, названное так прямо: контракт
виден в момент заведения issue (текст файла), но исполняется дисциплиной оператора, не кодом.
Отсутствие `CONTRIBUTING.md` в репозитории плагина сегодня (замер PM, требование) — причина, по
которой контракт до этого решения был виден только тому, кто помнил устно.

**4. Порог и пара цитат (FR-45, FR-46) — правило промта навыка и текста шаблона, не код.** Навык
`ktalk-eval` при формировании секции «Дефекты промта» проверяет условия текстом инструкции
(«не включай класс, встретившийся на одной записи»; «не включай случай без обеих цитат»), не
исполняемой функцией — верификация переходит с автоматической на дисциплинарную (см. таблицу
ниже). **Каталог классов дефекта сохраняется без урезания:** `skills/ktalk-eval/references/
defect-classes.md`, расширяемый append-only список `id`. Без общего `id` классы дефекта
несравнимы между прогонами и порог 2+ неисполним в принципе — единственная часть тяжёлого
варианта, которая переживает урезание, потому что она дешева (один markdown-файл) и не даёт
альтернативы дешевле себя.

**5. Обезличивание (NFR-26) — целиком человеческий барьер, без автоматической подстановки.**
Навык `ktalk-eval` при формировании тела issue несёт обязательный шаг промта «замени имена
сотрудников на роль, суммы — на плейсхолдер» и обязательный полный предпросмотр готового тела
оператору перед тем, как тот его копирует в GitLab. Автоматической подстановки имён/сумм регексом
или каталогом участников нет — тот же вывод, что уже был сделан для класса «клиент» в первой
редакции, распространён на весь барьер: он проверяем только чтением человеком, не кодом.
Последствие называется прямо, не маскируется формулировкой «промт обеспечивает»: утечка возможна
при невнимательном предпросмотре, и это принятый размен объёма, не недосмотр.

**6. Обратный путь — без изменений.** Столбец `Issue` таблицы «Defects» трекера качества несёт
номер/URL issue после заведения оператором; закрытие после правки промта и подъёма версии
(ADR-018) — ручное действие со ссылкой на версию в комментарии issue. Новый процесс не заводится.

Процедурная детализация — точный текст `CONTRIBUTING.md`, редакция промт-фрагментов, состав
каталога классов, брифы Dev, контракт QA-author — в companion-спеке.

## Последствия

**Позитивные:** объём решения соразмерен нагрузке (один пользователь, три дефекта за всю
историю); нет новых исполняемых файлов и персистентных сущностей на машине оператора; контракт
(шаблон, порог, пара цитат, обезличивание) виден в момент заведения issue текстом
`CONTRIBUTING.md` — устная передача, из-за которой три дефекта волны 8 не дошли до промт-слоя,
всё равно закрывается.

**Негативные:** ни порог 2+, ни полнота пары цитат, ни обезличивание не проверяются автоматически
— нарушение контракта (issue без пары цитат, issue по разовому наблюдению, утечка неочищенных
данных) обнаруживается постфактум чтением, а не отказом на публикации; единственный барьер
обезличивания — внимательность оператора в моменте, без второй линии защиты.

**Смягчения:** каталог классов дефекта делает нарушение порога 2+ хотя бы *видимым* при чтении
трекера (совпадающий `id` на одной записи виден сразу); `CONTRIBUTING.md` снижает шанс нарушения
неосведомлённостью — контракт больше не живёт только в памяти оператора; при накоплении фактов
нарушения решение пересматривается (условие возврата — Альтернативы).

## Альтернативы

- **Тяжёлый вариант: скрипт `ktalk-defect-issue.sh`, санкция `file_defect_issue`, журнал,
  проверяемые гейты `prepare` (коды 40/41/42).** Внутренне логичен, прецеденты (ADR-014, ADR-016)
  выбраны верно — **не отклонён по существу, отложен по объёму.** Условие возврата — проверяемый
  факт, не ощущение: появление второго пользователя плагина, либо накопленный факт нарушения
  контракта вручную (issue заведён без пары цитат, issue заведён ниже порога 2+, утечка
  неочищенных данных в опубликованном issue). Любое из трёх — основание пересмотреть это решение
  в пользу тяжёлого варианта, не повод ждать полного списка.
- **Ручное копирование без шаблона и без `CONTRIBUTING.md`.** Отклонено: воспроизводит ровно тот
  провал, что три дефекта волны 8 — контракт виден только тому, кто держит его в памяти.
- **Автоматическая подстановка имён/сумм регексом при сохранении остального барьера ручным.**
  Отклонено для этой волны: частичная автоматизация одного класса данных при полностью ручном
  остальном (клиент) создаёт ложное ощущение защищённости всего барьера — решение либо весь
  барьер человеческий и назван так честно, либо не экономит объём, ради которого урезание сделано.
- **Свободный текст класса дефекта вместо каталога.** Отклонено, как и в первой редакции: без
  общего `id` порог 2+ неисполним даже дисциплинарно — оператор не может сравнить формулировки
  между прогонами.

## Изменение способа верификации AC (для BA)

Урезание переводит часть AC исходного требования с автоматической проверки на дисциплинарную —
исполнение больше не гейтируется кодом:

| AC | Было (тяжёлый вариант) | Стало |
|---|---|---|
| FR-45 (порог 2+) | код `prepare`, счётчик по трекеру, код возврата 40 | текст `CONTRIBUTING.md` + инструкция промта навыка, проверка чтением |
| FR-46 (пара цитат) | код `prepare`, проверка полноты полей, код возврата 41 | текст `CONTRIBUTING.md` + инструкция промта навыка, проверка чтением |
| FR-47 (санкция на заведение) | файловая санкция, TTY/sanctioned-путь, коды возврата 30/31/33 | не применимо: заведение issue — действие человека в интерфейсе GitLab, агент операцию не выполняет — санкционировать нечего |
| NFR-26 (обезличивание) | код `prepare`, regex/каталог, блокирующий код возврата 42 | обязательный шаг промта + обязательный человеческий предпросмотр, проверка чтением |
