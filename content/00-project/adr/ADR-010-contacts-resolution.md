# ADR-010: Резолюция участника встречи через справочник контактов

**Дата:** 2026-08-18

## Context

ADR-009 §3 зафиксировал: операции «текст → числовой `key` участника» в контуре нет, и на этом
основании отдал резолюцию оператору — числовой `key` вводится вручную. Браузерный HAR (RES-003
§5, Ф-53) это опровергает: `GET /api/contacts?query=<текст>&top=25&fillInMeetingStatus=false&
includeKiosks=true` → `200 {"contacts": [{key, firstname, surname, patronymic, post, userType,
contactType, hasEmail, hasMobilePhone, mobilePhone, avatarUrl}, ...]}`. `key` — тот самый
идентификатор, ожидаемый в `requiredAttendees[].key` (build_required_attendees,
`meeting_body.py`). Операция существует; пробела в API нет.

**Оговорка Ф-53, дословно.** Поиск — по тексту имени/фамилии, не проверялся на приём логина как
значения `query`: 7 букв с опечаткой → 0 совпадений; корректная 6-буквенная основа фамилии → 16
совпадений; фамилия + начало имени → 1 совпадение. Нечёткого/фонетического сопоставления на этом
образце нет — опечатка обнуляет выдачу. Приём логина как `query` — N/A, отдельный непроверенный
живой замер, не допущение.

**Api-key-режим — N/A, не проверялся и не может быть проверен сейчас.** Единственный доступный
ключ проекта не имеет выданных scope на контакты (Р-4 постановки волны); негативный/позитивный
исход для api-key-режима не наблюдался ни разу. По дисциплине ADR-004 («рабочая запись только
когда доступ объясним, не когда просто наблюдался») — здесь даже наблюдения нет, тем более нет
записи.

## Decision

**1. `search_contacts` — новая операция чтения, session-режим, путь `/api/contacts`.** Регистрация
в `OPERATION_PROFILES` (`auth.py`) тем же приёмом, что `get_room`/`get_calendar` (ADR-003/ADR-004):
`AuthMode.SESSION: EndpointProfile("/api/contacts", None)`. `AuthMode.API_KEY: None` — fail-closed
до сетевого вызова, не «наблюдалось, но необъяснимо» (тот случай ADR-004 п.2 для календаря), а
«не наблюдалось вовсе» — тот же исход (нет рабочей записи), причина иная, обе фиксируются раздельно
по anti-fabrication: не смешивать «необъяснимый факт» и «отсутствие факта».

**2. Резолюция — отдельная read-операция, не встроенная в `create_meeting`.** Компоновщик тела
(`build_meeting_body`/`build_required_attendees`, ADR-005/ADR-009) продолжает принимать только
готовые числовые `key` — контракт не меняется. `search_contacts` — предшествующий, отдельно
вызываемый шаг: оператор (или вызывающий агент через MCP) ищет текстом, получает список кандидатов,
явно выбирает `key`, передаёт его в `--required-attendee-key`/MCP-параметр планирования, как и
сегодня. Причина разделения: allow-list компоновщик ADR-005 — структурная гарантия «сервер не
получит поле, которое вызывающий не решил явно»; сращивание поиска с компоновкой создало бы путь,
где решение «этот контакт» принимается implicit-но внутри одного вызова создания, а не отдельным
проверяемым шагом.

**3. Контракт по числу совпадений — явный, без автовыбора (NFR-9).**

| Совпадений | Поведение |
|---|---|
| 0 | Отказ до дальнейших действий: печатается точный текст запроса и факт «ничего не найдено»; оператор либо уточняет `query`, либо переходит на прямой ввод числового `key` (эскейп-люк ADR-009 §3 не отменяется, остаётся валидным путём) |
| 1 | `key` показывается оператору как единственный найденный кандидат вместе с ФИО и `post` — подтверждается тем же явным шагом, что и остальные поля NFR-9 (не подставляется автоматически в тело без показа); единственность результата — не эвристика (детерминированный факт выдачи API), не нарушает запрет на «обманчиво уверенные» автовыборы |
| >1 | Отказ: печатается полный список кандидатов (`key`, ФИО, `post`) без ранжирования по «похожести»; оператор сужает `query` или называет точный `key` из списка. Автовыбор первого/«наиболее похожего» — запрещён (NFR-9, тот же принцип, что отклонил эвристику по логину в ADR-009 §3) |

**4. Логин как значение `query` — не поддерживается контрактом.** Раз приём логина не проверен
(Ф-53, оговорка), контракт декларирует `query` как «текст имени/фамилии», не как логин. Попытка
передать логин может случайно сработать (если он похож на текст) или дать 0 совпадений — оба
исхода не гарантированы. Проверка — отдельная будущая задача, не допущение этого ADR.

## Consequences

**Positive:** ручной ввод `key` (ADR-009 §3) перестаёт быть единственным путём — оператор может
искать текстом; пробел, зафиксированный ADR-009 §3 как подтверждённый, закрыт по факту, а не
эвристикой; структурная гарантия ADR-005 (allow-list компоновщика) не расширяется и не ослабляется
— поиск живёт вне неё.

**Negative:** двухшаговый UX (поиск → подтверждение → ввод key в команду создания) добавляет шаг
по сравнению с гипотетическим «поиск встроен в создание»; api-key-режим резолюции недоступен до
появления нужных scope у ключа; приём логина как `query` не гарантирован — эскейп-люк на прямой
числовой ввод остаётся обязательным для случаев, где текстовый поиск не находит нужного контакта.

**Mitigations:** эскейп-люк «числовой `key` вручную» (ADR-009 §3) сохраняется явно, не удаляется
этим решением — контракт добавляет путь, не заменяет старый; api-key-режим ревизуется отдельной
задачей при появлении выданных scope, тем же приёмом, что ADR-004 п.2 для календаря.

## Alternatives Considered

- **Встроить резолюцию в `create_meeting`/`build_meeting_body` напрямую (текст → сетевой вызов →
  key внутри одного шага).** Отклонено: стирает разделение «явное решение оператора» и «поиск»,
  усложняет allow-list компоновщик сетевой зависимостью, которой у него сегодня нет (ADR-005 §1:
  предпросмотр физически не имеет доступа к сети).
- **Автовыбор при единственном совпадении внутри самого поиска, без показа оператору.** Отклонено:
  единственность результата сегодня — не гарантия навсегда (появление тёзки меняет число
  совпадений); показ кандидата перед использованием — тот же принцип NFR-9, что и остальные поля.
- **Ранжирование кандидатов по релевантности при >1 совпадении и автовыбор первого.** Отклонено:
  прямое нарушение NFR-9 — ровно тот класс «обманчиво уверенной эвристики», который ADR-009 §3 уже
  отклонил для сопоставления по логину внутри календарных элементов.
- **Считать логин допустимым значением `query` по аналогии с текстовым поиском.** Отклонено:
  непроверенное поведение не может стать частью контракта (anti-fabrication) — фиксируется как N/A,
  не как рабочее допущение.
