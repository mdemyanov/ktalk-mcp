# ADR-015: CLI — единственный развиваемый интерфейс контура; контракт передачи пишущей операции оператору

**Дата:** 2026-08-18

## Контекст

BA-005 (`ktalk-plugin-meetings.md`) ставит промт-поверхность плагина `ktalk` поверх CLI-команд
0.7.0 (FR-32…FR-38) и требует, чтобы граница «где заканчивается автономия агента и начинается
действие оператора» (NFR-22, NFR-23) была контрактом, а не молчаливым допущением каждого навыка.
ADR-012 §2а уже отдал приоритет CLI над MCP как решение владельца волны 3; в этой сессии владелец
уточнил формулировку: не «CLI приоритетен, MCP вторичен» (оставляет открытым, развивается ли MCP
медленнее), а «MCP не развивается вовсе». Замер PM: плагин `ktalk-plugin` использует MCP ровно в
двух местах — объявление сервера в `.mcp.json` и одна ссылка на контракт `ktalk_get_transcript` в
`agents/ktalk-processor.md:127` (упоминание, не вызов) — переписывать промты под заморозку не
требуется.

Отдельно ADR-005 §3 зафиксировал: подтверждение пишущей операции существует только подкомандой CLI
за `isatty()`, потому что вызов MCP-инструмента не несёт сигнала «решил человек». BA-005 переносит
это ограничение на уровень промт-поверхности (NFR-23) и добавляет новый запрет: автоматический
повтор `*-confirm` после сбоя (NFR-22). Оба факта существуют в коде (`cli_meeting.py`,
`confirmation.py`), но не были собраны в контракт, который навык/агент обязаны предъявить
оператору в момент передачи хода. Ключевой факт кода: `create-meeting-confirm`/
`cancel-meeting-confirm` не принимают `confirmation_id` предыдущего `*-preview` — `ConfirmationStore`
инстанцируется заново на каждый вызов процесса (`confirmation.py`, docstring), `confirmation_id` из
предпросмотра одного процесса физически бесполезен для подтверждения в другом. Единственное, что
переживает границу процессов, — параметры вызова (флаги команды), не токен.

## Решение

**1. Статус интерфейсов.** CLI `ktalk` — единственный развиваемый интерфейс контура в плагине.
MCP-сервер заморожен: новых инструментов не появляется, паритет с CLI больше не поддерживается.
Объявление stdio-сервера остаётся в `.mcp.json` плагина и продолжает работать как есть (чтение
контента — транскрипты, саммари); заморозка не отзывает уже работающие read-инструменты и не
требует правки плагина под неё (замер PM: переписывать промты не нужно). Уточняет ADR-012 §2а
(«CLI приоритетен, MCP вторичен») до «MCP не развивается» — ссылка внесена в ADR-012, само решение
и статус ADR-012 не переписываются (правило supersede, CLAUDE.md).

**2. Граница промт-слоя для пишущих операций.** Автономия агента заканчивается на вызове
`*-preview`: агент вправе вызывать `create-meeting-preview`/`cancel-meeting-preview` сколько угодно
раз, показывать и пересобирать предпросмотр по правкам оператора. Действие оператора начинается на
`*-confirm` — агент не вызывает эту команду, не оборачивает её в скрипт/subprocess, не предлагает
её выполнить «за оператора одной кнопкой» (NFR-23).

В момент передачи агент обязан отдать оператору три вещи одним сообщением:
- отрендеренный предпросмотр (`format_meeting_preview`/`format_cancel_preview` — то же, что покажет
  сам `*-confirm` перед запросом слова подтверждения);
- **точный текст команды `*-confirm` с теми же флагами**, что были переданы в `*-preview` —
  единственный артефакт, переживающий границу процессов (см. «Контекст»: `confirmation_id` не
  переносится, флаги — переносятся);
- явное указание, что команда выполняется лично оператором в его интерактивном терминале, и почему
  (без TTY `*-confirm` отклоняется — ADR-005 §3).

**Сбой на стороне `*-preview`** (валидация, недостающее поле NFR-9) — восстанавливаемая ошибка
внутри диалога агента: агент переспрашивает оператора и повторяет `*-preview` сам, это не пишущий
вызов и не требует нового захода оператора в терминал.

**Сбой на стороне `*-confirm`** («исход неизвестен», см. `cli_meeting.py`) наблюдает только
оператор — этот вызов происходит вне контроля агента. Агент, вернувшись к диалогу, не инициирует
повторный `*-confirm` и не формулирует его как рекомендованное следующее действие «от своего имени»
(NFR-22) — максимум, что уместно: напомнить оператору тот же путь эскалации, что уже несёт текст
самого CLI (`ktalk list-calendar` для проверки факта, FR-38 для диагностики прав), не изобретая
retry-цикл поверх него.

Состав и формулировки конкретных навыков/промтов — SA-006, не это решение.

## Последствия

**Positive:** одна граница автономии для всех операций FR-33/FR-34, а не решение навыка по месту;
явный список того, что агент обязан передать оператору, проверяем grep'ом промта (FR-33 AC,
NFR-23 AC); заморозка MCP снимает необходимость держать два места контракта пишущей операции
синхронными — его физически не существует в MCP.

**Negative:** оператор обязан вручную перепечатать/скопировать команду `*-confirm` — при большом
числе флагов (NFR-9: до 12 полей) шанс опечатки при ручном вводе есть; заморозка MCP закрывает путь
внешним интеграторам, которые уже полагались на MCP-паритет с CLI (не подтверждено, что такие есть).

**Mitigations:** агент отдаёт готовую команду текстом для копирования, не только описание параметров
— оператор не набирает флаги с нуля; при опечатке `*-confirm` откажет валидацией того же
allow-list-компоновщика, что и `*-preview` (ADR-005), не выполнит операцию с искажёнными данными
молча.

## Alternatives Considered

- **MCP развивается медленнее CLI, но не заморожен полностью.** Отклонено: оставляет открытым
  вопрос, когда конкретный MCP-инструмент получает обновление — решение владельца снимает эту
  неопределённость явно.
- **Передавать оператору `confirmation_id` вместо флагов.** Отклонено фактом кода: `ConfirmationStore`
  не переживает границу процессов — токен предыдущего `*-preview` не подходит для `*-confirm` в
  новом процессе оператора; передавать нечего, кроме флагов.
- **Агент сам вызывает `*-confirm` в псевдотерминале (обход `isatty()`).** Не рассматривается как
  решение — ADR-005 §3 прямо называет это «осознанным преодолением барьера», не легитимным путём.
