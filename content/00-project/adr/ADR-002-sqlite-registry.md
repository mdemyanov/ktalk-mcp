# ADR-002: SQLite — операционный source of truth реестра записей

**Дата:** 2026-06-25 (решение), 2026-08-13 (зафиксировано в контуре)

## Контекст

Записи Контур.Толк обрабатываются пачками: часть уже разобрана в заметки vault, часть ждёт,
часть протухла и разбираться уже не будет. Состояние этой очереди раньше жило в
markdown-реестрах в самом vault — их правили и человек, и фоновые агенты одновременно.

Markdown как носитель состояния даёт три проблемы: параллельная правка двух агентов теряет
запись; дедуп по строкам таблицы неустойчив к вариативной разметке (реальные архивы приезжали
с 7 и 8 колонками и с `|` внутри ячеек); машинное чтение требует парсера, который ломается о
каждую ручную правку.

## Решение

Операционное состояние переносится в SQLite (`.registry.db`, WAL, `busy_timeout=5000`,
транзакция на операцию) — это единственный источник правды для механики: статусы, дедуп,
экспирация. Markdown-реестр в vault становится генерируемым read-only зеркалом (`ktalk export`).

Разделение точек входа: `ktalk-mcp` (MCP-сервер) отдаёт **контент** — транскрипты и саммари;
`ktalk` (CLI) владеет **механикой** — sync, статусы, экспорт. Общие `client.py` и `config.py`.

Статусная модель: `new → done|skipped|partial`, `partial → done`. Записи в статусе `new` строго
старше N дней (по умолчанию 7) переводятся в `skipped` на `sync`.

## Последствия

- Параллельные `mark-*` из фоновых агентов безопасны — WAL плюс транзакция на операцию.
- `--json` у всех команд печатает валидный JSON в stdout, ошибки идут в stderr с ненулевым
  кодом возврата: навык или агент парсит stdout, не угадывая формат.
- Зеркало нельзя править руками — правка потеряется при следующем `ktalk export`.
- Файл БД бинарный, поэтому в vault он под gitignore вместе с `-wal` и `-shm`.
- Разовый импорт из старых markdown-реестров сделан командой `ktalk migrate <vault>`; парсер
  устойчив к 7/8-колоночным архивам и к `|` внутри ячеек.

## Альтернативы

- **Оставить markdown как source of truth.** Отвергнуто по потерям при параллельной записи.
- **JSON-файл вместо SQLite.** Снимает вопрос парсинга, но не конкурентности: атомарная замена
  файла целиком проигрывает транзакции при одновременных `mark-*`.
- **Хранить состояние на стороне MCP-сервера.** Смешало бы контент и механику в одной точке
  входа; CLI тогда невозможен без запущенного сервера.
