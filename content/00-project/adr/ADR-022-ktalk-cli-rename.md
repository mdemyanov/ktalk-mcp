# ADR-022: Пакет становится `ktalk-cli` — снятие MCP-слоя, версия 1.0.0

**Дата:** 2026-08-31

## Контекст

[ADR-015](ADR-015-cli-authority-and-write-handoff.md) §1 заморозил MCP-сервер («новых
инструментов не появляется, паритет с CLI больше не поддерживается»), но объявление сервера в
`.mcp.json` плагина и сам код (`server.py` + шесть `tools_*.py`) остались на месте. Сегодня
именно эти семь модулей — единственные во всём дереве, импортирующие `fastmcp`; сам пакет
объявляет `fastmcp>=2.0.0` жёсткой (не optional) зависимостью в `dependencies`. Замер: набор
без `fastmcp` — 9,7 МБ/14 пакетов против 56 МБ/70, холодный старт 23,1 с против 152,8 с; CLI без
`fastmcp` проверен запуском шести команд, включая сетевую `auth-status`.

Решение владельца (принято, не пересматривается): пакет переименовывается `ktalk-mcp` →
`ktalk-cli`, MCP-слой снимается **целиком** (не заморозка — удаление), `fastmcp` уходит из
зависимостей без остатка, версия — `1.0.0`; переименование — на месте в этом репозитории;
`ktalk-mcp` выпускает финальную версию-указатель с `DeprecationWarning`; имена в PyPI заранее не
занимаются.

Сиблинг-репозиторий `ktalk-plugin` несёт капабилити-спеку `openspec/specs/cli-only-boundary/spec.md`
(его собственный ADR-022, "CLI-граница"), которая на дату этой записи фиксирует более узкий
план: `fastmcp` — optional extra (не полное снятие), MCP-инструмент деградирует с понятным
сообщением, а не исчезает, и «тестовый набор, покрывающий MCP-слой, продолжает выполняться без
изменений» — план, который, по прямому указанию задачи, «не сделано». Настоящее решение
превышает и заменяет этот план: MCP-слой и его тесты снимаются, а не переводятся в опциональный
режим. Реконсиляция текста капабилити-спеки плагина под новый факт — задача параллельного SA
того дерева, не эта запись (тело и статус чужого ADR не редактируются, правило supersede).

## Решение

**1. MCP-слой снимается, не замораживается.** Удаляются `server.py` и шесть `tools_*.py`
(`contacts`, `meeting_cancel`, `meetings`, `recordings`, `rooms`, `scheduling`) — семь модулей,
единственные потребители `fastmcp`. Из тестов удаляются только функции, физически импортирующие
эти модули (`from ktalk_mcp.server import mcp` и т.п.) — 12 функций в семи файлах
(`test_calendar.py` — 3, `test_fr21_no_vault_layout.py` — 1, `test_fr39_calendar_inclusive_end.py`
— 1, `test_meeting_cancel.py` — 2, `test_public_interface.py` — 2, `test_rooms.py` — 2,
`test_search_contacts.py` — 1), не сами файлы: в каждом остаются тесты CLI/клиента, не
завязанные на MCP-инструмент. Уточняет ADR-015 §1 («MCP не развивается») до «MCP не
существует» — тело и статус ADR-015 не переписываются.

**2. `fastmcp` уходит из `dependencies` целиком.** Не в `optional-dependencies` (отклоняет план
плагинного ADR-022, см. «Контекст») — раз кода, использующего `fastmcp`, не остаётся вовсе,
опциональный extra держал бы зависимость ради нуля потребителей. Дев-группа тестов тоже не несёт
`fastmcp` — снятому коду нечего тестировать.

**3. Дистрибутив переименовывается `ktalk-mcp` → `ktalk-cli`, версия `1.0.0`.** Единственная
точка входа нового пакета — `ktalk = ktalk_cli.cli:main`; entry point `ktalk-mcp` новый пакет не
объявляет (это имя остаётся только за версией-указателем, п.6) — одно имя команды, один
легитимный владелец.

**4. Python-модуль переименовывается `ktalk_mcp` → `ktalk_cli`.** 75 файлов правки (`src/` +
`tests/`, механическая замена) против постоянного расхождения «имя дистрибутива — не имя
импорта» — цена разового рефакторинга ниже цены вечной путаницы, тем более что вся эта волна и
существует ради снятия MCP-имени с продукта: сохранение `ktalk_mcp` как имени модуля оставило бы
именно ту путаницу, которую волна устраняет с поверхности. Правка — один механический коммит,
проверяемый полным прогоном тестов до/после.

**5. `~/.config/ktalk-mcp/token` (`token_file.py`) не переименовывается.** Каталог уже выбран
независимо от имени дистрибутива — докстринг `token_file.py` объясняет это выбором «не `ktalk/`»
(там санкция записи, ADR-016, другой владелец), не выбором «= имя пакета». Переименование пути
не даёт функциональной выгоды и стоит дорого: `read_token()` — fail-closed, отсутствие файла по
новому пути читается как «файла нет», не как «файл переехал» — уже настроенные машины молча
теряют третий источник авторизации без диагностики. Разовая мех. правка ради единообразия имени
не оправдывает тихую деградацию боевой машины.

**6. Версия-указатель `ktalk-mcp` — финальный релиз `0.11.0`, без `ktalk`.** Пакет не несёт
прикладного кода и зависимостей (пустой `dependencies`), единственная точка входа —
`ktalk-mcp = ktalk_mcp:main` (без entry point `ktalk` — решение обязательно, см.
«Последствия»/companion-спека, эмпирика `uv tool`). Вызов печатает в stderr сообщение о
переименовании и команду `uv tool install ktalk-cli`, поднимает `DeprecationWarning`, завершается
ненулевым кодом — тот же контракт ошибок, что у остального CLI (`CLAUDE.md`, «ошибки — в stderr с
ненулевым кодом возврата»). Версия не `1.0.0`: `1.0.0` на пакете-указателе читалась бы как «новый
стабильный релиз», а не как надгробие.

**7. Идентичность пакета в рантайме читается из метаданных, не из литерала.** Находка SA-001:
`cli.py:381` печатает `f"ktalk-mcp {__version__}"` — имя дистрибутива жёстко зашито строкой;
механическое переименование модуля (п.4) её не задевает, потому что в строке нет идентификатора
модуля, только текст. То же имя литералом ещё в `__init__.py:12` (аргумент `_installed_version(
"ktalk-mcp")`) и в тексте `--help` (`cli.py:59`) — три места, набирающие одно и то же имя заново.
Цена: этот же класс бага (уже ударивший в 0.8.0 — литерал версии разошёлся с pyproject.toml,
`tests/test_cli.py::test_version_matches_pyproject`) воспроизводится на каждом следующем
переименовании, а для имени (в отличие от версии) сегодня нет теста, который ловит расхождение
до релиза. Решение: и версия, и имя читаются из метаданных установленного дистрибутива по ключу
`__package__` (имя реального Python-пакета), не по хардкод-строке — эмпирически подтверждено:
`importlib.metadata` нормализует `-`/`_`/регистр при подстановке ключа поиска (`version(
"ktalk_mcp")` и `version("ktalk-mcp")` разрешаются в один и тот же установленный дистрибутив), а
`metadata(...)["Name"]` возвращает исходную строку имени из `pyproject.toml` без промежуточного
хранения. Единственный литерал, который остаётся, — имя-заглушка в ветке `PackageNotFoundError`
(исходное дерево без установки, метаданные читать неоткуда); это один литерал вместо трёх, и его
позиция в коде сама указывает, что это заглушка, а не источник истины.

## Последствия

**Positive:** холодный старт и объём инсталляции падают на порядок (замерено, «Контекст»); один
владелец команды `ktalk` вместо двух конкурирующих пакетов; имя модуля и имя дистрибутива
совпадают, путаница «зачем в `ktalk-cli` лежит `ktalk_mcp`» не возникает; указатель никогда не
ухудшает положение `ktalk-cli` — он физически не может забрать команду `ktalk`, потому что не
объявляет её.

**Negative:** 75-файловая правка модуля — одноразовая, но широкая; машина, где уже установлен
старый `ktalk-mcp` (владеет обеими командами `ktalk`/`ktalk-mcp` — подтверждено `uv tool list` на
боевой машине), не получает `ktalk-cli` бесконфликтно простым `uv tool install ktalk-cli`: `uv
tool install` отказывает («Executable already exists: ktalk», без `--force`) до тех пор, пока
старый пакет не апгрейднут до пакета-указателя (снимает `ktalk`-shim, п.6) или не удалён явно;
капабилити-спека плагина временно расходится с фактом до реконсиляции в сиблинг-репозитории
(«Контекст»); механическое переименование модуля (п.4) само по себе не находит литералы имени
дистрибутива вне идентификаторов — п.7 закрывает найденные, но тот же класс риска возможен в
файлах, не входящих в состав `src/` (companion-спека даёт полный перечень на дату записи, не
гарантию на будущее).

**Mitigations:** эмпирически подтверждено (`uv tool install` дважды на одно имя команды: второй
получает отказ, первый не трогается; апгрейд пакета *на месте* до версии без `ktalk`-entry
корректно снимает старый shim) — порядок «сначала апгрейд `ktalk-mcp` до указателя (или явный
`uv tool uninstall ktalk-mcp`), потом `uv tool install ktalk-cli`» бесконфликтен независимо от
момента; этот порядок — обязательный вход для DevOps/онбординга плагина (companion-спека).
Метаданные вместо литерала (п.7) переводят имя в тот же режим защиты, что версия уже имеет с
0.8.0 (`test_version_matches_pyproject`) — расхождение имени и pyproject обязано ловиться тем же
приёмом, до релиза, не после (contract QA-author, companion-спека).

## Alternatives Considered

- **`fastmcp` — optional extra, MCP-слой остаётся с graceful degradation (план плагинного
  ADR-022).** Отклонено: код без потребителей не стоит держать даже опционально; задача прямо
  называет план «не сделано» и заменяет его.
- **Версия-указатель сохраняет entry point `ktalk`** (для «мягкого» перехода). Отклонено фактом
  `uv tool`: второй пакет с тем же именем команды не побеждает тихо — он получает жёсткий отказ
  установки без `--force`; сохранение `ktalk` в указателе создаёт риск конфликта в любом порядке
  установки без всякой пользы (указателю эта команда не нужна — у него нет функциональности CLI).
- **Версия-указатель — `1.0.0`.** Отклонено: тот же номер на решающем «финал» пакете читается как
  сигнал зрелости, а не прекращения; `0.11.0` (следующий свободный минор от `0.10.0`) не создаёт
  ложного впечатления.
- **Централизованная строковая константа имени** (одна вместо трёх литералов, п.7). Отклонено:
  дешевле сейчас (без нового вызова `importlib.metadata`), но остаётся литералом — тот же класс
  бага воспроизводится при следующем переименовании, только с меньшей поверхностью; метаданные
  устраняют его структурно ценой одного уже оплаченного вызова (тот же, что читает `__version__`).
- **Переименование `~/.config/ktalk-mcp/token` в `~/.config/ktalk-cli/token`.** Отклонено: файл —
  состояние машины пользователя с реальным секретом; переименование без миграции превращает
  «источник токена сработал» в молчаливое «источника нет» на уже настроенных машинах (fail-closed
  маскирует причину). Ни один FR/NFR не требует этого переименования.
- **Удаление MCP-тестов целиком по семь файлов.** Отклонено: в каждом файле остаются тесты
  CLI/клиента, не завязанные на `fastmcp` (12 из ~90+ тестов этих семи файлов относятся к MCP) —
  удаление файла стёрло бы непричастное покрытие.
