# ADR-020: Локальная проверка формата `--timezone`

**Дата:** 2026-08-19

**Нумерация.** [FR-40](../../30-requirements/rooms-calendar-scheduling.md) (строка 681) называет
ожидаемый номер «ADR-019» — на момент фиксации требования (коммит `700432f`, 08:45) это был
следующий свободный номер. Параллельная волна заняла его раньше (`ADR-019-prompt-defect-channel.md`,
коммит `793e8db`, 11:57 того же дня). Решение получает следующий фактически свободный номер,
ADR-020; переоткрывать/переносить принятый ADR-019 не входит в объём этой задачи.

## Контекст

[FR-40](../../30-requirements/rooms-calendar-scheduling.md#fr-40--формат-timezone--часть-контракта-отказ-локальный)
требует: неверная форма `--timezone` отклоняется до сетевого вызова и до выдачи `confirmation_id`,
без списания бюджета санкции записи; сообщение называет требуемый формат и пример, не пересказывает
сырой `CalendarTimeZoneParse`; `--help` CLI и докстринг `build_meeting_body` называют формат явно.
Нормализация входа отклонена решением владельца (FR-40 «Решение») — вне периметра.

Замер владельца (19.08.2026, боевой домен, 8 значений, cost 7 единиц бюджета санкции,
`content/30-requirements/rooms-calendar-scheduling.md:357-368`): рабочая форма ровно одна,
`GMT+3`; семь других форм (`Europe/Moscow`, `Russian Standard Time`, `+03:00`, `MSK`, `180`,
`RTZ 2 (MSK)`, `(UTC+03:00) Москва, Санкт-Петербург`) — `HTTP 400 CalendarTimeZoneParse`.

## Решение

**1. Место проверки — `meeting_body.py`, рядом с `MissingFieldError`.** `build_meeting_body`
(`src/ktalk_mcp/meeting_body.py:83`) — единственная точка сборки тела, вызываемая из трёх
поверхностей через один слой: `PreviewService.preview` (`meeting_scheduling.py:24`) вызывается из
CLI-предпросмотра (`cli_meeting.py:52`), CLI-подтверждения (`cli_meeting_confirm.py:132`,
`preview()` внутри `_run_confirm`) и MCP-инструмента (`tools_scheduling.py:69`). Проверка формы в
`build_meeting_body` покрывает все три без отдельной правки каждой. Альтернатива — парсер аргументов
CLI (`cli_meeting_args.py:31`) — отклонена: она физически не видит MCP-путь (`tools_scheduling.py`
не проходит через `argparse`), FR-40 требовал бы дублирования проверки в `tools_scheduling.py`, что
нарушает принцип единой точки, уже принятый для набора полей тела (докстринг `meeting_body.py:1`,
«Единая функция... без прохода через произвольный словарь»).

**2. Тип ошибки — новый класс `TimezoneFormatError(KTalkError)`, не `MissingFieldError`.**
`MissingFieldError` семантически «поле отсутствует» (`is None`); здесь поле присутствует, но не
проходит проверку формы — переиспользование исказило бы сообщение (`f'Поле «{field}» не передано
явно...'` неверно для непустого значения) и стёрло бы разницу для вызывающего кода, который решает
по тексту исключения. Оба потребителя (`cli_meeting_confirm.py:132`, `cli_meeting.py:52`) ловят
`except MissingFieldError as exc` — правка расширяется до `except (MissingFieldError,
TimezoneFormatError) as exc` в обоих местах; `tools_scheduling.py:87` ловит `_AUTH_ERRORS =
(KTalkError,)`, общий предок, — правка там не нужна.

**3. Регулярка — `^GMT[+-](?:[0-9]|1[0-4])$`.** Форма подтверждена замером только для `GMT+3` —
единственное измеренное значение. Диапазон `0..14` (обе стороны знака) — **экстраполяция, не
измерение**: граница взята по общемировому диапазону смещений UTC (крайние часовые пояса —
UTC-12…UTC+14), не по замеру владельца. Отклонённый вариант issue, `^GMT[+-]\d{1,2}$`
(диапазон `0..99`), даёт цену ошибки шире: `GMT+50` проходит локальную проверку и возвращает
отказ на сервер тем же `CalendarTimeZoneParse`, ради устранения которого делается вся задача —
именно тот сценарий, который FR-40 закрывает. Цена узкой стороны (`0..14`): значение вне диапазона
мировых смещений, которое сервер по гипотезе принял бы, инструмент отклонит локально
(не встречалось на 8 значениях замера, оценки нет — не измерено). Цена широкой стороны: значение
внутри `0..14`, отклоняемое сервером по причине, отличной от диапазона (не наблюдалось на замере),
уезжает на сеть и списывает бюджет санкции — тот же отказ, что до этого решения, но реже.

**4. Порядок проверок — обязательность раньше формы.** `timezone is None` проверяется существующим
циклом `_REQUIRED` (`meeting_body.py:113-115`) до всех дополнительных проверок формы, которые
следует добавить сразу после цикла и до `pin_code`/`anonymous_access_expiration`. Отсутствующее
значение — более общий отказ («поле не передано»), неверная форма присутствующего значения —
частный случай следующего порядка; сохранение существующего порядка держит сообщения
детерминированными (одно и то же входное состояние всегда даёт одно и то же первое исключение).

**5. `CalendarTimeZoneParse` в человекочитаемые сообщения не выносится.** `grep -rn
"CalendarTimeZoneParse" . --include="*.py"` — пусто; аналог для `create_meeting` (частных 400-текстов,
как `KNOWN_400_TEXTS` в `calendar_reader.py:42-51`) не существует и не заводится этим решением. Если
значение проходит локальную регулярку, но сервер всё равно возвращает `CalendarTimeZoneParse`
(гипотетически — значение вне подтверждённого `GMT+3`, но внутри принятого диапазона `0..14`),
вызывающий получает необработанный `KTalkWriteAuthMismatchError`/сырой текст ответа как атрибут
исключения (`meeting_scheduling.py`, комментарий «ADR-008... тело 4xx-ответа как атрибут
исключения»), без перевода на человекочитаемый текст. Перевод этого конкретного подтипа в отдельный
класс ошибки — расширение объёма за пределы FR-40 (FR-40 требует читаемое сообщение только для
*локального* отказа по форме, не для отказа сервера на форме, прошедшей регулярку); заводить его
без наблюдённого случая — необоснованная работа на неподтверждённый сценарий.

**6. Вне периметра.** `skills/ktalk-meetings/SKILL.md` — репозиторий `ktalk-plugin`, не трогается.

## Последствия

**Позитивные:** единая точка проверки покрывает все три поверхности без дублирования; отдельный
класс ошибки не искажает семантику существующего `MissingFieldError`; порядок проверок
детерминирован.

**Негативные:** диапазон `0..14` — экстраполяция за пределы единственного измеренного значения;
возможен как ложный локальный отказ (значение сервер принял бы), так и пропуск на сервер (значение
внутри диапазона, но сервер отклоняет по неизвестной причине) — оба случая не наблюдались на
замере, оценка вероятности отсутствует.

**Смягчения:** следующий боевой замер владельца с иным значением `GMT±N` (не `+3`) — источник
данных для сужения/расширения диапазона; до тех пор диапазон помечен в докстринге и в companion-спеке
как гипотеза, не факт.

## Alternatives Considered

- **Проверка в `cli_meeting_args.py`.** Отклонено: не видит MCP-путь `tools_scheduling.py`,
  требует дублирования проверки.
- **Переиспользование `MissingFieldError`.** Отклонено: искажает текст сообщения («поле не
  передано» при присутствующем значении), стирает различимость по типу исключения.
- **Регулярка `^GMT[+-]\d{1,2}$` (issue, диапазон 0..99).** Отклонено: пропускает на сервер
  заведомо бессмысленные смещения (`GMT+50`), которые дешевле отклонить локально.
- **Перевод `CalendarTimeZoneParse` в человекочитаемый текст сейчас.** Отклонено: нет
  наблюдённого случая, когда регулярка пропускает, а сервер всё равно отклоняет по этому подтипу —
  преждевременная работа без замера.
