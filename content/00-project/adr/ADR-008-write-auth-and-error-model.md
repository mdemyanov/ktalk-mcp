# ADR-008: Транспорт credential на мутирующих операциях, разграничение 401 и сохранение тела ответа

**Дата:** 2026-08-17

## Context

Второй боевой `POST /api/calendar` (приёмка 0.6.0, после коррекции пути ADR-007) вернул 401 с
сообщением «Токен сессии истёк или невалиден» ([разбор DEV-005](
../../60-implementation/rooms-calendar-dev-c3-notes.md)). Тем же процессом и тем же токеном:
`GET /api/calendar` → 200 (16 событий), `auth-status` → `alive: True`, до и после. **Факт**
(DEV-005 §2–3): один путь, один токен — GET успешен, POST — 401; `sessionToken` уходит в query
POST-запроса так же надёжно, как в GET (httpx client-level `params`, воспроизведено синтетически);
заголовка `Authorization` клиент не отправляет никогда ни для чтения, ни для записи.

Три независимых дефекта вскрыты одним инцидентом:

1. Механика передачи credential для записи не проверена и, возможно, не та же, что для чтения.
   **ГИПОТЕЗА** (DEV-005 §5, источник — `mainpart-ktalk-mcp.md` «Авторизация — механика целиком»
   п.1, другой токен и канал того проекта, не факт про наш контур): сервер принимает
   `?sessionToken=` в query как облегчённый механизм только для чтения, запись требует заголовок
   `Authorization: Session <token>`.
2. Модель сообщений (`CLAUDE.md`, `client.py::_classify`) знает два случая — 401 «токен
   истёк», 403 «доступ запрещён, токен рабочий». Третьего нет: 401 на операции, чья валидность
   токена в ту же секунду подтверждена независимой проверкой. Существующая корреляционная
   диагностика (ADR-004, `diagnose_undocumented_failure`) уже перехватывает `KTalkAuthError` как
   `TRANSIENT_ERRORS` и делает контрольный вызов, но при успехе контроля заворачивает исходную
   ошибку в `ContourDriftError`, чей текст интерполирует `str(error)` — буквально то же «токен
   истёк», только в другой обёртке. Корреляция уже происходит, диагноз всё равно неверный.
3. Тело ответа 401 нигде не сохранено. `meeting_scheduling.create_meeting` пишет его через
   `logger.warning` (ADR-007 §3) — в проекте нет ни одной конфигурации `logging`
   (`basicConfig`/`FileHandler`/`dictConfig`), сработал `lastResort` в stderr, ничем не
   зафиксирован (DEV-005 §4). Разбор причины 401 остался без единственного источника, который мог
   бы её прояснить напрямую.

Это третье подряд расхождение того же класса — часть механики скопирована с источника-
экстраполяции (mainpart), часть потеряна (ADR-004 — путь `get_room`/`get_calendar`; ADR-007 —
префикс `/api`; здесь — способ передачи credential). Общая причина в готовности принимать частичное
сходство с источником за полное — не устраняется точечной правкой одного из трёх случаев, отдельная
запись в `content/lessons-learned.md`, не предмет этого ADR.

## Decision

**1. Заголовок `Authorization: Session <token>` — дополнительно к query, только на мутирующих
операциях session-режима.** Не заменяет query (обе формы уходят одновременно — дешевле проверить
одним POST, чем выяснять по отдельности, что из двух требуется) и не трогает конструирование
`httpx.AsyncClient` (ADR-003: транспорт credential для чтения остаётся собран один раз при
создании клиента, инвариант не нарушается). `EndpointProfile` получает поле `mutating: bool`
(дефолт `False`); при `True` в session-режиме операция дополнительно передаёт заголовок. Область
действия — только `create_meeting` сегодня, механизм переиспользуем для будущих мутирующих
операций без дублирования. **ГИПОТЕЗА до следующего боевого POST** (новая санкция владельца,
отдельная задача PM) — эта задача не выполняет и не санкционирует сетевой вызов.

**2. Новый класс ошибки `KTalkWriteAuthMismatchError(KTalkAuthError)`.** Поднимается вместо
`ContourDriftError`, когда `diagnose_undocumented_failure` получает на вход ошибку, классификация
которой была 401/403 (`isinstance(error, KTalkAuthError)`), и контрольный вызов (тот же credential,
тот же процесс) проходит успешно. Сообщение не содержит «обновите токен»: явно утверждает, что
credential подтверждён рабочим независимой проверкой в ту же секунду, и называет операцию.
`ContourDriftError` остаётся для прочих классов сбоя (404, 5xx, неожиданная форма ответа) —
изменение не затрагивает существующее поведение вне пары (401/403 + успешный контроль).

**3. Тело ответа 4xx/5xx — атрибут исключения, не только строка лога.** `create_meeting` перед
`_classify` читает `response.text` (та же точка, что уже существует по ADR-007 §3) и, если
`_classify` поднимает исключение, переупаковывает его в тот же класс с тем же публичным
сообщением плюс телом ответа, обрезанным до 500 символов, как отдельным атрибутом
(`error.response_body`). CLI (`cli_meeting.py::_print_error`) и любой другой вызывающий печатают
`str(exc)`, куда тело подмешивается текстом — маскирование `redact_secrets` уже применяется к
результату на границе CLI (текущий вызов `_print_error`, без изменений), новой точки
редактирования не требуется. `logger.warning` (ADR-007 §3) не убирается — второй, не единственный
путь фиксации.

Детали — сигнатура `EndpointProfile`, псевдокод `diagnose_undocumented_failure`, формат сообщения,
брифы Dev/DevOps, контракт QA-author — в [companion-спеке](
../../40-architecture/ADR-008-write-auth-and-error-model-spec.md).

## Consequences

**Positive:** следующий боевой POST либо подтверждает гипотезу заголовка (встреча создаётся),
либо опровергает её тем же единственным запросом, не требуя второй попытки на диагностику
транспорта отдельно от диагностики авторизации; пользователь на будущем 401-после-успешной-
проверки получает диагноз, который не отправляет его чинить рабочий токен; тело ответа сервера
переживает прогон независимо от конфигурации `logging`, которой в проекте нет и не появится этим
решением.

**Negative:** заголовок отправляется вслепую до проверки боевым POST — если гипотеза неверна,
850-я строка `auth.py` несёт мёртвый код до следующей сессии приёмки; `KTalkWriteAuthMismatchError`
добавляет третий класс сообщения к и так небольшой модели ошибок (401/403/mismatch), что нужно
удерживать в голове при код-ревью новых мутирующих операций; атрибут `response_body` на исключении
— API-поверхность, которую нужно долго держать неизменной, если её начнут парсить программно.

**Mitigations:** заголовок помечен `ГИПОТЕЗА` по дисциплине ADR-007 п.2, снимается или
подтверждается конкретной следующей задачей, не тлеет неопределённо; `mutating`-флаг в
`EndpointProfile` — единая точка, которая решает и передачу заголовка, и (в будущем) любые другие
различия чтения/записи, не разрастание условий по коду; `response_body` документирован как
диагностический текст для человека (усечён, не структурирован), не контракт для парсинга.

## Alternatives Considered

- **Заменить query на заголовок целиком для мутирующих операций.** Отклонено: если ГИПОТЕЗА
  неверна и требуется именно query, замена сломала бы операцию тем же способом, каким сейчас
  ломает её отсутствие заголовка — аддитивная посылка не хуже ни при одном из двух исходов
  гипотезы.
- **Заменить query на заголовок для всего session-режима, включая чтение.** Отклонено: чтение
  (`get_room`, `get_calendar`, `list_recordings`) подтверждено живьём именно с query — трогать
  работающий механизм ради непроверенной гипотезы о записи меняет больше поверхности, чем нужно
  для проверки одной гипотезы.
- **Оставить `ContourDriftError` для случая 401+контроль-в-порядке, править только текст.**
  Отклонено: `ContourDriftError.detail` строится из `str(error)` — правка текста в одном месте
  не убирает «токен истёк» из другого, пока класс общий; отдельный класс делает намерение видимым
  в сигнатуре обработчика (`except KTalkWriteAuthMismatchError`), не только в тексте.
- **Настроить `logging.FileHandler` на старте CLI вместо атрибута на исключении.** Отклонено
  (см. вывод DEV-005 §4, где это названо минимальной правкой, но не выбрано здесь): файл лога —
  новая поверхность (путь, ротация, доступ) ради одного вызывающего пути; атрибут на исключении
  доставляет тело туда же, куда уже смотрит пользователь (stdout/stderr CLI), без нового файла.
