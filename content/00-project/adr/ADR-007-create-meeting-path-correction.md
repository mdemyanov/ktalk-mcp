# ADR-007: Коррекция пути create_meeting и дисциплина маркировки непроверенных экстраполяций

**Дата:** 2026-08-17

## Context

Санкционированный боевой `POST` (DEV-002, приёмка 0.6.0) на `create_meeting` вернул 404; живым
чтением календаря доказано, что встреча не создана
([разбор](../../60-implementation/rooms-calendar-dev-c2-notes.md)). Фактический запрос ушёл на
`{ktalk_base_url}/calendar` — единственная запись `OPERATION_PROFILES` без префикса `/api`, тогда
как оба других подтверждённых внутренних пути (`get_room`, `get_calendar`) префикс несут.

Источник пути — сопоставление с `create_meeting` стороннего проекта mainpart (Ф-38
[RES-003](../../10-domain/research/ktalk-calendar-api.md)). Собственное исследование mainpart
прямо документирует: «Все пути — относительно `base_url = f"{space_url}/api"`, то есть реальный
HTTP-путь всегда с префиксом `/api`»
([mainpart-ktalk-mcp.md](../../10-domain/research/mainpart-ktalk-mcp.md), строки 192–193), и в его
же таблице эндпоинтов `POST /calendar` — запись **относительно** этого `base_url`. При переносе в
наш профиль относительность потерялась: у нас `/calendar` стал буквальным путём без `/api`, хотя у
источника он таковым не был.

Комментарий `auth.py::OPERATION_PROFILES["create_meeting"]` (до этого решения) фиксировал
отсутствие `/api` как «намеренно, не опечатка» — притом что ни один живой запрос это не
подтверждал. Формулировка читалась как решение, а была непроверенной гипотезой.

Отдельно: `create_meeting` не подключён к корреляционной диагностике ADR-004
(`diagnose_undocumented_failure`), в отличие от `calendar_reader._fetch_segment`, а
`client.py::_classify` на 404 отбрасывает тело ответа безусловно. Из-за этого «пути не существует»
и «объект не найден» неразличимы по самому ответу — что и произошло на боевом 404.

## Decision

**1. Путь `create_meeting` (SESSION) меняется на `/api/calendar`.** Основание — тот же класс
довода, что уже принят ADR-004 п.3 («факт выдачи весомее декларации»), применённый здесь к самому
источнику декларации: у mainpart относительный путь `/calendar` подразумевает `/api/calendar` по
его собственному правилу base_url, и оба уже подтверждённых внутренних пути этой волны несут
`/api`. Это вторая экстраполяция, не факт — она не проверена живым POST и проверена быть не может в
рамках этой задачи (следующий боевой POST не выполняется здесь). Она надёжнее первой не потому, что
подтверждена, а потому что первая опиралась на неверное прочтение источника (относительный путь
принят за абсолютный), а вторая — на согласованность с 2 из 2 уже живьём подтверждённых путей
контура плюс исправленное прочтение того же источника. `API_KEY`-строка остаётся `None`
(fail-closed, ADR-004 п.2) — новых данных по api-key-режиму нет.

**2. Комментарии о происхождении пути/scope недокументированного контура обязаны маркировать
статус проверки, не только источник.** Два маркера: `ФАКТ (Ф-NN, живой <метод> <дата>)` — для
утверждений, подтверждённых конкретным живым запросом; `ГИПОТЕЗА (источник, не проверено живым
запросом)` — для документарной экстраполяции. Комментарий, объясняющий выбор пути/параметра/scope
недокументированной операции без одного из двух маркеров, недопустим — именно такая формулировка
(«намеренно, не опечатка») превратила непроверенную гипотезу в решение, которое никто больше не
подверг сомнению до боевого 404. Маркер не заменяет верификацию; он делает статус верификации
видимым тому, кто читает код без доступа к истории задач.

**3. `create_meeting` подключается к корреляционной диагностике ADR-004.** Решение уточняет ADR-004
spec (раздел «Механизм детекции», пункт про `POST /calendar`) в части, оказавшейся неверной по
факту: там корреляционный механизм считался неприменимым к POST на том основании, что POST не
выполняется живьём вне санкционированной приёмки — но именно в момент санкционированной приёмки
корреляция и была нужна. `create_meeting` оборачивает POST тем же приёмом, что
`_fetch_segment` — network-исключения и исключения `_classify` идут через
`diagnose_undocumented_failure` (контрольный вызов `list_recordings(top=1)`, уже рабочий в
session-режиме). Отдельно: тело ответа на нестандартный код сохраняется в диагностическое
сообщение/лог до того, как `_classify` его отбросит — раздельные тексты «путь не смаршрутизирован»
и «объект не найден» в теле 404 сами по себе различают причину без второго POST. Секретов в теле
ответа сервера на собственный запрос не бывает (NFR-10 не нарушается).

## Consequences

**Positive:** путь `create_meeting` согласован с обоими уже подтверждёнными путями контура,
а не единственное расходящееся исключение; будущий читатель `auth.py` видит статус проверки прямо в
комментарии, не должен поднимать историю задач, чтобы отличить решение от гипотезы; следующий
боевой POST (при новой санкции владельца) получит корреляционный вердикт и, при удаче, различимое
тело ответа — а не только код 404.

**Negative:** путь `/api/calendar` для создания встречи остаётся непроверенным живым POST — эта
задача сама по себе ничего не подтверждает, только исправляет прочтение источника; маркировка
`ФАКТ`/`ГИПОТЕЗА` — дисциплина, которую можно не соблюсти в будущем коммите так же, как не
соблюли в этом; она снижает вероятность повтора, не исключает его.

**Mitigations:** новый боевой POST для проверки пути — отдельная задача PM с новой санкцией
владельца, не входит в эту работу; до неё путь остаётся помеченным как непроверенный (маркер
`ГИПОТЕЗА` в коде). Дисциплина маркировки распространяется код-ревью/чек-листом Dev, не
автоматической проверкой — граница честно называется в companion-спеке.

## Alternatives Considered

- **Оставить `/calendar` без `/api`, дождаться единственно возможного нового POST для проверки.**
  Отклонено: путь основан на прочтении источника, о котором уже известно, что оно неверно
  (источник сам документирует `/api`-префикс) — нет причины оставлять заведомо худшую из двух
  экстраполяций действующей записью профиля до следующей боевой попытки.
- **Третье состояние `EndpointProfile` для «неверифицированный путь».** Отклонено тем же доводом,
  что ADR-004 «Альтернативы» отклонил третье состояние доверия — усложняет модель ради записей,
  число которых меньше, чем стоимость новой абстракции; маркер в комментарии решает ту же задачу
  читаемости дешевле.
- **Распространить чтение `response.text` на весь `_classify` для всех операций.** Отклонено:
  меняет поведение документированных путей без необходимости и без замера риска для NFR-10 по
  всей поверхности API, не только по недокументированному контуру; текст сохраняется точечно, в
  месте вызова `create_meeting`, не в общем классификаторе.
