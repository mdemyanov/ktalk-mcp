# ADR-024: Ужесточение сверки идентичности транскрипта

**Дата:** 2026-09-04

## Context

Три открытых issue пакета `ktalk-cli` (#5, #8, #9) обнажают один и тот же механизм — сверку
идентичности `get-transcript` (NFR-17, ADR-023 §1, `transcript_identity.py`) — с трёх разных
сторон: причина исходной подмены (#5), достоверность сверки на анонимных встречах (#8), потеря
результата сверки на границе чанка (#9). RES-006 уже исключило все клиентские носители подмены,
предметно проверенные в дереве (кэш, синглтон-клиент, путь запроса, cookie-jar, прокси-код,
журнал) — причина не локализована этим ADR, только наблюдаемость отказа.

## Decision

### Д1 (issue #5) — причина не установлена; отказ становится громким

**Причина НЕ установлена.** Перепроверка кода (методика и находки — companion-спека §1)
подтверждает RES-006: в дереве нет ни одного механизма, способного объяснить межпроцессную
подмену — включая структурный довод, которого не было в RES-006: любой per-process кэш в
принципе не может объяснить утечку между четырьмя ОТДЕЛЬНЫМИ ОС-процессами, а не только
конкретно отсутствующий. Единственный общий носитель — session-токен (RES-006, Г1); проверка
требует живого скоординированного теста, санкции на который нет ни у RES-006, ни у этого решения.

**Решение — не «гонка устранена», а «отказ становится громким».** Сверка ADR-023 детектирует
`mismatch`, но не эскалирует его — `cmd_get_transcript` сегодня возвращает код 0 даже на
расходящихся множествах (регресс-тест зафиксировал это явно, companion-спека §1) — тот же силуэт
тихого отказа, что называет issue #5, на уровень глубже: признак есть в теле ответа, но не в коде
возврата, а часть потребителей читает только код. `get-transcript` завершается кодом **3** ровно
при `identity_check.result == "mismatch"`, отдельно от кода 1 (отказ вызова, содержимого нет) и
кода 2 (ошибка использования CLI); тело ответа не меняется. `not_checked`/`inconclusive`/`match`
остаются кодом 0 (ADR-023 AC3).

**Отклонено:** `--verify-identity` opt-in (ADR-023 уже отклонил, довод не изменился); ключевание
несуществующего кэша (нечего ключевать); ревизия ранее обработанных записей (issue п.3) — до
ADR-023 сверка не выполнялась и сырые ответы не сохранялись, восстанавливать нечего.

**Признак закрытия:** `get-transcript` на фикстуре с расходящимися множествами возвращает код 3.

### Д2 (issue #8) — устойчивость `anonymousId` подтверждена измерением, не иначе

Живой контур доступен (`ktalk auth-status --json` → `"alive": true`). Измерено 2026-09-04 на
живых данных оператора (метод, объём выборки и её границы — companion-спека §2, значения ID не
публикуются — не нужны сверх факта совпадения): у всех говоривших анонимных участников выборки
`anonymousId` и `anonymousName` из `get_recording.participants` совпали буквально с одноимёнными
полями `tracks[].speaker` того же анонима.

**Решение — заметка, не код.** `anonymousId` подтверждён устойчивым на измеренной (малой) выборке.
Ограничение ADR-023 Consequences («не проверено живым тестом») закрывается этим измерением для
наблюдавшегося случая; категорического «устойчиво всегда» это не доказывает. Код не меняется:
сверка остаётся включённой по умолчанию (issue прямо запрещает иное), ключ сравнения — тот же.
Смягчающий фактор архитектуры: `check_identity` требует непустого ПЕРЕСЕЧЕНИЯ множеств, не
полного равенства — встреча с хотя бы одним именованным участником не может дать ложный
`mismatch` из-за нестабильности анонимного идентификатора; риск ограничен встречами, где ВСЕ
участники анонимны.

**Отклонено:** менять ключ сравнения для анонимов или исключать их из сверки с `inconclusive` —
измерение (при всей малости выборки) не показало расхождения, вводить обходной путь под
неподтверждённый риск преждевременно; при первом реальном ложном `mismatch` на полностью
анонимной встрече — новое ADR по факту, не по гипотезе.

**Признак закрытия:** запись в этом ADR фиксирует измерение; issue #8 закрывается ссылкой на этот
раздел, без изменений в `transcript_identity.py`.

### Д3 (issue #9) — сигнал сверки не теряется на границе чанка

`render_transcript_output` при `--chunk N` вне диапазона возвращает нестрого-JSON текст
(`formatters.py:344`), а `cli_content.py:151` ловит `JSONDecodeError` и печатает его как есть,
теряя уже вычисленный `identity_check` — комментарий «сверять нечего» неточен: сверка (сетевой
вызов `get_recording`) на этом пути СЕГОДНЯ УЖЕ выполняется (перепроверено, companion-спека §3),
её результат просто выбрасывается сборкой вывода.

**Решение — не выполнять сверку при заведомо неверном номере чанка (направление 1 issue),**
переиспользуя словарь исходов ADR-023, не изобретая новый: диапазон чанка вычислим локально из
уже полученного `data` (без сети) ДО решения о вызове `get_recording` — `cmd_get_transcript`
определяет валидность `--chunk` раньше, чем запускает сверку; при заведомо неверном номере
сверка не запускается (сетевой вызов не оплачивается), а `identity_check` получает
`{"result": "not_checked", "reason": "chunk_out_of_range"}` — тот же исход `not_checked`, что уже
используется для отказа `get_recording`, не новое понятие (markdown-хвост
`_render_transcript_with_identity` уже умеет печатать `reason`). В `--json`-режиме тело этой
ветки становится валидным JSON (`{"error": "...", "identity_check": {...}}`) вместо текущей
нестрого-JSON строки — устраняет источник `JSONDecodeError`, а не только ловит его.

**Отклонено:** второе направление issue (отдавать исход сверки в текущей нестрого-JSON ветке как
есть) — сохраняло бы оплаченный, но не нужный сетевой вызов и опиралось бы на хрупкое
распознавание формы строки (`try: json.loads except JSONDecodeError`) там, где заранее известный
диапазон чанка снимает саму неопределённость.

**Признак закрытия:** `get-transcript --chunk <вне диапазона> --json` не делает вызов
`get_recording` (0, не 2, сетевых вызова на сверку) и возвращает валидный JSON с
`identity_check.result == "not_checked"`, `reason == "chunk_out_of_range"`.

## Consequences

**Positive:**
- Д1: `mismatch` больше не тонет в коде возврата 0 — автоматизация, читающая только код,
  перестаёт молча доверять подменённому содержимому.
- Д2: известное ограничение ADR-023 закрыто измерением на реальном контуре, не гипотезой.
- Д3: `get-transcript --chunk` вне диапазона дешевле (без лишнего сетевого вызова) и не стирает
  различение «не сверено»/«сверка не запускалась».

**Negative:**
- Д1: меняет ранее закреплённый тестом контракт (`rc == 0` на mismatch) — поведенческая правка
  для потребителей, проверяющих только код возврата; версия пакета — как минимум минорная (не
  патч), решает Dev/владелец при релизе.
- Д1: причина подмены по-прежнему не локализована — громкий отказ снижает последствие, не
  устраняет источник; живой скоординированный тест (RES-006, Г1) остаётся не выполненным.
- Д2: n=2 — измерение не исключает нестабильность на будущей встрече другой формы (много
  одновременных анонимов, гостевой режим иной версии контура).
- Д3: ветка `--json` вне диапазона меняет форму (строка → объект) — потребитель, парсящий эту
  ветку регулярным выражением по прежнему тексту, ломается; ветка и ранее не была валидным JSON
  по документированному контракту `--json`, поэтому это не breaking change контракта, а
  исправление дефекта.

**Mitigations:**
- Д1: код 3 документируется рядом с кодами 1/2 в брифе Dev и README пакета.
- Д2: измерение и его малость выборки фиксируются здесь текстом, не заявляются как гарантия;
  следующий инцидент на полностью анонимной встрече — повод для нового ADR, не для тихой правки.
- Д3: сообщение `"Чанк N не существует..."` сохраняется буквально под ключом `error` — потребитель
  markdown-режима не видит изменений вовсе.

## Alternatives Considered

- Д1: `--verify-identity` opt-in — отклонено ADR-023, довод не изменился.
- Д1: ревизия истории обработанных записей — нет данных для восстановления, п. Decision.
- Д2: другой ключ сравнения для анонимов / `inconclusive` вместо `mismatch` для анонимных
  встреч — отклонено, измерение не показало расхождения на доступной выборке.
- Д3: отдавать исход сверки в существующей нестрого-JSON ветке как есть — отклонено, сохраняет
  оплаченный лишний вызов и хрупкое распознавание формы.
