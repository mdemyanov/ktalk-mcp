# ADR-018: Калибровка промт-слоя анализа плагина ktalk

**Дата:** 2026-08-19

## Контекст

Замер `ktalk-eval` на трёх записях (1-1, status, session) держит средний overall 4,33 и не находит
точечных ошибок (Accuracy 4–5), но находит три системных дефекта: обязательство, названное прозой
протокола, не попадает в таблицу «Договорённости» (Completeness 3/5 при status-встрече); `confidence`
калибруется по наклонению реплики-запроса, а не по факту согласия в реплике-акцепте; искажённое
ASR-имя маркируется непоследовательно или не маркируется вовсе. [FR-40…FR-43, NFR-25](../../30-requirements/ktalk-plugin-analysis-calibration.md)
описывают дефекты и инварианты, прямо оставляя SA форму реализации в промт-слое. Промт-слой живёт в
отдельном репозитории `ktalk-plugin` (ADR-012 §1: три дома, плагин — код/промты, не пакет); правку
самих файлов промта выполняет Dev по этому решению, не SA.

## Решение

**1. Финальная сверка FR-40 — шаг ядра `agents/ktalk-processor.md`, не пункт чек-листа
`two-pass-analysis.md`.** Новый шаг 4.5, между сборкой черновика и определением места сохранения.
Чек-лист прохода 2 исполняется параллельно с загрузкой чанков транскрипта и на длинных записях
проигрывает конкуренцию за внимание; шаг ядра исполняется над уже собранным текстом целиком —
объект сверки (проза vs таблица) физически существует к этому моменту, а не собирается по ходу.

**2. Маркер неопределённого имени — `[ASR?]` сразу после имени, отдельно от `[UNCLEAR]`.**
`[UNCLEAR]` занят открытыми вопросами встречи и входит в `unclear_count`; маркер имени — другой
лексический токен (не подстрока `UNCLEAR`), не участвует в `unclear_count`. Синтаксис и место
объявления — `agents/references/protocol-template.md`, единая точка, на которую ссылаются оба
промта качества.

**3. Источник истины при дублировании — по теме, не по файлу целиком.**
`agents/references/two-pass-analysis.md` — нормативный для алгоритма двух проходов (структура,
разделы A…E); `skills/ktalk-registry/references/analysis-quality.md` — нормативный для шкалы
confidence и калибровочных примеров. Каждый файл ссылается на другой по своей неосновной теме
вместо копирования текста — расхождение редакций снимается тем, что копии не остаётся.

**4. Пример 3 (`analysis-quality.md`, приложение) — не переразметка, а пара примеров рядом.**
Текущий Пример 3 (условный запрос + односложная реакция → неверно HIGH) заменяется на пару:
тот же случай, исправленный на MEDIUM, и новый пример с условным запросом и явным акцептом →
HIGH. Пара калибрует различающий признак (реплика-акцепт, не наклонение запроса) нагляднее
одиночного примера — то же наблюдение, что в FR-41 AC1/AC2 (регрессионные пары требования).

**5. «Ключевые тезисы» — опциональная секция шаблона, последняя в порядке, применяется только к
`session`.** Фиксированный порядок семи секций (`protocol-template.md`) не меняется; секция
добавляется восьмой, после «Заметки», с явной пометкой в шаблоне «только для `meeting_type:
session`, отсутствует у прочих типов». Схема Consistency рубрики проверяет наличие/порядок
обязательных секций — добавление опциональной секции в конце не требует правки самой рубрики,
только явного знания о её опциональности (входит в контракт с QA-author, спека).

**6. Резолвинг третьих лиц (FR-42) — пакетный поиск с порогом по позиции в тексте, с кешем.**
Grep выполняется не на каждое упоминание, а один раз на собранный после прохода 1 список
уникальных имён; в список попадают только имена, встретившиеся в тексте, который уже отнесён к
«Договорённостям»/«Ключевым решениям»/«Обновлениям статуса» — не в проходной речи. Имя, once
резолвленное или помеченное, кешируется на весь прогон — повторное упоминание не порождает
повторный Grep.

**7. Гейт NFR-25 — расширение существующего `scripts/check-plugin-composition.sh`
(репозиторий `ktalk-plugin`), не новая инфраструктура.** Единственный существующий механизм
проверки состава плагина в том репозитории — этот скрипт; новых pre-commit хуков там нет
(в отличие от `ktalk-mcp`, где гейты — payload плагина nauta). Минимальный работающий вариант —
добавить в него проверку: если `git diff` коммита/PR затрагивает `agents/` или
`skills/ktalk-registry/`, а `.claude-plugin/plugin.json` без изменения `version` — код возврата
≠0. Ручное правило в `CONTRIBUTING` — резервный вариант при отсутствии CI, применяющего скрипт;
не заменяет проверку, а описывает её словами для контрибьютора без CI.

## Последствия

**Позитивные:** дефект Completeness закрывается шагом, для которого объект сверки уже собран
целиком; связка «маркер + счётчик» больше не смешивает два разных смысла; дублирование
confidence/двух-проходного алгоритма перестаёт быть риском рассинхрона — каждая копия удалена,
осталась одна нормативная версия на тему; калибровочные примеры больше не противоречат
собственному правилу и рубрике `eval-rubric.md` §4; резолвинг третьих лиц не растёт линейно с
числом упоминаний по всей записи; версия плагина и правка промт-слоя синхронизированы механически,
не по памяти контрибьютора.

**Негативные:** шаг 4.5 — дополнительный проход над уже собранным текстом, стоимость токенов
растёт на объём черновика (не измерено, замера стоимости нет — см. companion-спеку); порог
«имя встретилось в договорённости/решении/статусе» может пропустить третье лицо, упомянутое в
причине отказа сделки или другом контексте вне трёх категорий — сознательный компромисс бюджета,
не полное покрытие; расширение `check-plugin-composition.sh` полезно только если скрипт
фактически запускается в CI/pre-commit репозитория `ktalk-plugin` — не проверено этим решением
(вне периметра ADR-012).

**Смягчения:** стоимость шага 4.5 — предмет измерения на следующем прогоне `ktalk-eval`
(A/B на трёх записях замера), не гипотеза, принимаемая без проверки; порог резолвинга третьих лиц
называется явно в companion-спеке как ручка Dev, расширяемая при находке пропуска на будущих
записях; факт подключения `check-plugin-composition.sh` к CI репозитория `ktalk-plugin` —
предпосылка, которую подтверждает DevOps того репозитория, не эта ADR.

## Альтернативы

- **Чек-лист прохода 2 вместо шага ядра (FR-40).** Отклонено: чек-лист конкурирует за внимание с
  загрузкой чанков на длинных транскриптах — ровно тот механизм, которым объясняется пропущенная
  строка в замере (status-встреча).
- **Маркер, переиспользующий слово `UNCLEAR` с уточнением (`[UNCLEAR: имя, ASR]`).** Отклонено:
  подстрока `UNCLEAR` делает счётчик `unclear_count` уязвимым к наивному текстовому подсчёту
  вхождений — риск, который явный отдельный токен снимает физически, не дисциплиной промта.
  Наблюдалось в замере как одна из трёх реальных форм записи.
- **Один файл поглощает содержимое другого (слияние `two-pass-analysis.md` в
  `analysis-quality.md` или наоборот).** Отклонено: файлы уже разделены по адресату (первый —
  алгоритм для агента, второй — качество для скилла-обёртки, `_meta.md`); слияние ломает эту
  границу ради решения проблемы, у которой есть более дешёвое решение (владение по теме).
- **Переразметка Примера 3 без добавления пары.** Отклонено явно в постановке требования: пара
  ценна как обучающий контраст, одиночный исправленный пример этот контраст теряет.
- **Секция «Ключевые тезисы» — отдельный шаблон для типа `session`, не опциональная секция общего
  шаблона.** Отклонено: два шаблона протокола удваивают поверхность правки при следующей калибровке
  порядка секций; опциональная секция в конце — меньшее изменение поверхности.
- **Резолвинг третьих лиц без порога — Grep на каждое упомянутое имя.** Отклонено расчётом
  (companion-спека): десятки третьих лиц на часовой встрече — десятки вызовов инструмента на один
  прогон, без верхней оценки стоимости.
- **Новый CI-пайплайн в репозитории `ktalk-plugin` под NFR-25.** Отклонено: там нет вообще
  никакой гейт-инфраструктуры сегодня — проектирование нового пайплайна с нуля превышает объём
  калибровочного решения; расширение уже существующего скрипта — минимальный рабочий вариант.
