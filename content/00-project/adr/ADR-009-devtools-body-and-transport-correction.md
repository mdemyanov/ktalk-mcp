# ADR-009: Коррекция тела и транспорта create_meeting по браузерному снимку DevTools

**Дата:** 2026-08-17

**Статус решения по пунктам (2026-08-18, BA-010).** Пятый боевой POST (Ф-55, Ф-56 RES-003 §6)
подтвердил п.1 (транспорт) и п.2 (состав тела) живым запросом — они больше не `ГИПОТЕЗА`. П.3
(резолюция логина в числовой `key`) параллельно пересматривается задачей SA-010 по опровергающему
факту Ф-53 (`GET /api/contacts`), не этой ревизией. Свойство `Статус` в шапке этой статьи —
единое на весь документ, расщепить его по пунктам решения формально нельзя; статус остаётся
**Draft**, пока не закрыт и п.3. Ссылаться на подтверждённость конкретного пункта — по этой
пометке, не по общему полю `Статус`.

## Context

Владелец снял в DevTools реальный `POST https://naumen.ktalk.ru/api/calendar` → 200 из UI Толка
(обезличенный разбор — [companion-спека](../../40-architecture/ADR-009-devtools-body-and-transport-correction-spec.md)).
Это первый **живой факт** о форме мутирующего запроса за всю волну — предыдущие решения
(ADR-005 состав полей, ADR-007 путь, ADR-008 транспорт) опирались на документарную экстраполяцию
(RES-003 Ф-37–Ф-43) или на непроверенную гипотезу, ещё не подтверждённую боевым POST нашего
процесса.

Три расхождения с текущей реализацией:

1. **Транспорт.** Браузер шлёт только заголовок `Authorization: Session <token>` — **без**
   `?sessionToken=` в query, плюс `X-Platform: web`. ADR-008 уже ввёл заголовок аддитивно к query
   для `mutating=True`-профилей как непроверенную гипотезу — снимок её не опровергает (аддитивность
   не мешает работать запросу без query), но не проверяет и то, что `X-Platform` не требуется.
2. **Состав тела.** Реальный запрос — 14 полей, не 11 (ADR-005 «Решение» §1). Отсутствует
   `enableSip` (поля нет в реальном контуре вовсе); `requiredUserKeys: [строка-логин]` заменяется на
   `requiredAttendees: [{"type": "user", "key": "<числовой id>"}]`; `start`/`end` — UTC с суффиксом
   `Z`, не локальное смещение; добавлены `anonymousAccessExpirationDate`, `autoRunDeepFakeDetection`,
   `isRecurring`, `maskingSettings`, отсутствовавшие в аллов-листе полностью.
3. **`roomName`.** В реальном запросе — сгенерированный идентификатор (`vi4clkg9gyq9`), не
   человекочитаemое имя.

## Decision

**1. На `mutating=True`-профилях session-режима query `?sessionToken=` не отправляется — только
заголовок `Authorization: Session <token>` + `X-Platform: web`.** Пересмотрено против первой версии
решения (аддитивность query+заголовок): при одном оплаченном выстреле важна не абстрактная
безопасность добавки, а расстояние до известной рабочей точки. Эмпирика: боевые попытки 3 и 4 этой
приёмки (`rooms-calendar-dev-d1/d2-notes.md`) уже шли с исправленным путём (ADR-007) и заголовком
(ADR-008) поверх query — обе дали 401; единственная известная конфигурация с 200 (снимок) — тот же
заголовок + `X-Platform`, **без** query. Менять сразу два параметра относительно единственного
успеха (оставлять query и добавлять `X-Platform`) — значит при новом провале снова не знать, какой
из факторов виноват; минимальное расстояние до успеха — убрать query, добавить `X-Platform`.
Решение **строго скоуплено `profile.mutating`** — читающие пути query не теряют, инвариант ADR-003
для чтения цел; query вырезается точечно после построения запроса, конструктор клиента не
меняется (детали — companion-спека). Куки (`kontur_ngtoken`, `ngtoken`) по-прежнему **не
воспроизводятся** — источника браузерного логина у процесса нет; явный пробел (см. «Consequences»).
Транспорт (п.1) и состав тела (п.2) — **подтверждены** пятым боевым POST 2026-08-18 (Ф-55, Ф-56
RES-003 §6): 200, встреча создана в ровно этой конфигурации; статус `ГИПОТЕЗА` с них снят.

**2. Состав тела `build_meeting_body` приводится к 13 полям** (14-е, `subject`, уже входит в текущий
список): убирается `enableSip` (структурная невозможность параметра — поля с таким значением в
реальном API нет, тот же приём, каким ADR-005 исключил `isRecurring`); `required_user_keys`
переименовывается в `required_attendees` и меняет форму на список объектов
`{"type": "user", "key": str}`; `start`/`end` нормализуются к UTC перед отправкой (конвертация —
деталь `meeting_body.py`, компоновщик остаётся источником единственной точки правки). Три поля
становятся **архитектурно-фиксированными литералами, не параметрами вызывающего**: `isRecurring: False`,
`autoRunDeepFakeDetection: None`, `maskingSettings` — дефолтный объект без маскирования
(`{"nameMaskingMode": "none", "postMaskingMode": "none", "showAdditionalInfo": true}`). Это
**расширение**, не отмена структурной гарантии ADR-005: значение задаёт архитектура, не
вызывающий, — тот же принцип, каким `isRecurring` уже был закрыт, применён к двум новым полям.
`anonymousAccessExpirationDate` — `None`, когда `allow_anonymous=False` (безопасно: доступ выключен,
поле неприменимо); когда `allow_anonymous=True` — становится **новым обязательным параметром**
NFR-9 (без вычисляемого дефолта — формула из одного примера недостаточна, см. companion-спека
«Anti-fabrication»). `pinCode` начинает явно принимать `None` как валидное решение «без PIN»
(JSON `null`), а не только непустую строку — CLI получает симметричный CLI-флаг по образцу
`--no-required-users` (деталь — companion-спека).

**3. Резолюция логина в числовой `key` — известный пробел, не решается этим ADR.** В контуре нет
операции «логин → числовой id пользователя» ни в `auth.py`, ни в `enrichment.py` (там `key` берётся
из объекта участника уже состоявшейся записи, не из справочника пользователей домена). До появления
такой операции — как отдельного факта, не выдумки — CLI/MCP принимают числовой `key` явно от
вызывающего (новый параметр, замещающий текущий `required_user_key`-логин), перекладывая резолюцию
на оператора. Замена не проходит по NFR-9 автоматической эвристикой (сопоставление по логину внутри
уже полученных календарных элементов было бы частичным и обманчиво уверенным — сработало бы только
для тех, кто уже фигурирует организатором/участником в видимой выдаче).

**4. `roomName` остаётся непрозрачным строковым идентификатором — контракт не меняется.** ADR-006
уже установил: сервер принимает произвольную строку как `roomName` без валидации формата (200 на
любое имя). Снимок не опровергает это — генерированный слаг в примере не доказывает, что
человекочитаемое имя было бы отклонено, только то, что конкретно эта сессия UI использовала
генерированный идентификатор для того конкретного (вероятно, одноразового) сценария. Решение:
для следующей боевой попытки — новое, явно помеченное тестовое имя, не переиспользование
`probe-fresh-*`, оставшихся от предыдущей разведки (те несут не связанное с этим сценарием
состояние конфигурации) — операционная рекомендация, не структурное изменение контракта.

## Consequences

**Positive:** тело и транспорт впервые основаны на живом снимке успешного запроса, не на
экстраполяции с чужого пути; структурная гарантия ADR-005 (`isRecurring` невозможно передать
вызывающим) расширена на два новых поля тем же приёмом, не ослаблена; пробел резолюции id
пользователя назван явно, а не замаскирован эвристикой.

**Negative (актуально на 2026-08-17, снято собственным боевым POST на 2026-08-18 — см. пометку о
статусе выше):** ни один пункт не проверен собственным боевым POST в новой конфигурации — снимок
принадлежит другому процессу/сессии; удаление query — поведенческое изменение транспорта, не
чистая надстройка, при провале по причине, не связанной с query (например, куки), придётся
отдельно восстанавливать, какой фактор решающий. Остаётся актуальным: `anonymousAccessExpirationDate`
при `allow_anonymous=True` — новое обязательное поле без готовой формулы дефолта (не проверялось
живым запросом, наблюдалось только с `allow_anonymous=False`); куки не воспроизводятся, но их
отсутствие подтверждено пятым боевым POST как не требуемое (Ф-55) — риск снят фактом, не остаётся
негативным следствием.

**Mitigations:** все гипотезы промаркированы `ГИПОТЕЗА` по дисциплине ADR-007 п.2, ревизуются
единственным следующим санкционированным боевым POST; при провале по куки — решение (получить их
через отдельный ручной браузерный логин или отказаться от этого класса операций) откладывается до
факта отказа, не проектируется заранее по домыслу.

## Alternatives Considered

- **Оставить query аддитивно к заголовку (первая версия решения, довод ADR-008).** Отклонено при
  пересмотре: «аддитивность не хуже» верно для абстрактного риска, но не учитывает одноразовость
  ставки — эмпирика уже разделилась (401 дважды с query+заголовком, 200 один раз без query); держать
  query — сознательно остаться в уже проверенной проигрышной точке.
- **Убрать query и для читающих операций «на всякий случай».** Отклонено: `get_room`/`get_calendar`/
  `list_recordings` подтверждены живьём именно с query — трогать работающий механизм ради симметрии
  с мутирующим путём меняет больше, чем нужно для проверки одной гипотезы о записи.
- **Вычислить `anonymousAccessExpirationDate` по дельте из снимка (~29 часов) как дефолт.** Отклонено:
  один пример недостаточен для формулы — anti-fabrication правило запрещает подставлять правдоподобное
  число вместо `N/A`.
- **Эвристически резолвить `key` по уже прочитанным календарным элементам.** Отклонено: покрывает
  только пользователей, уже видимых в выдаче (Ф-48 — `vkuznetsov` там отсутствует) — неполное
  покрытие с ложным впечатлением надёжного механизма.
