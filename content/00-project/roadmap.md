### Что починено в 0.5.0 сверх постановки

Живая проверка на боевом домене вскрыла три дефекта, которых постановка не знала:

1. **`ktalk sync` не работал вовсе.** Слал `top=1000`, API отвечает
   `400 «The field Top must be between 1 and 100»`. В репозитории фикса не было — синхронизация
   держалась на ручном патче в установленном пакете.
2. **Пагинация обрывалась после первой страницы.** Код ждал `nextPageToken`, которого внутренний
   контур не отдаёт вовсе. Переведено на `skip`-офсет.
3. **Окно `--days` не соблюдалось.** API игнорирует `startFrom`/`startTo`, и после починки
   пагинации `sync --days 30` затянул весь домен — 1318 записей вместо 99, из них 1220 сразу
   помечены `skipped`. Окно перенесено на сторону клиента с ранней остановкой обхода.

Первые два дефекта маскировали друг друга: обрыв пагинации случайно приближал окно к «последним
ста записям», и отсутствие серверной фильтрации не проявлялось.

## Что дальше

Бэклог не зафиксирован: следующая фича начинается с `/nauta:pm decompose <описание>`, дальше
цепочка Researcher → BA → SA → Dev → QA. Кандидаты, которые уже видны из кода и обсуждений:

- **Боевая приёмка api-key-режима** — заблокирована правами ключа. Выданный ключ имеет только
  `application.profiles.read`; нужны `application.recording.read` и `application.reporting.read`.
  До этого сверка идентификаторов между контурами (FR-15) не выполнена, то есть риск задвоения
  реестра при первом боевом sync под ключом остаётся открытым.
- **Ограничение корня записи для `ktalk_download_recording`** — вынесено ревью безопасности как
  архитектурное решение: нужна явная модель угроз (см.
  [отчёт](../40-architecture/security-review-personal-api-key.md), SEC-001-07).
- **Расщепление `Registry`** — класс на 208 строк, заморожен грандфазером в
  [.nauta-gates.yaml](../../.nauta-gates.yaml); рост блокирует коммит (см. [ADR-001](adr/ADR-001-nauta-contour.md)).
- **Требования к реестру постфактум** — статусная модель и правила экспирации сегодня описаны
  только в [CLAUDE.md](../../CLAUDE.md); при следующей правке механики их место в
  [30-requirements/](../30-requirements/).

### Что осталось незакрытым в 0.6.0

**Боевое создание встречи ни разу не выполнялось.** `POST /calendar` реализован по документарной
экстраполяции с соседнего пути ([RES-003](../10-domain/research/ktalk-calendar-api.md) §2) и
покрыт моками; форма тела, реакция сервера на отсутствие `start`/`end`/`timezone`, поведение при
неизвестных полях и идемпотентность повтора не подтверждены ни одним живым запросом. Красная линия
разведки запрещает пробный POST без санкции владельца на конкретный запрос — приглашения уходят
реальным людям, и удаление события их не отзывает. Соответствующие AC требования помечены
непройденными, а не ожидающими планового прогона.

Также не закрыто: чтение комнаты и календаря в режиме персонального ключа (обе операции
fail-closed по [ADR-004](adr/ADR-004-undocumented-contour.md) — календарь отвечает 200 живьём, но
причина неизвестна, и закреплять необъяснённое поведение отказались осознанно); поведение
`GET /api/rooms/{roomName}` для несуществующего имени; принадлежность выдачи календаря (26
организаторов за 7 дней — похоже на доменную выборку, не личный календарь, вторым аккаунтом не
проверено).

Кандидат на упрощение: `ConfirmationStore` после того, как межпроцессная связка между
MCP-предпросмотром и CLI-подтверждением оказалась физически нереализуемой, охраняет только
истечение TTL внутри одной интерактивной команды.
